# 阶段3-第1章第2章正文初稿.md

## 第1章 绪论

### 1.1 项目背景及意义

食品安全关系人民群众身体健康和社会公共安全，是公共治理中的重要组成部分。随着食品生产、流通和消费环节不断延伸，监管对象数量持续增加，监管业务流程也呈现出参与主体多、业务链条长、处置环节复杂等特点。在传统管理方式下，企业备案、日常检查、抽样检测、问题整改、公众投诉和信息公开等工作往往分散在不同业务环节中，容易出现信息分散、过程衔接不足和协同效率不高等问题。因此，围绕食品安全监管业务建立统一的信息化平台，已经成为提升监管规范化、流程化和协同化水平的重要手段。

从本项目实际实现内容来看，食品安全监管工作并不是单一环节的业务处理，而是覆盖多个主体共同参与的闭环过程。企业需要完成基础信息备案并维护产品档案，监管部门需要开展企业审核、检查任务派发、抽检结果发布和整改复核，公众需要获取公告、公示信息并进行投诉反馈，系统管理员还需要对监管人员账号和基础权限进行维护。上述业务天然具有明显的角色分工特征和数据协同需求，如果采用高度耦合的实现方式，后续在功能扩展、权限控制、服务协同和数据维护方面都容易受到限制。基于这一背景，本项目以“基于微服务的食品安全监管平台”为题，围绕实际监管业务链构建面向多角色的管理平台。

本项目的研究意义主要体现在以下几个方面。第一，在业务层面，平台将企业备案、产品档案、监督检查、抽检公示、整改管理、投诉处理、预警协同和统计查询等业务纳入统一系统，形成较为完整的监管业务闭环，有助于提升业务过程的连续性与可追溯性。第二，在技术层面，项目采用前后端分离与微服务架构，将用户认证、监管主数据、监管操作、投诉、预警和统计等能力按职责进行拆分，并通过网关统一入口、服务注册发现和服务间调用机制实现协同处理，体现了现代软件工程中面向业务边界进行系统拆分的设计思路。第三，在应用层面，平台同时面向系统管理员、区域管理员、执法人员、企业用户和公众用户，能够更真实地反映食品安全监管场景下多方参与、分角色协作的业务特点，对本科毕业设计中软件开发研究类型论文的写作具有较好的支撑作用。

需要说明的是，本项目的研究与实现范围以代码中已经落地的功能为准。当前系统已经实现用户认证、企业备案、产品管理、检查与抽检、整改管理、投诉处理、公告管理、预警处理和统计查询等核心功能，但未实现消息队列驱动的异步通信、容器化部署编排等扩展能力。因此，论文中的背景与意义分析将围绕已实现的平台功能和架构特点展开，不对未实现内容作超出事实范围的扩展表述。

### 1.2 国内外研究现状

从现有信息化建设趋势来看，围绕公共监管业务构建数字化平台已经成为普遍方向。相关系统的研究和实践通常聚焦于业务流程电子化、数据集中管理、跨角色协同处理以及监管结果可追溯等方面。在食品安全领域，平台化建设的重点一般集中在企业主体信息维护、监管检查记录留痕、抽检信息发布、问题处置闭环以及公众参与渠道建设等内容。这类研究说明，食品安全监管系统已经不再局限于基础数据录入，而是逐步向流程联动、业务集成和服务化方向发展。

在系统架构层面，随着业务复杂度提升，越来越多的行业平台开始采用分层、模块化甚至服务化的实现方式。相较于传统单体架构，基于服务拆分的架构更适合处理多角色、多模块、多业务链条并行的场景，便于根据不同业务边界进行职责划分，并提升后续扩展和维护能力。与此同时，统一网关、服务注册发现、分布式鉴权和缓存机制等配套技术也逐渐成为这类平台的重要组成部分。对于监管类系统而言，这种架构思路有助于将用户认证、业务主数据管理、业务处理、统计查询等不同职责进行分离，从而降低模块之间的直接耦合程度。

在业务功能层面，现有相关平台建设通常已经覆盖企业信息管理、执法检查、抽检管理和基础查询等内容，但在完整业务闭环方面仍然存在进一步整合的空间。一方面，不同业务流程之间的数据衔接往往不够紧密，例如检查结果、整改任务和风险预警之间缺少统一联动；另一方面，面向公众的信息公开和投诉反馈机制在许多系统中仍然与内部监管流程相对分离，难以形成从问题发现、任务处理到结果反馈的连续链条。对于食品安全监管业务而言，仅实现单点功能并不能充分体现平台价值，真正有效的系统应当能够支撑多角色协同、状态流转与信息共享。

在技术选型方面，主流研究与实践通常会围绕微服务框架、网关组件、注册发现方案、持久化技术和前端框架进行组合应用。其共同目标是提高系统可维护性、可扩展性和可用性。然而，从本科毕业设计的实现角度看，许多研究更重视技术概念层面的讨论，而对“技术如何与具体业务边界对应”“不同服务如何围绕业务流程协同”“系统如何在已实现功能范围内体现架构价值”等问题关注不足。基于此，本项目的切入点不是简单构建一个技术演示系统，而是围绕食品安全监管平台的实际业务需求，将企业备案、检查抽检、整改处理、投诉流转、公告公示、预警协同和统计查询等功能纳入统一架构，并在代码层面落实服务划分、统一鉴权和跨服务协作机制。

总体来看，国内外相关研究已经为监管信息化、平台化和服务化建设提供了较为丰富的思路，但如何在一个面向真实业务链条的平台中实现多角色协同和完整监管闭环，仍然具有较强的实践价值。本项目在已有技术体系基础上，结合食品安全监管场景完成微服务化平台实现，具有一定的工程研究意义和教学应用价值。

### 1.3 论文研究内容

本文围绕“基于微服务的食品安全监管平台”展开研究与实现，重点结合项目代码中已经完成的系统功能与技术方案，对平台的需求分析、架构设计、功能实现和测试验证进行系统论述。论文的主要研究内容包括以下几个方面。

第一，围绕食品安全监管业务场景，分析平台所面向的主要用户角色和核心业务需求。项目实际面向系统管理员、区域管理员、执法人员、企业用户和公众用户五类角色，已形成企业备案、产品档案、监督检查、抽样检测、整改复核、投诉处理、公告公示、预警管理和统计查询等业务模块。因此，本文将首先从业务流程和角色分工出发，对系统功能需求与非功能需求进行分析。

第二，针对食品安全监管业务链条长、协同环节多的特点，完成平台总体架构设计与模块划分设计。项目采用前后端分离的实现方式，前端基于 Vue 3 构建单页应用，后端采用 Spring Boot 与 Spring Cloud 技术体系构建网关服务、用户服务、监管服务、监管操作服务、投诉服务、预警服务和查询服务，并通过 Nacos、Gateway、OpenFeign、Redis 等技术完成统一入口、服务治理和服务协作。论文将对这种架构组织方式及其设计依据进行说明。

第三，围绕核心业务对象完成数据库设计与实体关系梳理。项目按服务划分独立数据库，分别管理用户与角色、企业与产品、检查与抽检、整改、投诉、统计预留数据和预警记录等内容。本文将基于各服务的数据库脚本，对系统核心数据表、实体关系以及对业务流程的支撑方式进行分析。

第四，结合项目实际代码实现，对系统核心功能模块进行说明。系统已经实现统一登录认证与角色访问控制、企业备案审核与产品档案维护、检查任务与抽检任务管理、整改闭环处理、公众投诉与监管处置、公告管理、预警处理和统计查询等功能。论文将在后续章节中结合控制器、服务实现、前端路由与 API 调用等内容说明系统的实现过程。

第五，对系统测试情况进行验证分析。项目中已经包含多项基于 JUnit、Spring Boot Test 和 MockMvc 的测试代码，覆盖部分业务模块与统计接口。本文将在测试章节中结合功能测试与接口验证内容，对系统实现效果进行说明，并在已实现能力范围内分析系统的适用性与不足。

综上，本文的研究重点不是对某一单一算法或理论模型进行推导，而是围绕食品安全监管业务需求，完成一个基于微服务架构的平台型系统设计与实现，并对其技术方案和工程实践过程进行总结。

## 第2章 相关技术

### 2.1 项目选用技术简介

#### 2.1.1 Spring Boot 与 Spring Cloud 微服务开发框架

本项目后端采用 Java 17 作为开发语言，并基于 Spring Boot 3.2.5 构建各个业务服务。Spring Boot 具有自动配置能力强、工程结构清晰、生态成熟等特点，适合快速构建面向业务的独立服务。项目父工程采用 Maven 聚合管理方式，将 `user-service`、`gateway-service`、`regulation-service`、`regulation-operation-service`、`complaint-service`、`query-service`、`warning-service` 和 `platform-common` 组织在同一工程下，既便于统一依赖版本管理，也便于按服务边界进行独立开发与部署。

在微服务层面，项目引入 Spring Cloud 2023.0.1 与 Spring Cloud Alibaba 2023.0.1.0 作为技术基础，使各服务能够围绕统一的服务治理体系协同运行。对于本项目这类多角色、多模块的监管平台而言，将用户认证、监管主数据、业务操作、投诉、预警和统计等功能拆分为多个服务，有利于减少单体系统中业务逻辑高度集中带来的复杂性，也使后续功能扩展更符合业务边界。项目中的微服务并非停留在概念层面，而是通过独立启动类、独立端口、独立服务名和独立数据库等方式在代码中得到落实。

#### 2.1.2 Nacos 服务注册发现与配置管理

为了支持多服务协同运行，本项目在各服务中统一引入 Nacos Discovery 和 Nacos Config。Nacos Discovery 主要用于服务注册与发现，使网关和服务调用方能够通过服务名访问目标服务，而不必将服务地址硬编码在系统中。项目中各服务均在 `application.yml` 中配置了 `spring.application.name` 和 Nacos 服务地址，并通过服务名参与系统调用，这为微服务架构提供了基础支撑。

Nacos Config 则用于统一配置管理。虽然本项目仓库中没有实现独立配置中心模块，但各服务已经接入 Nacos Config，并关闭了本地导入检查机制，说明系统在运行时具备接入外部配置中心的能力。对于需要多环境切换和多服务协同的监管平台而言，注册发现和配置管理机制能够显著降低运维复杂度。

#### 2.1.3 Spring Cloud Gateway 网关技术

本项目采用 Spring Cloud Gateway 作为统一网关。网关服务运行于 8080 端口，承担系统统一入口职责，并在配置文件中明确配置了针对认证、用户、监管、监管操作、投诉、查询和文件等多个路径前缀的路由规则。前端系统默认也是通过 `http://localhost:8080` 访问后端接口，这说明网关在整个系统中处于前后端连接的核心位置。

除路由转发外，网关还负责跨域处理、统一鉴权和登录限流。项目在网关中实现了 `JwtAuthFilter`，对除白名单之外的请求进行 JWT 签名校验、令牌内省和角色访问控制，并根据访问路径匹配不同角色规则。同时，网关中还配置了登录限流参数，结合 Redis 支撑访问频率控制。对于食品安全监管平台而言，统一网关能够将复杂的鉴权逻辑和接口入口集中处理，从而降低各业务服务重复实现安全控制的负担。

#### 2.1.4 OpenFeign 服务间调用机制

项目使用 OpenFeign 完成服务间调用。实际代码中，`regulation-service` 会调用 `user-service` 和 `warning-service`，`regulation-operation-service` 会调用 `regulation-service` 和 `warning-service`，`complaint-service` 会调用 `regulation-service`，`query-service` 则会调用多个服务聚合统计数据。这表明系统已经形成较为明确的服务协同关系。

OpenFeign 的作用在于将远程调用以接口形式进行封装，使开发者能够以较为直观的方式组织跨服务业务逻辑。对于本项目而言，检查、抽检、整改、投诉和统计等业务并非孤立存在，而是依赖监管主数据、用户身份和预警信息进行协同处理，因此服务间调用是系统正常运行的重要组成部分。采用 OpenFeign 能够在保持模块边界清晰的同时，提高调用实现的可维护性。

#### 2.1.5 MyBatis-Plus 与 MySQL 持久化技术

在数据持久化方面，项目采用 MyBatis-Plus 与 MySQL 组合。MyBatis-Plus 在保留 MyBatis 灵活性的基础上，提供了更便捷的单表操作能力和条件构造能力，适合本项目这类以业务实体管理和状态流转为主的后台系统。项目各业务服务均引入了 MyBatis-Plus 依赖，并在配置文件中启用了下划线到驼峰命名映射，说明该技术已经作为统一持久层方案在多个服务中使用。

数据库方面，项目采用 MySQL 存储业务数据，并按服务划分多个独立数据库，包括用户库、监管库、监管操作库、投诉库、查询库和预警库。对微服务系统而言，按服务拆分数据库能够减少不同业务模块在数据层面的耦合，也便于围绕服务职责维护数据表结构。本项目的数据库脚本中已完整定义用户、企业、产品、监管人员、公告、检查、抽检、整改、投诉、预警等核心表，能够支撑食品安全监管平台的主要业务闭环。

#### 2.1.6 Redis 与 Redisson

项目在多个服务中统一配置了 Redis，用于支撑会话缓存、限流控制和业务缓存。用户服务通过 Redis 保存认证会话和令牌黑名单信息，网关利用 Redis 实现登录限流，监管服务、监管操作服务、查询服务和预警服务则通过 Redis 与 Redisson 实现区域数据缓存、公共数据缓存、统计缓存和分布式锁控制等功能。

在此基础上，项目还通过 `platform-common` 模块引入 Redisson 自动配置，为各服务提供分布式锁能力。对于本项目中的整改复核、预警定时扫描、投诉处理和公共数据缓存场景而言，Redis 与 Redisson 的组合既能提升访问效率，也有助于在多服务环境下保证部分关键操作的一致性和稳定性。

#### 2.1.7 JWT 与统一认证鉴权机制

本项目采用 JWT 作为身份认证令牌。用户服务中的 `TokenUtil` 负责生成和解析 JWT，令牌中包含用户编号、用户名、用户类型和角色等信息，并设置有效期。用户登录后，系统将令牌返回给前端，前端在后续接口访问中通过 `Authorization` 请求头携带令牌。

在鉴权实现上，项目采用“用户服务签发令牌，网关统一校验”的方式。网关中的 `JwtAuthFilter` 会对令牌签名进行校验，并调用 `user-service` 的内省接口判断令牌是否有效，再依据路径规则限制不同角色对不同接口的访问。这种实现方式避免了各业务服务重复处理复杂的身份校验逻辑，也使权限控制更集中、更易维护。对于多角色监管平台而言，统一认证与统一鉴权是保障业务安全和角色隔离的重要基础。

#### 2.1.8 MinIO 文件存储技术

在文件处理方面，项目通过 `regulation-service` 引入 MinIO，用于支撑图片类附件上传。系统并未将文件直接上传到业务服务，而是通过文件接口生成预签名上传地址，前端获取上传地址后直接将文件上传至对象存储。这种实现方式可以降低业务服务在文件传输上的压力，同时提升上传过程的灵活性。

从已实现功能来看，企业备案附件和公众投诉图片等场景都依赖该能力。项目中的 `MinioFileService` 对文件大小、内容类型和对象路径进行了控制，说明对象存储并非概念性引入，而是已经在实际业务流程中得到应用。

#### 2.1.9 Vue 3 前端技术栈

本项目的前端采用 Vue 3、Vue Router 4 和 Vite 5 进行开发。Vue 3 适合构建组件化的单页应用，能够较好地支持多角色视图拆分和页面状态组织；Vue Router 用于管理系统的前端路由，并根据不同角色跳转到不同功能入口；Vite 则提供了高效的开发与构建能力。前端工程 `food-web` 中已经按系统管理员、企业用户、公众用户、区域管理员和执法人员等角色划分了对应页面目录和路由配置，说明该前端结构是围绕监管业务场景设计的。

前端 API 层通过统一封装的 `fetch` 请求访问后端网关地址，并在收到未授权响应时清理本地会话信息。该实现与后端网关统一入口模式相对应，构成了较为清晰的前后端协作方式。

#### 2.1.10 OpenAPI 文档与测试技术

在接口文档方面，项目中的 `query-service` 已集成 Springdoc OpenAPI，并通过 `OpenApiConfig` 明确定义接口文档基本信息，主要服务于监管统计查询接口的说明。与此同时，`user-service` 中虽然引入了 Knife4j 依赖，但当前代码中未发现对应启用配置，因此论文中不应将其写为已经完整启用的接口文档能力。

在测试方面，项目统一引入 Spring Boot Test 和 JUnit 5，并在多个服务中编写了测试代码，覆盖公告、产品、公开企业、检查记录、抽检任务、投诉处理、预警统计和监管概览等内容。这些测试代码为后续测试章节的编写提供了客观依据，也说明系统并非只有界面实现，而是具备一定的代码级验证基础。

### 2.2 相关技术选型对比研究

#### 2.2.1 微服务架构与单体架构对比

对于食品安全监管平台而言，系统需要同时支撑用户认证、企业备案、产品档案、检查抽检、整改管理、投诉处理、预警协同和统计查询等多类业务。如果采用单体架构，所有功能集中在同一工程和同一部署单元中，虽然初期开发相对直接，但随着业务模块增多，代码结构、权限逻辑和数据访问都会不断集中，容易造成模块边界不清和维护成本上升。相比之下，微服务架构能够围绕业务职责进行拆分，使不同服务各自承担明确功能，并通过统一网关与服务治理机制协同工作。

本项目最终选择微服务架构，主要原因有三点。第一，系统具有明显的多角色、多模块特征，用户服务、监管主数据服务、监管操作服务、投诉服务、预警服务和统计服务之间存在天然业务边界，适合按服务拆分。第二，项目需要统一管理访问入口和权限控制，通过网关集中鉴权更有利于降低重复实现。第三，按服务拆分数据库后，用户数据、监管数据、投诉数据和预警数据能够独立维护，更符合本项目当前的工程组织方式。因此，相较于单体架构，微服务架构更适合本项目的业务复杂度和后续扩展需要。

#### 2.2.2 Gateway 网关方案与传统直接暴露服务方式对比

在后端服务对外访问方式上，一种简单做法是由前端分别访问不同业务服务地址，各服务自行处理跨域、鉴权和权限控制。这种方式虽然实现门槛较低，但在服务数量较多时会带来入口分散、前端配置复杂和安全逻辑重复的问题。另一种做法是通过统一网关对外提供访问入口，将路由转发、跨域处理、身份校验和部分限流能力集中在网关层完成。

本项目选择 Spring Cloud Gateway 作为统一网关，而没有采用直接暴露各服务接口的方式。其原因在于，系统已经划分为多个服务，若让前端直接访问各个服务，将增加前端维护成本，并使认证与权限逻辑分散在多个位置。通过 Gateway，前端只需面向统一接口入口访问系统，后端则可以在网关层集中处理 JWT 校验、令牌内省、角色规则匹配和登录限流，同时由网关根据路径将请求转发给对应服务。这种方案更符合多服务监管平台的统一管理需求。

#### 2.2.3 Nacos 与静态服务地址配置方式对比

在多服务系统中，如果采用静态服务地址配置方式，服务调用方需要明确配置被调服务的固定地址和端口。当服务数量较多、环境发生切换或者部署地址调整时，系统维护成本会显著增加。相比之下，基于注册中心的方式可以通过服务名完成寻址，将地址变更对业务逻辑的影响降到较低水平。

本项目采用 Nacos 作为服务注册发现和配置管理组件，而没有采用纯静态地址配置方式。由于本项目包含多个微服务，并且网关和服务之间存在较多协同调用关系，使用 Nacos 可以使系统通过 `lb://服务名` 和 `@FeignClient` 的方式完成路由和调用，这与项目当前的微服务组织结构高度一致。同时，配置管理能力也有助于支撑后续环境扩展。因此，相较于手工维护固定地址的方案，Nacos 更适合本项目的运行需求。

#### 2.2.4 OpenFeign 与手工 HTTP 调用方式对比

跨服务调用既可以通过直接编写底层 HTTP 请求来实现，也可以通过声明式客户端进行封装。手工 HTTP 调用方式灵活性较强，但调用代码分散、重复逻辑较多，维护时需要自行处理请求地址拼接、参数组织和响应解析等问题。OpenFeign 则通过接口声明方式封装远程调用，能够使调用关系更清晰，也更便于与 Spring Cloud 服务治理体系结合使用。

本项目选择 OpenFeign 作为主要服务间调用方式，是因为系统中存在大量围绕业务边界展开的服务协同。例如监管操作服务需要查询企业、产品和监管人员信息，查询服务需要聚合多个业务服务统计数据，监管服务需要与用户服务和预警服务协同处理部分逻辑。采用 OpenFeign 后，服务间依赖关系可以在接口层面得到明确表达，更有利于系统结构维护。因此，该方案较手工 HTTP 调用更适合本项目。

#### 2.2.5 MyBatis-Plus 与更重型 ORM 方案对比

在后端持久层实现中，既可以采用更加接近 SQL 的轻量级方案，也可以采用更强调对象关系映射自动化的重型 ORM 方案。对于本项目而言，系统数据表数量较多，业务逻辑以状态变更、条件查询和分页处理为主，如果使用过度复杂的 ORM 方案，虽然能够减少部分基础代码，但在处理多条件查询和显式业务状态控制时未必具有优势。

项目最终选择 MyBatis-Plus 作为持久层框架，主要考虑其与 Spring Boot 集成简单、单表操作便捷、查询条件构造清晰，并且能够保留较强的 SQL 控制能力。对于企业、产品、公告、检查任务、抽检结果、投诉和预警等实体管理场景而言，MyBatis-Plus 既能提高开发效率，又不会削弱对业务查询和状态流转的表达能力，因此较为适合本项目的实现需求。

#### 2.2.6 MySQL 与其他类型数据存储方案对比

食品安全监管平台中的核心数据主要包括用户信息、企业备案信息、产品档案、检查记录、抽检结果、整改任务、投诉记录和预警记录等。这些数据具有结构清晰、关系明确、状态字段较多和事务性要求较强等特点，因此更适合采用关系型数据库进行管理。如果选择以非关系型数据库作为主存储，虽然在某些场景下具有灵活性优势，但在复杂业务关系表达、数据一致性控制和结构化查询方面不如关系型数据库直观。

本项目选择 MySQL 作为主要业务数据库，是因为 MySQL 在结构化数据存储、事务支持、表关系组织和工程应用成熟度方面均较适合本项目需求。项目中多个数据库脚本已经围绕服务边界建立了完整的数据表结构，能够较好支撑多模块监管业务。因此，相较于以非关系型数据库为主的数据方案，MySQL 更符合本项目的数据特征。

#### 2.2.7 Redis 缓存方案与纯数据库访问方式对比

如果所有请求都直接访问数据库，不仅会增加数据库读写压力，也不利于对会话状态、频率控制和热点公共数据进行统一管理。相比之下，Redis 作为内存型数据存储，适合处理认证会话、限流计数、短期缓存和部分分布式协调场景。

本项目选择 Redis，并在部分场景下配合 Redisson 使用，原因在于系统存在明显的缓存与协调需求。用户服务需要保存会话和令牌状态，网关需要实现登录限流，监管服务和查询服务需要缓存公共数据与统计数据，整改和预警场景还需要使用分布式锁避免并发冲突。因此，与完全依赖数据库的方案相比，Redis 更能满足本项目对访问效率和协同控制的需要。

#### 2.2.8 JWT 统一鉴权方案与服务器会话鉴权方案对比

常见的身份认证方案既包括基于服务器会话的认证方式，也包括基于令牌的认证方式。对于单体应用而言，传统会话认证实现较为直接，但在多服务场景下，如果完全依赖服务器本地会话，往往会增加会话同步和鉴权扩展的复杂度。JWT 则可以在令牌中携带必要身份信息，便于在网关层和各服务之间传递认证结果。

本项目选择 JWT 作为认证令牌，并通过用户服务签发、网关统一校验的方式实现权限控制。这种方案适合当前微服务结构：前端只需持有令牌，网关对请求进行签名校验和角色判定，再将身份信息透传到后续服务。同时，项目结合 Redis 会话和黑名单机制弥补了纯令牌方案在状态控制方面的不足。因此，相较于完全基于传统服务器会话的方案，JWT 更适合本项目的多服务访问场景。

#### 2.2.9 Vue 3 与传统多页面开发方式对比

在前端实现方式上，可以采用传统多页面模式，也可以采用单页应用模式。传统多页面方式结构相对简单，但在多角色系统中容易出现页面切换逻辑分散、状态管理不统一和前后端协作成本较高的问题。Vue 3 适合构建组件化的单页应用，可以通过路由和模块划分清晰组织不同角色下的页面结构。

本项目选择 Vue 3、Vue Router 和 Vite 构建前端，是因为系统同时面向多个角色，页面数量较多，交互逻辑需要围绕角色进行组织。通过单页应用方式，可以将登录、公众端、企业端、系统管理员端和监管端页面统一纳入一个工程中，并通过前端路由完成角色跳转和界面组织。这种方式较传统多页面实现更符合本项目的交互结构。

#### 2.2.10 本项目技术选型结论

综合来看，本项目的技术选型并不是对流行技术的简单堆叠，而是围绕食品安全监管平台的业务特征进行组织的。Spring Boot 与 Spring Cloud 支撑了多服务结构，Nacos 提供服务治理基础，Gateway 实现统一入口与安全控制，OpenFeign 支撑服务协同，MyBatis-Plus 与 MySQL 负责结构化业务数据管理，Redis 与 Redisson 提升了缓存和并发控制能力，JWT 保障统一认证鉴权，MinIO 满足文件上传场景，Vue 3 则承担前端多角色交互界面的实现任务。

这些技术共同服务于本项目的核心目标，即在食品安全监管场景下构建一个能够支撑企业、监管人员、公众和系统管理员协同工作的微服务平台。由于选型与项目实际代码结构、服务职责和业务流程保持一致，因此该技术路线具有较好的合理性和可实施性。
