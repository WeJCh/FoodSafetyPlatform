# 食品安全监管平台 — 需求分析说明书

| 项目 | 内容 |
|------|------|
| 系统名称 | 基于微服务的食品安全监管平台 |
| 文档版本 | V1.0 |
| 编写说明 | 功能需求与论文第 3 章、后端实现及网关角色规则对齐；非功能需求结合当前部署形态 |

---

## 1. 引言

### 1.1 编写目的

明确系统用户角色、功能需求、业务流程约束及接口可见性，作为设计、实现与验收的需求基线。

### 1.2 系统定位

面向食品安全生产监管场景，连接**监管部门**、**食品企业**与**社会公众**，实现企业备案、监督检查、抽检公示、投诉处理、风险预警与数据统计等闭环管理。

### 1.3 需求来源

- 毕业设计业务目标与论文第 3 章需求分析
- 当前可运行系统：`food-web` 各角色菜单 + 后端 Service/Controller + `JwtAuthFilter` 角色规则

## 2. 用户角色与权限

### 2.1 角色定义

| 角色编码 | 说明 | 典型能力 |
|----------|------|----------|
| ADMIN | 系统管理员 | 用户与角色管理、辖区维护、全局配置类操作 |
| REGULATOR_ADMIN | 监管管理员 | 企业审批、任务创建与分派、公告发布、预警处理、统计 |
| REGULATOR_ENFORCER | 执法员 | 执行检查/抽检、处理投诉、办理整改审核、预警处理 |
| ENTERPRISE | 企业用户 | 备案与产品维护、查看检查与整改、提交整改材料 |
| PUBLIC | 社会公众 | 注册、提交投诉、查看公示公告与抽检公示 |

用户类型（`user_type`）与角色（`sys_role`）通过 `sys_user_role` 关联；网关按 **角色编码** 控制 API 访问。

### 2.2 认证需求

- 用户通过 `/api/auth/login` 登录，获取 JWT。
- 除白名单接口外，所有 `/api/**` 请求须经网关校验 Token 有效性及用户状态（introspect）。
- 支持公众注册、企业注册（白名单路径）。
- 登录接口具备 IP/账号维度限流，防暴力破解。

### 2.3 数据隔离原则

- 监管员仅能处理**其辖区或指派给自己**的任务（由业务服务按 `regulator_id`、`region_id`、`assigned_to` 过滤）。
- 企业用户仅能访问**本企业**相关数据（`enterprise_id` / `user_id` 绑定）。
- 公众仅能访问本人投诉与公开公示数据。

## 3. 功能需求

### 3.1 用户与账户管理（user-service）

| 编号 | 需求描述 | 优先级 |
|------|----------|--------|
| UR-01 | 管理员维护系统用户（增删改查、启用禁用） | 高 |
| UR-02 | 管理员维护角色及用户-角色绑定 | 高 |
| UR-03 | 各角色用户修改个人资料与密码 | 中 |
| UR-04 | 记录登录、注册等审计日志 | 中 |

### 3.2 企业备案与主数据（regulation-service）

| 编号 | 需求描述 | 优先级 |
|------|----------|--------|
| ER-01 | 企业用户提交备案申请（含附件上传 MinIO） | 高 |
| ER-02 | 监管管理员审批企业（通过/驳回） | 高 |
| ER-03 | 维护行政区划与地址信息 | 高 |
| ER-04 | 企业维护产品档案（启用/停用） | 高 |
| ER-05 | 维护监管人员档案及辖区绑定 | 高 |
| ER-06 | 支持将企业设为重点监管并记录原因 | 中 |
| ER-07 | 监管员/管理员按辖区查询企业 | 高 |

**企业审批状态**：`PENDING` → `APPROVED` / `REJECTED`。

### 3.3 检查任务（regulation-operation-service）

| 编号 | 需求描述 | 优先级 |
|------|----------|--------|
| IN-01 | 监管管理员创建检查任务并指派执法员 | 高 |
| IN-02 | 执法员开始检查、录入检查记录与检查项 | 高 |
| IN-03 | 检查结果为不合格时触发整改流程 | 高 |
| IN-04 | 连续不合格等规则触发预警（Outbox→warning） | 中 |
| IN-05 | 任务状态流转：CREATED→ASSIGNED→IN_PROGRESS→COMPLETED→CLOSED | 高 |

### 3.4 整改管理（regulation-operation-service）

| 编号 | 需求描述 | 优先级 |
|------|----------|--------|
| RC-01 | 检查不合格自动生成整改任务 | 高 |
| RC-02 | 企业提交整改说明与材料 | 高 |
| RC-03 | 监管员审核：确认通过或要求返工 | 高 |
| RC-04 | 超期未整改触发 SLA 预警 | 中 |
| RC-05 | 整改状态：ONGOING→SUBMITTED→REWORK/CONFIRMED | 高 |

### 3.5 抽检与公示（regulation-operation-service）

| 编号 | 需求描述 | 优先级 |
|------|----------|--------|
| SA-01 | 创建抽检任务、指派执法员、录入抽检结果 | 高 |
| SA-02 | 抽检不合格触发预警 | 中 |
| SA-03 | 监管员发布/下线抽检公示（public_status） | 高 |
| SA-04 | 社会公众查看已发布抽检公示列表与详情 | 高 |

### 3.6 投诉处理（complaint-service）

| 编号 | 需求描述 | 优先级 |
|------|----------|--------|
| CP-01 | 公众提交投诉（关联企业、上传材料） | 高 |
| CP-02 | 监管受理：通过进入待分派或驳回 | 高 |
| CP-03 | 管理员分派至执法员 | 高 |
| CP-04 | 执法员**开始处理**后进入处理中状态 | 高 |
| CP-05 | 处理完成并反馈公众 | 高 |
| CP-06 | 投诉量超阈值同步触发预警（Feign upsert） | 中 |

**状态主路径**（与实现一致）：

`SUBMITTED` →（受理）`PENDING` → `ASSIGNED` → `PROCESSING` → `FEEDBACKED`；驳回为 `REJECTED`。

> 注意：受理后须完成分派并开始处理，不可从受理直接跳到办结。

### 3.7 公告公示（regulation-service）

| 编号 | 需求描述 | 优先级 |
|------|----------|--------|
| PB-01 | 监管管理员起草、发布、下线公告 | 高 |
| PB-02 | 公众查看已发布公告 | 高 |

### 3.8 预警管理（warning-service + regulation 代理）

| 编号 | 需求描述 | 优先级 |
|------|----------|--------|
| WA-01 | 业务事件自动生成/更新预警（去重 dedup_key） | 高 |
| WA-02 | 监管员查看、分派、处理、办结预警 | 高 |
| WA-03 | 支持 L1/L2 等级升级与自动归档 | 中 |
| WA-04 | 前端仅通过 `/api/regulation/warnings/**` 访问，禁止直连 warning 服务 | 高 |

### 3.9 统计查询（query-service）

| 编号 | 需求描述 | 优先级 |
|------|----------|--------|
| ST-01 | 按辖区/时间维度统计企业、检查、投诉、预警等指标 | 高 |
| ST-02 | 监管管理员、执法员、管理员按角色查看统计大屏/列表 | 高 |
| ST-03 | 数据来源于各服务 internal 聚合，非 stat_* 表主链路 | 说明 |

### 3.10 文件服务

| 编号 | 需求描述 | 优先级 |
|------|----------|--------|
| FL-01 | 企业/公众上传附件至对象存储 | 高 |
| FL-02 | 按角色控制 `/api/files/**` 访问 | 高 |

## 4. 业务流程需求（摘要）

与论文图 3-6～3-9 及第 4.3 节设计一致，核心约束如下：

1. **企业备案**：注册 → 提交备案 → 审批 → 通过后开展业务。
2. **检查整改**：任务指派 → 开始检查 → 不合格 → 整改 → 审核（可返工）→ 关闭。
3. **抽检公示**：完成任务 → 录入结果 → 监管发布公示 → 公众可查。
4. **投诉**：提交 → 受理 → 分派 → 开始处理 → 反馈。
5. **预警**：业务触发 → 记录 OPEN → 分派处理 → RESOLVED/CLOSED。

## 5. 接口需求（外部可见）

### 5.1 统一约定

- 基础路径：`/api/{域}/...`
- 认证：`Authorization: Bearer {token}`
- 响应格式：统一 `ApiResponse` 包装（`code`、`message`、`data`）

### 5.2 按角色 API 可见性（网关层）

| 路径模式 | 允许角色 |
|----------|----------|
| /api/admin/**、/api/roles/** | ADMIN |
| /api/regulation/**（除 public、enterprise 子路径） | REGULATOR_* |
| /api/regulation/enterprise/** | ENTERPRISE + REGULATOR_* |
| /api/regulation-operation/** | REGULATOR_*（整改/检查企业视图另含 ENTERPRISE） |
| /api/complaints/public、/api/complaints/my/** | PUBLIC |
| /api/complaints/**（监管处理） | REGULATOR_* |
| /api/query/** | ADMIN、REGULATOR_* |
| /api/warning/** | **禁止（403）** |

完整规则以 `JwtAuthFilter.ROLE_RULES` 为准。

## 6. 非功能需求

| 类别 | 需求 |
|------|------|
| 性能 | 演示环境支持 1C/1.8G 虚拟机；JVM 参数见 `.env` 中 `JAVA_OPTS_*` |
| 安全 | 默认密码仅用于演示；生产须修改数据库、Redis、MinIO、JWT、内部 Token |
| 可部署 | 支持 Docker Compose 全栈启动；支持本机构建 jar + dist 上传 |
| 可维护 | 微服务分库；审计日志；预警 Outbox 可重试 |
| 兼容性 | 浏览器访问 `WEB_HOST_PORT`（默认 80）；开发环境 Vite 5173 |

---

## 7. 约束与假设

1. 单组织演示部署，不要求多租户。
2. 消息中间件未引入；跨服务异步采用 **数据库 Outbox + 定时重试** 及 **同步 Feign**。
3. Nacos 以 standalone 模式运行，满足服务发现即可。
4. `food_query_db.stat_*` 为预留，当前版本统计以 Feign 聚合为准。

## 8. 验收要点（建议）

| 场景 | 验收标准 |
|------|----------|
| 五角色登录 | 各角色菜单与 API 403/200 符合权限表 |
| 企业备案审批 | 状态流转正确，未审批企业不可开展监管业务 |
| 检查→整改 | 不合格生成整改；企业提交；监管审核 |
| 投诉闭环 | 受理→分派→开始处理→反馈 |
| 预警 | 业务触发后监管端可见；直连 /api/warning 返回 403 |
| 统计 | 管理端统计页有数据且与各业务一致 |
| Docker 部署 | `docker compose up` 后 80 端口可访问并完成登录 |

演示账号见 `deploy/mysql/init/02-user-init.sql`（如 `admin`/`admin123`、`regulator_admin_1`/`regulator123`、`enforcer_1`/`enforcer123`、`enterprise_1`/`enterprise123`、`public_1`/`public123`）。
