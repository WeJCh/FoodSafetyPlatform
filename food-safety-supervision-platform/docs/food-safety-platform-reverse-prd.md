【项目可直接证明】当前代码已经不是早期“只有企业、检查、投诉的半成品”。代码中已存在产品档案、抽检任务、抽检结果公示、抽检不合格联动重点监管、监管概览聚合等能力。

【项目可直接证明】P0、P1、P2-1 到 P2-4 有验收记录。P2-5 配置治理未执行，且当前范围决策为不再推进；P3 整体放弃。

【基于代码结构推断】如果按用户“开发中期”的表述理解，本 PRD 可作为中期纠偏版使用；但以 2026-04-07 的当前仓库为准，项目更接近“业务主线已成型、交付收口前”的状态，而不是旧文档中的中期偏差状态。

### 三、现有业务能力梳理

已实现或基本实现：

- 企业注册、备案、审核、驳回、公众公示。
- 监管人员账号、辖区、角色类型。
- 产品档案维护与监管查看。
- 检查任务创建、派发、执行、记录提交。
- 检查不合格生成整改任务，企业提交整改，监管复核。
- 整改 SLA 预警、预警处理、预警升级/归档。
- 公众投诉提交、受理、派发、处理、反馈、驳回、进度查询。
- 重点监管原因沉淀，覆盖连续检查不合格、投诉高发、抽检不合格。
- 公告管理与公众公告展示。
- 抽检任务、抽检结果录入、结果发布/下线、公众查询。
- 监管概览聚合统计。

部分实现：

- 食品安全专业对象：已有产品与抽检，但没有批次、原料、生产过程、检测机构报告。
- 风险分析：已有重点监管和预警统计，但不是完整风险画像模型。
- 审计留痕：整改、投诉、预警有动作记录，但没有通用操作日志中心。
- 部署运维：可本地多服务运行，但未发现 Docker Compose/K8s 编排。

缺失或不纳入：

- 检测机构独立角色和实验室报告流转。
- 批次级追溯与问题食品召回。
- 行政处罚案件全流程。
- 全国级大屏 BI 或离线数仓。
- 生产级配置治理、密钥管理、通用审计中心。

偏离平台定位的风险点：

- 系统管理员方向容易变成通用后台，但 P0 已收缩。
- 统计表曾有“看板先行”倾向，但当前 `query-service` 已收束为轻量聚合。
- 若继续扩 P3，项目会从食品安全监管主线偏向通用政务后台或大而全监管系统。

### 五、当前项目存在的核心问题

需求层面：

- 【项目可直接证明】旧 PRD 中“缺少产品/抽检”等判断已被 P2-1 到 P2-4 改变，旧需求口径必须更新。
- 【基于代码结构推断】当前需求边界应从“继续补所有食品安全能力”调整为“围绕现有主线交付收口”。

- 【项目可直接证明】企业、检查、整改、投诉、预警、公示、产品、抽检已形成可讲述的监管闭环。
- 【基于业务合理性建议】不应继续加入检测机构、追溯、召回、处罚、大屏 BI，否则会把毕业设计做成大而空的平台。

业务流程层面：

- 【项目可直接证明】检查整改、投诉反馈、抽检公示均有链路。
- 【基于代码结构推断】完整浏览器级人工联调仍需补充，不能只用静态代码存在来等同于线上可演示。

数据设计层面：

- 【项目可直接证明】核心数据对象已经覆盖企业、产品、检查、整改、投诉、预警、抽检、公告。
- 【项目可直接证明】`stat_enterprise/stat_inspection/stat_complaint` 仍是预留统计表，不应作为真实离线统计来源。
- 【基于业务合理性建议】`schema.sql` 中存在 `DROP TABLE`，应标注为原型初始化脚本，不应作为生产迁移脚本。

系统架构层面：

- 【项目可直接证明】服务边界基本成立。
- 【项目可直接证明】默认 JWT secret、内部 token、MinIO 默认凭据仍存在。
- 【基于业务合理性建议】当前不宜引入 MQ、Redis、Seata、K8s 等新复杂度。

毕业设计可落地性层面：

- 【基于业务合理性建议】最适合展示的主线是：企业备案公示、检查整改预警、投诉反馈、抽检结果公示、重点监管、监管概览。
- 【基于业务合理性建议】最不适合继续扩展的是：追溯召回、处罚案件、检测机构、复杂权限、通用日志、大屏数仓。

### 六、建议的纠偏方向

删减或冻结：

- 通用后台、操作日志中心、区域交接、复杂角色体系、大屏 BI、离线数仓、检测机构、追溯召回、处罚案件。

- 配置风险说明：默认 secret/token/MinIO 凭据不可写成生产级完成态。

优先级：

- S0：文档口径收束，明确 P2-5/P3 不再推进。
- S1：准备 6 条演示路径和数据。
- S2：只修复阻断性 bug，不新增业务线。

## 3. 当前项目偏差识别

### 3.1 当前实际被做成了什么系统

【基于代码结构推断】当前项目实际上是一个“区域食品安全监管协同平台原型”，核心是企业主体纳管、监管检查、整改复核、投诉处理、预警协同、产品档案、抽检公示和监管概览。

它不是全链路食品安全监管系统，也不是实验室检测平台、食品追溯平台、行政处罚系统或全国级数据监管平台。

### 3.2 理论上应优先建设的核心目标

作为毕业设计范围内的食品安全监管平台，应优先建设：

1. 企业主体纳管。
2. 监管检查与整改闭环。
3. 投诉举报与处理反馈。
4. 风险预警与重点监管。
5. 公众信息公示。
6. 最小食品专业对象：产品档案与抽检结果。
7. 轻量统计概览。

当前代码已经覆盖这些主线的大部分，不宜继续扩展到追溯、召回、处罚、实验室生态。

### 3.3 有效且应保留的功能

- 企业备案/审批/公示。
- 监管人员/辖区。
- 检查任务/检查记录/整改复核。
- 投诉受理/派发/处理/反馈/驳回。
- 预警事件/处理/升级/归档/统计。
- 重点监管原因。
- 产品档案。
- 抽检任务/抽检结果/公众公示。
- 公告发布与公众公告。
- 监管概览。

### 3.4 方向跑偏或容易跑偏的功能

| 功能方向 | 跑偏风险 | 修正方式 |
| --- | --- | --- |
| 系统管理员通用后台 | 容易做成通用管理系统 | 只保留监管账号和基础状态维护。 |
| `stat_*` 离线统计表 | 容易出现空壳数据看板 | 标为预留，不作为当前统计来源。 |
| 检测机构/追溯/召回 | 容易把毕设做成全链路大平台 | 明确非目标范围。 |
| 生产级安全治理 | 需要较大配置和部署改造 | 当前只作为风险说明，未来单独立项。 |

### 3.5 最缺失的监管能力

当前最缺失的不是新的业务主线，而是交付层能力：

- 完整在线手工验收记录。
- 演示数据和演示脚本。
- 最小运行说明。
- 生产级配置治理说明。

业务上如果继续补，只能补很小的展示性增强，不应新增大模块。

### 3.6 如果继续按旧思路开发会出现的问题

- 继续扩 P3 会导致范围失控。
- 继续补检测机构、追溯、召回会导致核心闭环讲不清。
- 继续做 BI/数仓会和当前 `stat_*` 预留表脱节。
- 继续改配置治理可能影响多服务联调稳定性。
- 毕设答辩时会被追问“到底是监管平台、后台系统、追溯平台还是大屏系统”。

### 3.7 边界收束建议

当前边界应定义为：

> 以企业主体纳管为基础，以日常检查、整改闭环、投诉协同、风险预警、产品档案、抽检结果、公示公告和监管概览为主线的区域食品安全监管协同平台。

## 4. 《微服务食品安全监管平台》PRD（完整）

### 4.1 文档说明

#### 4.1.1 文档目的

本文档用于基于当前半成品项目的真实代码和已完成整改状态，反向整理系统需求，明确当前产品定位、角色边界、业务流程、功能结构、数据需求、接口需求、非功能需求和迭代方向。

#### 4.1.2 文档背景

项目前期需求分析不足，导致早期系统存在业务主语不清、食品专业对象弱、页面入口与后端能力不完全匹配、统计服务定位不清等问题。经过 P0、P1、P2-1 到 P2-4 整改后，当前系统已经形成较明确的监管协同主线，因此需要一份新的 PRD 作为后续收口依据。

#### 4.1.3 适用范围

- 毕业设计中期纠偏说明。
- 后续迭代边界确认。
- 答辩展示路径设计。
- 文档与代码现状对齐。
- 阻断性 bugfix 范围判断。

#### 4.1.4 版本说明

本版本以 2026-04-07 当前仓库为基线。P0、P1、P2-1 到 P2-4 视为已完成；P2-5 配置治理不纳入完成范围；P3 整体不纳入当前版本。

#### 4.1.5 注意事项

- 本文档不是凭空设计的理想平台 PRD。
- 本文档不把未来愿景写成当前能力。
- 本文档不宣称 P2 原始清单全量完成。
- 本文档不宣称生产级配置安全完成。
- 本文档不把追溯、召回、检测机构、处罚案件、大屏 BI 纳入当前交付范围。

### 4.2 项目背景

食品安全监管通常涉及企业主体备案、监管辖区划分、检查任务执行、问题整改、公众投诉、抽检结果、公示公告和风险预警等环节。线下或分散系统容易造成企业底数不清、监管任务跟踪困难、投诉处理不透明、整改超期失管、风险信息无法沉淀和公示窗口不足。

本项目希望通过微服务架构，将用户认证、监管主数据、监管执行、投诉协同、风险预警、统计查询和前端工作台拆分，实现一个适合毕业设计规模的区域食品安全监管协同平台。

### 4.3 项目目标

总体目标：

- 构建一个可演示、可解释、边界清晰的区域食品安全监管协同平台。

业务目标：

- 实现企业备案、审核、监管和公示。
- 实现检查任务、检查记录、整改复核和预警联动。
- 实现公众投诉、监管处理和反馈追踪。
- 实现产品档案、抽检任务、抽检结果和公众公示。
- 实现重点监管原因沉淀和监管概览。

管理目标：

- 支持区域管理员按辖区管理企业、任务、投诉、预警和公告。
- 支持执法人员处理分派任务。
- 支持企业查看监管结果并提交整改。
- 支持公众查询公开信息并提交投诉。

技术目标：

- 保留微服务拆分、网关鉴权、Feign 调用、Outbox、MinIO 文件上传、Nacos/Sentinel 等已有技术亮点。
- 不新增不必要的服务和中间件。
- 保持现有服务边界稳定。

毕业设计目标：

- 能围绕 5 到 6 条主线完成答辩演示。
- 能讲清微服务拆分与业务协同价值。
- 能明确说明未纳入能力和风险边界。

### 4.4 项目定位

本平台是：

- 区域食品安全监管协同平台。
- 企业主体纳管平台。
- 日常检查与整改闭环平台。
- 投诉举报协同处置平台。
- 风险预警与重点监管平台。
- 产品档案与抽检结果最小闭环平台。
- 公众公示与监管公告窗口。

本平台不是：

- 商城系统。
- ERP 或生产过程管理系统。
- 全链路食品追溯系统。
- 召回管理系统。
- 行政处罚案件系统。
- 检测机构/实验室报告平台。
- 全国级大数据监管大屏。
- 通用后台管理系统。

核心边界：

- 当前版本只围绕企业、产品、检查、整改、投诉、预警、抽检、公示、概览建设。
- 不做批次级追溯、召回、处罚、实验室流程、大屏数仓。

### 4.7 核心业务流程

#### 4.7.1 企业入驻/备案流程

触发条件：企业用户注册并提交企业资料。  
参与角色：企业用户、区域管理员、公众用户。  
输入：企业名称、许可证号、地址、负责人、联系方式等。  
输出：审核状态、企业公示信息、监管企业档案。

流程：

1. 企业用户注册账号。
2. 企业提交备案资料。
3. 区域管理员按辖区审核。
4. 审核通过后企业进入监管池。
5. 公众端可查询企业公开信息。

异常分支：

- 资料不完整或不符合要求时驳回。
- 已被重点监管时展示监管状态与原因。

#### 4.7.2 食品信息上报流程

触发条件：企业备案后维护产品档案。  
参与角色：企业用户、区域管理员、执法人员。  
输入：产品名称、类别、规格、状态、备注。  
输出：企业产品列表、抽检任务可选产品。

流程：

1. 企业进入产品档案页。
2. 新增或更新产品。
3. 监管端查看企业产品。
4. 抽检任务创建时选择企业和产品。

异常分支：

- 未备案或无企业档案时不应允许新增产品。
- 产品停用后不应作为优先抽检对象。

#### 4.7.3 抽检任务下发与结果回传流程

触发条件：区域管理员发起抽检任务。  
参与角色：区域管理员、执法人员、公众用户。  
输入：企业、产品、任务标题、任务描述、抽检结果、结论、处置建议。  
输出：抽检任务、抽检结果、公众公示结果、重点监管原因、预警事件。

流程：

1. 区域管理员创建抽检任务。
2. 区域管理员派发给执法人员。
3. 执法人员提交抽检结果。
4. 不合格结果写入重点监管原因，并进入预警 outbox。
5. 区域管理员发布或下线抽检结果。
6. 公众查看已发布抽检结果。

异常分支：

- 抽检结果未发布时公众不可见。
- 不合格结果需联动风险提示。

#### 4.7.4 风险预警处理流程

触发条件：整改超期、连续检查不合格、抽检不合格等事件。  
参与角色：区域管理员、执法人员。  
输入：预警事件类型、业务对象、辖区、责任人、标题、内容。  
输出：预警记录、处理日志、解决状态、统计指标。

流程：

1. 上游业务生成预警事件。
2. 预警服务按 dedupKey 合并或创建预警。
3. 区域管理员查看并分派。
4. 执法人员处理。
5. 预警解决、关闭或自动升级/归档。
6. `query-service` 聚合预警统计。

异常分支：

- 重复事件应幂等合并。
- 超期未处理可升级。

#### 4.7.5 问题食品追溯流程

当前不纳入完整实现。  
处理原则：本项目只通过企业、产品和抽检结果保留最小问题来源信息，不做批次、流向、召回和供应链追踪。

建议后续方向：

- 若未来扩展，可从 `sampling_result` 关联 `food_product` 入手，补充批次号、生产日期、流向单位等字段。
- 当前毕业设计不建议展开。

#### 4.7.6 监管整改闭环流程

触发条件：执法人员提交不合格检查记录。  
参与角色：区域管理员、执法人员、企业用户。  
输入：检查任务、检查记录、问题描述、整改说明、附件、复核意见。  
输出：整改任务、整改日志、复核状态、预警事件。

流程：

1. 区域管理员派发检查任务。
2. 执法人员执行检查并提交检查记录。
3. 不合格时系统生成整改任务。
4. 企业提交整改说明与附件。
5. 区域管理员或执法人员复核。
6. 复核通过则关闭，复核不通过则打回。
7. 超期提交或超期复核触发预警。

异常分支：

- 企业未按时提交，触发 SLA 预警。
- 复核不通过，进入重做状态。

#### 4.7.7 投诉举报处理流程

触发条件：公众提交投诉。  
参与角色：公众用户、区域管理员、执法人员。  
输入：企业、投诉类型、内容、图片、联系方式、处理摘要、驳回原因。  
输出：投诉单、处理记录、公众反馈、重点监管原因。

流程：

1. 公众提交投诉。
2. 区域管理员受理或驳回。
3. 区域管理员派发执法人员。
4. 执法人员处理并填写反馈摘要。
5. 公众查看处理结果或驳回原因。
6. 投诉高发时写入重点监管原因。

异常分支：

- 无效投诉可驳回，必须填写驳回原因。
- 处理反馈必须形成公众可见摘要。

| 前置条件 | 上游业务产生风险事件。 |
| 功能描述 | 预警事件 upsert、去重、处理、解决、升级、归档，重点监管原因写入。 |
| 业务规则 | 预警按 dedupKey 幂等；重点监管原因保留来源类型和来源 ID。 |
| 输入项 | eventType、bizType、bizId、dedupKey、regionId、ownerRegulatorId、title、content。 |
| 输出项 | 预警记录、处理日志、重点监管原因。 |
| 异常处理 | 重复事件合并；超期处理升级。 |
| 数据涉及 | `warning_record`、`warning_process_log`、`enterprise_key_reason`。 |
| 当前实现情况 | 基本完成。 |
| 后续建议 | 不做复杂规则引擎和长期画像。 |

#### 4.9.6 抽检管理与结果公示

| 后续建议 | 不新增检测机构和实验室报告。 |

核心业务对象：

| 对象 | 当前数据实体 | 说明 |
| --- | --- | --- |
| 用户 | `sys_user` | 账号与用户类型。 |
| 角色 | `sys_role`、`sys_user_role` | 角色绑定。 |
| 企业 | `food_enterprise` | 监管主体。 |
| 产品 | `food_product` | 企业产品档案。 |
| 监管人员 | `food_regulator` | 管理员/执法人员。 |
| 辖区 | `addr_region`、`food_regulator_region` | 区域权限基础。 |
| 检查任务 | `inspection_task` | 检查执行任务。 |
| 检查记录 | `inspection_record`、`inspection_item` | 检查结果与明细。 |
| 整改任务 | `rectification_task` | 问题整改闭环。 |
| 整改日志 | `rectification_action_log` | 过程留痕。 |
| 投诉 | `complaint`、`complaint_handle` | 投诉闭环。 |
| 预警 | `warning_record`、`warning_process_log` | 预警闭环。 |
| 预警 outbox | `warning_event_outbox` | 轻量跨服务一致性。 |
| 抽检 | `sampling_task`、`sampling_result` | 抽检任务与结果。 |
| 公告 | `public_bulletin` | 公示公告。 |
| 重点监管 | `enterprise_key_reason` | 风险原因沉淀。 |
| 统计预留 | `stat_enterprise/stat_inspection/stat_complaint` | 当前不作为真实来源。 |

数据关联关系：

- 企业 1 对多产品。
- 企业 1 对多检查任务、检查记录、整改任务、投诉、抽检任务、抽检结果、重点监管原因。
- 抽检任务关联企业和产品。
- 抽检结果关联抽检任务、企业、产品。
- 预警通过 `biz_type/biz_id/dedup_key` 关联业务来源。
- 投诉高发、连续检查不合格、抽检不合格可写入重点监管原因。

当前表设计问题：

- `stat_*` 表未接入真实统计链路。
- 部分 schema 含 `DROP TABLE`，适合原型初始化，不适合作为生产迁移。
- 检查模型仍较轻，没有复杂检查模板、风险标签和处罚衔接。
- 未建批次、流向、召回、实验室报告等模型。

建议补充的数据模型：

- 当前版本不建议补新大表。
- 如未来转生产，可补：审计日志、批次、抽检样品、检测报告、召回记录、配置密钥管理记录。

### 4.11 接口需求

核心接口分类：

| 分类 | 服务对象 | 当前接口能力 |
| --- | --- | --- |
| 认证接口 | 全部用户 | 登录、注册、token verify/introspect。 |
| 企业接口 | 企业/监管/公众 | 备案、审核、企业详情、企业公示。 |
| 产品接口 | 企业/监管/执行域 | 企业产品维护、监管查看、内部产品查询。 |
| 检查接口 | 监管/企业 | 检查任务、检查记录、企业检查记录。 |
| 整改接口 | 企业/监管 | 我的整改、提交整改、复核、动作日志。 |
| 投诉接口 | 公众/监管 | 提交、我的投诉、列表、详情、受理、派发、处理、驳回。 |
| 预警接口 | 监管/内部服务 | 预警列表、详情、指派、处理、解决、内部 upsert。 |
| 抽检接口 | 监管/执法/公众 | 抽检任务、我的抽检、提交结果、发布/下线、公众结果。 |
| 公告接口 | 监管/公众 | 公告管理、公众公告列表和详情。 |
| 统计接口 | 监管 | 预警统计、监管概览聚合。 |
| 文件接口 | 公众/企业 | 投诉、整改场景预签名上传。 |

关键调用关系：

- `gateway-service` -> `user-service` introspect。
- `regulation-operation-service` -> `regulation-service` 获取企业/产品/监管人员和写重点监管。
- `complaint-service` -> `regulation-service` 校验企业、监管员、写重点监管。
- `regulation-operation-service` -> `warning-service` 通过 outbox 投递预警。
- `query-service` -> 企业/执行/投诉/预警内部统计接口聚合概览。

当前缺失的重要接口类型：

- 完整追溯/召回接口：不纳入。
- 检测机构报告接口：不纳入。
- 行政处罚案件接口：不纳入。
- 通用操作日志接口：不纳入。
- 生产级配置治理接口：不纳入当前版本。

### 4.12 非功能需求

安全性：

- 网关受保护接口默认 fail-closed。
- JWT 用于用户身份识别。
- 内部接口通过 `X-Internal-Token` 保护。
- 文件上传按角色和业务类型限制。
- 默认 JWT secret、内部 token、MinIO 默认凭据仍为风险，不能表述为生产级安全完成。

可用性：

- 当前目标是本地或演示环境稳定运行。
- 交付前应补完整在线手工验收记录。

可维护性：

- 保持现有微服务边界。
- 不新增复杂服务和中间件。
- 前端当前不做 Vue Router 大重构。

扩展性：

- 可未来扩展批次、召回、检测机构，但当前版本不做。
- `query-service` 可未来接入离线统计，但当前不启用 `stat_*`。

性能：

- 列表接口应分页。
- 监管概览适配中小规模演示数据。
- 不承诺生产级性能指标。

日志审计：

- 整改、投诉、预警已有业务过程记录。
- 不做通用操作日志中心。

权限控制：

- 角色路径控制 + 服务内企业/辖区/任务归属校验。
- 不做复杂 ABAC/RBAC 权限平台。

数据一致性：

- 预警事件通过 Outbox + 重试增强一致性。
- 不引入分布式事务。

微服务治理：

- 使用 Nacos、Sentinel、Gateway、OpenFeign。
- 不新增 Redis/MQ/Seata/K8s 作为当前交付依赖。

### 4.13 当前项目与理想需求的差距分析

已有基础：

- 主体纳管、检查整改、投诉反馈、预警处理、产品档案、抽检结果、公示公告、概览统计均已形成。

当前不足：

- 不是生产级安全配置完成态。
- 不是完整全链路食品安全平台。
- 没有追溯、召回、检测机构、处罚案件、离线数仓。
- 演示和部署材料仍需收口。

偏差原因：

- 前期需求分析偏弱，先搭微服务和页面，后补业务闭环。
- 旧阶段偏向通用后台和统计看板，食品安全专业对象不足。
- 后期 P1/P2 已补主线，但旧文档未及时更新。

修正建议：

- 以当前主线为准，不再扩新域。
- 旧文档标为历史分析，新 PRD 作为当前基线。
- 交付前补演示脚本、数据、运行说明和验收记录。

### 4.14 迭代规划建议

阶段 1：收束功能边界  
建设重点：冻结 P2-5/P3，不新增追溯、召回、检测机构、处罚、大屏。  
目标成果：交付口径一致，PRD、纠偏方案、验收报告不冲突。  
优先级理由：避免继续跑偏。

阶段 2：补齐核心演示链路  
建设重点：准备企业备案公示、检查整改、投诉反馈、抽检公示、重点监管、监管概览 6 条演示路径。  
目标成果：能完成浏览器级演示。  
优先级理由：毕业设计答辩最需要可讲通的闭环。

阶段 3：完善统计预警与展示  
建设重点：确保概览指标、预警列表、重点监管原因展示稳定。  
目标成果：监管价值可被直观看到。  
优先级理由：展示微服务协同与监管闭环深度。

阶段 4：优化文档与答辩材料  
建设重点：运行说明、风险说明、架构图、接口说明、演示脚本。  
目标成果：答辩材料可直接使用。  
优先级理由：当前代码已足够支撑主线，文档收口比继续开发更重要。

### 4.15 毕业设计视角建议

最适合答辩展示的功能：

- 企业备案 -> 审核 -> 公众公示。
- 检查任务 -> 不合格记录 -> 整改 -> 复核 -> 预警。
- 公众投诉 -> 受理 -> 派发 -> 处理 -> 公众反馈。
- 产品档案 -> 抽检任务 -> 不合格结果 -> 重点监管 -> 公众公示。
- 监管概览查看。

不宜继续扩展的功能：

- 检测机构角色。
- 批次级追溯。
- 召回管理。
- 行政处罚案件。
- 大屏 BI/离线数仓。
- 通用操作日志中心。
- 复杂权限系统。

如何体现微服务架构价值：

- 用服务边界解释业务域：用户、网关、主数据、执行、投诉、预警、查询。
- 用 Feign 调用解释跨域协作。
- 用 Outbox 解释预警事件可靠投递。
- 用网关鉴权和服务内归属校验解释权限控制。

如何平衡技术深度和业务完整性：

- 技术深度集中在网关鉴权、服务拆分、Feign、Outbox、统计聚合。
- 业务完整性集中在企业、检查、整改、投诉、抽检、公示和预警闭环。
- 不用新增中间件堆技术名词。

如何避免大而空：

- 不做“全链路食品安全监管平台”承诺。
- 不把预留表写成已实现能力。
- 不把默认密钥写成生产级安全。
- 不把 P3 放弃项写成后续必做。

## 5. 后续建议：下一步优先改什么

### 5.1 立即优先项

1. 固化 PRD 和纠偏方案口径：P2 业务增强主线完成，P2-5 不再推进，P3 放弃。
2. 准备 6 条演示路径脚本：企业备案公示、检查整改、投诉反馈、抽检公示、重点监管、监管概览。
3. 准备演示数据：普通企业、重点监管企业、产品、抽检任务、不合格抽检结果、投诉、整改、预警。
4. 补最小运行说明：启动顺序、依赖、环境变量、数据库初始化、前端地址。
5. 补完整在线手工验收记录。

### 5.2 只在发现阻断时处理

- 接口调用失败。
- 页面无法进入。
- 演示路径状态流转断裂。
- 测试或前端构建失败。

### 5.3 不建议继续处理

- P2-5 配置治理。
- P3 通用日志、复杂角色、区域交接。
- 检测机构、实验室、追溯、召回、处罚、大屏 BI。
- 新增微服务、新增中间件、前端路由大重构。

### 5.4 当前最终建议

> 当前项目最有价值的方向不是继续扩功能，而是把“企业纳管、检查整改、投诉反馈、风险预警、产品抽检、公示公告、监管概览”这条主线讲清楚、演示稳定、文档一致。
