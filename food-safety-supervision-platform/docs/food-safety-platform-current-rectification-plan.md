# 微服务食品安全监管平台当前版纠偏方案

版本：V1.0  
日期：2026-04-07  
文档性质：基于当前代码、P0/P1/P2 验收结果和最新范围决策形成的当前版纠偏方案  

---

## 1. 当前项目状态摘要

当前项目已经不再处于旧 PRD 和旧纠偏方案描述的“中期纠偏半成品”状态。

当前真实状态如下：

- P0 已完成：前端空入口、网关 fail-open、文件上传权限、`query-service` 职责收束均已有验收记录。
- P1 已完成：企业公示、公告发布与展示、企业检查记录、投诉反馈、重点监管联动均已有验收记录。
- P2-1 到 P2-4 已完成：产品档案、抽检任务与结果、公示与风险联动、监管概览统计均已有代码和测试证据。
- P2-5 配置治理未执行，且当前决策为不再推进。
- 原纠偏方案中的 P3 低优先级/可放弃项，当前决策为整体放弃。
- 当前项目应进入“交付收口与演示稳定”阶段，不再进入新的功能建设阶段。

当前最合理的项目定位是：

> 基于微服务架构的区域食品安全监管协同平台，已覆盖企业纳管、检查整改、投诉反馈、风险预警、公众公示、产品档案、抽检结果和监管概览等核心演示闭环。

## 2. 本轮纠偏目标

本轮纠偏不是继续补新功能，而是完成当前项目的交付收口。

目标包括：

1. 修正旧 PRD 和旧纠偏方案中已经过时的项目判断。
2. 明确 P0/P1/P2-1 到 P2-4 已完成的问题不再重复整改。
3. 明确 P2-5 不再推进，并作为已接受风险处理。
4. 明确 P3 整体放弃，不再作为后续待办。
5. 固化当前版本 PRD、验收口径、演示路径和风险说明。
6. 将后续工作限制为文档、演示、验收记录和阻断性 bugfix。

## 7. 根因分析

### 7.1 历史根因

旧阶段的问题主要来自：

- 需求分析不足，项目名称和核心对象不匹配。
- 微服务和前端页面先行，业务闭环后补。
- 统计、门户、后台管理等方向容易扩大范围。
- 食品安全专业对象最初不足。

这些问题已经通过 P0/P1/P2 主线整改大幅缓解。

### 7.2 当前根因

当前剩余问题的根因不是业务功能缺失，而是：

- 交付口径没有同步升级。
- 配置治理被放弃后需要明确风险接受。
- 历史文档仍容易引导继续扩展。
- 演示和部署材料尚未收口。

## 10. 每项整改的目标、范围与验收标准

### 10.1 当前版 PRD

目标：

范围：

- 文档新增。
- 不改业务代码。

验收标准：

- 明确项目定位。
- 明确当前版本能力。
- 明确非目标范围。
- 明确 P2-5 和 P3 处理原则。
- 明确风险说明。

### 10.2 当前版纠偏方案

目标：

- 基于当前真实问题给出新的整改路线。

范围：

- 文档新增。
- 不重复处理 P0/P1/P2-1 到 P2-4 已完成事项。

验收标准：

- 问题分类清晰。
- 优先级清晰。
- 已解决、遗留、新发现问题区分清楚。
- 后续路线不继续扩功能线。

### 10.3 演示脚本

目标：

- 保证答辩时能讲清楚系统价值。

范围：

- 文档或演示材料。
- 不强制改代码。

验收标准：

- 至少覆盖：
  - 企业备案公示
  - 公告发布展示
  - 检查整改闭环
  - 投诉反馈闭环
  - 抽检结果公示
  - 监管概览统计

### 10.4 演示数据

目标：

- 保证每条演示路径有稳定数据。

范围：

- 本地数据库数据准备。
- 可选新增数据脚本，但不新增业务功能。

验收标准：

- 至少有普通企业、重点监管企业、产品、抽检任务、不合格抽检结果、投诉单、整改任务、预警记录。

### 10.5 最小运行说明

目标：

- 降低复现和验收成本。

范围：

- 文档。
- 不要求 Docker Compose 或 K8s。

验收标准：

- 写清楚基础设施依赖。
- 写清楚服务启动顺序。
- 写清楚前端环境变量。
- 写清楚默认配置风险。
- 写清楚 SQL 初始化脚本注意事项。

## 13. 当前事实 / 推断 / 待验证项

### 13.1 事实

- 当前代码存在产品档案、抽检任务、公众抽检结果、监管概览聚合接口。
- `food_product`、`sampling_task`、`sampling_result`、`public_bulletin`、`enterprise_key_reason` 表存在。
- P0、P1、P2-1 到 P2-4 有验收记录。
- P2-5 未执行，且当前决策为不再推进。
- P3 已整体放弃。
- 默认 JWT secret、内部 token、MinIO 默认凭据仍存在。
- `query-service` 的 `stat_*` 表仍是预留表。

### 13.2 推断

- 当前项目应定义为“交付收口态的区域食品安全监管协同平台”。
- 当前纠偏重点应从功能建设转为交付、演示、验收记录和风险说明。
- P3 放弃对当前交付价值影响可接受，因为当前主线已经能支撑毕业设计叙事。

### 13.3 待验证项

- 拉起完整 Nacos、MySQL、MinIO、网关和全部服务后的浏览器级手工验收。
- 演示数据是否覆盖重点监管、抽检不合格、投诉反馈、整改逾期等关键场景。
- SQL 初始化脚本在实际本地数据库执行策略中是否存在误删风险。
- 若未来转向生产部署，配置治理、审计日志、容器化和密钥管理需要重新立项。

## 14. 总结

当前项目不需要继续沿用旧纠偏方案的开发路线，也不应继续扩展 P3。

当前版纠偏结论为：

> 保留 P0、P1、P2-1 到 P2-4 的业务整改成果；P2-5 不再推进；P3 整体放弃；后续只做交付、演示、验收记录和阻断性 bugfix。
