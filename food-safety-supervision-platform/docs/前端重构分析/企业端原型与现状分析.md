更新时间：2026-04-10

## 1. 目的

本文档用于后续“新前端项目”的企业端模块落地实现，基于当前仓库内已存在代码与企业端原型页面的实际扫描结果整理而成。

- 可运行前端项目：`food-web`
- 企业端原型目录：`企业端原型页面/stitch_`
- 只做结构与实现现状分析，不包含代码改造

## 5. 原型页面之间是否已有跳转关系

当前没有真实跳转关系，只有页面结构和文案上的流程意图。

已确认情况如下：

- 原型页中的侧边导航、卡片按钮、操作按钮大量使用 `href="#"` 或纯按钮
- 未发现路由配置
- 未发现页面间脚本跳转
- 未发现统一入口文件将这些页面串联为单个应用

但从页面标题、面包屑和操作文案，可以明确看出原型希望表达的业务流向：

- 工作台 -> 企业备案 / 产品档案 / 检查记录 / 整改任务
- 企业备案 -> 产品档案
- 产品档案列表 -> 新增产品档案 / 产品详情 / 编辑产品
- 检查记录列表 -> 检查记录详情 -> 关联整改任务
- 整改任务列表 -> 整改任务详情 -> 提交整改 -> 提交成功

结论：

- 当前企业端 Stitch 原型页彼此独立
- 还没有被路由系统、请求层、状态系统真正串联

## 7. 当前可运行前端项目中的企业端现状

### 7.1 企业端入口位置

当前 `food-web` 中，企业用户登录成功后并不会进入独立路由，而是由：

- `food-web/src/App.vue`

通过顶层 `view` 状态切到企业端视图：

- `view === "enterprise"`

实际承接组件为：

- `food-web/src/views/EnterpriseProfileView.vue`

### 7.2 企业端页面组织方式

当前项目没有独立的企业端路由系统，也没有按原型拆成多个页面。

当前企业端实现方式是：

- 用一个 `EnterpriseProfileView.vue` 承载主要企业端功能
- 通过组件内部 `section` 状态切换四个一级模块：
  - `profile`：企业备案
  - `products`：产品档案
  - `inspections`：检查记录
  - `rectification`：整改任务

这意味着当前实现更接近“单页面后台面板”，而不是原型中的“多页面工作台”结构。

基于实际代码，当前企业端与原型相比，至少存在以下结构差异：

- 没有独立的企业工作台页面，对应原型 `_9`

- 整改提交不是独立页，而是列表内联操作

## 10. 企业端原型与现有实现的核心差异

可以把当前差异概括为两类：

### 10.1 页面结构差异

- 原型是“多页面、多详情页、多成功页”的信息架构
- 当前实现是“单组件内部分栏 + 弹窗 + 内联操作”

### 10.2 交互粒度差异

- 原型强调明确的页面跳转和任务流转
- 当前实现更强调在同一页面内快速完成操作

这会直接影响后续新前端项目的改造方式：

- 如果继续沿用旧结构，改造成本低，但很难还原原型的页面层级
- 如果要贴近 Stitch 原型，应该拆出正式路由，并把“列表 / 详情 / 编辑 / 提交成功”分开实现

## 11. 后续建议的最小改造顺序

建议继续按“小步改造”的方式推进，不要一次性搬完整个企业端。

推荐顺序如下：

1. 先做企业端信息架构整理，只搭骨架，不急着全接接口。
2. 第一批优先落地四个一级页面：
   - 工作台
   - 企业备案
   - 产品档案
   - 整改任务
3. 第二批再补详情页和操作页：
   - 产品详情
   - 检查记录详情
   - 整改任务详情
   - 提交整改
4. 最后再补反馈页与细节页：
   - 提交成功
   - 编辑产品
   - 企业备案详情细化

更具体地说，如果和前面的注册登录改造方式保持一致，企业端第一步最稳妥的是：

- 先新建独立企业端前端骨架，不改 `food-web`
- 引入 `vue-router`
- 先把原型中的四个一级入口页串起来
- 优先复用现有请求封装与字段命名
- 对“详情页 / 成功页”先做静态路由骨架，再逐步接入真实接口

## 12. 当前阻塞点

基于当前代码扫描，后续企业端真正开始改造前，需要注意以下阻塞或不确定项：

- 当前企业端原型是多页面结构，但旧项目企业端是单组件结构，后续拆分时需要先确定页面边界
- 产品详情页、整改提交成功页在旧项目中没有直接对应接口输出，需要先明确前端如何组装展示数据
- 原型中的工作台页 `_9` 在旧项目中没有直接对应实现，需要明确是否新建独立首页
- 当前没有正式路由体系，后续企业端一旦拆页，就需要同步确定导航、返回路径和登录后的承接方式
