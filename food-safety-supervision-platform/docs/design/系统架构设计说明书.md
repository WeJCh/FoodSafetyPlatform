# 食品安全监管平台 — 系统架构设计说明书

| 项目 | 内容 |
|------|------|
| 系统名称 | 基于微服务的食品安全监管平台 |
| 文档版本 | V1.0 |
| 编写说明 | 以当前仓库模块、`gateway-service`、Feign 客户端与调度器实现为准 |

---

## 1. 引言

### 1.1 编写目的

描述系统总体架构、微服务划分、服务间协作、网关与安全策略及关键技术选型，为开发与验收提供架构层依据。

### 1.2 架构风格

采用 **Spring Cloud 微服务架构**：API 网关统一入口、Nacos 服务发现、OpenFeign 服务间调用、按业务域分库部署。

---

## 2. 系统总体架构

### 2.1 逻辑分层

```
┌─────────────────────────────────────────────────────────┐
│  表现层：food-web（Vue3 + Vite，Nginx 静态托管）           │
└───────────────────────────┬─────────────────────────────┘
                            │ HTTP /api/*
┌───────────────────────────▼─────────────────────────────┐
│  网关层：gateway-service（8080）                          │
│  JWT 校验、角色鉴权、登录限流、禁止直连 warning-service    │
└───────────────────────────┬─────────────────────────────┘
                            │ lb://*
┌───────────────────────────▼─────────────────────────────┐
│  业务服务层（7 个 Spring Boot 服务，8081～8086）           │
└───────────────────────────┬─────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────┐
│  基础设施：MySQL 8、Redis 7、Nacos 2.3、MinIO             │
└─────────────────────────────────────────────────────────┘
```

### 2.2 部署形态（当前仓库）

- **Docker Compose 一键部署**：`docker-compose.yml` 包含 MySQL、Redis、Nacos、MinIO、全部后端服务、网关及 `food-web`（Nginx 80 端口反代网关）。
- **本机构建 + 上传部署**：见 `deploy/build/README.md` 与 `deploy/build/build-artifacts.ps1`。

> 说明：`docs/` 下部分早期文档曾描述「无 Docker / 无 compose」，与当前仓库不符，以 `docker-compose.yml` 为准。

## 3. 微服务划分

| 服务 | 端口 | 数据库 | 职责概要 |
|------|------|--------|----------|
| gateway-service | 8080 | — | 路由、认证鉴权、CORS、登录限流 |
| user-service | 8081 | food_user_db | 注册登录、用户/角色、Token 签发与 introspect |
| regulation-service | 8082 | food_regulation_db | 企业/产品/辖区/监管员、公告、文件（MinIO）、**预警代理** |
| query-service | 8083 | food_query_db（预留） | 统计聚合（Feign 拉取各服务 internal API） |
| warning-service | 8084 | food_warning_db | 预警记录、去重、升级、归档 |
| complaint-service | 8085 | food_complaint_db | 公众投诉受理与处理 |
| regulation-operation-service | 8086 | food_regulation_operation_db | 检查、抽检、整改、预警 Outbox |

前端：`food-web`，开发默认 `5173`，生产由 Nginx 提供静态资源并将 `/api/` 转发至 `gateway-service:8080`。

## 4. API 网关设计

### 4.1 路由规则（application.yml）

| 路径前缀 | 目标服务 |
|----------|----------|
| /api/auth/**、/api/user/**、/api/users/**、/api/roles/**、/api/admin/** | user-service |
| /api/regulation/**、/api/files/** | regulation-service |
| /api/regulation-operation/** | regulation-operation-service |
| /api/complaints/** | complaint-service |
| /api/query/** | query-service |
| /api/warning/** | warning-service（**外部禁止访问**，见 4.2） |

同时启用 `discovery.locator`，支持通过服务名发现实例（`lb://服务名`）。

### 4.2 安全策略（JwtAuthFilter）

1. **白名单**（无需 Token）：`/api/auth/login`、`/api/auth/verify`、公众/企业注册、健康检查等。
2. **JWT 签名校验** + 调用 user-service **introspect** 校验用户状态与角色。
3. **角色路由规则**：按路径前缀绑定 `ADMIN`、`REGULATOR_ADMIN`、`REGULATOR_ENFORCER`、`ENTERPRISE`、`PUBLIC` 等。
4. **禁止外部访问 warning-service**：凡 `path.startsWith("/api/warning/")` 直接返回 403；监管端通过 **`/api/regulation/warnings/**`** 由 regulation-service 代理（`WarningProxyController` + `WarningServiceClient`）。
5. 鉴权通过后向下游注入请求头：`X-User-Id`、`X-Username`、`X-User-Type`、`X-User-Roles`。
6. **登录限流**：基于 Redis，按 IP / 用户名窗口限制（可配置 fail-open）。

### 4.3 跨域

网关全局 CORS 允许本地开发前端源（`localhost:5173/5174` 等），生产需在配置中扩展 `allowed-origin-patterns`。

## 5. 服务间协作（OpenFeign）

### 5.1 调用关系总览

```
query-service ──Feign──► regulation-service / regulation-operation-service
                        complaint-service / warning-service

regulation-operation-service ──Feign──► regulation-service（企业/产品/监管员）
                                      warning-service（Outbox 投递）

complaint-service ──Feign──► regulation-service（企业校验等）
                            user-service
                            warning-service（同步 upsert）

regulation-service ──Feign──► user-service（用户信息）
                              warning-service（预警代理，带 internal token）

warning-service ──Feign──► regulation-service（监管员 internal 查询）
```

### 5.2 内部接口与 Token

跨服务 **internal** 接口使用配置项：

- `REGULATION_INTERNAL_TOKEN`
- `WARNING_INTERNAL_TOKEN`

由调用方在 Feign 请求头携带，防止绕过网关的未授权访问。具体 Header 名以实现类为准（如 `X-Internal-Token`）。

### 5.3 统计查询实现

`query-service` **不依赖** `food_query_db` 中 `stat_*` 表的主链路写入；运行时通过 Feign 调用：

- `RegulationEnterpriseStatsClient`
- `RegulationOperationStatsClient`
- `ComplaintStatsClient`
- `WarningStatsClient`
- `RegulationRegionClient`、`RegulatorProfileClient`

聚合后返回前端统计接口。

## 6. 预警子系统架构（双通道）

| 来源 | 机制 | 典型场景 |
|------|------|----------|
| regulation-operation-service | **Outbox 表** `warning_event_outbox` + 即时/定时重试 | 检查连续不合格、抽检不合格、整改 SLA 超期 |
| complaint-service | **同步 Feign** `upsertInternalEvent` | 投诉量溢出等重点监管触发 |

warning-service 侧：

- 按 `dedup_key` 幂等写入 `warning_record`
- `WarningEscalationScheduler` 等定时任务处理 L1→L2 升级、自动归档（Redis 分布式锁）

监管人员前端仅访问 `/api/regulation/warnings/**`，不直接调用 `/api/warning/**`。

---

## 7. 定时任务与后台作业

| 服务 | 调度器（示例） | 作用 |
|------|----------------|------|
| regulation-operation-service | `WarningEventOutboxRetryScheduler` | Outbox 失败重投 |
| regulation-operation-service | `RectificationSlaScheduler` | 整改 SLA 检测并触发预警 Outbox |
| warning-service | `WarningEscalationScheduler` | 预警升级与归档 |

调度器普遍结合 Redis 锁（`WarningSchedulerLockSupport`）避免多实例重复执行。

---

## 8. 文件与对象存储

`regulation-service` 集成 **MinIO**（`MINIO_ENDPOINT`、`MINIO_BUCKET` 等），用于企业备案附件、投诉材料等；对外 URL 可使用 `MINIO_PUBLIC_ENDPOINT` 供浏览器访问。

网关对 `/api/files/**` 限制为 `PUBLIC`、`ENTERPRISE` 角色。

## 10. 非功能设计要点

| 维度 | 设计 |
|------|------|
| 可用性 | 各服务无状态，可水平扩展；网关 introspect 支持可配置 fail-open（默认关闭，仅排障） |
| 安全 | 网关统一鉴权；warning 内网化；BCrypt 密码；内部 Token |
| 可观测 | 各服务 audit_log；网关与业务 INFO 级鉴权/关键操作日志 |
| 一致性 | 跨库最终一致：Outbox + 重试；投诉预警同步调用带业务异常回滚 |
