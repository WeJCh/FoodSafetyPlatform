# 阶段6-第5章系统实现正文初稿.md

## 第5章 系统实现

### 5.1 系统实现概述

#### 5.1.1 开发环境与运行环境

根据父工程 `pom.xml` 和前端 `package.json` 配置，本项目后端采用 Java 17 作为开发语言，基于 Spring Boot 3.2.5、Spring Cloud 2023.0.1 和 Spring Cloud Alibaba 2023.0.1.0 实现微服务开发；前端采用 Vue 3、Vue Router 4 和 Vite 5 构建单页应用。后端工程通过 Maven 进行依赖管理与构建，前端工程通过 Node.js 环境下的 npm 脚本完成开发与构建。

从运行依赖看，系统本地运行至少需要 MySQL、Redis 和 Nacos 环境。其中 MySQL 用于各服务独立业务数据存储，Redis 用于会话、缓存、限流和分布式锁支持，Nacos 用于服务注册发现与配置管理。`regulation-service` 还额外依赖 MinIO，用于生成文件预签名上传地址。各服务配置文件中同时存在 Sentinel 相关参数，说明系统运行过程中保留了流量治理接入能力。

#### 5.1.2 主要开发工具与工程组织

系统后端采用 Maven 多模块工程组织方式，父工程统一管理版本依赖，子模块分别对应网关服务、用户服务、监管基础服务、监管操作服务、投诉服务、统计查询服务、预警服务和公共模块。前端以 `food-web` 目录独立存在，与后端形成前后端分离结构。

从代码结构看，后端各服务均采用较为清晰的分层方式组织，包括控制器、服务、数据访问、实体对象、数据传输对象和返回对象等部分。前端则按照角色和业务页面划分视图目录，并通过 `src/api` 统一封装接口调用，通过 `src/router` 管理页面路由，通过 `src/session` 管理本地会话恢复逻辑。该组织方式使论文中的“系统已实现”能够具体落实到工程目录、模块边界和调用结构上，而不是停留在抽象设计层面。

#### 5.1.3 项目结构与启动方式

项目启动入口由各服务的 `*Application.java` 提供。`gateway-service`、`user-service`、`regulation-service`、`regulation-operation-service`、`complaint-service`、`query-service` 和 `warning-service` 均定义了独立的 Spring Boot 启动类，其中部分服务启用了 `@EnableFeignClients`，`regulation-service`、`regulation-operation-service` 和 `warning-service` 还启用了 `@EnableScheduling`，用于整改 SLA 与预警事件重试等定时任务处理。

前端 `food-web` 通过 `npm run dev` 启动 Vite 开发服务，通过 `npm run build` 生成生产构建文件。后端各服务可分别以 Spring Boot 应用方式独立启动，默认端口分别为网关 8080、用户服务 8081、监管服务 8082、查询服务 8083、预警服务 8084、投诉服务 8085、监管操作服务 8086。网关配置中已对前端本地开发地址 `http://localhost:5173` 和 `http://localhost:5174` 开启跨域支持，因此项目具备本地前后端联调运行条件。

需要说明的是，项目代码中未发现 Docker、Docker Compose 或 Kubernetes 部署文件，因此本章仅将启动方式表述为本地多服务独立启动和常规分服务部署，不扩展到未实现的容器化部署方案。

### 5.2 功能模块实现

#### 5.2.1 登录认证与权限控制实现

统一认证是本系统实现层最基础、也是最关键的模块之一。该模块的实现目标是完成多角色用户登录、令牌签发、令牌校验、会话失效和接口权限控制。

在后端实现中，`user-service` 的 `AuthController` 提供登录、登出、校验和内省接口；`AuthServiceImpl` 负责令牌校验与内省逻辑。其实现并非只做 JWT 签名验证，而是在签名通过后进一步检查 Redis 黑名单、查询缓存的内省结果，并在必要时回源数据库读取用户、角色和状态信息，再将结果缓存回 Redis。这样一来，系统既保留了 JWT 的无状态特性，又通过 Redis 会话缓存和黑名单机制实现了令牌失效控制。

在网关实现中，`gateway-service` 的 `JwtAuthFilter` 负责统一拦截认证请求。该过滤器首先放行登录、注册和健康检查等白名单请求，然后对其余请求提取 `Authorization` 头中的令牌并校验签名；签名通过后，网关通过 `http://user-service/api/auth/introspect` 调用用户服务的内省接口，获取当前用户是否有效、用户类型及角色列表，再依据接口路径与角色规则进行访问控制。认证通过后，网关会将 `X-User-Id`、`X-Username`、`X-User-Type` 和 `X-User-Roles` 等头信息传递给下游服务，从而为业务服务提供统一的身份上下文。

该实现体现了本项目在认证层的两个特点。第一，权限控制不是单点实现，而是“用户服务签发与内省 + 网关统一鉴权”的组合方式。第二，权限控制规则直接围绕真实业务路径配置，例如公众用户可以访问投诉提交接口和公开查询接口，企业用户可访问备案、产品和整改相关接口，监管人员则可访问监管、操作和统计接口。这使权限实现与系统角色模型保持一致。

在前端实现中，`food-web/src/api/auth.js` 对登录、注册、校验、内省和登出接口进行了统一封装；`food-web/src/session/authRuntime.js` 实现了浏览器端会话恢复逻辑。在页面刷新或路由切换时，前端会先读取本地保存的会话，再调用 `verify` 和 `introspect` 接口确认令牌是否仍然有效，并用返回的身份信息恢复当前登录态。`food-web/src/router/index.js` 中的路由守卫则进一步根据 `requiresRole` 元数据限制不同角色访问不同页面。这部分实现保证了页面权限与后端接口权限保持一致。

从论文展示角度看，本模块最适合引用的关键代码位置包括：`user-service` 中的 `AuthController`、`AuthServiceImpl`、`AuthRedisServiceImpl`、`TokenUtil`，以及 `gateway-service` 中的 `JwtAuthFilter`，前端则可引用 `authRuntime.js` 和 `router/index.js`。

#### 5.2.2 网关路由与服务调用实现

网关与服务调用模块的实现目标是将分散的微服务对外组织成统一访问入口，并在服务间建立清晰的协作关系。

在网关路由实现上，`gateway-service/src/main/resources/application.yml` 中使用 `lb://服务名` 方式将 `/api/auth/**`、`/api/users/**`、`/api/regulation/**`、`/api/regulation-operation/**`、`/api/complaints/**`、`/api/query/**` 和 `/api/warning/**` 等路径分别转发到对应服务。由于网关同时开启了服务发现定位器和全局跨域配置，因此前端在开发阶段只需访问网关地址，而不需要直接感知各个服务端口。

在服务调用实现上，项目使用 OpenFeign 组织跨服务协作。`regulation-service` 通过 Feign 调用 `user-service` 和 `warning-service`，`regulation-operation-service` 调用 `regulation-service` 和 `warning-service`，`complaint-service` 调用 `regulation-service`，`query-service` 则聚合调用多个服务的内部统计接口。与单体项目中直接调用本地业务类相比，这种实现方式更符合项目的微服务拆分结构。

本模块中较有论文价值的一个实现细节，是系统对预警访问采取了代理式路径控制。虽然网关配置中存在 `/api/warning/**` 路由，但 `JwtAuthFilter` 在实现中明确禁止前端直接访问该路径；监管端页面访问预警时，实际调用的是 `regulation-service` 中的 `WarningProxyController` 和 `WarningProxyServiceImpl`。该代理服务会根据当前监管人员身份构造辖区或责任人过滤条件，再转发给 `warning-service`。这一实现既复用了预警服务能力，又避免了前端绕过监管域边界直接访问预警服务。

从论文展示角度看，本模块适合引用的关键代码位置包括：`gateway-service/application.yml`、`JwtAuthFilter.java`、各服务中的 `@FeignClient` 接口，以及 `WarningProxyController`、`WarningProxyServiceImpl`。

#### 5.2.3 企业备案与基础监管数据实现

企业备案与基础监管数据模块是监管业务的主数据基础。其实现目标是完成企业档案建档、备案审核、产品档案维护、监管人员档案维护以及公开查询。

在企业备案实现中，`EnterpriseProfileController` 对外提供企业提交备案、查询备案、查看待审核企业、审核通过、审核驳回、批量审核和删除等接口。控制器先通过 `JwtUserResolver` 解析当前用户身份，再根据企业用户或监管用户角色进行访问限制，随后调用 `EnterpriseProfileService` 完成具体业务处理。

`EnterpriseProfileServiceImpl` 的实现体现了较完整的业务落地过程。企业提交备案时，服务会校验区域信息、写入或更新地址信息、保存企业基础字段，并将审核状态统一重置为 `PENDING`；若企业存在附件，则通过附件表保存附件信息；最后清理企业主数据缓存和公开缓存，保证后续查询获取到更新后的数据。审核通过或驳回逻辑则围绕 `approval_status`、`approved_by`、`approved_time` 和审核意见等字段展开，体现了主数据与审核状态在同一业务服务中集中管理的实现思路。

在产品档案实现中，`ProductController` 提供企业用户的产品查询、新增、修改，以及监管端查看企业产品的接口。由于抽检任务依赖产品档案，因此产品模块与后续监管操作模块形成了直接联动。

在监管人员数据实现中，系统管理员通过用户服务创建监管账号，监管服务再通过 `RegulatorProfileController` 完成监管人员档案维护和辖区配置。这样实现了“账号创建”与“监管档案维护”在不同服务内的分工协同。

在前端实现上，企业端提供备案总览、备案详情、产品列表、新增产品、编辑产品和产品详情等页面；监管端提供备案审核、企业管理和企业详情页面。页面层通过 `food-web/src/api/regulation.js` 中的接口封装完成与后端的联调。

本模块适合论文展示的关键代码位置包括：`EnterpriseProfileController`、`EnterpriseProfileServiceImpl`、`ProductController`、`RegulatorProfileController`，以及前端的企业备案和产品档案相关页面。

#### 5.2.4 检查、抽检与整改闭环实现

检查、抽检与整改模块构成了本项目最能体现食品安全监管业务特色的实现链路。其实现目标是把监管任务从创建、分派、执行、结果记录一直推进到整改复核和公开结果展示，形成完整闭环。

在检查任务实现中，`InspectionTaskController` 提供任务创建、分派、分页查询、执法人员我的任务、任务启动、结果提交和任务关闭等接口。控制器层通过 `RequestIdentityResolver` 获取当前请求身份，并将角色限制在监管用户范围内，再调用 `InspectionTaskService` 完成业务处理。

`InspectionTaskServiceImpl` 是这一链路中的核心实现类。区域管理员创建任务时，服务先通过 `OperationMasterDataSupport` 校验当前监管人员身份、核验目标企业已通过备案审核，并检查企业是否在当前监管人员辖区内；任务创建后会写入 `inspection_task` 表。任务分派时，服务进一步校验被分派执法人员是否属于可分派辖区。执法人员启动任务后，提交结果时系统会在事务中写入 `inspection_record` 和多条 `inspection_item`，如果检查结果或检查项存在不合格情况，则立即调用整改服务创建整改任务。

整改实现由 `RectificationController` 和 `RectificationServiceImpl` 完成。该服务在检查不合格后自动生成整改任务，设置企业提交截止时间；企业端提交整改时，服务会更新整改进展、变更状态并写入整改动作日志；监管端复核时，可执行确认或退回重改，系统同步更新整改状态、复核时间与整改日志。服务内部还通过 `OperationLockSupport` 对提交和复核操作加锁，避免同一整改任务在并发情况下出现重复处理。

抽检实现由 `SamplingTaskController`、`SamplingResultManageController` 和 `SamplingTaskServiceImpl` 共同完成。区域管理员创建抽检任务时，系统会校验企业是否处于已审核状态、产品是否为该企业的有效产品；执法人员提交抽检结果后，服务写入 `sampling_result` 表，并将结果初始设置为 `DRAFT`；只有监管端执行发布操作后，结果才会进入公众查询范围。该实现使抽检业务同时覆盖了内部任务流转和外部信息公示两个层面。

这一模块中还有一个重要实现细节，即业务异常与预警事件的联动。无论是检查连续不合格还是抽检不合格，监管操作服务都会构造 `WarningEventUpsertDTO`，并通过 `WarningEventOutboxService` 记录到 `warning_event_outbox` 表。后续 `WarningEventOutboxRetryScheduler` 会定时扫描待投递事件，并调用预警服务内部接口进行重试投递。该实现说明项目并未使用消息队列，而是采用了基于出站事件表和定时重试的可靠事件投递机制。

前端方面，区域管理员端实现了任务派发、检查记录、抽检任务、整改复核等页面，执法人员端实现了我的任务、检查结果提交、抽检结果提交、整改跟进等页面，企业端实现了整改任务查看、整改详情和整改提交等页面。由此可以证明该业务闭环不仅在后端完成了接口和服务实现，也在前端完成了交互落地。

本模块适合论文展示的关键代码位置包括：`InspectionTaskController`、`InspectionTaskServiceImpl`、`RectificationController`、`RectificationServiceImpl`、`SamplingTaskController`、`SamplingTaskServiceImpl`、`SamplingResultManageController`、`WarningEventOutboxServiceImpl` 和 `WarningEventOutboxRetryScheduler`。

#### 5.2.5 投诉处理与监管协同实现

投诉模块体现了平台面向公众监督的实现能力。其实现目标是使公众投诉能够进入监管内部流转，并形成可查询、可反馈的处理结果。

在公众端实现中，`PublicComplaintController` 提供投诉提交、我的投诉列表和投诉详情接口；`ComplaintCommandService` 中的 `submitPublic` 方法会先校验被投诉企业是否存在，再生成投诉单号、写入投诉人信息、投诉内容、图片地址和投诉状态，并返回可供前端展示的投诉跟踪结果。

在监管端实现中，`RegulatorComplaintController` 提供投诉分页查询、详情查看、受理、分派、开始处理、办结和驳回等接口。核心业务逻辑集中在 `ComplaintCommandService` 中。该类对投诉处理流程进行了较完整的状态控制：区域管理员受理投诉后将状态转为 `PENDING`；再由区域管理员将投诉分派给执法人员；执法人员启动处理后状态转为 `PROCESSING`；提交处理结果后，系统会写入单条处理记录并将投诉状态转为 `FEEDBACKED`；如不予受理，则由管理员执行驳回并记录驳回原因。

该模块还有一个较有价值的监管联动实现，即在受理投诉后，系统会统计一定时间窗口内企业被受理投诉的数量；若达到阈值，则调用监管基础服务将企业自动标记为重点监管对象。这说明投诉模块并不是孤立存在，而是能够将社会监督数据回流到监管主数据管理中。

前端方面，公众端实现了我要投诉、提交成功、我的投诉和投诉详情页面；监管端实现了投诉流转列表和投诉详情页面。页面调用主要集中在 `food-web/src/api/complaint.js`，前后端交互链路完整。

本模块适合论文展示的关键代码位置包括：`PublicComplaintController`、`RegulatorComplaintController`、`ComplaintCommandService`、`ComplaintDataSupport`，以及前端公众投诉与监管投诉页面。

#### 5.2.6 统计查询与预警代理实现

统计查询模块的实现目标是向监管端提供跨服务聚合后的概览结果，而不是依赖单个业务表直接出报表。

在后端实现中，`SupervisionOverviewController` 和 `WarningStatsController` 对外提供监管概览、预警概览、趋势、类型分布和处置效率等接口。其核心业务逻辑分别在 `SupervisionOverviewQueryServiceImpl` 和 `WarningStatsQueryServiceImpl` 中实现。以监管概览为例，服务会先构造查询范围，再分别调用企业统计、监管操作统计、投诉统计和预警统计接口，最后组合成一个统一的 `SupervisionOverviewVO` 返回给前端。与此同时，查询服务还利用 `QueryRedisCacheSupport` 为统计结果生成带作用域指纹的缓存键，以降低重复聚合查询带来的开销。

该实现说明本项目中的统计查询并不是通过 `query-service` 自己的统计表直接读取完成，而是通过内部接口聚合形成。数据库脚本中的 `stat_enterprise`、`stat_inspection` 和 `stat_complaint` 在当前阶段仍属于扩展预留设计，没有进入主运行链路。

预警访问实现则体现为“网关禁直连、监管服务做代理”的模式。监管端页面调用 `regulation-service` 中的预警代理接口，代理服务会根据当前监管人员身份补充辖区或责任人过滤条件，再转发至 `warning-service`。这种实现使预警能力在系统中以监管业务的一部分呈现，而不是作为前端直接访问的独立域。

前端方面，区域管理员和执法人员都实现了数据统计页面，区域管理员和执法人员还分别实现了预警列表与预警详情页面。对应接口主要分布在 `food-web/src/api/regulation.js` 中，包括预警查询、预警操作以及监管概览和预警统计查询接口。

本模块适合论文展示的关键代码位置包括：`SupervisionOverviewController`、`WarningStatsController`、`SupervisionOverviewQueryServiceImpl`、`WarningStatsQueryServiceImpl`、`WarningProxyController` 和 `WarningProxyServiceImpl`。
