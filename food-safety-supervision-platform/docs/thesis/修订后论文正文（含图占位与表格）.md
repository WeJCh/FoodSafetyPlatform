# 修订后论文正文（含图占位与表格）.md

## 第1章 绪论

### 1.1 项目背景及意义

食品安全直接关系到公众身体健康和社会公共安全，是公共治理中的重要内容。随着食品生产、流通和消费环节不断延伸，监管对象数量持续增加，监管业务流程也呈现出参与主体多、业务链条长、协同要求高等特点。在传统管理方式下，企业备案、监督检查、抽检公示、问题整改、公众投诉和风险预警等工作通常分散在不同业务环节中，容易出现信息分散、过程脱节和追踪困难等问题。因此，围绕食品安全监管业务建设统一的信息化平台，已成为提升监管规范化、流程化和协同化水平的重要手段。

结合本项目实际实现内容，食品安全监管并不是单一环节的信息录入，而是覆盖企业、监管部门和公众多方参与的闭环过程。企业需要完成基础信息备案并维护产品档案，监管部门需要开展备案审核、检查任务派发、抽检结果发布和整改复核，公众需要获取公开信息并进行投诉反馈，系统管理员还需要维护监管人员账号、角色类型和状态信息。上述业务天然具有明显的角色分工特征和数据协同需求，如果采用高度耦合的实现方式，后续在功能扩展、权限控制和服务协同方面都容易受到限制。基于这一背景，本课题以“基于微服务的食品安全监管平台”为题，围绕真实监管业务链构建面向多角色的管理平台。

本项目的研究意义主要体现在以下几个方面。第一，在业务层面，平台将企业备案、产品档案、检查任务、抽检结果、整改管理、投诉处理、公告公示、预警协同和统计查询等功能纳入统一系统，形成覆盖主要监管环节的业务闭环，有助于提高业务过程的连续性和可追溯性。第二，在技术层面，项目采用前后端分离与微服务架构，将用户认证、基础监管数据、监管操作、投诉处理、预警处理和统计查询按业务边界拆分为多个服务，并通过统一网关、服务注册发现和服务间调用机制实现协同处理，体现了面向业务边界进行系统拆分的设计思路。第三，在应用层面，系统同时面向系统管理员、区域管理员、执法人员、企业用户和公众用户，能够较真实地反映食品安全监管场景下多主体协同工作的业务特征，对本科毕业设计中软件开发研究类型论文的写作具有较好的支撑作用。

需要说明的是，本文所有结论均以仓库中已经实现的代码、配置、数据库脚本、页面和测试材料为依据。当前系统已经实现统一认证、企业备案、产品管理、检查与抽检、整改管理、投诉处理、公告管理、预警处理和统计查询等核心功能，但并未实现消息队列驱动的异步通信、容器化编排部署等扩展能力。因此，本文中的背景与意义分析均围绕已实现的平台能力展开，不对未实现内容作超出事实范围的延伸表述。

### 1.2 国内外研究现状

从信息化建设趋势看，围绕公共监管业务构建数字化平台已经成为普遍方向。相关系统研究与实践通常聚焦于业务流程电子化、数据集中管理、跨角色协同处理以及监管结果可追溯等方面。在食品安全领域，平台化建设的重点通常集中在企业主体信息维护、监督检查留痕、抽检信息发布、问题处置闭环以及公众参与渠道建设等内容。这说明食品安全监管系统已经不再局限于基础数据录入，而是逐步向流程联动、业务集成和服务化方向发展。

在系统架构层面，随着业务复杂度提升，越来越多的平台开始采用分层、模块化甚至服务化的实现方式。相较于传统单体架构，基于服务拆分的架构更适合处理多角色、多模块、多业务链条并行的场景，便于根据不同业务边界进行职责划分，并提升后续扩展和维护能力。与此同时，统一网关、服务注册发现、分布式鉴权和缓存机制等配套技术，也逐渐成为此类平台的重要组成部分。

在业务功能层面，现有相关平台通常已经覆盖企业信息管理、执法检查、抽检管理和基础查询等内容，但在完整业务闭环方面仍存在进一步整合空间。一方面，不同业务流程之间的数据衔接往往不够紧密；另一方面，面向公众的信息公开和投诉反馈机制在许多系统中仍与内部监管流程相对分离。对于食品安全监管业务而言，仅实现单点功能并不能充分体现平台价值，真正有效的系统应当能够支撑多角色协同、状态流转和信息共享。

在技术选型方面，主流实践通常围绕微服务框架、网关组件、注册发现方案、持久层技术和前端框架进行组合应用，其共同目标是提高系统的可维护性、可扩展性和可用性。本项目的切入点不是简单构建一个技术演示系统，而是围绕食品安全监管平台的实际业务需求，将企业备案、检查抽检、整改处理、投诉流转、公告公示、预警协同和统计查询纳入统一架构，并在代码层面落实服务划分、统一鉴权和跨服务协作机制。

第四，结合项目实际代码实现，对系统核心功能模块进行说明。系统已经实现统一登录认证与角色访问控制、企业备案审核与产品档案维护、检查任务与抽检任务管理、整改闭环处理、公众投诉与监管处置、公告管理、预警代理访问和统计查询等功能。

第五，对系统测试情况进行验证分析。项目中已经包含多项基于 JUnit 5、Spring Boot Test 和 MockMvc 的测试代码，覆盖网关鉴权、文件上传权限、产品档案、检查记录、抽检任务、投诉处理、预警统计和监管概览等内容。

## 第2章 相关技术

### 2.1 项目选用技术简介

#### 2.1.1 Spring Boot 与 Spring Cloud 微服务开发框架

本项目后端采用 Java 17 作为开发语言，并基于 Spring Boot 3.2.5 构建各个业务服务。项目父工程采用 Maven 聚合管理方式，将 `gateway-service`、`user-service`、`regulation-service`、`regulation-operation-service`、`complaint-service`、`warning-service`、`query-service` 和 `platform-common` 组织在同一工程中，既便于统一依赖版本管理，也便于按服务边界进行独立开发与部署。

在微服务层面，项目引入 Spring Cloud 2023.0.1 和 Spring Cloud Alibaba 2023.0.1.0 作为技术基础，使各服务能够围绕统一的服务治理体系协同运行。对于本项目这类多角色、多模块的监管平台而言，将用户认证、监管主数据、业务操作、投诉处理、预警处理和统计查询拆分为多个服务，有利于降低单体系统中业务逻辑高度集中的复杂性，也使后续功能扩展更符合业务边界。

#### 2.1.2 Nacos 服务注册发现与配置管理

为了支撑多服务协同运行，本项目在各服务中统一引入 Nacos Discovery 和 Nacos Config。Nacos Discovery 用于服务注册与发现，使网关和服务调用方能够通过服务名访问目标服务。Nacos Config 用于统一配置管理。虽然仓库中没有独立配置中心模块，但各服务已接入相关配置，说明系统具备外部配置治理能力。

#### 2.1.3 Spring Cloud Gateway 网关技术

本项目采用 Spring Cloud Gateway 作为统一网关。网关负责请求路由、跨域处理、JWT 校验、令牌内省和部分接口限流，是前后端交互中的统一入口。`gateway-service` 中配置了 `/api/auth/**`、`/api/regulation/**`、`/api/regulation-operation/**`、`/api/complaints/**`、`/api/query/**` 等路由规则，并基于 `JwtAuthFilter` 对请求进行统一鉴权处理。

#### 2.1.4 OpenFeign 服务间调用技术

在服务间协作方面，项目使用 OpenFeign 组织跨服务调用。监管服务需要调用用户服务和预警服务，监管操作服务需要调用监管服务和预警服务，投诉服务需要调用监管服务，查询服务需要聚合调用多个统计接口。这些调用关系均通过 `@FeignClient` 接口实现。

#### 2.1.5 MyBatis-Plus 持久层技术

本项目后端持久层采用 MyBatis-Plus。系统中存在较多结构清晰、状态字段较多、查询条件复杂但以业务表为核心的数据操作场景，例如企业备案、产品档案、检查任务、抽检结果、投诉记录和预警记录等。MyBatis-Plus 既保留了较强的 SQL 控制能力，又能减少单表基础操作的重复开发工作。

#### 2.1.6 MySQL 数据库技术

项目使用 MySQL 作为主要业务数据库。系统核心数据包括用户与角色、企业与产品、检查与整改、抽检、公示、投诉和预警等，均具有结构明确、关系清晰、事务性要求较强的特点，因此采用关系型数据库更为合适。

#### 2.1.7 Redis 缓存与协同控制技术

本项目中 Redis 主要用于会话缓存、令牌黑名单、公共数据缓存、统计结果缓存、限流计数和分布式锁支持。Redis 的引入提升了系统在读写效率和协同处理方面的能力。

#### 2.1.8 JWT 统一认证技术

项目采用 JWT 作为身份认证令牌。用户在登录成功后由用户服务签发令牌，后续请求统一由网关进行校验并调用内省接口确认令牌有效性，再将用户身份信息传递给下游业务服务。

#### 2.1.9 MinIO 文件存储技术

在文件处理方面，项目通过 `regulation-service` 引入 MinIO，用于支持备案附件和投诉、整改等场景中的文件上传。系统通过预签名上传方式生成文件上传地址，前端获得地址后直接上传到对象存储。

#### 2.1.10 Vue 3 前端技术栈

前端采用 Vue 3、Vue Router 4 和 Vite 5。项目中前端页面已按系统管理员、区域管理员、执法人员、企业用户和公众用户进行划分，并通过统一 API 客户端与网关交互，形成了较清晰的前后端协同结构。

#### 2.1.11 OpenAPI 文档与测试技术

在接口文档方面，`query-service` 集成了 Springdoc OpenAPI，并通过配置类定义接口文档信息。测试方面，项目统一引入 JUnit 5、Spring Boot Test 和 MockMvc，并在多个服务中编写了测试类，为后续系统测试章节提供了客观依据。

## 第3章 系统分析

### 3.1 系统业务需求

#### 3.1.1 平台建设目标

结合项目实际实现内容，平台建设目标主要包括以下几个方面：一是建立统一的食品安全监管业务平台，将企业备案、产品档案、检查任务、抽检任务、整改管理、投诉处理、公告发布、预警跟踪和统计查询纳入统一系统；二是支撑多角色协同监管，使系统管理员、区域管理员、执法人员、企业用户和公众用户围绕各自职责完成工作；三是提高监管过程的规范化和可追溯性，通过结构化数据记录业务状态流转；四是兼顾监管内部管理与公众服务需求，使平台同时具备内部监管与外部信息公开能力。

#### 3.1.2 主要业务对象与用户角色

系统管理员主要负责监管人员账号创建、信息查看和状态维护。区域管理员主要负责监管业务组织，包括企业备案审核、企业信息查看、检查与抽检任务管理、整改复核、投诉流转、公告管理、预警中心和统计概览等功能。执法人员主要承担一线业务执行工作，包括查看辖区企业、执行检查任务、提交检查结果、执行抽检任务、录入抽检结果、处理投诉和跟进整改等。企业用户主要负责企业备案资料维护、产品档案维护、查看检查记录、查看整改任务和提交整改结果。公众用户可以注册登录系统，查看公告、公示企业和抽检结果，并进行投诉提交与投诉跟踪。

#### 3.1.3 核心监管业务场景

结合后端控制器、前端页面和数据库设计，可以确认本项目围绕以下核心监管业务场景展开。

一是企业备案与基础信息审核场景。企业用户提交企业名称、许可证编号、统一社会信用代码、法定代表人、所属区域、地址及附件等备案信息，区域管理员对待审核企业进行查看、审核通过或驳回。

二是产品档案管理场景。企业用户在备案完成后维护本企业产品档案，监管人员端可以按企业查看产品信息，为抽检任务创建提供基础数据。

三是监督检查场景。区域管理员围绕企业创建检查任务并指派给执法人员，执法人员启动任务并提交检查结果，系统生成检查记录和检查项明细。若发现问题，后续可形成整改任务。

四是抽检与公示场景。区域管理员创建抽检任务并指定企业和产品，执法人员提交抽检结果，区域管理员决定是否发布抽检结果，公众用户查询已发布结果。

五是整改复核场景。检查发现问题后形成整改任务，企业提交整改进展和附件，监管人员查看整改详情和动作日志，并执行复核确认或退回整改。

六是投诉受理与处理场景。公众用户选择企业并提交投诉内容，区域管理员和执法人员围绕投诉完成受理、指派、处理、反馈或驳回。投诉信息既是社会监督的体现，也为后续监管重点识别和风险预警提供输入。

七是公告公示与预警统计场景。监管人员端管理公告发布与下线，公众用户查询公开信息；系统围绕整改超时、抽检不合格、投诉过载等业务事件形成预警记录，并通过查询服务向监管人员提供统计概览。

#### 3.1.4 主要业务流程

为保证系统分析与后续设计、实现章节保持一致，本项目主要业务流程可归纳为以下几条主线：企业备案流程、检查与整改流程、抽检与公示流程、投诉处理流程。

第一条主线为企业备案流程。企业用户注册登录后提交备案资料和附件，系统保存企业基础信息与附件信息，区域管理员查看待审核企业并执行审核或驳回，审核通过后企业进入可正常纳管状态。

第二条主线为检查与整改流程。区域管理员创建检查任务并分派给执法人员，执法人员执行检查并提交结果，系统生成检查记录；若结果不合格，则自动生成整改任务，企业提交整改内容，监管人员执行复核并形成闭环。

第三条主线为抽检与公示流程。区域管理员创建抽检任务，执法人员执行抽检并提交结果，系统保存抽检结果，区域管理员发布或下线结果，公众用户查询已发布的抽检信息。

第四条主线为投诉处理流程。公众用户提交投诉，区域管理员受理并指派给执法人员，执法人员处理后形成反馈结果，公众用户查看本人投诉详情和处理进度。

#### 3.2.2 用户与认证功能需求

系统需要提供统一的用户认证能力，以支撑多角色用户安全访问平台。具体包括公众用户和企业用户注册功能、统一登录与退出功能、令牌校验与身份识别功能，以及基于角色的访问控制功能。该部分需求对应用户服务中的认证逻辑、网关中的统一鉴权逻辑和前端中的路由权限控制。

#### 3.2.3 系统管理员功能需求

系统管理员主要负责监管人员管理，因此其功能需求集中在账号与人员初始化层面。具体包括监管人员账号创建、监管人员信息查看和监管人员状态维护等功能。

#### 3.2.4 区域管理员功能需求

区域管理员是系统中最核心的监管管理角色，其功能需求覆盖企业备案审核、企业信息监管、检查任务管理、抽检任务管理、整改复核、投诉流转管理、公告管理、预警中心和统计概览等方面。

#### 3.2.5 执法人员功能需求

执法人员承担监管执行任务，其功能需求主要围绕执行和反馈展开，包括辖区企业查看、检查任务执行、检查记录查看、抽检任务执行、抽检结果提交、投诉处理、整改跟进和个人预警处理等功能。

#### 3.2.6 企业用户功能需求

企业用户是被监管主体，其功能需求包括企业备案资料维护、产品档案管理、检查记录查看、整改任务处理和整改结果追踪等。企业端功能与监管人员端流程形成对应关系，共同完成企业纳管与问题整改闭环。

#### 3.2.7 公众用户功能需求

公众用户功能主要体现平台的信息公开与社会监督能力，包括公众注册登录、公告查询、企业公示查询、抽检结果查询、投诉提交和投诉跟踪等功能。

#### 3.2.8 统计查询功能需求

统计查询功能主要面向监管人员，要求系统能够围绕辖区范围聚合企业、监管操作、投诉和预警相关数据，并输出监管概览、预警概览、趋势、类型分布和处理效率等信息。

### 3.3 系统非功能性需求

#### 3.3.1 性能需求

系统需要具备基本的并发处理与响应能力。结合代码可确认，项目通过 Redis 支持热点数据缓存，通过网关和部分接口实现访问限流，通过服务间调用和缓存机制控制统计查询开销。当前未发现专项性能压测结果，因此本节性能需求主要体现为设计与实现上的性能保障方向，而非具体量化指标。

#### 3.3.2 安全性需求

系统涉及用户身份信息、企业备案信息、投诉信息和监管处理记录，因此需要明确的安全控制要求。项目已通过 JWT、网关统一鉴权、角色访问控制、Redis 会话管理、关键接口限流和文件上传约束等机制对安全风险进行控制。

#### 3.3.3 可维护性需求

为降低后续维护难度，系统需要具备良好的可维护性。项目已按业务边界将用户、监管主数据、监管操作、投诉、预警和统计查询拆分为独立服务，后端统一采用 Spring Boot、Spring Cloud、MyBatis-Plus、MySQL 和 Redis 技术栈，前端统一采用 Vue 3 技术栈，并通过 `platform-common` 提供公共能力。

#### 3.3.4 可扩展性需求

系统需要具备较好的扩展能力，以便在现有业务边界基础上增加新的监管流程和统计能力。当前项目已经通过服务拆分、统一网关和独立数据库设计为后续扩展预留了结构基础。

#### 3.3.5 可用性需求

系统需要满足多角色用户日常使用需求，至少保证本地开发与联调环境下可以完成主要业务访问。现有前端页面、网关跨域配置、各服务端口配置和测试材料均表明系统具备基本可用性。

### 3.4 可行性分析

#### 3.4.1 技术可行性

项目采用的 Spring Boot、Spring Cloud、Nacos、Gateway、OpenFeign、MyBatis-Plus、MySQL、Redis、JWT、MinIO 和 Vue 3 等技术均为成熟技术体系，能够满足多角色、多业务模块监管平台的开发需求。项目代码已经完整体现了微服务划分、统一网关、独立数据库、跨服务调用和前后端分离等核心实现路径，因此该技术路线在项目中具有明确可行性。

#### 3.4.2 操作可行性

从前端页面结构和路由设计看，系统已按角色划分独立功能空间，页面入口和导航路径较为清晰。不同角色进入系统后均可直接进入与自身职责匹配的页面，具备基本操作可行性。

#### 3.4.3 法律与合规可行性

系统处理的数据主要包括用户信息、企业备案资料、投诉信息、公告信息、检查记录、抽检结果和预警处理记录。项目已通过统一鉴权、角色隔离、文件类型控制和公开信息范围限制等机制对部分安全风险进行控制，公开内容也主要集中于公告、企业公示和已发布抽检结果，内部处理信息则通过权限隔离。

#### 3.4.4 社会可行性

食品安全问题与公众生活密切相关，监管平台建设不仅关系到内部监管效率，也关系到公众获取信息和参与监督的便利性。项目中已实现的公告查询、企业公示、抽检结果公示和投诉提交等功能，使公众能够获取公开信息并反馈问题，体现了平台在提升监管透明度和公众参与度方面的现实意义。

#### 4.1.3 服务关系与信息流设计

系统访问链路为：浏览器端页面发起请求，经网关完成跨域处理、令牌校验和路由转发后，再进入具体业务服务处理；各业务服务通过 Nacos 完成注册发现，并通过 OpenFeign 进行跨服务调用；数据最终分别写入各自服务对应的业务数据库。该结构使认证、企业主数据、监管操作、投诉处理、预警处理和统计查询形成既分工明确又可协同联动的服务体系。

系统中的服务协同关系由实际 Feign 调用定义。`regulation-service` 调用 `user-service` 和 `warning-service`；`regulation-operation-service` 调用 `regulation-service` 和 `warning-service`；`complaint-service` 调用 `regulation-service`；`query-service` 调用 `regulation-service`、`regulation-operation-service`、`complaint-service` 和 `warning-service`。这些调用关系构成了系统主要信息流。

#### 4.1.4 前后端交互与权限设计

权限控制采用“前端路由限制 + 网关统一鉴权”的双层方式。前端通过 `requiresRole` 元数据控制页面访问，网关通过 `JwtAuthFilter` 对请求路径执行角色校验。需要特别说明的是，网关代码中对 `/api/warning/**` 做了直接阻断，监管人员端对预警能力的访问通过 `regulation-service` 中的预警代理接口完成，因此预警访问在设计上应表述为代理式访问，而不是前端直接访问预警服务。

### 4.2 数据库设计

#### 4.2.1 数据库总体设计

系统采用按服务分库的数据库设计方式。`user-service`、`regulation-service`、`regulation-operation-service`、`complaint-service`、`warning-service` 和 `query-service` 均具备独立的数据库脚本和数据源配置，符合微服务架构下“服务独立、数据独立”的设计原则。这种设计有利于将用户认证、监管基础数据、监管执行数据、投诉数据、预警数据和统计扩展数据分别管理，降低数据库层面的耦合度。

系统没有建立跨库外键约束，而是通过业务主键、服务接口和业务规则维护实体关联关系。例如企业信息在监管数据库中维护，而检查任务、抽检任务、投诉记录和预警记录分别在各自服务数据库中引用企业编号或业务编号。该方式与服务拆分策略一致。

#### 4.2.2 核心实体与关系设计

系统核心实体包括用户、角色、企业、产品、监管人员、区域、检查任务、检查记录、抽检任务、抽检结果、整改任务、投诉、投诉处理记录、预警记录和公告。用户与角色之间通过 `sys_user`、`sys_role` 和 `sys_user_role` 构成多对多关系。企业实体以 `food_enterprise` 为核心，通过 `user_id` 对应企业账号，并通过附件、产品、区域等表形成主数据关系。检查、整改、抽检、投诉和预警数据分别围绕各自业务主表展开。

#### 4.3.1 用户与认证模块设计

该模块设计目标是为五类用户提供统一登录入口，并保证页面访问与接口访问的一致控制。输入包括注册信息、登录凭证和令牌；处理逻辑包括用户注册、密码校验、令牌签发、令牌失效、角色绑定和网关内省校验；输出为认证结果、用户身份信息和授权后的访问许可。模块关系上，`user-service` 负责认证核心能力，`gateway-service` 负责请求入口拦截与角色校验，前端路由负责页面级访问约束。

#### 4.3.2 企业备案与产品档案模块设计

该模块设计目标是完成企业主数据建档、备案审核和产品档案维护。输入包括企业基础信息、附件信息和产品信息；处理逻辑包括企业提交备案、区域管理员审核备案、企业查询自身档案、监管人员端查询企业信息以及企业维护产品档案；输出包括企业档案状态、审核结果和产品档案数据。该模块为后续检查、抽检、投诉和统计模块提供主数据支撑。

#### 4.3.3 检查与抽检模块设计

该模块设计目标是支持监管部门围绕企业开展任务派发、现场执行和结果留痕。检查子模块的输入包括任务标题、企业对象、辖区信息、执法人员和检查结果；处理逻辑包括任务创建、任务分派、执法执行、检查记录生成和记录查询；输出为检查任务状态和检查记录。抽检子模块的输入包括抽检企业、抽检产品、执行人员和抽检结论；处理逻辑包括任务创建、任务分派、结果录入、结果发布或下线；输出为抽检任务状态、抽检结论和公众可见结果。

#### 4.3.4 整改管理模块设计

该模块设计目标是将检查发现的问题转化为可跟踪、可复核的整改流程。输入包括检查记录、不合格问题描述、企业整改进展、整改附件和监管复核意见；处理逻辑包括依据检查记录生成整改任务、企业提交整改、监管人员查看整改详情与动作日志、执行复核确认或退回；输出为整改任务状态、整改动作日志和整改闭环结果。

#### 4.3.5 投诉处理模块设计

该模块设计目标是为公众监督提供结构化入口，并将投诉数据纳入监管处理流程。输入包括投诉人信息、联系方式、被投诉企业、投诉内容和图片材料；处理逻辑包括投诉提交、投诉查询、区域管理员受理与分派、执法人员处理、结果反馈和驳回；输出为投诉单状态、处理摘要和处理记录。该模块既服务公众用户，也服务监管人员，并向预警与统计模块提供输入数据。

#### 4.3.6 公告公示与预警模块设计

公告公示子模块的设计目标是实现监管信息公开。输入包括公告标题、类别和内容，或经发布的企业与抽检结果信息；处理逻辑包括公告创建、编辑、发布、下线，以及公众端公告、企业公示和抽检结果查询；输出为公众可见的公开信息。

预警子模块的设计目标是将投诉、整改、抽检等业务异常统一纳入预警记录和处置流程。输入包括预警事件、业务对象标识、预警类型、责任人和处理意见；处理逻辑包括预警事件写入、预警记录生成、分派、处理、解决和日志记录；输出为预警状态、预警轨迹和预警统计结果。由于网关禁止前端直接访问 `warning-service`，监管人员端预警访问在设计上采用 `regulation-service` 代理 `warning-service` 的方式实现。

#### 4.3.7 统计查询模块设计

该模块设计目标是为监管人员端提供跨服务的汇总视图。输入包括当前登录用户角色、辖区范围和查询参数；处理逻辑包括调用企业、监管操作、投诉和预警相关服务，聚合形成监管概览与预警统计结果；输出包括监管概览、预警概览、预警趋势、类型分布和处理效率统计。该模块的设计重点在于服务层聚合，而不是依赖查询服务自身预留统计表。

### 4.4 系统界面设计

#### 4.4.1 界面设计原则

从前端代码可确认，系统界面设计遵循按角色组织功能入口、按业务流程组织页面结构的原则。系统未单独给出完整视觉规范文档，因此本节不对颜色、字体和动画等视觉细节作超出代码证据的描述，仅依据实际路由、页面组件和角色分组说明界面组织方式。需要说明的是，部分系统管理员页面中的审计日志、筛选器和权限等级展示仍存在占位交互或待接入提示，因此本节仅将其作为界面结构的一部分进行说明，不将其写为已完整落地的后端能力。

#### 4.4.2 主要页面结构设计

公众端页面主要包括首页、公告列表与详情、企业公示、抽检结果、我要投诉、投诉提交成功、我的投诉和投诉详情等页面。企业端页面主要包括企业工作台、企业备案、备案详情、产品档案、检查记录、整改任务、整改详情和整改提交等页面。系统管理员端页面主要包括工作台、监管人员列表、添加监管人员、人员详情、编辑人员和状态切换确认等页面。区域管理员端页面主要包括监管概览、企业管理、备案审核、检查任务、抽检任务、整改复核、投诉流转、预警中心和统计页面。执法人员端页面主要包括企业监管、我的任务、检查结果提交、抽检结果提交、投诉处理、整改跟进、个人预警和统计页面。

#### 4.4.3 路由与导航设计

前端使用 Vue Router 进行统一路由管理，并通过路由守卫控制登录态恢复和角色权限校验。系统根据不同角色设定默认进入页面：系统管理员进入管理工作台，企业用户进入企业工作台，公众用户进入公众首页，区域管理员进入监管概览页，执法人员进入企业监管页。该设计与后端统一认证设计相配合，使用户登录后能够进入与自身职责匹配的功能空间。

项目启动入口由各服务的 `*Application.java` 提供，`gateway-service`、`user-service`、`regulation-service`、`regulation-operation-service`、`complaint-service`、`query-service` 和 `warning-service` 均定义了独立 Spring Boot 启动类。部分服务启用了 `@EnableFeignClients`，`regulation-service`、`regulation-operation-service` 和 `warning-service` 还启用了 `@EnableScheduling` 用于整改 SLA 与预警事件重试等定时任务处理。

前端 `food-web` 通过 `npm run dev` 启动 Vite 开发服务，通过 `npm run build` 生成生产构建文件。后端各服务可分别以 Spring Boot 应用方式独立启动，默认端口分别为网关 8080、用户服务 8081、监管服务 8082、查询服务 8083、预警服务 8084、投诉服务 8085、监管操作服务 8086。网关配置中已对前端本地开发地址 `http://localhost:5173` 和 `http://localhost:5174` 开启跨域支持，因此项目具备本地前后端联调运行条件。项目中未发现 Docker、Docker Compose 或 Kubernetes 部署文件，因此本章仅将启动方式表述为本地多服务独立启动和常规分服务部署。

#### 5.2.1 登录认证与权限控制实现

统一认证是本系统实现层最基础、也是最关键的模块之一。该模块的实现目标是完成多角色用户登录、令牌签发、令牌校验、会话失效和接口权限控制。

在后端实现中，`user-service` 的 `AuthController` 提供登录、登出、校验和内省接口，`AuthServiceImpl` 负责令牌校验与内省逻辑。其实现不仅执行 JWT 签名验证，还会进一步检查 Redis 黑名单、查询缓存的内省结果，并在必要时回源数据库读取用户、角色和状态信息，再将结果缓存回 Redis。

在网关实现中，`gateway-service` 的 `JwtAuthFilter` 负责统一拦截认证请求。过滤器先放行登录、注册和健康检查等白名单请求，再对其余请求提取令牌并校验签名。签名通过后，网关调用 `user-service` 的内省接口获取当前用户是否有效、用户类型及角色列表，再依据接口路径与角色规则进行访问控制。认证通过后，网关将用户身份头透传给下游业务服务，为业务服务提供统一身份上下文。

#### 5.2.2 网关路由与服务调用实现

网关与服务调用模块的实现目标，是使前端只面向统一入口访问系统，并使各业务服务能够通过服务名完成内部协作。`gateway-service` 在配置文件中定义了用户认证、监管操作、监管基础、投诉、查询和预警等路由规则；各业务服务则通过 Feign 客户端围绕用户服务、监管服务、投诉服务、预警服务和查询服务展开协作。

在服务调用实现上，项目使用 OpenFeign 组织跨服务协作。`regulation-service` 通过 Feign 调用 `user-service` 和 `warning-service`，`regulation-operation-service` 调用 `regulation-service` 和 `warning-service`，`complaint-service` 调用 `regulation-service`，`query-service` 则聚合调用多个服务的内部统计接口。与单体系统中直接调用本地业务类相比，这种实现方式更符合项目的微服务拆分结构。

该模块中较有代表性的实现细节，是系统对预警访问采取了代理式路径控制。虽然网关配置中存在 `/api/warning/**` 路由，但 `JwtAuthFilter` 明确禁止前端直接访问该路径；监管人员端访问预警时，实际调用的是 `regulation-service` 中的 `WarningProxyController` 和 `WarningProxyServiceImpl`。代理服务会根据当前监管人员身份构造辖区或责任人过滤条件，再转发给 `warning-service`。

#### 5.2.3 企业备案与基础监管数据实现

企业备案与基础监管数据模块是监管业务的主数据基础。其实现目标是完成企业档案建档、备案审核、产品档案维护、监管人员档案维护以及公开查询。

在企业备案实现中，`EnterpriseProfileController` 对外提供企业提交备案、查询备案、查看待审核企业、审核通过、审核驳回、批量审核和删除等接口。控制器通过 `JwtUserResolver` 解析当前用户身份，再根据企业用户或监管人员角色进行访问限制，随后调用 `EnterpriseProfileService` 完成具体业务处理。

在产品档案实现中，`ProductController` 提供企业用户的产品查询、新增、修改，以及监管人员端查看企业产品的接口。由于抽检任务依赖产品档案，因此产品模块与后续监管操作模块形成了直接联动。

在监管人员数据实现中，系统管理员通过用户服务创建监管账号，监管服务再通过 `RegulatorProfileController` 完成监管人员档案维护和辖区配置，实现了“账号创建”与“监管档案维护”在不同服务内的协同。

在文件处理实现中，`FileController` 与 MinIO 文件服务配合完成预签名上传地址生成，用于备案、投诉和整改等文件场景。前端页面层通过 `food-web/src/api/regulation.js` 完成与后端接口的联调。

#### 5.2.4 检查、抽检与整改闭环实现

检查、抽检与整改模块构成了本项目最能体现食品安全监管业务特色的实现链路。其实现目标是把监管任务从创建、分派、执行、结果记录一直推进到整改复核和公开结果展示，形成完整闭环。

在检查任务实现中，`InspectionTaskController` 提供任务创建、分派、分页查询、执法人员我的任务、任务启动、结果提交和任务关闭等接口。控制器通过 `RequestIdentityResolver` 获取当前请求身份，并将角色限制在监管人员范围内，再调用 `InspectionTaskService` 完成业务处理。

`InspectionTaskServiceImpl` 是该链路的核心实现类。区域管理员创建任务时，服务先校验当前监管人员身份、目标企业备案状态和辖区范围；任务分派时继续校验执法人员是否属于可分派辖区；执法人员提交结果时，系统在事务中写入检查记录和检查项，如果存在不合格情况，则立即调用整改服务创建整改任务。

整改实现由 `RectificationController` 和 `RectificationServiceImpl` 完成。服务在检查不合格后自动生成整改任务，设置企业提交截止时间；企业端提交整改时，服务更新整改进展、变更状态并写入整改动作日志；监管人员复核时，可执行确认或退回重改。

抽检实现由 `SamplingTaskController`、`SamplingResultManageController` 和 `SamplingTaskServiceImpl` 共同完成。区域管理员创建抽检任务时，系统校验企业处于已审核状态、产品为该企业有效产品；执法人员提交抽检结果后，服务写入 `sampling_result` 表，并将结果初始设置为 `DRAFT`；只有区域管理员执行发布操作后，结果才进入公众查询范围。

该模块中还有一个重要实现细节，即业务异常与预警事件联动。无论是检查连续不合格还是抽检不合格，监管操作服务都会构造预警事件并通过 `WarningEventOutboxService` 记录到 `warning_event_outbox` 表，后续由 `WarningEventOutboxRetryScheduler` 定时扫描待投递事件并调用预警服务内部接口进行重试投递。

#### 5.2.5 投诉处理与监管协同实现

投诉模块体现了平台面向公众监督的实现能力。其实现目标是使公众投诉能够进入监管内部流转，并形成可查询、可反馈的处理结果。

在公众端实现中，`PublicComplaintController` 提供投诉提交、我的投诉列表和投诉详情接口，`ComplaintCommandService` 中的 `submitPublic` 方法先校验被投诉企业是否存在，再生成投诉单号、写入投诉人信息、投诉内容、图片地址和投诉状态，并返回可供前端展示的投诉跟踪结果。

在监管人员端实现中，`RegulatorComplaintController` 提供投诉分页查询、详情查看、受理、分派、开始处理、办结和驳回等接口。核心业务逻辑集中在 `ComplaintCommandService` 中。该类对投诉处理流程进行了较完整的状态控制：区域管理员受理投诉后将状态转为 `PENDING`，再由区域管理员将投诉分派给执法人员，执法人员启动处理后状态转为 `PROCESSING`，提交处理结果后将投诉状态转为 `FEEDBACKED`，如不予受理，则由区域管理员执行驳回并记录驳回原因。

该模块还有一个较有价值的监管联动实现，即在投诉受理后，系统会统计一定时间窗口内企业被受理投诉的数量；若达到阈值，则调用监管基础服务将企业自动标记为重点监管对象。

#### 5.2.6 统计查询与预警代理实现

统计查询模块的实现目标是向监管人员端提供跨服务聚合后的概览结果，而不是依赖单一业务表直接出报表。

在后端实现中，`SupervisionOverviewController` 和 `WarningStatsController` 对外提供监管概览、预警概览、趋势、类型分布和处置效率等接口。其核心业务逻辑分别在 `SupervisionOverviewQueryServiceImpl` 和 `WarningStatsQueryServiceImpl` 中实现。以监管概览为例，服务先构造查询范围，再分别调用企业统计、监管操作统计、投诉统计和预警统计接口，最终组合成统一的概览结果返回给前端。

该实现说明项目中的统计查询并不是通过 `query-service` 自身统计表直接读取完成，而是通过内部接口聚合形成。数据库脚本中的 `stat_enterprise`、`stat_inspection` 和 `stat_complaint` 在当前阶段仍属于扩展预留设计，并未进入主运行链路。

预警访问实现则体现为“网关禁直连、监管服务做代理”的模式。监管人员端页面调用 `regulation-service` 中的预警代理接口，代理服务根据当前监管人员身份补充辖区或责任人过滤条件，再转发至 `warning-service`。这种实现使预警能力在系统中以监管业务的一部分呈现，而不是作为前端直接访问的独立域。

## 第7章 总结与展望

### 7.1 工作总结

本文围绕“基于微服务的食品安全监管平台”这一课题，结合项目代码、配置文件、数据库脚本、前端页面、接口调用链和测试材料，对系统的需求分析、架构设计、功能实现与测试验证进行了系统整理与论述。论文完成的主要工作，是在真实工程实现基础上形成一套较完整的软件开发研究型毕业设计成果，使系统从需求、设计、实现到测试之间具备较清晰的对应关系。

从系统建设结果看，项目已经完成了食品安全监管业务中的多条核心主线。系统实现了统一登录认证与权限控制机制，实现了企业备案、产品档案、监管人员档案、公告管理和公开查询等基础数据能力，实现了检查任务、检查记录、整改任务、抽检任务、抽检结果、投诉处理和预警处置等核心监管流程，也实现了公众公告查询、企业公示、抽检结果公示和公众投诉等功能，并通过监管概览与预警统计查询为监管人员提供基础的数据支持。

在架构层面，本项目的微服务设计并非停留在概念层面，而是围绕业务边界完成了较明确的服务划分。网关服务、用户服务、监管基础服务、监管操作服务、投诉服务、预警服务和查询服务分别承担不同职责，并通过 Nacos、OpenFeign、Redis 和统一网关机制协同工作。尤其是预警代理访问、出站事件表重试和监管概览聚合查询等实现方式，都体现了微服务架构服务于业务落地的实际意义。

从食品安全监管业务价值看，本系统体现了“企业纳管、过程监管、问题整改、社会监督和数据辅助决策”相结合的建设思路。企业备案与产品档案帮助监管部门建立被监管对象基础底数，检查、整改和抽检功能支撑监管执行闭环，投诉处理和公开公示增强了公众参与和信息透明，预警与统计功能则为监管重点识别和辅助分析提供了数据支持。总体而言，本课题已在既定题目范围内完成了一个可运行、可说明、可验证的食品安全监管平台原型系统。

### 7.2 未来展望

虽然本系统已经完成了毕业设计要求范围内的主要工作，但从工程完善程度和后续应用角度看，仍存在继续优化的空间。

第一，可以继续完善现有业务链路中的细节能力。在当前实现中，企业备案、检查整改、抽检、公示、投诉和预警已经形成主线，但系统管理员侧的审计日志、企业侧的部分设置能力、产品档案的个别管理操作以及部分页面中的占位交互仍未与完整后端能力闭合。后续可在不扩张业务边界的前提下，围绕现有角色与流程补齐这些细节。

第二，可以进一步提升系统的安全与治理能力。当前系统已经实现 JWT、网关鉴权、角色隔离、Redis 会话缓存和部分接口限流，但默认密钥、内部令牌和部分运行配置的规范化程度仍有提升空间。后续可以围绕配置外置化、敏感配置治理、网关严格模式、细粒度归属校验和上传资源安全控制等方向继续增强系统安全性。

第三，可以继续增强测试与交付验证能力。当前项目已经具备后端自动化测试基础，并完成了阶段性联合测试和前端构建验证，但尚未形成完整浏览器级联调记录，也未覆盖全部前端页面交互。后续可围绕登录认证、企业备案、检查整改、抽检公示、投诉闭环和预警处置等关键路径补充更完善的手工验收记录或自动化测试。

第四，可以逐步提升统计分析与数据支撑能力。当前 `query-service` 主要采用聚合调用方式组织监管概览和预警统计，数据库中的 `stat_enterprise`、`stat_inspection` 和 `stat_complaint` 等表仍处于扩展预留状态。后续若业务场景进一步稳定，可以在保持当前轻量聚合结构基础上，逐步完善统计数据沉淀、主题分析和趋势展示能力。

第五，可以完善系统部署与运维支撑能力。当前项目具备本地分服务启动与前后端联调条件，但尚未形成容器化部署、统一持续集成流水线和完整运行说明。后续可继续补充更规范的部署文档、环境说明、配置模板和服务启动顺序，在此基础上再逐步推进更标准化的部署和运维方案。

综上所述，本课题已经完成了食品安全监管平台的核心功能实现和论文写作基础工作，后续改进方向也较为明确。未来若继续围绕现有业务边界开展迭代，在安全治理、测试验证、统计分析和部署规范等方面逐步完善，系统将具备更好的工程质量和更强的实际应用价值。
