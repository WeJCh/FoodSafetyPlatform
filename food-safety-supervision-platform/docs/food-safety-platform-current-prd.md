## 2. 项目背景

食品安全监管工作通常涉及企业主体备案、监管辖区划分、日常检查、公众投诉、问题整改、风险预警、抽检结果和信息公开等多个环节。

传统线下或分散式信息化方式容易造成：

- 企业底数不清
- 监管责任边界不清
- 检查任务分派和执行过程不透明
- 投诉处理缺少全过程跟踪
- 整改事项容易超期或失管
- 风险信息无法及时汇总和上报
- 抽检结果和企业监管状态缺少统一公示窗口

本项目基于微服务架构，围绕区域食品安全监管的最小核心链路进行建设，并通过 P0/P1/P2 整改将项目从“中期纠偏半成品”推进到“业务主线已成型、进入交付收口”的状态。

## 3. 项目定位

当前项目定位为：

> 以企业主体纳管为基础，以日常检查、整改闭环、投诉协同、风险预警、产品档案、抽检结果、公示公告和监管概览为主线的区域食品安全监管协同平台。

本平台是：

- 区域食品安全监管协同平台
- 企业主体纳管平台
- 检查整改闭环平台
- 投诉协同处置平台
- 风险预警与重点监管平台
- 产品档案与抽检结果最小闭环平台
- 公众信息公示窗口

本平台不是：

- 全链路食品追溯平台
- 召回管理系统
- 行政处罚案件全流程系统
- 检测机构/实验室业务平台
- 全国级监管大数据平台
- 通用后台管理系统
- 生产级安全运维平台
- ERP、商城、供应链协同系统

## 4. 产品目标

### 4.1 业务目标

1. 支持企业备案、审核、监管状态管理与公众公示。
2. 支持监管任务派发、执法检查、整改提交、复核和 SLA 预警。
3. 支持公众投诉提交、受理、派发、处理、反馈和进度查询。
4. 支持重点监管原因沉淀，覆盖连续检查不合格、投诉高发、抽检不合格。
5. 支持企业产品档案维护和监管查看。
6. 支持最小抽检任务、结果录入、失败联动和公众公示。
7. 支持轻量监管概览统计，不建设大屏 BI 或离线数仓。

### 4.2 管理目标

- 让监管部门能按辖区查看企业、任务、投诉、预警和抽检情况。
- 让企业能查看自身备案、产品、检查记录和整改任务。
- 让公众能提交投诉、查询进度、查看企业公示、公告和抽检结果。
- 让答辩或交付时能围绕清晰业务闭环进行演示。

### 4.3 技术目标

- 保留现有微服务边界。
- 保留网关统一鉴权与用户身份透传。
- 保留 OpenFeign 内部服务协作。
- 保留 Outbox + 定时重试的轻量预警事件一致性方案。
- 保持 `query-service` 为轻量统计聚合层。
- 不再新增微服务、中间件或复杂基础设施。

## 7. 核心业务流程

### 7.1 企业纳管流程

业务目标：

- 将企业从账号注册变成可审批、可纳管、可公开查询的监管对象。

核心步骤：

1. 企业用户注册并提交备案资料。
2. 区域管理员按辖区审核通过或驳回。
3. 审核通过后企业进入监管企业池。
4. 企业基础信息对监管端可见。
5. 公开字段进入公众企业公示列表和详情。
6. 如企业触发重点监管规则，公众和监管端可查看监管状态和原因。

### 7.2 检查整改流程

业务目标：

- 形成“发现问题 -> 督促整改 -> 逾期预警 -> 复核关闭”的监管执行主线。

核心步骤：

1. 区域管理员创建检查任务。
2. 区域管理员指派执法人员。
3. 执法人员启动并提交检查记录和检查项。
4. 如检查不合格，系统自动生成整改任务。
5. 企业提交整改说明和附件。
6. 区域管理员复核通过或打回。
7. 整改提交或复核超时后触发预警。
8. 预警进入处理、解决或归档流程。

### 7.3 投诉反馈流程

业务目标：

- 让公众投诉从“提交成功”变成“真实处理可反馈”。

核心步骤：

1. 公众提交投诉并生成投诉编号。
2. 区域管理员受理或驳回。
3. 区域管理员派发给执法人员。
4. 执法人员处理并填写反馈摘要。
5. 公众在“我的投诉”查看状态、反馈摘要或驳回原因。
6. 投诉高发时写入企业重点监管原因。

### 7.4 重点监管流程

业务目标：

- 将风险事件沉淀为企业监管状态和原因记录。

当前触发来源：

- 连续检查不合格
- 投诉高发
- 抽检不合格

核心步骤：

1. 业务服务识别风险事件。
2. 通过 `regulation-service` 内部接口写入 `enterprise_key_reason`。
3. 企业状态更新为 `KEY`。
4. 监管端和公众端可查看重点监管状态与最近原因。

### 7.5 抽检结果流程

业务目标：

- 用最小代价补足“食品安全监管”的专业对象和专业流程。

核心步骤：

1. 企业维护产品档案。
2. 区域管理员创建抽检任务，选择企业和产品。
3. 区域管理员派发给执法人员。
4. 执法人员录入抽检结果。
5. 不合格结果写入重点监管原因并进入预警 outbox。
6. 区域管理员发布或下线抽检结果。
7. 公众查看已发布的抽检结果列表和详情。

### 7.6 监管概览流程

业务目标：

- 提供企业、检查、抽检、投诉、预警的轻量聚合视图。

核心步骤：

1. 前端监管工作台请求 `query-service` 概览接口。
2. `query-service` 按当前监管用户范围补全查询范围。
3. `query-service` 调用企业、执行、投诉、预警内部统计接口。
4. 返回聚合指标。

说明：

- 当前概览为实时聚合口径。
- `stat_enterprise/stat_inspection/stat_complaint` 仍为预留表，不作为当前统计来源。

| 统计预留表 | `stat_enterprise/stat_inspection/stat_complaint` | 当前不作为真实统计来源 |

### 10.2 数据流转要求

- 企业必须审批通过后才能进入检查和抽检任务池。
- 产品必须归属于企业，抽检任务必须同时关联企业和产品。
- 抽检不合格必须触发重点监管原因写入，并进入预警 outbox。
- 检查不合格必须生成整改任务。
- 整改超时必须生成预警事件。
- 投诉处理必须能向公众返回反馈摘要或驳回原因。
- 重点监管原因必须保留来源类型和来源 ID。

## 11. 权限与审计要求

### 11.1 当前已实现要求

- 网关默认 `introspect-fail-open=false`。
- 网关按路径进行基础角色控制。
- 文件上传按用户类型限制业务类型：
  - PUBLIC 仅允许 COMPLAINT
  - ENTERPRISE 仅允许 RECTIFICATION
- 内部接口使用 `X-Internal-Token`。
- 业务服务继续做企业、监管员、辖区、任务归属校验。

### 11.2 当前未承诺要求

- 不承诺完整操作审计日志中心。
- 不承诺生产级密钥管理。
- 不承诺配置中心密钥隔离。
- 不承诺 Vault、KMS 或容器 Secret 管理。

## 12. 非功能要求

### 12.1 可维护性

- 不新增微服务。
- 不新增复杂中间件。
- 不把 `query-service` 扩成通用 BI。
- 保留当前主数据、执行域、投诉域、预警域、统计聚合域边界。

### 12.2 可测试性

- 保留并持续执行现有关键测试。
- 后续 bugfix 必须保证后端联合测试和前端构建通过。
- 不以手工点击替代核心链路的回归测试。

### 12.3 可部署性

- 当前按本地多服务运行和演示交付口径处理。
- 不承诺 Docker Compose、K8s 或一键部署。
- 需要单独补充最小运行说明和演示数据说明。

### 12.4 安全性

- 当前适合演示和毕业设计交付。
- 当前不适合作为生产安全完成态表述。
- 默认 JWT secret、内部 token、MinIO 默认凭据仍为已知风险。

### 12.5 性能

- 查询接口应保持分页。
- 统计接口应限制范围和 TopN。
- 当前目标为中小规模演示数据和毕业设计答辩场景，不按生产级性能指标验收。

### 15.2 当前约束

- SQL schema 中存在原型初始化用途的 `DROP TABLE`，不应直接作为生产迁移脚本使用。

- P2-5 已放弃，因此默认 secret/token/MinIO 凭据必须在交付材料中写为风险。

## 16. 验收标准

### 16.1 自动化验证

后端联合测试：

```powershell
mvn -q -pl regulation-service,regulation-operation-service,complaint-service,warning-service,query-service -am test
```

前端生产构建：

```powershell
cd food-web
npm run build
```

### 16.2 人工演示路径

至少准备以下 6 条路径：

1. 企业备案 -> 区域管理员审核 -> 公众企业公示
2. 区域管理员发布公告 -> 公众查看公告
3. 区域管理员派发检查 -> 执法人员提交不合格 -> 企业整改 -> 管理员复核
4. 公众提交投诉 -> 管理员受理派单 -> 执法人员处理 -> 公众查看反馈
5. 企业维护产品 -> 管理员创建抽检任务 -> 执法人员录入不合格 -> 发布抽检结果 -> 公众查看
6. 监管端查看概览统计 -> 查看重点监管企业与风险预警

### 16.3 口径验收

- 可以表述为“P2 业务增强主线通过”。
- 不能表述为“P2 原始清单全量完成”。
- 不能表述为“生产级安全配置治理完成”。
- 不能将 P3 放弃项列为当前待开发功能。

## 18. 结论

当前项目已经从旧 PRD 所描述的“中期纠偏半成品”推进到“业务主线已成型、进入交付收口”的状态。

当前最合理的产品口径是：

> 基于微服务架构的区域食品安全监管协同平台，已覆盖企业纳管、检查整改、投诉反馈、风险预警、公众公示、产品档案、抽检结果和监管概览等核心演示闭环。

后续不应继续扩功能线，应围绕文档、演示、验收记录和阻断性 bugfix 做交付收口。
