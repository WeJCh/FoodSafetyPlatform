## 1.2 项目现状认知结论

### 1.2.1 架构层面

- 【项目可直接证明】这是一个前后端分离项目，后端为多模块 Maven 微服务工程，前端为独立 `food-web` Vite + Vue 3 项目。
- 【项目可直接证明】根 POM 声明了 8 个后端模块：`user-service`、`gateway-service`、`regulation-service`、`regulation-operation-service`、`complaint-service`、`warning-service`、`query-service`、`platform-common`。
- 【项目可直接证明】网关统一暴露 `/api/auth`、`/api/regulation`、`/api/regulation-operation`、`/api/complaints`、`/api/query`、`/api/warning` 等路径，说明项目已经形成基本微服务入口。
- 【基于代码结构推断】当前拆分并非“全链路食品安全平台”的成熟服务群，更像是围绕“监管主数据 + 执法执行 + 投诉 + 预警 + 看板”组织起来的毕业设计型微服务原型。

### 1.2.2 技术层面

- 【项目可直接证明】后端主技术栈为 Spring Boot 3.2.5、Spring Cloud 2023、Spring Cloud Alibaba、MyBatis-Plus、MySQL、OpenFeign、JWT。
- 【项目可直接证明】基础设施已接入 Nacos、Sentinel、Gateway、MinIO。
- 【项目可直接证明】文档工具同时出现 Knife4j 与 SpringDoc，但主要完整开放文档能力集中在 `query-service`。
- 【项目中未发现】Redis、Kafka、RabbitMQ、RocketMQ、Seata、Docker Compose、K8s 编排文件等完整配套落地。

### 1.2.3 业务层面

- 【项目可直接证明】当前已形成两个比较清晰的业务闭环：
  - 闭环 A：企业备案 -> 监管审核 -> 企业纳管
  - 闭环 B：检查任务 -> 检查记录 -> 整改任务 -> SLA 预警 -> 预警处理
- 【项目可直接证明】还存在一个独立闭环：
  - 闭环 C：公众投诉 -> 受理 -> 派发 -> 执法处理 -> 反馈
- 【基于代码结构推断】项目最像“区域食品安全监管协同平台原型”，而不是“覆盖食品生产经营全链条的完整食品安全监管平台”。

### 1.2.4 阶段判断

- 【基于代码结构推断】当前属于“开发中期偏后”阶段，而非收尾阶段。
- 依据：
  - 前端已有 11 个业务页面和 2 个复用组件，但仍大量存在“功能占位”“后续版本实现”“演示数据”。
  - 后端已完成多服务接口与部分跨服务调用，但只有预警统计相关测试相对完整，其他业务域缺少测试。
  - 前端没有 Vue Router，`App.vue` 仍以 `view` 状态切页面，说明更偏演示型原型而非成熟应用。

# 2. 项目现状分析报告

## 2.1 项目现状概述

### 2.1.1 项目名称

《微服务食品安全监管平台》

### 2.1.2 项目类型

- 【项目可直接证明】区域监管业务型平台
- 【基于代码结构推断】更准确的现状定位应为：  
  “面向区县/街道监管体系的食品安全监管协同平台原型”

### 2.1.3 当前架构概况

| 项目项 | 现状判断 |
| --- | --- |
| 前后端形态 | 前后端分离 |
| 后端架构 | Spring Cloud 微服务 |
| 前端架构 | Vue 3 + Vite 单体前端演示应用 |
| 注册/发现 | Nacos |
| 网关 | Spring Cloud Gateway |
| 熔断/限流 | Sentinel |
| 持久层 | MyBatis-Plus + MySQL |
| 鉴权 | JWT + 网关统一转发用户头 |
| 文件存储 | MinIO 预签名上传 |
| 服务通信 | OpenFeign + 内部接口 |
| 统计方式 | `query-service` 代理 `warning-service` 统计接口 |
| 事件一致性 | Outbox + 定时重试推送预警服务 |

### 2.1.4 当前开发阶段判断

- 【基于代码结构推断】项目处于毕业设计“中期纠偏”的典型阶段。
- 主要特征：
  - 已有较完整的业务域切分和部分闭环
  - 但产品边界未完全收束
  - 页面与模块完成度差异大
  - 食品安全专业属性还不够强

### 2.1.5 当前整体完成度评估

- 【基于代码结构推断】整体完成度建议评估为 55% - 65%
- 其中：
  - 架构搭建完成度：80% 左右
  - 核心监管闭环完成度：60% 左右
  - 产品边界与需求定义完成度：40% 左右
  - 食品安全专业业务深度完成度：35% 左右

## 2.5 当前项目存在的核心问题

### 2.5.1 需求层面

- 【基于代码结构推断】项目一开始没有把“食品安全监管平台”的核心目标收束清楚，导致后续功能既想做备案，又想做投诉，又想做预警，又想做看板，但缺少统一产品主线。
- 【项目可直接证明】缺少食品、抽检、检测、追溯等专业对象，说明最初需求并未真正围绕“食品安全”拆解业务域。

### 2.5.2 产品层面

- 【项目可直接证明】前端有多个角色入口，但不少模块仍是占位或演示数据。
- 【项目可直接证明】公众首页“企业公示”“预警与公告”按钮未接线，说明公众服务能力尚未形成可用产品。
- 【基于代码结构推断】产品主线目前主要依赖“检查/整改/投诉/预警”四块，企业、公示、统计都围绕这四块打补丁。

### 2.5.3 业务流程层面

- 【项目可直接证明】检查->整改->预警闭环较完整，但“抽检/检测->问题认定->处罚/召回”闭环缺失。
- 【项目可直接证明】投诉闭环已完成，但投诉结果不会自动沉淀为企业风险等级或重点监管原因。
- 【项目可直接证明】企业状态有 `KEY`，也有 `enterprise_key_reason` 表，但未真正进入运行流程。

### 2.5.4 数据设计层面

- 【项目可直接证明】当前主数据以企业、监管人员、辖区为核心，缺少食品、批次、样品、检测、召回等核心实体。
- 【项目可直接证明】`query-service` 存在 `stat_enterprise`、`stat_inspection`、`stat_complaint`，但代码中并未实际使用，说明数据模型与真实实现脱节。
- 【项目可直接证明】附件仅保存 URL 字符串，没有独立附件元数据表，不利于后续审计、删除、归档。

### 2.5.5 系统架构层面

- 【基于代码结构推断】微服务拆分方向基本合理，但对毕业设计而言偏重。
- 【项目可直接证明】`query-service` 目前只服务预警统计，服务价值还不足以支撑一个独立微服务的说服力。
- 【项目可直接证明】预警并未接入真实消息队列，而是采用 Outbox + 定时 HTTP 重试，更像“轻量事件一致性方案”而非完整消息驱动架构。
- 【项目可直接证明】网关配置 `introspect-fail-open=true`，以及多个服务存在默认内部 Token/JWT Secret，生产级安全性不足。

### 2.5.6 毕业设计可落地性层面

- 【基于代码结构推断】如果继续把项目往“全功能食品安全平台”方向扩，会迅速失控。
- 【基于代码结构推断】如果收束为“区域食品安全监管协同平台”，当前代码基础反而是可救、可答辩、可完善的。

## 2.6 建议的纠偏方向

### 2.6.1 保留什么

- 企业备案与审核
- 监管人员与辖区体系
- 检查任务与检查记录
- 整改闭环
- 投诉闭环
- 预警中心与预警统计
- MinIO 附件上传
- 内部接口 + Outbox 的微服务协同思路

### 2.6.2 删减什么

- 不要继续把系统往“商城、ERP、溯源码平台、综合后台管理系统”方向扩
- 不要同时开太多泛后台模块，如完整用户中心、完整日志中心、完整公告 CMS、完整配置中心
- 对于管理员侧的“角色调整、区域交接、日志”等占位能力，如果无法做深，建议降级为答辩中说明的扩展能力，不要强行补 UI 壳子

### 2.6.3 补充什么

- 最小化的食品安全专业实体补充方案
  - 至少补“抽检/检测结果录入与公示”的最小能力，哪怕不引入完整检测机构协同
- 企业重点监管状态联动
  - 将投诉超量、连续不合格、预警升级与 `enterprise_key_reason` 关联
- 公众公示闭环
  - 企业公示详情
  - 风险公告/抽检公告的真实后台数据
- 审计日志
  - 至少记录关键审批、派发、复核、处理动作

### 2.6.4 优先级建议

1. 先收束范围与角色边界  
2. 再补“检查/整改/投诉/预警”之间的数据联动  
3. 最后补公众展示与统计说明  
4. 如时间充裕，再做“抽检/检测最小模块”增强食品安全专业属性

### 2.6.5 更符合毕业设计范围的建议定位

建议把题目实际落地为：

> “基于微服务架构的区域食品安全监管协同平台”

而不是笼统的“食品安全监管平台”。

这样既保留现有代码成果，也能避免答辩时被追问“为什么没有抽检、追溯、召回、检测机构、案件处罚、食品档案”时陷入被动。

# 3. 当前项目偏差识别

## 3.1 当前这个半成品项目，实际上被做成了一个什么系统

### 结论

【基于代码结构推断】当前项目实际上更像：

> “面向基层监管部门的企业纳管 + 监管工单 + 整改闭环 + 投诉处理 + 预警看板系统”

而不是完整意义上的“食品安全监管平台”。

### 原因

- 【项目可直接证明】主数据中心是企业和监管人员，不是食品与样品
- 【项目可直接证明】执行主线是任务、整改、投诉、预警，不是抽检、检测、召回、追溯
- 【项目可直接证明】统计中心也是围绕“预警”而不是围绕“食品安全风险全景”

## 3.2 作为食品安全监管平台，理论上应优先围绕哪些核心业务目标建设

### 当前最适合保留的优先目标

基于当前代码基础，建议本项目的理论核心目标收束为以下五项：

1. 企业主体纳管  
2. 日常检查与问题发现  
3. 整改闭环与时限约束  
4. 公众投诉协同处理  
5. 风险预警与监管看板

### 理论上存在但不宜本轮强做完整闭环的能力

- 抽检/检测管理
- 食品追溯/召回
- 行政处罚/案件管理
- 多主体供应链协同

这些能力可以作为扩展方向，不建议在当前毕业设计周期内全部展开。

## 3.3 当前项目哪些功能是有效的、能保留的

- 【项目可直接证明】监管角色体系和辖区边界设计合理
- 【项目可直接证明】企业备案审批闭环可保留
- 【项目可直接证明】检查任务-检查记录-整改闭环是本项目最强主线之一
- 【项目可直接证明】投诉受理派发处理闭环可保留
- 【项目可直接证明】预警中心和统计看板可保留
- 【项目可直接证明】Outbox + 内部接口 + 作用域权限控制体现了微服务设计价值，可保留

## 3.4 当前项目哪些功能方向跑偏了

### 跑偏点 1：食品安全专业对象太弱

- 【项目可直接证明】项目名叫食品安全监管平台，但数据表中没有食品、批次、样品、检测、召回等对象
- 偏向方向：通用监管流程系统/工单系统

### 跑偏点 2：统计服务拆得像“大屏服务”，但数据基础并不完整

- 【项目可直接证明】`query-service` 现阶段几乎只做预警统计代理
- 偏向方向：为了“有微服务而微服务”的技术拆分

### 跑偏点 3：前端有“公众公示、公告、企业信息公开”表达，但并未形成真实业务模块

- 【项目可直接证明】公众首页按钮未接线、公告为静态演示
- 偏向方向：页面看起来像政务门户，但后台能力不足

### 跑偏点 4：系统管理员模块容易往通用后台方向发散

- 【项目可直接证明】用户管理、操作日志、角色调整、区域交接均为占位
- 偏向方向：通用后台管理系统

## 3.5 当前项目最缺失的监管能力是什么

### 必须直说的缺失点

1. 缺少食品/产品层对象  
2. 缺少抽检/检测结果链路  
3. 缺少企业风险分级联动  
4. 缺少问题食品追溯/召回  
5. 缺少处罚/执法案件闭环  
6. 缺少公众信息公示后台

其中第 1、2、3 点最影响“食品安全监管平台”的专业说服力。

## 3.6 如果继续按照现状开发，最终会出现什么问题

- 产品边界越来越散，最后什么都做一点但都不深
- 毕设答辩时会被质疑“为什么叫食品安全监管平台，却没有食品和抽检”
- 微服务数量多，但每个服务的业务价值解释不充分
- 前端页面越来越多，但主线不清，展示重点分散
- 最终看起来更像“综合监管后台 + 工单系统 + 演示门户”

## 3.7 应该如何重新收束项目边界，避免毕业设计过大或继续跑偏

### 建议边界

将本项目边界明确为：

> 以“企业主体纳管、日常检查、投诉处理、整改闭环、风险预警、公众查询”为核心的区域食品安全监管协同平台。

### 明确不做

- 不做商城交易
- 不做 ERP 生产管理
- 不做完整溯源平台
- 不做全国级监管大数据平台
- 不做复杂案件处罚全流程系统

### 可选增强

如果需要增强食品安全专业属性，只增加“抽检/检测结果最小模块”，不再扩大到全链路追溯。

## 4.2 项目背景

### 4.2.1 为什么需要食品安全监管平台

食品安全监管工作通常涉及企业主体备案、监管辖区划分、日常检查、公众投诉、问题整改、风险预警和信息公开等多个环节。传统线下或分散式信息化方式容易造成：

- 企业底数不清
- 监管责任边界不清
- 检查任务分派和执行过程不透明
- 投诉处理缺乏全过程跟踪
- 整改事项容易超期或失管
- 风险信息无法及时汇总和上报

### 4.2.2 当前食品安全监管的常见痛点

- 主体信息分散，企业纳管与监管台账脱节
- 检查发现问题后缺少闭环整改跟踪
- 公众投诉受理后缺少过程透明和结果反馈
- 风险事件依赖人工汇总，缺少自动提醒与统计分析
- 公众公示能力薄弱，社会监督价值不足

### 4.2.3 本项目希望解决的问题

结合当前代码基础，本项目希望优先解决以下问题：

1. 建立企业主体与监管人员的基础主数据  
2. 建立检查任务分派和执行机制  
3. 对检查不合格问题形成整改闭环  
4. 对投诉举报形成受理、派发、处理、反馈闭环  
5. 对超时整改等风险进行自动预警和统计展示  
6. 向公众提供投诉入口与基础企业查询能力  

### 4.2.4 为什么采用平台化、信息化、微服务化建设

- 平台化：统一企业、监管人员、任务、投诉、整改、预警等入口
- 信息化：实现过程留痕、状态流转、公开可查
- 微服务化：将主数据、执行域、投诉域、预警域、查询域分离，体现架构设计价值

【基于业务合理性建议】对于毕业设计，应强调“微服务服务于业务边界”，而不是单纯追求服务数量。

## 4.7 核心业务流程

### 4.7.1 企业入驻/备案流程

- 触发条件：企业完成账号注册后进入企业工作台
- 参与角色：企业用户、区域管理员
- 关键步骤：
  1. 企业注册账号
  2. 企业填写备案信息并提交
  3. 系统保存企业档案并置为 `PENDING`
  4. 区域管理员查看待审核企业
  5. 管理员通过或驳回备案
  6. 通过后企业进入纳管范围并可被检查任务引用
- 输入：
  - 企业名称
  - 许可证编号
  - 区域
  - 地址
  - 负责人
  - 联系电话
- 输出：
  - 企业档案
  - 审核状态
  - 审核意见
- 异常分支：
  - 区域为空或无效
  - 企业信息不完整
  - 审核驳回后需重新提交

### 4.7.2 检查任务下发与结果回传流程

- 触发条件：区域管理员对已审批纳管企业发起日常检查
- 参与角色：区域管理员、执法人员
- 关键步骤：
  1. 区域管理员选择企业并创建检查任务
  2. 系统校验企业是否已审批
  3. 管理员选择辖区内可执行的执法人员进行派发
  4. 执法人员开始任务
  5. 执法人员提交检查日期、总体结果、问题描述、检查项结果
  6. 系统沉淀检查记录
- 输入：
  - 企业 ID
  - 任务标题、描述、优先级、截止时间
  - 检查日期、结果、检查项
- 输出：
  - 检查任务状态变化
  - 检查记录
  - 检查明细项
- 异常分支：
  - 企业未通过备案，禁止创建任务
  - 派发对象不在辖区内
  - 超过任务截止时间不可派发/不可启动
  - 检查项为空则不允许提交

### 4.7.3 风险问题触发整改流程

- 触发条件：检查结果为不合格，或任一检查项为不合格
- 参与角色：执法人员、企业用户、区域管理员
- 关键步骤：
  1. 执法人员提交检查结果
  2. 系统识别不合格结果
  3. 系统自动创建整改任务
  4. 企业在时限内提交整改说明和附件
  5. 区域管理员复核整改结果
  6. 通过则确认完成，驳回则打回重做
- 输入：
  - 检查问题说明
  - 企业整改进展
  - 整改附件
  - 复核意见
- 输出：
  - 整改任务
  - 整改动作日志
  - 状态从 `ONGOING` -> `SUBMITTED` -> `CONFIRMED/REWORK`
- 异常分支：
  - 企业未按期提交
  - 监管未按期复核
  - 打回重做后再次提交

### 4.7.4 风险预警处理流程

- 触发条件：整改任务超过提交或复核时限
- 参与角色：系统调度器、区域管理员、执法人员
- 关键步骤：
  1. 定时任务扫描整改 SLA
  2. 生成预警事件并写入 outbox
  3. 通过 HTTP 重试机制推送至预警服务
  4. 预警服务按 `dedupKey` 幂等入库
  5. 管理员按辖区查看预警，执法人员按本人查看预警
  6. 预警可标记处理中、已解决
  7. 长时间未处理可升级为 L2
  8. 已解决预警可自动归档
- 输入：
  - 预警事件类型
  - 整改任务标识
  - 所属区域
  - 责任执法人员
  - 截止时间与逾期分钟数
- 输出：
  - 预警记录
  - 预警处理日志
  - 预警统计数据
- 异常分支：
  - outbox 推送失败触发重试
  - 重复上报合并触发次数
  - 权限范围不匹配时禁止查看

### 4.7.5 投诉举报处理流程

- 触发条件：公众发起食品安全投诉
- 参与角色：公众用户、区域管理员、执法人员
- 关键步骤：
  1. 公众选择企业并提交投诉
  2. 系统生成投诉编号并记录状态 `SUBMITTED`
  3. 区域管理员受理投诉，状态变为 `PENDING`
  4. 管理员派发给辖区执法人员，状态变为 `ASSIGNED`
  5. 执法人员开始处理，状态变为 `PROCESSING`
  6. 执法人员填写处理结果，状态变为 `FEEDBACKED`
  7. 对无效投诉，管理员可驳回为 `REJECTED`
- 输入：
  - 企业 ID
  - 投诉类型
  - 投诉内容
  - 图片
  - 处理结果或驳回原因
- 输出：
  - 投诉单
  - 投诉处理记录
  - 公众可查看的状态进度
- 异常分支：
  - 非公众身份禁止提交
  - 非辖区内企业投诉禁止查看/处理
  - 执法人员不能处理未派发给自己的投诉

### 4.7.6 公众查询与公示流程

- 触发条件：公众进入公共首页或投诉跟踪页面
- 参与角色：公众用户、系统
- 关键步骤：
  1. 公众查询本人投诉记录
  2. 公众查看投诉状态和处理结果
  3. 公众搜索已通过审核的企业列表
  4. 后续应支持查看企业基础公示详情与风险公告
- 输入：
  - 公众登录身份
  - 企业名称关键词
  - 投诉状态
- 输出：
  - 投诉列表/详情
  - 企业公示列表
- 异常分支：
  - 未登录公众不可查看个人投诉
  - 企业公示暂仅支持列表，不支持完整详情闭环

## 4.9 详细功能需求

### 4.9.1 功能：企业备案管理

- 功能目标：建立被监管企业的统一档案与审批纳管入口
- 角色权限：
  - 企业：提交、更新备案
  - 区域管理员：审核、驳回、批量审批
- 前置条件：
  - 企业已注册账号
  - 已具备区域字典
- 功能描述：
  - 企业填写基础档案，进入待审核状态
  - 区域管理员对辖区企业进行审核
  - 通过后企业纳入监管范围，并可被检查任务引用
- 业务规则：
  - `regionId` 必填
  - `enterpriseName`、`addressDetail` 必填
  - 提交后审批状态重置为 `PENDING`
  - 仅已审批企业可参与检查任务
- 输入项：
  - 企业名称
  - 许可证编号
  - 区域
  - 详细地址
  - 负责人
  - 联系方式
- 输出项：
  - 企业档案 ID
  - 审批状态
  - 审批意见
  - 审批时间
- 异常处理：
  - 区域无效时报错
  - 企业档案不存在时报 404
- 数据涉及：
  - `food_user_db.sys_user`
  - `food_regulation_db.food_enterprise`
  - `food_regulation_db.addr_location`
  - `food_regulation_db.addr_region`
- 当前项目实现情况：已实现
- 后续完善建议：
  - 增加经营类型、许可证有效期、主体分类
  - 增加公共详情页，而不只是公共列表

### 4.9.2 功能：监管人员与辖区管理

- 功能目标：建立区县管理员与街道执法人员的责任边界
- 角色权限：
  - 平台管理员：创建、启停监管人员
- 前置条件：
  - 平台已有管理员账号
  - 已初始化行政区划
- 功能描述：
  - 平台管理员创建监管账号与监管档案
  - 角色分为区县管理员和街道执法人员
  - 一人绑定一个直接辖区
- 业务规则：
  - 区域管理员辖区必须是区县级
  - 执法人员辖区必须是街道级
  - 执法人员只能被派发到其覆盖辖区内的任务
- 输入项：
  - 监管人员姓名
  - 电话
  - 角色类型
  - 工作证件 URL
  - 辖区
- 输出项：
  - 监管档案
  - 监管账号
- 异常处理：
  - 角色与辖区级别不匹配时报错
  - 用户名重复时报错
- 数据涉及：
  - `food_user_db.sys_user`
  - `food_user_db.sys_user_role`
  - `food_regulation_db.food_regulator`
  - `food_regulation_db.food_regulator_region`
- 当前项目实现情况：部分实现
- 后续完善建议：
  - 若时间不足，不做复杂“区域交接”和“角色调整”页面，只保留接口说明

### 4.9.3 功能：检查任务与检查记录

- 功能目标：形成日常监管检查的任务下发和结果留痕机制
- 角色权限：
  - 区域管理员：创建、派发、归档
  - 执法人员：启动、提交检查结果
- 前置条件：
  - 企业必须已审批通过
  - 执法人员必须在任务区域可执行
- 功能描述：
  - 区域管理员针对企业创建检查任务
  - 执法人员接收并执行
  - 提交检查结果后生成检查记录与检查明细
- 业务规则：
  - 截止时间必须是未来时间
  - 至少填写一个检查项
  - 任务流转：`CREATED -> ASSIGNED -> IN_PROGRESS -> COMPLETED -> CLOSED`
- 输入项：
  - 企业
  - 任务标题
  - 任务描述
  - 优先级
  - 截止时间
  - 检查项、检查结果、问题描述
- 输出项：
  - 任务号
  - 检查记录
  - 检查明细
- 异常处理：
  - 超期任务不可再派发或启动
  - 非本人任务不可提交
- 数据涉及：
  - `food_regulation_operation_db.inspection_task`
  - `food_regulation_operation_db.inspection_record`
  - `food_regulation_operation_db.inspection_item`
- 当前项目实现情况：已实现

### 4.9.4 功能：整改闭环管理

- 功能目标：对检查发现问题形成明确整改链路和时限控制
- 角色权限：
  - 企业：提交整改说明和附件
  - 区域管理员：复核通过或打回
- 前置条件：
  - 检查结果中存在不合格项
- 功能描述：
  - 系统自动生成整改任务
  - 企业在规定时间内提交整改
  - 区域管理员在规定时间内复核
  - 复核可通过或打回重做
- 业务规则：
  - 首次整改提交时限 72 小时
  - 打回后重提时限 48 小时
  - 监管复核时限 24 小时
  - 状态流转：`ONGOING -> SUBMITTED -> CONFIRMED/REWORK -> SUBMITTED`
- 输入项：
  - 整改进展说明
  - 附件 URL
  - 复核意见
- 输出项：
  - 整改任务
  - SLA 状态
  - 整改动作时间线
- 异常处理：
  - 非企业本人不可提交
  - 非辖区管理员不可复核
  - 非法状态流转禁止提交
- 数据涉及：
  - `food_regulation_operation_db.rectification_task`
  - `food_regulation_operation_db.rectification_action_log`
- 当前项目实现情况：已实现
- 后续完善建议：

  - 公众：提交与查看本人投诉
  - 区域管理员：受理、派发、驳回
  - 执法人员：开始处理、填写处理结果

  - 公众已登录

  - 执法人员处理后回传结果
  - 公众可查看处理进度
- 业务规则：
  - 图片最多 5 张
  - 投诉流转：`SUBMITTED -> PENDING -> ASSIGNED -> PROCESSING -> FEEDBACKED/REJECTED`
  - 执法人员只能处理派发给自己的投诉
  - 区域管理员仅能处理自己辖区范围内企业投诉
- 输入项：
  - 企业 ID
  - 投诉类型
  - 投诉内容
  - 现场图片
  - 处理结果/驳回原因

  - 投诉编号

### 4.9.6 功能：风险预警中心

- 功能目标：对整改超时等风险进行自动识别、预警分派和过程追踪
- 角色权限：
  - 区域管理员：查看辖区预警、分派、处理、解决
  - 执法人员：查看本人预警、处理、解决
- 前置条件：
  - 存在整改超时事件
- 功能描述：
  - 系统扫描整改 SLA，自动生成预警
  - 预警按区域或责任执法人员可见
  - 支持处理中、解决、自动升级、自动归档
- 业务规则：
  - `dedupKey` 保证同一风险事件幂等合并
  - 预警状态：`OPEN -> PROCESSING -> RESOLVED -> CLOSED`
  - 当前主要业务类型为 `RECTIFICATION`
  - 预警统计按作用域进行限制
- 输入项：
  - 预警事件类型

### 4.11.1 核心接口分类

### 4.11.2 关键输入输出

- 登录接口：输入用户名密码，输出 Token、用户类型、角色
- 企业备案接口：输入企业档案，输出企业档案 VO

- 检查提交接口：输入检查结果和检查项，输出任务完成状态
- 整改提交接口：输入进展与附件 URL，输出整改任务当前状态
- 投诉提交接口：输入投诉内容与图片，输出投诉编号
- 预警查询接口：输入分页与筛选条件，输出预警分页列表
- 统计接口：输入时间区间/预警筛选条件，输出总览、趋势、类型、效率

### 4.11.3 业务调用关系

- 网关 -> 用户服务：认证、鉴权 introspect
- 网关 -> 业务服务：统一转发并透传用户头
- 投诉服务 -> 监管主数据服务：企业、监管人员、辖区作用域查询
- 执行域服务 -> 监管主数据服务：企业与监管人员范围校验
- 执行域服务 -> 预警服务：通过 outbox 重试推送预警事件
- 查询服务 -> 预警服务：获取预警统计
- 查询服务 -> 监管主数据服务：获取监管角色作用域

### 4.11.4 当前缺失的重要接口类型

- 企业公示详情接口
- 公告发布与查询接口
- 重点监管企业状态维护接口
- 抽检/检测结果接口
- 审计日志查询接口

## 4.12 非功能需求

### 4.12.1 安全性

- 必须通过网关统一鉴权
- 必须按角色和辖区做数据范围限制
- JWT Secret、内部 Token 必须外部化管理
- 【基于业务合理性建议】生产模式应关闭 fail-open 鉴权策略

### 4.12.2 可用性

- 核心查询接口支持分页
- 预警事件推送失败必须具备重试能力
- 服务不可用时应有明确错误信息

### 4.12.3 可维护性

- 公共响应结构统一
- 内部接口职责清晰
- 业务规则集中在 service/application 层

### 4.12.4 扩展性

- 主数据、执行域、投诉域、预警域应保持服务边界
- 新增预警来源应可复用预警事件结构

### 4.12.5 性能

- 普通列表接口分页默认 10 条左右
- 统计接口应控制时间范围与 TopN 上限
- 预警看板允许轻量缓存，但当前可先关闭

### 4.12.6 日志审计

- 关键业务动作必须可审计
- 当前仅有业务日志与部分动作日志，不足以支撑完整审计要求

### 4.12.7 权限控制

- 平台管理员：系统级账号与监管人员维护
- 区域管理员：辖区级企业、任务、投诉、整改、预警管理
- 执法人员：本人任务、本人投诉、本人预警处理
- 企业：本人档案与本人整改
- 公众：本人投诉与公共查询

### 4.12.8 数据一致性

- 主数据在 `regulation-service` 统一维护
- 投诉、执行、查询等服务通过内部接口获取主数据
- 预警事件采用 Outbox + 重试确保最终一致

### 4.12.9 微服务治理要求

- 服务发现统一走 Nacos
- 入口统一走 Gateway
- 熔断与限流预留给 Sentinel
- 接口契约需保持清晰并持续文档化

## 4.13 当前项目与理想需求的差距分析

### 4.13.1 已有基础

- 有清晰的微服务结构
- 有明确的角色体系
- 有可演示的监管闭环
- 有投诉闭环
- 有预警和统计能力

### 4.13.2 当前不足

- 食品安全专业对象缺失
- 公众公示能力不完整
- 部分后台能力只是占位
- 统计服务与数据模型未完全一致
- 风险联动不足

### 4.13.3 偏差原因

- 前期需求边界没有收束
- 技术架构先行，业务对象定义滞后
- 为了丰富展示而增加了部分界面壳子
- 对“食品安全监管平台”理解停留在监管流程，未落到食品安全专业数据层

### 4.13.4 修正建议

1. 明确平台定位为区域监管协同平台  
2. 优先保住已有闭环  
3. 把未接线/占位功能要么删掉，要么缩成说明项  
4. 用最小模块补足食品安全专业属性  

## 4.14 迭代规划建议

### 第一阶段：收束功能边界

- 建设重点：
  - 明确最终题目与平台定位
  - 精简无力完成的占位模块
  - 补齐 PRD、用例、ER 关系图
- 目标成果：
  - 统一需求边界
  - 形成可答辩的系统主线
- 优先级理由：
  - 不先收束，后续所有开发都会继续跑偏

### 第二阶段：补齐核心监管闭环

- 建设重点：
  - 完善企业备案、检查、整改、投诉、预警联动
  - 打通 `enterprise_key_reason` 与重点监管状态
  - 补最小操作审计
- 目标成果：
  - 形成“问题发现 -> 问题处置 -> 风险上浮”的闭环
- 优先级理由：
  - 这是最能体现监管业务价值的主线

### 第三阶段：完善公众服务与统计展示

- 建设重点：
  - 完善企业公示详情
  - 补公告/风险提示后台数据
  - 优化预警看板和多角色统计说明
- 目标成果：
  - 强化社会监督展示效果
- 优先级理由：
  - 公众能力可显著提升系统完整度和展示感

### 第四阶段：增强食品安全专业属性

- 建设重点：
  - 增加抽检/检测结果最小模块
- 目标成果：
  - 回答“为什么是食品安全监管平台”的专业问题
- 优先级理由：
  - 这是增强项，不应挤压主线闭环开发时间

### 第五阶段：答辩与交付准备

- 建设重点：
  - 补测试
  - 补架构图、流程图、时序图
  - 固化演示脚本
- 目标成果：
  - 可稳定展示的毕业设计成品
- 优先级理由：
  - 没有稳定演示和文档，再好的架构都难以答辩

## 4.15 毕业设计视角建议

### 4.15.1 最适合答辩展示的功能

建议重点展示两条主线：

1. 企业检查 -> 整改 -> 预警 -> 统计看板  
2. 公众投诉 -> 受理 -> 派发 -> 执法处理 -> 反馈

这两条主线既能体现业务闭环，也能体现微服务协作。

### 4.15.2 不宜继续扩展的功能

- 完整用户管理后台
- 复杂权限配置中心
- 完整公告 CMS
- 全国级数据大屏
- 全链路追溯与召回系统

### 4.15.3 如何体现微服务架构的设计价值

- `regulation-service` 统一持有企业与监管人员主数据
- `complaint-service` 独立承载投诉业务
- `regulation-operation-service` 独立承载检查整改执行域
- `warning-service` 独立承载风险预警域
- `query-service` 收口统计和作用域控制
- `gateway-service` 做统一认证与角色路径隔离
- Outbox + 重试机制说明跨服务最终一致性

### 4.15.4 如何平衡技术深度与业务完整性

- 不追求多做功能，而要追求闭环完整
- 技术深度体现在：
  - 微服务边界
  - 网关统一鉴权
  - 内部接口协同
  - 作用域权限控制
  - Outbox 事件一致性
- 业务完整性体现在：
  - 检查与整改闭环
  - 投诉与反馈闭环
  - 风险预警与看板闭环

### 4.15.5 如何避免做成“大而空”的系统

- 页面少一点没有关系，但每条主线必须走通
- 占位功能宁可删除，不要堆在界面上
- 不做“百科式模块大全”，只做“问题闭环链路”
- 所有新增功能都要回答一个问题：
  - 它是否强化了“监管闭环”？

# 5. 后续建议（下一步应该优先改什么）

## 5.1 第一优先级：先改定位和范围

建议你先把项目口径从“泛食品安全监管平台”调整为：

> “基于微服务架构的区域食品安全监管协同平台”

这一步最重要，因为它决定后续所有文档、代码和答辩叙事。

## 5.2 第二优先级：把现有主线做扎实

优先完善以下闭环，而不是继续横向开新模块：

1. 企业备案 -> 审核 -> 纳管  
2. 检查任务 -> 检查记录 -> 整改闭环  
3. 投诉提交 -> 受理 -> 派发 -> 处理 -> 反馈  
4. 整改超时 -> 预警 -> 处理 -> 统计  

## 5.3 第三优先级：删掉或降级占位模块

建议处理方式：

- 管理员“用户管理、日志、区域交接、角色调整”  
  - 如果做不深，改为“后续扩展能力”，不要继续扩 UI 壳子
- 企业“检查结果”  
  - 要么补最小查询，要么临时隐藏入口
- 公众“公告、公示”  
  - 要么补真实后端数据，要么删除入口按钮

## 5.4 第四优先级：补一个最小食品安全专业增强点

如果你想让题目更像“食品安全监管平台”，我建议只补一个最小增强模块：

> 抽检/检测结果录入与公示

理由：

- 比追溯/召回更容易落地
- 比单纯工单流转更有食品安全专业属性
- 可以与公众公告、公示联动

## 5.5 第五优先级：补测试和答辩材料

至少需要补齐：

- 核心业务流程图
- 服务调用关系图
- 数据库 ER 图
- 2 条完整演示脚本
- 关键接口截图或 Swagger 截图
- 至少为投诉闭环或整改闭环增加测试
