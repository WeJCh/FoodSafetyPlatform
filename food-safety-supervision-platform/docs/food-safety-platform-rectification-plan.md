# 微服务食品安全监管平台纠偏方案与整改落地建议

版本：V0.1  
日期：2026-03-19  
文档性质：基于现有项目分析结果、PRD 初稿和代码复核证据形成的整改落地方案

## 1. 项目纠偏目标确认

### 1.1 现在最应该回归的核心目标

【基于代码结构推断】项目应回归为：

> 以企业主体纳管为基础，以日常检查、整改闭环、投诉协同、风险预警、公众公示为主线的区域食品安全监管协同平台。

这一定义有三个关键约束：

- 不追求全链路食品产业数字化
- 不追求大型通用后台平台
- 只做监管最需要、当前代码最有基础、最适合毕业设计讲清楚的闭环

### 1.2 当前最严重的跑偏点

最严重的跑偏不是“功能少”，而是“业务主语跑偏”。

- 【项目可直接证明】`food_enterprise`、`inspection_task`、`rectification_task`、`complaint`、`warning_record` 是当前核心对象，但项目中没有真正成型的食品、产品、样品、检测结果对象。
- 【项目可直接证明】`query-service` 存在 `stat_enterprise`、`stat_inspection`、`stat_complaint` 三张统计表，但当前实现只做代理查询 `warning-service` 统计，统计数据底座和服务定位不一致。
- 【项目可直接证明】前端公众首页展示了企业公示和公告入口，但 `App.vue` 没有接线，后端也没有相应完整公示能力。
- 【项目可直接证明】系统管理员视图中“用户管理、操作日志、角色调整、区域交接”多数是占位，容易继续往通用后台方向发散。

结论：

- 第一跑偏点：食品安全专业对象弱，系统更像监管工单系统
- 第二跑偏点：为了微服务而拆微服务，统计服务价值表达不足
- 第三跑偏点：展示层想做政务门户，但业务底座未跟上

### 1.3 最应该优先保证的核心业务闭环

当前最值得优先保住并补齐的闭环只有四条：

1. 企业备案/审批/纳管闭环
2. 检查任务/检查记录/整改复核/预警联动闭环
3. 公众投诉/受理/派单/处理/反馈闭环
4. 公众查询/企业公示/风险公告最小闭环

如果需要增强“食品安全”专业属性，只建议补一条最小增强闭环：

5. 抽检任务/检测结果/问题处置/公示闭环

### 1.4 最不应该继续扩展的方向

当前不应该继续扩展的方向如下：

- 完整追溯链平台
- 全量召回系统
- 商城、交易、供应链协同
- ERP 式生产过程管理
- 全国级监管大数据平台
- 复杂案件处罚全流程
- 通用后台功能堆砌
- 过度丰富的统计大屏和无数据支撑的 BI 模块

### 1.5 毕业设计范围内最合理的规模边界

【基于毕业设计落地建议】建议将范围收束为 5 个业务域 + 1 个支撑域：

- 主体纳管域：企业、监管人员、辖区、备案审批
- 监管执行域：检查任务、检查记录、整改任务、整改日志
- 协同处置域：公众投诉、受理派发、处理反馈
- 风险预警域：预警生成、预警分派、预警处置、预警统计
- 公众服务域：企业公示、风险公告、投诉入口、投诉进度
- 支撑域：认证鉴权、文件上传、日志审计、基础字典

如果时间允许，再补一个最小“抽检/检测结果”子域，不再继续扩大。

## 2. 项目纠偏总方案

### 2.1 产品纠偏

| 模块 | 处理方向 | 原因 | 落地建议 |
| --- | --- | --- | --- |
| 企业备案审批 | 保留并强化 | 当前已有真实数据模型和审批流程 | 补备案状态说明、审批意见、公众可见字段 |
| 监管人员与辖区 | 保留 | 当前角色边界较清晰，是权限模型基础 | 增加辖区变更规则和审计 |
| 检查任务/检查记录 | 保留并重构 | 是当前最强主线之一，但食品安全专业性偏弱 | 增加检查模板、检查附件、问题分类 |
| 整改闭环 | 保留并强化 | 已具备时限、日志、复核、预警联动 | 增加整改结果标签、超期处置策略 |
| 投诉处理 | 保留并强化 | 当前闭环较完整，公众演示价值高 | 增加反馈结果、超时提醒、公众可见处理摘要 |
| 预警中心 | 保留并收束 | 当前可形成技术亮点，但不应无限扩展 | 聚焦整改超期和投诉高发两类预警 |
| 统计看板 | 弱化并收敛 | 当前统计底座不足，容易成为空壳 | 只保留与闭环直接相关的监管指标 |
| 公示与公告 | 必须补齐最小闭环 | 前端已有表达，后端能力缺失 | 至少补企业公示详情和公告发布 |
| 系统管理员通用后台 | 弱化 | 容易偏成通用管理系统 | 只保留监管账号开通、停用、辖区配置 |
| 通用日志、角色调整、区域交接占位模块 | 删除或延期 | 当前没有业务支撑，答辩价值低 | 先隐藏前端入口，不扩开发 |
| 抽检/检测结果 | 最小新增 | 是最能提升食品安全专业属性的能力 | 做最小版，不做实验室生态和复杂流转 |

产品组织建议：

- 监管端首页只围绕“主体纳管、检查整改、投诉处置、风险预警、公众公示”组织
- 企业端只围绕“备案维护、食品档案、整改反馈、公示查看”组织
- 公众端只围绕“投诉、投诉进度、企业公示、风险公告”组织

### 2.2 业务纠偏

当前断裂或不合理的流程包括：

- 公众首页展示了企业公示和公告，但无真实闭环
- 企业端有“检查结果”入口，但当前只是占位
- 企业重点监管能力停留在 `enterprise_key_reason` 表层，没有真正与预警、投诉、检查失败联动
- 统计服务预留了企业/检查/投诉统计表，但没有生成、汇总、读取闭环
- 文件上传只校验文件类型和业务类型枚举，没有按角色限制业务场景

建议重建的核心流程如下：

1. 企业备案 -> 审批 -> 纳入监管 -> 进入检查池
2. 检查任务 -> 检查记录 -> 问题发现 -> 自动生成整改 -> 逾期触发预警 -> 监管复核关闭
3. 公众投诉 -> 受理 -> 派发 -> 处理 -> 结果反馈 -> 公众查询
4. 风险预警 -> 指派 -> 处置 -> 关闭 -> 统计分析
5. 企业公示/风险公告 -> 公众查询 -> 形成公开窗口
6. 可选增强：抽检任务 -> 检测结果 -> 不合格处置 -> 公示

最适合毕业设计展示的闭环是：

- 检查整改预警闭环
- 投诉协同闭环
- 企业备案公示闭环

### 2.3 角色纠偏

当前角色体系总体可用，但要收缩而不是继续加角色。

| 角色 | 当前状态 | 问题 | 纠偏建议 |
| --- | --- | --- | --- |
| 系统管理员 | 已支持 | 容易向通用后台发散 | 只保留账号开通、停用、辖区配置，不再扩展杂项后台 |
| 区域管理员 | 已支持 | 权责边界可用，但统计、公示、重点监管未串联 | 负责企业审批、任务下发、投诉受理、预警分派、公示发布 |
| 执法人员 | 已支持 | 与预警、投诉、检查之间协同能力还可加强 | 聚焦“我的任务、我的投诉、我的预警、我的复核” |
| 企业用户 | 已支持 | 只有备案和整改，缺少食品安全对象维护 | 增加食品/产品档案维护，保留整改提交 |
| 公众用户 | 已支持 | 只有投诉，不足以体现公众服务窗口 | 增加企业公示和公告查询 |

不建议本轮新增独立角色：

- 检测机构
- 供应链主体
- 高级分析员
- 多级审批管理员

如果需要检测结果，建议由监管端先代录或简化为管理员录入，不新增独立机构角色。

### 2.4 数据纠偏

| 数据问题 | 现状证据 | 风险 | 纠偏方向 |
| --- | --- | --- | --- |
| 企业是主对象，但食品/产品对象缺失 | `food_enterprise` 存在，产品类表缺失 | 难以证明“食品安全”专业属性 | 增加最小产品档案表 |
| 重点监管只有表，没有闭环 | `enterprise_key_reason` 有表、实体、Mapper，但业务未使用 | 风险分级能力停留在概念层 | 将投诉高发、整改超期、连续失败联动写入该表 |
| 查询统计表未使用 | `stat_enterprise/stat_inspection/stat_complaint` 无代码使用 | 数据模型与实现脱节 | 暂不扩展；要么补 ETL，要么删表或标记延期 |
| 投诉状态注释不完整 | `complaint.status` 注释未体现 `REJECTED` | 语义不一致，影响文档和接口理解 | 修正字段注释和接口枚举说明 |
| 检查记录语义偏工单 | `inspection_record` 只有 PASS/FAIL 和问题描述 | 无法承载检查项分类、证据、结论 | 增加问题类别、附件、结论等级 |
| 文件上传没有角色-业务绑定 | `MinioFileService` 仅验证 `bizType` 枚举 | 公众可请求不属于自身业务的上传类型 | 在文件预签名接口增加角色与业务类型校验 |

### 2.5 接口纠偏

| 接口类型 | 当前问题 | 纠偏方向 |
| --- | --- | --- |
| 通用 CRUD 接口 | 容易多，但业务动作不足 | 优先补动作型接口，不继续堆列表/增删改查 |
| 企业公示接口 | 只有公开列表，没有公开详情和公告接口 | 增加公开详情、公告列表、公告详情 |
| 重点监管接口 | 没有企业风险分级和原因查询接口 | 增加重点监管原因查询、风险状态更新接口 |
| 检查接口 | 缺少检查附件、公示结论、风险标签 | 增加检查完成动作、问题分类、证据上传 |
| 投诉接口 | 缺少超时提醒、反馈摘要 | 增加投诉 SLA、反馈结果查询、公众摘要接口 |
| 文件接口 | 只有预签名，没有角色约束 | 增加角色校验和业务归属校验 |
| 统计接口 | 统计服务定位漂移 | 只保留与闭环有关的概览、趋势、待办统计 |

### 2.6 前端/交互纠偏

| 页面/入口 | 当前问题 | 纠偏建议 |
| --- | --- | --- |
| `PublicHomeView` | 有企业公示和公告按钮，但未接线 | 要么立即接线补页面，要么临时隐藏 |
| 企业端“检查结果” | 当前为占位 | 要么改成“检查记录查询”最小页，要么先隐藏 |
| 管理员“用户管理/操作日志” | 当前为占位 | 本轮不做，直接隐藏入口 |
| 监管端菜单 | 功能有，但业务分组不够清晰 | 按“主体纳管、检查整改、投诉处置、预警中心、公示统计”重组 |
| 公众端首页 | 文案像政务门户，数据却是演示数据 | 如果没有后台支撑，不要展示“抽检公示”“召回信息”等强承诺文案 |

### 2.7 技术与架构纠偏

| 架构问题 | 当前现状 | 建议 |
| --- | --- | --- |
| 网关鉴权 `fail-open` | 当前为 `true` | 演示环境至少改为可配置的严格模式，默认不建议放开 |
| 默认密钥和内部 Token 写在配置默认值中 | 多服务存在默认值 | 迁移到环境变量，文档中说明 |
| `query-service` 过轻 | 当前几乎是 warning 统计代理 | 不强行物理合并，但明确其职责仅为统计聚合服务，不再额外造壳 |
| 统计表无消费链路 | 表存在但无汇总实现 | 本轮不做离线统计；如果保留，只做接口层说明和延期标识 |
| 业务服务边界 | 当前总体还算清晰 | 保持 `regulation` 主数据、`operation` 执行、`complaint` 投诉、`warning` 预警 的边界，不再细拆 |
| 中间件复杂度 | 已有 Nacos、Sentinel、Gateway、MinIO | 不再引入 MQ、Redis、Seata 等新复杂度，Outbox 足够支撑毕设 |

架构层的核心原则是：

- 逻辑收束优先于物理合并
- 不再新增服务
- 优先修复边界漂移和安全配置问题

## 3. 漏洞与缺陷排查清单

### 3.1 需求漏洞

| 问题 | 项目证据 | 影响 | 修复建议 |
| --- | --- | --- | --- |
| 项目名称与核心对象不匹配 | 当前缺少食品、产品、抽检、检测对象 | 容易被质疑名不副实 | 增加最小产品档案与抽检结果模块 |
| 公众服务目标不完整 | 公众端只有投诉闭环 | 平台公共属性偏弱 | 增加企业公示和公告查询 |
| 风险分级目标未落地 | 有 `status=KEY` 和 `enterprise_key_reason`，但无联动 | 监管价值表达不足 | 建立重点监管识别与展示能力 |
| 统计目标超前于数据基础 | `query-service` 统计表未使用 | 容易形成“看板先行、业务缺席” | 收缩统计目标，只做闭环结果看板 |

### 3.2 业务漏洞

| 问题 | 项目证据 | 影响 | 修复建议 |
| --- | --- | --- | --- |
| 企业公示流程断裂 | 公开企业列表有，详情和公告缺失 | 公众窗口不成立 | 补公开详情、公告发布、公示入口 |
| 检查结果未真正向企业开放 | 企业端检查结果页为占位 | 企业无法查看监管结果 | 增加企业侧检查记录查看页 |
| 重点企业识别未触发 | `enterprise_key_reason` 未参与流程 | 无法展示风险分级监管 | 将投诉、整改超期、连续失败写入重点监管 |
| 抽检链路不存在 | 无抽检任务、结果、处置对象 | 食品安全专业性不足 | 最小新增抽检结果闭环 |
| 预警后企业侧跟踪较弱 | 预警主要在监管侧处理 | 企业整改与风险联动不够直观 | 在企业侧展示关联整改与风险标签 |

### 3.3 数据漏洞

| 问题 | 项目证据 | 影响 | 修复建议 |
| --- | --- | --- | --- |
| 投诉字段缺少 SLA 与反馈摘要 | `complaint` 无超时、反馈摘要字段 | 不利于监管效率统计与公众展示 | 增加处理时限、反馈摘要、驳回原因 |
| 检查记录缺少附件与问题分类 | `inspection_record`、`inspection_item` 结构较薄 | 无法支撑专业检查展示 | 增加附件 URL、问题分类、风险等级 |
| 预警与企业风险档案未关联沉淀 | `warning_record` 与企业风险档案缺少闭环 | 风险长期画像缺失 | 增加企业风险状态更新时间和来源记录 |
| 统计表无更新时间来源 | `stat_*` 表没有生成链路 | 统计可信度无法证明 | 延后或补离线汇总任务 |
| 食品对象缺失 | 无产品表 | 无法关联抽检、投诉、公告 | 增加产品档案表 |

### 3.4 接口漏洞

| 问题 | 项目证据 | 影响 | 修复建议 |
| --- | --- | --- | --- |
| 公开企业只有列表接口 | `PublicEnterpriseController` 仅 `@GetMapping` 列表 | 公众查询半成品 | 增加详情和关键风险提示接口 |
| 统计服务只做代理 | `WarningStatsQueryServiceImpl` 全量代理 warning 内部接口 | 服务独立价值弱 | 明确其只做聚合层，补最小监管概览聚合 |
| 文件上传接口缺少角色限制 | `FileController` 仅凭登录用户可申请预签名，`MinioFileService` 仅校验业务枚举 | 存在越权上传风险 | 增加角色-业务类型矩阵校验 |
| 投诉接口缺少公众可见摘要 | 公众端只能看进度，不适合展示处理结果结构化信息 | 用户感知弱 | 增加投诉处理摘要字段返回 |
| 缺少重点监管相关接口 | 当前无原因查询、状态查询接口 | 重点监管能力不可见 | 新增风险档案查询接口 |

### 3.5 权限漏洞

| 问题 | 项目证据 | 影响 | 修复建议 |
| --- | --- | --- | --- |
| 网关鉴权 fail-open | `gateway.auth.introspect-fail-open: true` | 用户服务异常时可能放行请求 | 默认关闭，开发时按环境开关控制 |
| 默认 JWT 密钥硬编码 | 网关配置中存在默认密钥 | 安全性和演示规范性不足 | 改为环境变量并清理默认值 |
| 文件上传越权 | 公众和企业都可访问 `/api/files/**`，且未按业务类型进一步限制 | 业务边界不严 | 增加 PUBLIC 仅可 COMPLAINT，ENTERPRISE 仅可 RECTIFICATION 等约束 |
| 数据访问粒度仍偏粗 | 多处按角色放行，具体业务归属校验依赖各服务自行处理 | 后续扩展易出错 | 统一补充 enterpriseId、regionId、ownerRegulatorId 归属校验 |

### 3.6 页面漏洞

| 问题 | 项目证据 | 影响 | 修复建议 |
| --- | --- | --- | --- |
| 菜单存在空入口 | `PublicHomeView` 未接线、企业检查页占位、管理员多个占位 | 演示割裂 | 立即隐藏或补最小页面 |
| 录入页多，监管页少 | 目前以录入和列表为主 | 监管感不强 | 补风险处置、待办总览、重点监管视图 |
| 公示层缺乏真实承载 | 公告为演示数据 | 公众服务不可信 | 增加公告发布与公开展示 |
| 前端整体是单文件状态切换 | `App.vue` 手工切换 view | 扩展成本高，状态混乱风险高 | 毕设阶段可暂不切路由，但需收缩页面数量与入口 |

### 3.7 架构漏洞

| 问题 | 项目证据 | 影响 | 修复建议 |
| --- | --- | --- | --- |
| `query-service` 职责漂移 | 有统计库，却主要做代理 | 架构解释成本高 | 定义为“监管统计聚合服务”，不再扩张 |
| 预警与重点监管未形成域协作 | warning 有记录，regulation 有重点监管表，但未联动 | 领域间协同价值没有释放 | 通过事件或服务调用落地联动 |
| 引入中间件多于实际落地能力 | Nacos、Sentinel、MinIO 都已接入，但业务仍不完整 | 容易被质疑“技术先行” | 停止新增基础设施，优先讲清现有价值 |

### 3.8 毕业设计风险漏洞

| 风险 | 表现 | 后果 | 修复建议 |
| --- | --- | --- | --- |
| 主线分散 | 企业、投诉、预警、门户都做一点 | 答辩叙事不集中 | 锁定三条主线展示 |
| 名称与实现不完全匹配 | 没有食品和抽检对象 | 易被追问 | 补最小产品/抽检模块 |
| 页面多但演示深度不足 | 多个页面是占位或静态演示 | 成果感不足 | 优先做深，不继续做多 |
| 微服务很多但价值讲不清 | `query-service` 等边界偏弱 | 架构亮点反变负担 | 调整服务定位说明，停止新增拆分 |

## 6. 核心业务闭环重建方案

### 6.1 企业主体备案/管理闭环

业务目标：

- 将企业从账号注册变成可审批、可纳管、可公开查询的监管对象

触发条件：

- 企业注册后首次提交备案资料

参与角色：

- 企业用户
- 区域管理员
- 公众用户

核心步骤：

1. 企业用户提交备案资料
2. 区域管理员按辖区审核通过或驳回
3. 审核通过后企业进入可检查企业池
4. 企业基础信息对监管端可见
5. 公开字段同步进入公众公示列表和详情

关键数据：

- `food_enterprise`
- `addr_region`
- `addr_location`

系统支撑模块：

- `user-service`
- `regulation-service`
- `food-web`

当前项目缺口：

- 无公众详情
- 公开字段和内部字段未明确分层
- 企业风险级别未沉淀

最小代价补齐方式：

- 增加企业公开详情接口
- 在企业表补 `risk_level/public_status/license_expire_time` 等最小字段
- 在公众端增加“企业公示详情”页

### 6.2 检查任务 -> 整改 -> 预警闭环

业务目标：

- 形成监管执行主线，体现“发现问题 -> 督促整改 -> 逾期预警 -> 复核关闭”

触发条件：

- 区域管理员创建检查任务
- 执法人员提交不合格检查记录
- 企业整改超期

参与角色：

- 区域管理员
- 执法人员
- 企业用户

核心步骤：

1. 区域管理员创建并派发检查任务
2. 执法人员执行检查并提交检查记录、检查项和问题说明
3. 如有不合格项，系统自动生成整改任务
4. 企业提交整改材料和整改说明
5. 区域管理员或执法人员复核，确认或打回
6. 超期未提交或超期未复核，系统生成预警
7. 预警处置完成后闭环结束

关键数据：

- `inspection_task`
- `inspection_record`
- `inspection_item`
- `rectification_task`
- `rectification_action_log`
- `warning_record`
- `warning_process_log`

系统支撑模块：

- `regulation-operation-service`
- `warning-service`
- `regulation-service`
- `food-web`

当前项目缺口：

- 检查记录对企业侧不可见
- 检查结果食品安全语义不足
- 重点监管联动未落地

最小代价补齐方式：

- 增加企业端检查记录查询页
- 增加检查附件、问题分类字段
- 当连续失败或整改超期时写入 `enterprise_key_reason`

### 6.3 举报投诉闭环

业务目标：

- 让公众投诉从“提交成功”变成“真实处理可反馈”

触发条件：

- 公众提交投诉

参与角色：

- 公众用户
- 区域管理员
- 执法人员

核心步骤：

1. 公众提交投诉并生成投诉编号
2. 区域管理员受理或驳回
3. 区域管理员派发给执法人员
4. 执法人员处理并填写结果
5. 公众在“我的投诉”查看状态与反馈摘要
6. 投诉高发或严重投诉可触发重点监管或预警

关键数据：

- `complaint`
- `complaint_handle`
- `food_enterprise`
- `enterprise_key_reason`

系统支撑模块：

- `complaint-service`
- `regulation-service`
- `food-web`

当前项目缺口：

- 投诉反馈摘要不足
- 缺少超时提醒
- 投诉高发未联动重点监管

最小代价补齐方式：

- 在投诉表增加 `deadline_time/feedback_summary/reject_reason`
- 在公众端展示处理摘要
- 新增投诉高发写入重点监管原因的规则

### 6.4 风险预警 -> 研判 -> 处理 -> 跟踪闭环

业务目标：

- 让预警不是单独的数据中心，而是监管动作的结果与放大器

触发条件：

- 整改超期
- 连续检查失败
- 投诉集中爆发

参与角色：

- 区域管理员
- 执法人员

核心步骤：

1. 上游业务触发预警事件
2. 预警中心按辖区/责任人生成或合并预警
3. 区域管理员查看并分派
4. 执法人员处理并反馈
5. 处理完成后预警关闭
6. 预警结果同步影响企业风险状态

关键数据：

- `warning_record`
- `warning_process_log`
- `enterprise_key_reason`
- `food_enterprise.status`

系统支撑模块：

- `warning-service`
- `regulation-service`
- `query-service`

当前项目缺口：

- 预警到重点监管的沉淀缺失
- 预警类型过少
- 看板只反映预警，不反映风险对象

最小代价补齐方式：

- 补投诉高发、连续失败两类预警事件来源
- 将 `warning_record` 关闭前后的企业状态变更沉淀到监管主数据
- 统计看板增加“重点监管企业数”和“新增风险企业数”

### 6.5 信息公示闭环

业务目标：

- 让平台具备最基本的公众服务窗口属性

触发条件：

- 企业审批通过
- 监管发布公告
- 抽检结果或风险提示产生

参与角色：

- 区域管理员
- 公众用户

核心步骤：

1. 企业审批通过后自动进入可公示名单
2. 区域管理员发布风险公告或监管通知
3. 公众查询企业公示详情和最新公告
4. 如存在抽检不合格结果，可同步公示

关键数据：

- 企业公开信息
- 公告信息
- 风险提示信息

系统支撑模块：

- `regulation-service`
- `food-web`
- 可选 `query-service`

当前项目缺口：

- 企业详情缺失
- 公告后台缺失
- 当前公众页大量内容是静态演示

最小代价补齐方式：

- 增加公告表与后台发布接口
- 公众端接线企业公示页和公告页
- 删除没有真实数据的演示文案

### 6.6 抽检任务 -> 检测结果 -> 问题处置闭环（建议最小增强）

业务目标：

- 用最小代价补足“食品安全监管”最缺的专业对象和专业流程

触发条件：

- 区域管理员发起抽检

参与角色：

- 区域管理员
- 执法人员或管理员录入结果
- 企业用户
- 公众用户

核心步骤：

1. 创建抽检任务，选择企业和产品
2. 录入检测结果，标记合格或不合格
3. 如不合格，触发整改或重点监管
4. 必要信息进入公示页面

关键数据：

- 企业产品档案
- 抽检任务
- 抽检结果
- 处置结果

系统支撑模块：

- `regulation-service`
- `regulation-operation-service`
- `food-web`

当前项目缺口：

- 产品对象不存在
- 抽检任务和结果对象不存在

最小代价补齐方式：

- 只加 2 到 3 张表：产品档案、抽检任务、抽检结果
- 不引入检测机构角色
- 不做复杂实验室流程和电子报告流转

## 7. 适合毕业设计的最小可行整改方案（MVP 纠偏版）

### 7.1 有限时间内最少应该完成哪些功能

最小可行范围建议如下：

1. 企业备案审批
2. 检查任务与检查记录
3. 整改闭环与预警联动
4. 公众投诉闭环
5. 企业公示详情与公告展示
6. 重点监管原因联动

### 7.2 哪几个闭环做出来后，项目就能站得住

至少要做成三条闭环：

- 企业备案 -> 审批 -> 公示
- 检查 -> 整改 -> 预警 -> 复核
- 投诉 -> 受理 -> 派单 -> 处理 -> 反馈

如果还能再做一个增强闭环：

- 抽检 -> 结果 -> 处置 -> 公示

### 7.3 哪些内容可以先不做

- 复杂角色体系
- 通用日志中心
- 区域交接
- 全链路追溯
- 召回系统
- 大而全 BI 看板
- 独立检测机构

### 7.4 如何平衡业务完整性和技术展示度

建议的平衡方式：

- 业务上，做少但做闭环
- 技术上，保留微服务、网关鉴权、Outbox、MinIO、辖区权限控制这些已有亮点
- 架构表达上，强调“主数据服务 + 执行服务 + 投诉服务 + 预警服务 + 聚合统计服务”的分工

### 7.5 怎样让老师一眼看明白这是食品安全监管平台

必须补齐三个识别点：

1. 企业不是唯一监管对象，还要有最小产品档案或抽检结果对象
2. 公众端不是只有投诉，还要能看到企业公示和风险公告
3. 监管端不是只派工单，还要能看到风险分级、重点监管、问题处置结果

### 10.1 应新增的业务接口

| 接口能力 | 建议示例 | 目的 |

| 企业风险状态刷新 | `POST /api/regulation/enterprise/{id}/risk-refresh` | 支撑重点监管联动 |
| 产品档案管理 | `POST/GET /api/regulation/enterprise/products` | 增加最小产品对象 |
| 抽检任务/结果 | `POST /api/regulation-operation/sampling/tasks`、`POST /api/regulation-operation/sampling/results` | 增强食品安全专业能力 |

### 10.2 应删除或不再扩展的接口方向

| 接口方向 | 建议 |
| --- | --- |
| 通用后台式日志接口 | 本轮不做 |
| 复杂角色交接接口 | 本轮不做 |
| 无数据基础的大而全统计接口 | 不再扩展 |

### 10.3 应重构的接口设计

| 接口 | 当前问题 | 重构建议 |
| --- | --- | --- |
| 文件预签名接口 | 无角色与业务场景限制 | 增加用户角色、业务类型、对象归属三重校验 |
| 查询统计接口 | 与统计表不一致 | 只暴露已真实可解释的指标 |
| 投诉详情接口 | 缺少结构化处理结果 | 返回反馈摘要、驳回原因、处理时限 |
| 检查记录接口 | 企业端无视图支撑 | 增加企业可见 DTO，过滤监管内部字段 |

### 10.4 应补充的校验与状态流转逻辑

- 企业必须审批通过后才能：
  - 接收检查任务
  - 出现在公众公示中
  - 进入抽检任务池
- 文件上传必须校验：
  - 当前用户角色
  - 对应业务类型
  - 对应业务对象归属
- 投诉流转必须校验：
  - 驳回原因必填
  - 反馈摘要必填
  - 处理人必须与被指派人一致
- 重点监管写入必须校验：
  - 触发来源
  - 来源 ID
  - 是否重复写入

## 12. 最终建议：我下一步应该先做什么

先做下面 5 件事，不要同时摊开太多线：

1. 先收边界：把项目正式定位改成“区域食品安全监管协同平台”，并冻结不做清单。
2. 先清前端：隐藏所有占位入口和未接线入口，只保留真实可走通的页面。
3. 先补安全：关闭网关 `fail-open`，修复文件上传越权问题，清理默认密钥。
4. 先补闭环：优先完成“企业公示详情 + 企业检查记录 + 重点监管联动 + 投诉反馈增强”。
5. 最后再做增强：如果时间还够，再加“产品档案 + 抽检结果最小模块”。

具体建议实施顺序：

1. 前端入口收缩
2. 网关与文件权限修复
3. 企业公示与公告闭环
4. 企业检查记录页
5. 重点监管联动
6. 投诉增强
7. 看板收敛
8. 产品档案与抽检最小增强

一句话结论：

> 不要再把项目做大，先把“主体纳管、检查整改、投诉协同、预警处置、公众公示”五件事做深做通，这个项目就能重新站住。
