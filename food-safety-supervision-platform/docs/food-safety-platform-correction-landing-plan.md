日期：2026-04-07  
文档性质：基于当前 PRD、历史纠偏方案、P0/P1/P2 验收记录和当前代码结构形成的纠偏设计、漏洞修复规划、功能收敛重构与可执行落地方案

## 1. 项目纠偏目标确认

### 1.1 这个项目现在最应该回归的核心目标

当前项目最应该回归的核心目标是：

> 以企业主体纳管为基础，以检查整改、投诉协同、抽检公示、风险预警、公众公示和监管概览为主线的区域食品安全监管协同平台。

这个目标对应当前代码中的真实能力：

| 主线 | 当前落点 |
| --- | --- |
| 企业主体纳管 | `food_enterprise`、企业备案、审批、公众企业详情 |
| 产品档案 | `food_product`、企业端产品维护、监管端产品查看 |
| 检查整改 | `inspection_task`、`inspection_record`、`inspection_item`、`rectification_task`、`rectification_action_log` |
| 投诉协同 | `complaint`、`complaint_handle`、受理、派发、处理、驳回、反馈 |
| 风险预警 | `warning_record`、`warning_process_log`、`warning_event_outbox` |
| 抽检公示 | `sampling_task`、`sampling_result`、公众抽检结果页面 |
| 信息公示 | `public_bulletin`、公众公告、公众企业公示 |
| 监管概览 | `query-service` 聚合企业、检查、抽检、投诉、预警指标 |

### 1.2 当前项目最严重的跑偏点

以当前 2026-04-07 代码和文档为准，最严重的跑偏点已经从“业务主线缺失”转变为“后续继续扩张导致交付失控”。

| 跑偏点 | 当前判断 | 必须采取的纠偏动作 |
| --- | --- | --- |
| 继续沿用旧缺口 | 旧文档中“缺产品、缺抽检、缺公示、重点监管未联动”等判断在历史阶段成立，但当前 P1/P2 已补齐主线 | 新文档和答辩材料必须使用当前 PRD 和当前纠偏口径 |
| 功能继续横向膨胀 | 如果继续做追溯、召回、处罚、检测机构、大屏、复杂权限，会破坏毕设可落地性 | 冻结 P2-5 和 P3，不再新增业务线 |
| 把演示环境写成生产级 | 默认 JWT secret、内部 token、MinIO 默认凭据仍存在 | 明确为已接受风险，不宣称生产级配置治理完成 |
| 统计表与真实聚合口径混淆 | `query-service` 的 `stat_*` 表仍是预留表，真实概览来自 Feign 聚合 | 文档中标明 `stat_*` 不作为验收数据来源 |
| 缺少浏览器级手工验收 | P0/P1/P2 有测试和构建证据，但未完整拉起全服务录屏式验收 | 交付前补 6 条主线手工验收记录 |

### 1.3 当前最应该优先保证的核心业务闭环

当前项目最应该优先保证以下闭环，按答辩价值和开发成本排序：

| 优先级 | 闭环 | 价值 | 当前状态 |
| --- | --- | --- | --- |
| 1 | 企业备案 -> 审批 -> 公众公示 | 证明监管对象从源头纳管 | 已实现，需准备演示数据 |
| 2 | 检查任务 -> 检查记录 -> 整改 -> 复核 -> 预警 | 最能体现监管闭环和微服务协作 | 基本实现，需全链路手工验收 |
| 3 | 公众投诉 -> 受理 -> 派发 -> 处理/驳回 -> 反馈查询 | 体现社会监督和监管协同 | 已实现，需准备投诉演示样例 |
| 4 | 产品档案 -> 抽检任务 -> 抽检结果 -> 不合格联动 -> 公众公示 | 证明项目是食品安全平台，不只是工单平台 | 已实现最小版，需演示不合格联动 |
| 5 | 风险预警 -> 指派/处理 -> 解决/归档 -> 统计概览 | 体现风险监管和技术亮点 | 基本实现，需核对统计口径 |
| 6 | 公告发布 -> 公众公告展示 -> 下线 | 补足信息公示窗口 | 已实现最小版，作为辅助展示 |

### 1.4 当前最不应该继续扩展的方向

以下方向不应继续扩展，除非项目重新立项为更大范围的商用系统：

| 不应扩展方向 | 原因 | 当前处理 |
| --- | --- | --- |
| 批次级追溯、召回管理 | 数据模型、业务角色、页面和流程都会大幅增加 | 放弃，最多在答辩中列为未来展望 |
| 检测机构独立角色和实验室报告流转 | 会引入机构账号、样品流转、报告签发等新系统 | 不新增角色，抽检结果由监管/执法端代录 |
| 行政处罚案件全流程 | 超出当前检查整改闭环，容易变成执法案件系统 | 不纳入当前毕设范围 |
| 大屏 BI、离线数仓、ETL | 当前 `query-service` 是轻量聚合，不应硬扩数仓 | 保留监管概览，不接 `stat_*` 离线表 |
| 通用后台、通用操作日志中心、区域交接 | 会偏离食品安全监管主线 | P3 放弃，后续不恢复 |
| 新增 Redis/MQ/Seata/K8s | 技术复杂度高，当前 Outbox 与 Feign 已足够展示 | 不新增中间件 |
| 前端 Vue Router 大重构 | 当前状态切换式前端适合演示，重构风险大 | 不在收口阶段改架构 |

### 1.5 毕业设计范围内最合理的规模边界

合理边界是 6 个业务域加 2 个支撑域：

| 范围 | 保留内容 | 明确不做 |
| --- | --- | --- |
| 主体纳管域 | 企业、监管人员、辖区、备案审批、公示 | 多级复杂审批、区域交接 |
| 食品对象域 | 产品档案、抽检结果最小模型 | 批次、原料、供应链、检测机构 |
| 监管执行域 | 检查任务、检查记录、整改任务、整改日志 | 处罚案件、检查模板库深度配置 |
| 协同处置域 | 投诉提交、受理、派发、处理、反馈 | 完整行政案件办理 |
| 风险预警域 | 预警事件、处理日志、升级、归档、重点监管原因 | 可配置规则引擎、长期风险画像平台 |
| 公众服务域 | 企业公示、公告公示、抽检结果公示、投诉追踪 | 大型门户、匿名全功能政务服务 |
| 查询统计支撑域 | 监管概览、预警统计 | 离线数仓、大屏 BI |
| 技术支撑域 | 网关鉴权、Feign、Outbox、MinIO、公共响应 | 新增 MQ/Seata/复杂权限平台 |

## 2. 项目纠偏总方案

### 2.1 产品纠偏

| 模块 | 处理方向 | 当前理由 | 落地建议 |
| --- | --- | --- | --- |
| 企业备案与审核 | 保留并作为主线入口 | 监管平台必须先有被监管主体 | 准备企业待审、通过、重点监管三类演示数据 |
| 监管人员与辖区 | 保留但不继续复杂化 | 当前角色路径和辖区模型可支撑演示 | 不做区域交接和复杂权限配置 |
| 产品档案 | 保留 | 已通过 P2 补齐食品专业对象 | 只保留企业产品最小模型，不扩批次和原料 |
| 检查任务与检查记录 | 保留并稳定演示 | 当前最强监管执行闭环 | 不扩复杂模板；如演示需要，后续只补附件或问题分类小增强 |
| 整改闭环 | 保留并作为核心展示 | 能展示状态流转、企业参与、监管复核和 SLA | 保证整改提交、打回、确认三种路径可演示 |
| 投诉处理 | 保留并作为公众闭环展示 | 已有反馈摘要、驳回原因和办理时限 | 准备有效投诉和驳回投诉两个样例 |
| 风险预警 | 保留并收束 | 展示 Outbox、幂等、处理日志和统计价值 | 聚焦整改超期、连续不合格、抽检不合格，不扩规则引擎 |
| 重点监管 | 保留 | 已与投诉、检查、抽检联动 | 在企业详情和公众企业详情中展示原因即可 |
| 抽检任务与结果 | 保留最小版 | 最能补足食品安全属性 | 不新增检测机构，执法端录入结果即可 |
| 公告与公示 | 保留最小版 | 支撑公众服务窗口 | 不扩 CMS，不做置顶、分类、附件等 |
| 系统管理员 | 弱化 | 容易变通用后台 | 仅保留监管账号创建和启停 |
| `query-service` | 保留轻量聚合 | 当前已承担监管概览和预警统计 | 不接离线表，不扩 BI |
| P3 类功能 | 删除或冻结 | 低收益、高发散 | 不新增页面、接口和表 |

### 2.2 业务纠偏

当前业务纠偏的重点不是重建所有业务，而是保证已经落地的闭环能够被讲清、点通和验证。

| 业务问题 | 当前状态 | 纠偏动作 |
| --- | --- | --- |
| 旧阶段业务流程断裂 | 企业公示、公告、抽检、重点监管已在 P1/P2 补齐 | 不再重复开发，转为准备演示路径 |
| 抽检后处置深度不足 | 当前已实现不合格联动重点监管和预警，但未做召回/处罚 | 维持最小闭环，不继续扩处罚和召回 |
| 预警后跟进深度有限 | 当前有指派、处理、解决、升级、归档和日志 | 演示中聚焦预警处理闭环，不承诺长期画像 |
| 统计来源容易被误解 | 真实概览来自服务聚合，`stat_*` 是预留 | 文档和答辩中明确说明 |
| 线上手工闭环未完整证明 | 自动化测试和构建通过，但缺真实多服务点击验收 | P0 级收口任务是补 6 条浏览器级手工验收记录 |

建议重建和固化的业务流程：

| 流程 | 固化方式 |
| --- | --- |
| 企业备案 -> 审批 -> 公众公示 | 用 1 个新企业从提交到审核通过，再在公众端查看详情 |
| 检查 -> 不合格 -> 整改 -> 复核 -> 预警 | 用 1 个不合格检查生成整改，演示提交和复核；另准备一个超期样例展示预警 |
| 投诉 -> 受理 -> 派发 -> 处理 -> 公众反馈 | 用 1 个公众投诉走完整流程，公众端查看反馈摘要 |
| 产品 -> 抽检 -> 结果 -> 公示 -> 重点监管 | 用 1 个产品和 1 条 FAIL 抽检结果展示风险联动 |
| 预警 -> 处理 -> 统计 | 从预警列表处理一条预警，再看监管概览和预警统计 |
| 公告 -> 发布 -> 展示 -> 下线 | 作为辅助闭环展示公众服务能力 |

### 2.3 角色纠偏

当前角色体系总体可用，不建议新增角色。

| 角色 | 当前职责 | 纠偏结论 |
| --- | --- | --- |
| 系统管理员 `ADMIN` | 创建监管账号、启停监管人员 | 保留最小账号管理，不扩通用后台 |
| 区域管理员 `REGULATOR_ADMIN` | 企业审批、检查/抽检派发、整改复核、投诉受理派发、公告发布、预警处理、概览查看 | 作为监管端核心角色 |
| 执法人员 `REGULATOR_ENFORCER` | 执行检查、录入抽检结果、处理投诉、跟进整改、处理本人预警 | 作为执行端核心角色 |
| 企业用户 `ENTERPRISE` | 企业备案、产品档案、检查记录查看、整改提交 | 保留，不扩生产过程管理 |
| 公众用户 `PUBLIC` | 投诉提交、进度查询、企业/公告/抽检结果公示查询 | 保留，不扩大型公众门户 |
| 检测机构 | 当前未支持 | 不新增，抽检结果由监管/执法端录入 |
| 供应链主体 | 当前未支持 | 不新增 |
| 领导大屏角色 | 当前未支持 | 不新增，监管管理员可使用概览面板 |

权限纠偏原则：

| 原则 | 说明 |
| --- | --- |
| 网关路径级约束保留 | 当前 `JwtAuthFilter` 已按角色路径限制，并默认 fail-closed |
| 服务内归属校验保留 | 企业、辖区、任务、投诉等归属校验仍应在服务层保留 |
| 不抽象复杂权限中心 | 当前毕设不需要 ABAC/RBAC 权限平台 |
| 高危操作只给监管管理员 | 企业审批、公告发布、抽检结果发布、整改复核应由监管管理员承担 |
| 企业和公众数据隔离 | 企业只能看自身档案、产品、检查、整改；公众只能看公开信息和本人投诉 |

### 2.4 数据纠偏

| 数据对象 | 当前状态 | 纠偏结论 |
| --- | --- | --- |
| `sys_user`、`sys_role`、`sys_user_role` | 账号和角色基础表已存在 | 保留，不扩复杂权限表 |
| `food_enterprise` | 企业主体表，含审批和重点监管状态 | 保留，作为核心主表 |
| `food_product` | 产品档案已存在 | 保留，不扩批次和原料 |
| `food_regulator`、`food_regulator_region` | 监管人员和辖区绑定已存在 | 保留，不做区域交接 |
| `inspection_task`、`inspection_record`、`inspection_item` | 检查任务和记录已存在 | 保留；附件、问题分类是可选增强 |
| `rectification_task`、`rectification_action_log` | 整改闭环和动作日志已存在 | 保留，作为过程留痕 |
| `complaint`、`complaint_handle` | 投诉闭环已含反馈、驳回和时限 | 保留 |
| `warning_record`、`warning_process_log` | 预警和处理日志已存在 | 保留，不补复杂规则引擎 |
| `warning_event_outbox` | 轻量事件一致性表 | 保留，作为技术亮点 |
| `sampling_task`、`sampling_result` | 抽检任务和结果已存在 | 保留，不扩实验室报告 |
| `enterprise_key_reason` | 重点监管原因表已存在 | 保留，确保演示数据中有原因 |
| `public_bulletin` | 公告表已存在 | 保留 |
| `stat_enterprise`、`stat_inspection`、`stat_complaint` | 预留统计表，当前不作为真实统计来源 | 不删除但标注预留，不接 ETL |

必须修正的不是大量表结构，而是数据使用口径：

| 问题 | 修正方式 |
| --- | --- |
| schema 中含 `DROP TABLE` | 标注为原型初始化脚本，禁止作为生产迁移脚本 |
| `stat_*` 表未接入业务链路 | 文档和运行说明中标为预留，不用于答辩演示数据来源 |
| 检查记录专业字段偏少 | 当前不作为阻断项；如演示需要再补附件、问题分类 |
| 抽检模型偏最小 | 当前可支撑毕设；不补样品流转和检测报告 |

### 2.5 接口纠偏

接口纠偏原则是：优先保证动作型接口和状态流转接口，不继续堆泛 CRUD。

| 接口类别 | 当前状态 | 纠偏动作 |
| --- | --- | --- |
| 认证与账号 | 登录、注册、监管账号创建、introspect 已存在 | 保留，不扩通用用户中心 |
| 企业备案审批 | 企业提交、待审、审批、驳回、批量操作已存在 | 保证演示路径可走通 |
| 公众企业公示 | 列表和详情已存在 | 保证只展示公开/已审核数据 |
| 产品档案 | 企业维护和监管查看已存在 | 保证抽检任务可关联产品 |
| 检查任务 | 创建、派发、开始、提交、关闭已存在 | 重点验证状态流转和权限 |
| 整改任务 | 我的整改、提交、复核、动作日志已存在 | 重点验证企业提交和监管复核 |
| 投诉处理 | 提交、我的投诉、列表、详情、受理、派发、处理、驳回已存在 | 重点验证反馈摘要和驳回原因 |
| 预警处理 | 列表、详情、指派、处理、解决、内部 upsert 已存在 | 重点验证状态校验和幂等 |
| 抽检任务/结果 | 创建、派发、录入结果、发布、下线、公众查看已存在 | 重点验证 FAIL 联动和公众可见状态 |
| 公告 | 管理端草稿/发布/下线、公众列表/详情已存在 | 保持最小闭环 |
| 查询统计 | 预警统计、监管概览已存在 | 不新增大屏接口 |

## 3. 漏洞与缺陷排查清单

这里的漏洞按广义问题理解，不限于安全漏洞。

### 3.1 需求漏洞

| 问题 | 当前证据 | 影响 | 修复规划 |
| --- | --- | --- | --- |
| 旧需求口径没有同步当前实现 | 旧纠偏文档中的部分缺口已被 P1/P2 修复 | 容易重复开发或答辩表述冲突 | 以当前 PRD 和本文档作为交付口径 |

| 交付需求不完整 | 缺完整在线手工验收、演示数据、运行说明 | 答辩演示风险高 | 把交付收口列为 P0/P1 |
| 生产级安全需求被放弃但需说明 | P2-5 不再推进 | 如果误称已完成会被质疑 | 写入风险接受说明 |

### 3.2 业务漏洞

| 问题 | 当前证据 | 影响 | 修复规划 |
| --- | --- | --- | --- |
| 浏览器级业务闭环未完整验收 | P0/P1/P2 报告均说明未拉起全服务录屏式验收 | 演示时可能出现环境或数据断点 | 补 6 条手工验收记录 |
| 抽检后未做处罚/召回 | 当前抽检只到不合格联动、预警和公示 | 不是企业级完整食品安全处置 | 明确不做处罚/召回，保留最小闭环 |

### 3.3 数据漏洞

| 问题 | 当前证据 | 影响 | 修复规划 |
| --- | --- | --- | --- |

| 检查证据能力 | 检查记录无附件字段 | 可选补附件字段和文件上传场景 | 检查整改闭环 |

### 5.4 建议新增的功能

当前 MVP 不建议新增大功能。建议新增的是交付型资产和少量可选增强。

| 新增项 | 为什么必须或可选新增 | 弥补缺口 | 毕设范围内是否值得做 | 优先级 |
| --- | --- | --- | --- | --- |

| 最小运行说明 | 必须 | 多服务复现成本高 | 值得 | P1 |
| 配置风险说明 | 必须 | P2-5 放弃后的风险交代 | 值得 | P0 |
| ER 图/服务调用图/核心时序图 | 建议 | 提升答辩表达 | 值得 | P2 |
| 检查附件 | 可选 | 增强证据链 | 时间充裕才做 | P2 |
| 抽检样品编号/报告编号 | 可选 | 增强抽检专业感 | 时间充裕才做 | P2 |

## 6. 核心业务闭环重建方案

### 6.1 闭环优先级筛选

| 闭环 | 当前建议 | 原因 |
| --- | --- | --- |
| 企业主体备案/管理闭环 | 必做并演示 | 监管对象基础 |
| 食品档案/产品管理闭环 | 必做并演示 | 证明食品安全属性 |
| 抽检任务 -> 检测结果 -> 问题处置闭环 | 必做最小版 | 已实现，展示价值高 |
| 风险预警 -> 研判 -> 处理 -> 跟踪闭环 | 必做并演示 | 技术和业务亮点 |
| 问题食品追溯闭环 | 不做完整闭环 | 超范围，最多用企业+产品+抽检结果做“最小问题来源定位”说明 |
| 监管整改闭环 | 必做并演示 | 最强监管闭环 |
| 举报投诉闭环 | 必做并演示 | 公众参与亮点 |
| 信息公示闭环 | 必做辅助演示 | 公告、企业、抽检公示已存在 |

### 6.2 企业主体备案/管理闭环

| 项 | 设计 |
| --- | --- |
| 业务目标 | 建立被监管企业底数，支持审批、纳管、公示和后续检查/抽检 |
| 触发条件 | 企业用户注册后提交企业档案 |
| 参与角色 | 企业用户、区域管理员、公众 |
| 核心步骤 | 企业提交档案 -> 区域管理员审核/驳回 -> 审核通过进入监管对象池 -> 公众查询企业详情 |
| 关键数据 | `food_enterprise`、`addr_region`、`addr_location`、`enterprise_key_reason` |
| 系统支撑模块 | `regulation-service`、`food-web` 企业端和公众端 |
| 当前项目缺口 | 主要缺演示数据和真实点击验收 |
| 最小代价补齐 | 准备 1 个待审企业、1 个通过企业、1 个重点监管企业并完成手工验收 |

### 6.3 食品档案/产品管理闭环

| 项 | 设计 |
| --- | --- |
| 业务目标 | 让企业监管从“企业主体”扩展到“企业产品” |
| 触发条件 | 企业备案通过后维护产品档案，监管人员创建抽检任务时选择产品 |
| 参与角色 | 企业用户、区域管理员、执法人员 |
| 核心步骤 | 企业维护产品 -> 监管查看企业产品 -> 抽检任务关联产品 |
| 关键数据 | `food_product`、`food_enterprise`、`sampling_task` |
| 系统支撑模块 | `regulation-service`、`regulation-operation-service`、企业端页面 |
| 当前项目缺口 | 没有批次、原料、生产过程 |
| 最小代价补齐 | 不补批次；为演示企业准备 2 到 3 个产品即可 |

### 6.4 抽检任务 -> 检测结果 -> 问题处置闭环

| 项 | 设计 |
| --- | --- |
| 业务目标 | 形成食品安全专业闭环：抽检、结果、风险联动、公示 |
| 触发条件 | 区域管理员创建抽检任务并派发给执法人员 |
| 参与角色 | 区域管理员、执法人员、公众 |
| 核心步骤 | 创建抽检任务 -> 派发 -> 执法人员录入结果 -> FAIL 触发重点监管和预警 -> 管理员发布结果 -> 公众查看 |
| 关键数据 | `sampling_task`、`sampling_result`、`food_product`、`enterprise_key_reason`、`warning_event_outbox`、`warning_record` |
| 系统支撑模块 | `regulation-operation-service`、`regulation-service`、`warning-service`、公众抽检页面 |
| 当前项目缺口 | 无检测机构和实验室报告 |
| 最小代价补齐 | 保持“监管代录结果”的最小闭环；准备 1 条 PASS 和 1 条 FAIL 抽检结果 |

### 6.5 风险预警 -> 研判 -> 处理 -> 跟踪闭环

| 项 | 设计 |
| --- | --- |
| 业务目标 | 将整改超期、连续不合格、抽检不合格等风险转为可处理预警 |
| 触发条件 | 业务服务通过 outbox 或内部事件 upsert 预警 |
| 参与角色 | 区域管理员、执法人员 |
| 核心步骤 | 风险事件生成 -> 预警去重入库 -> 分派/处理 -> 解决/归档 -> 概览统计 |
| 关键数据 | `warning_event_outbox`、`warning_record`、`warning_process_log` |
| 系统支撑模块 | `regulation-operation-service`、`warning-service`、`query-service` |
| 当前项目缺口 | 没有复杂规则配置和长期画像 |
| 最小代价补齐 | 准备几类预警样例；答辩中说明规则引擎不在范围内 |

### 6.6 问题食品追溯闭环

| 项 | 设计 |
| --- | --- |
| 业务目标 | 当前不做完整追溯，只做问题来源定位说明 |
| 触发条件 | 抽检结果 FAIL |
| 参与角色 | 区域管理员、执法人员、公众 |
| 核心步骤 | 抽检结果 -> 关联企业和产品 -> 公众查看结果 -> 企业被标记重点监管 |
| 关键数据 | `sampling_result.enterprise_id`、`sampling_result.product_id`、`food_product`、`food_enterprise` |
| 系统支撑模块 | 抽检、公示、重点监管模块 |
| 当前项目缺口 | 没有批次、流向、召回、供应链 |
| 最小代价补齐 | 不补表；在答辩中表述为“最小问题来源定位”，不称为完整追溯 |

### 6.7 监管整改闭环

| 项 | 设计 |
| --- | --- |
| 业务目标 | 将检查发现问题转化为企业整改和监管复核 |
| 触发条件 | 执法人员提交 FAIL 检查记录 |
| 参与角色 | 区域管理员、执法人员、企业用户 |
| 核心步骤 | 检查任务 -> 提交不合格记录 -> 自动生成整改 -> 企业提交整改 -> 监管复核通过/打回 -> 超期触发预警 |

| 最小代价补齐 | 不补复杂模板；演示时以检查项、问题描述、整改附件支撑即可 |

### 6.8 举报投诉闭环

| 项 | 设计 |
| --- | --- |
| 业务目标 | 公众举报投诉可受理、派发、处理和反馈 |
| 触发条件 | 公众提交投诉 |
| 参与角色 | 公众、区域管理员、执法人员 |

### 6.9 信息公示闭环

| 项 | 设计 |
| --- | --- |

## 7. 适合毕业设计的 MVP 纠偏方案

### 7.1 有限时间内最少应该完成哪些功能

最少应完成的不是新功能，而是以下交付闭环：

| 最小项 | 说明 |
| --- | --- |
| 企业备案审批和公示 | 用于讲清监管对象纳管 |
| 企业产品档案 | 用于支撑食品安全属性 |
| 检查整改和预警 | 用于讲清“发现问题 -> 整改 -> 风险预警” |
| 投诉反馈 | 用于讲清公众参与和监管处置 |
| 抽检结果和公示 | 用于讲清食品抽检专业闭环 |
| 重点监管原因展示 | 用于讲清风险沉淀 |
| 监管概览 | 用于讲清平台整体监管价值 |
| 演示脚本、演示数据、手工验收 | 用于保证答辩可演示 |

### 7.2 哪几个闭环做出来后项目就能站得住

只要以下 4 个闭环能稳定演示，项目就能站得住：

| 闭环 | 为什么足够支撑毕设 |
| --- | --- |
| 企业备案 -> 审批 -> 公示 | 说明监管主体从哪里来 |
| 检查 -> 整改 -> 预警 -> 复核 | 说明监管怎么发现和处理问题 |
| 投诉 -> 受理 -> 派发 -> 处理 -> 反馈 | 说明公众监督和部门协同 |
| 产品 -> 抽检 -> 结果 -> 重点监管 -> 公示 | 说明为什么是食品安全监管平台 |

监管概览作为辅助展示，公告作为信息公开补充。

### 7.3 哪些内容可以先不做，避免开发失控

| 可以不做 | 原因 |
| --- | --- |
| 追溯、召回、处罚 | 超出 MVP，需大量新表和流程 |
| 检测机构角色 | 会打开新角色和报告流程 |
| 通用操作日志中心 | 不是核心监管闭环 |
| 复杂权限平台 | 当前角色已够毕设 |
| 离线数仓和大屏 BI | 当前聚合概览足够 |
| Docker/K8s | 非业务核心，时间成本高 |
| Vue Router 重构 | 对答辩收益低，风险高 |
| P2-5 配置治理 | 已决策不推进，只说明风险 |

### 7.4 如何平衡业务完整性和技术展示度

| 维度 | 做法 |
| --- | --- |
| 业务完整性 | 只展示企业、检查整改、投诉、抽检、公示、预警、概览 |
| 技术展示度 | 重点讲网关鉴权、服务拆分、Feign、Outbox、统计聚合 |
| 风险控制 | 不新增中间件、不重构前端、不开新角色 |
| 答辩表达 | 用 4 条主闭环串起所有服务，而不是逐模块介绍 |

### 7.5 怎样让老师一看就明白是食品安全监管平台

演示顺序建议：

| 顺序 | 展示内容 | 老师能看到的食品安全特征 |
| --- | --- | --- |
| 1 | 企业备案和许可证信息 | 食品经营主体纳管 |
| 2 | 产品档案 | 食品对象，而不是普通工单对象 |
| 3 | 抽检任务和不合格抽检结果 | 食品安全抽检 |
| 4 | 不合格联动重点监管和预警 | 风险监管 |
| 5 | 公众查看企业、公告、抽检结果 | 信息公示 |
| 6 | 检查整改和投诉反馈 | 监管处置闭环 |

## 12. 最终建议：我下一步应该先做什么

下一步不要再新增业务模块。建议按以下顺序执行：

| 顺序 | 具体动作 | 目标 |
| --- | --- | --- |
| 1 | 以本文档、当前 PRD、P0/P1/P2 验收报告作为后续唯一口径 | 防止旧缺口和当前状态混淆 |
| 2 | 准备演示数据 | 保证企业、产品、检查、整改、投诉、抽检、预警、公告都有样例 |
| 3 | 写 6 条演示脚本 | 企业备案公示、检查整改预警、投诉反馈、产品抽检公示、重点监管、监管概览 |
| 4 | 补最小运行说明 | 写清依赖、启动顺序、环境变量、schema 风险 |
| 5 | 拉起全服务做浏览器级手工验收 | 把“代码已实现”变成“演示能跑通” |
| 6 | 只修真实阻断 bug | 接口失败、页面进不去、状态流转卡住才改代码 |
| 7 | 准备答辩图 | 服务边界图、核心 ER 图、检查整改时序图、投诉时序图、抽检预警时序图 |

一句话结论：

> 当前项目已经具备毕业设计站得住的主线，不要再扩功能；先用演示数据、手工验收和答辩材料把“企业纳管、检查整改、投诉反馈、产品抽检、公示预警、监管概览”这条主线稳定讲清楚。
