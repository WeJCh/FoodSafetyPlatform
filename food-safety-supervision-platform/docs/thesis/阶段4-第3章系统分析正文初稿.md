# 阶段4-第3章系统分析正文初稿.md

## 第3章 系统分析

### 3.1 系统业务需求

#### 3.1.1 平台建设目标

食品安全监管业务具有监管对象数量多、业务参与主体复杂、流程链条长和信息协同要求高等特点。在实际监管场景中，企业基础信息备案、监管人员管理、日常检查、抽样检测、整改复核、公众投诉、公告公示和风险预警等工作通常并不是孤立存在的，而是围绕食品安全治理目标相互关联、相互影响。若缺少统一的信息平台，各业务环节容易形成数据分散、处理脱节和追踪困难等问题，难以支撑监管业务闭环。

结合本项目实际实现内容，平台建设的主要目标可以概括为以下几个方面。

第一，建立统一的食品安全监管业务平台。系统需要将企业备案、产品档案、检查任务、抽检任务、整改管理、投诉处理、公告发布、预警跟踪和统计查询等功能纳入统一系统，以支撑食品安全监管工作从基础信息管理到问题处置反馈的完整流程。

第二，支撑多角色协同监管。项目实际面向系统管理员、区域管理员、执法人员、企业用户和公众用户五类角色，不同角色在系统中的职责与操作范围明显不同。因此，平台需要围绕角色差异组织业务流程，并通过统一登录认证、角色访问控制和分角色页面入口实现协同工作。

第三，提高监管业务过程的规范化和可追溯性。系统中的检查任务、抽检结果、整改任务、投诉记录和预警记录都具有状态流转特征，需要通过结构化数据记录业务过程，为后续监督、查询和统计分析提供依据。

第四，兼顾监管内部管理与公众服务需求。除了监管部门内部的任务派发、审核和处置流程外，系统还需要支持公众查询公告、公示企业和抽检结果，并提供投诉提交与跟踪入口，使平台既服务于内部监管，也服务于外部信息公开与社会监督。

#### 3.1.2 主要业务对象与用户角色

根据项目中的用户角色定义、网关权限规则和前端路由配置，系统涉及的主要业务对象包括监管部门、食品生产经营企业、社会公众以及系统运行维护人员。进一步从系统用户角度分析，可将平台角色划分为以下五类。

（1）系统管理员。系统管理员主要负责监管人员账号的创建和维护，对应前端中的系统管理员工作台和监管人员管理相关页面。该角色关注平台基础账户和权限初始化，是系统管理层面的核心角色。

（2）区域管理员。区域管理员负责监管业务管理，主要包括企业备案审核、企业信息查看、检查任务创建与派发、抽检任务创建、整改复核、投诉流转、公告管理、预警中心和统计概览等功能。该角色是平台中监管管理流程的主要组织者。

（3）执法人员。执法人员主要承担一线业务执行工作，包括查看辖区企业、执行检查任务、提交检查结果、执行抽检任务、录入抽检结果、处理投诉、跟进整改和处理预警等。该角色是监管执行链条的直接参与者。

（4）企业用户。企业用户主要负责企业备案资料维护、产品档案维护、查看检查记录和整改任务、提交整改进展等。该角色对应被监管主体，是平台业务数据的重要来源之一。

（5）公众用户。公众用户可以注册登录系统，查看公告、企业公示和抽检结果，并进行投诉提交与投诉跟踪。该角色体现了系统对社会监督和信息公开需求的支持。

上述角色之间并非简单并列关系，而是围绕同一监管目标参与不同业务环节。系统需要在保证角色边界清晰的前提下，实现数据共享与流程衔接，这也是本项目业务需求分析的核心出发点。

#### 3.1.3 核心监管业务场景

结合后端控制器、前端路由和数据库设计，可以确认本项目围绕以下核心监管业务场景展开。

（1）企业备案与基础信息审核场景。企业用户提交企业名称、许可证编号、统一社会信用代码、法定代表人、所属区域、地址及附件等备案信息，区域管理员对待审核企业进行查看、审批或驳回。审核通过后，企业进入可进一步开展产品管理和接受监管的状态。

（2）产品档案管理场景。企业用户在备案完成后维护本企业产品档案，包括产品名称、类别、规格和状态等信息。监管端可以按企业查看相关产品，为抽检任务创建和企业监管提供基础数据支撑。

（3）监督检查场景。区域管理员围绕企业创建检查任务并指派给执法人员，执法人员启动任务并提交检查结果，系统生成检查记录和检查项明细。如果发现问题，后续可进一步形成整改任务。

（4）抽样检测与公示场景。区域管理员创建抽检任务并指派执法人员执行，执法人员完成抽样后提交结果，监管端根据需要发布或下线抽检结果，公众端则能够查看已经发布的抽检结果信息。该场景体现了内部执法流程与外部信息公开的衔接。

（5）整改复核场景。检查过程中发现问题后，系统形成整改任务，企业用户提交整改进展和附件，监管人员查看整改详情、动作日志并进行复核确认或退回整改。该场景构成从问题发现到问题闭环的重要环节。

（6）投诉受理与处理场景。公众用户可以选择企业并提交投诉内容，监管端对投诉进行受理、指派、处理、反馈或驳回。投诉信息既是社会监督的体现，也为后续监管重点识别和风险预警提供输入。

（7）公告公示与信息公开场景。监管端可以创建、编辑、发布和下线公告，公众端能够查看公告列表与详情。同时，企业公示和抽检结果公示共同构成平台对社会公开信息的重要组成部分。

（8）风险预警与统计场景。系统围绕整改超时、抽检不合格等业务事件形成预警记录，并提供预警分派、处理和解决能力。同时，查询服务聚合企业、监管操作、投诉和预警数据，向监管端提供统计概览和预警统计信息。

#### 3.1.4 主要业务流程分析

为保证系统分析与后续设计、实现章节保持一致，本项目的主要业务流程可归纳为以下几条主线。

（1）企业备案业务流程。企业用户注册并登录系统后，提交企业备案资料及附件；系统保存企业基础信息与附件信息；区域管理员查看待审核企业并执行审核或驳回操作；审核通过后，企业进入已审核状态，并可继续维护产品档案。该流程对应了平台中企业主数据建立和审核的起点。

（2）检查与整改业务流程。区域管理员创建检查任务并分派给执法人员；执法人员执行检查并提交检查结果与检查项明细；系统生成检查记录；若检查发现问题，则创建整改任务；企业用户提交整改进展；监管端查看整改详情与整改日志，并执行复核确认或退回整改。该流程体现了从发现问题到问题闭环的监管核心链条。

（3）抽检与公示业务流程。区域管理员创建抽检任务并指定被抽检企业及产品；执法人员执行抽检任务并提交抽检结果；系统保存抽检结果后，监管端可选择发布或下线该结果；公众端查询已发布的抽检结果。该流程体现了抽检监管与社会公开之间的业务衔接。

（4）投诉处理业务流程。公众用户在登录后提交投诉信息；系统保存投诉记录；监管端对投诉进行受理和分派；执法人员对投诉进行处理并形成处理结果；系统记录处理状态和反馈摘要；公众用户可以在前端查看本人投诉记录及详情。该流程体现了社会监督信息进入监管链条后的处置机制。

（5）预警与统计业务流程。监管操作服务和投诉、整改等业务事件会触发预警事件写入或预警状态变更，系统形成预警记录及处理日志；监管端可查看预警详情并执行分派、处理和解决操作；查询服务进一步聚合多业务服务的统计数据，形成监管概览和预警统计结果，用于监管决策支持。该流程体现了平台在业务执行之外的辅助监管能力。

综上，本项目的业务需求并不是单点功能堆叠，而是围绕企业、监管部门和公众之间的互动关系形成多条相互衔接的业务主线。后续功能设计与实现都需要围绕这些业务主线展开。

### 3.2 系统功能需求

#### 3.2.1 功能需求总体划分

依据项目实际实现情况，系统功能需求可以按照角色和业务模块进行划分。为了保证后续设计与实现章节表达一致，本文将功能需求统一归纳为用户与认证、系统管理员功能、监管管理功能、执法执行功能、企业用户功能、公众用户功能以及统计查询功能七个部分。

#### 3.2.2 用户与认证功能需求

系统首先需要提供统一的用户认证能力，以支撑多角色用户安全访问平台。结合实际代码，平台在该方面具有以下功能需求。

（1）用户注册功能。系统需要支持公众用户注册和企业用户注册，并为不同类型用户分配相应角色。

（2）用户登录与登出功能。系统需要为各类用户提供统一登录入口，登录成功后签发身份令牌，并在登出时使当前会话失效。

（3）令牌校验与身份识别功能。系统需要能够校验用户身份令牌的有效性，并在后续请求处理中识别用户编号、用户类型和角色信息。

（4）角色绑定与权限隔离功能。系统需要依据用户角色控制访问范围，避免无权限角色访问不属于自身职责的接口和页面。

该部分功能对应后端的认证、用户、角色控制器以及网关统一鉴权逻辑，是平台运行的基础能力。

#### 3.2.3 系统管理员功能需求

系统管理员主要负责监管人员管理，因此该角色的功能需求主要集中在账户与人员初始化层面。

（1）监管人员账号创建功能。系统管理员需要能够创建监管人员账号，为后续区域管理员和执法人员的业务登录提供基础账户。

（2）监管人员信息查看功能。系统管理员需要查看监管人员列表和详情，掌握监管队伍基本信息。

（3）监管人员状态维护功能。系统管理员需要对监管人员状态进行调整，以支持在岗、停用等管理需要。

该角色功能在系统中规模相对较小，但对平台的角色管理具有基础性作用。

#### 3.2.4 区域管理员功能需求

区域管理员是系统中最核心的监管管理角色，其功能需求覆盖企业审核、任务管理、问题复核、信息公开和监管概览等多个方面。

（1）企业备案审核功能。区域管理员需要查看待审核企业信息，对企业备案进行审批、驳回以及批量审核，并查看企业详情和企业产品信息。

（2）企业信息监管功能。区域管理员需要对辖区企业进行列表查询和详情查看，以掌握企业基础情况和产品档案情况。

（3）检查任务管理功能。区域管理员需要创建检查任务、选择企业和辖区、指派执法人员、查看任务状态和检查记录。

（4）抽检任务管理功能。区域管理员需要创建抽检任务、指定被抽检产品、查看抽检任务详情，并对抽检结果执行发布或下线操作。

（5）整改复核功能。区域管理员需要查看整改任务详情、整改历史和附件信息，对企业提交的整改结果进行确认或退回处理。

（6）投诉流转管理功能。区域管理员需要查看投诉列表与详情，对投诉执行受理、指派、驳回等操作。

（7）公告管理功能。区域管理员需要创建、编辑、发布和下线公告，并维护对公众公开的公告信息。

（8）预警中心功能。区域管理员需要查看预警列表与详情，并对预警记录进行分派、处理和解决。

（9）统计概览功能。区域管理员需要查看系统统计信息，包括监管概览和预警统计结果，为监管决策提供辅助信息。

以上功能共同构成了监管管理端的主要需求。

#### 3.2.5 执法人员功能需求

执法人员承担监管执行任务，因此其功能需求主要围绕“执行”和“反馈”展开。

（1）企业监管查看功能。执法人员需要查看辖区企业信息及其产品、检查、整改和预警情况，为执法决策提供上下文信息。

（2）检查任务执行功能。执法人员需要查看本人待办检查任务、启动任务、录入检查结果并提交。

（3）检查记录查看功能。执法人员需要查看本人执行后的检查记录和具体详情，以支持后续跟进。

（4）抽检任务执行功能。执法人员需要查看本人抽检任务、进入任务详情并提交抽检结果。

（5）投诉处理功能。执法人员需要查看分派到本人的投诉任务，并对投诉执行处理和反馈操作。

（6）整改跟进功能。执法人员需要查看与自己相关的整改任务及其进展情况。

（7）预警处置功能。执法人员需要查看分派到本人的预警记录，并执行处理和解决操作。

（8）统计查看功能。执法人员需要查看部分统计信息，以辅助日常监管执行工作。

执法人员功能强调任务执行和处理反馈，与区域管理员的管理职能形成互补。

#### 3.2.6 企业用户功能需求

企业用户是平台中的被监管主体，其功能需求主要围绕企业资料维护和监管结果响应展开。

（1）企业备案资料维护功能。企业用户需要填写和提交企业基础信息，包括企业名称、许可证信息、统一社会信用代码、负责人信息和附件材料。

（2）企业备案信息查看功能。企业用户需要查看本企业已提交的备案资料及审核状态。

（3）产品档案管理功能。企业用户需要维护本企业产品档案，支持产品新增、修改和详情查看。

（4）检查记录查看功能。企业用户需要查看与本企业有关的检查记录及详情，了解监管结果。

（5）整改任务处理功能。企业用户需要查看整改任务、填写整改进展、上传附件并提交整改结果。

（6）整改结果追踪功能。企业用户需要查看整改任务后续状态变化，了解是否通过复核或需要再次整改。

从业务上看，企业用户的功能需求与监管端形成呼应，共同完成被监管对象的信息维护与问题整改闭环。

#### 3.2.7 公众用户功能需求

公众用户功能主要体现平台的信息公开与社会监督能力。

（1）公众注册登录功能。公众用户需要完成注册和登录，以使用投诉跟踪等功能。

（2）公告查询功能。公众用户需要浏览公告列表与公告详情，获取监管公开信息。

（3）企业公示查询功能。公众用户需要查看企业公示信息和企业详情。

（4）抽检结果查询功能。公众用户需要查看已发布的抽检结果列表和详情。

（5）投诉提交功能。公众用户需要选择被投诉企业并提交投诉内容、联系方式及相关图片资料。

（6）投诉跟踪功能。公众用户需要查看本人投诉列表及投诉处理详情。

该类功能体现出系统不仅是内部监管平台，同时也是一个面向公众的信息服务平台。

#### 3.2.8 统计查询功能需求

除面向具体业务处理的功能外，系统还需要具备统计查询能力。

（1）监管概览查询功能。系统需要能够汇总企业数量、检查次数、抽检情况、投诉数量和预警数量等关键数据。

（2）预警统计功能。系统需要提供预警概览、趋势、类型分布和处置效率等统计结果。

（3）多服务聚合功能。统计功能不应局限于单一业务服务内部数据，而需要跨企业、监管操作、投诉和预警等多个服务进行聚合。

该部分需求为后续监管看板和辅助决策功能提供基础。

### 3.3 系统非功能性需求

#### 3.3.1 性能需求

食品安全监管平台面向多角色使用，既需要支撑日常业务操作，也需要支撑公众查询、投诉提交和统计访问，因此系统需要具备基本的并发处理和响应能力。结合项目代码可以确认，系统在性能需求方面重点体现在以下几个方面。

第一，系统应支持热点数据缓存。监管服务、监管操作服务、查询服务和预警服务均配置了 Redis 缓存相关参数，用于区域数据、公共数据、统计数据等内容的缓存处理。这说明系统需要减少对数据库的重复访问，提高常用数据读取效率。

第二，系统应具备基础访问限流能力。网关对登录接口配置了限流参数，投诉提交、文件预签名和统计查询接口也设置了限流参数，说明系统需要在关键入口处控制访问频率，避免异常访问对系统造成过大压力。

第三，系统应能够支撑多服务协同处理。查询服务通过聚合其他业务服务数据形成统计结果，预警相关业务依赖多个服务之间的协作，因此系统需要具备稳定的跨服务调用能力和合理的调用超时控制。

需要指出的是，当前项目代码中未发现专门的性能压测结果，因此本节所述性能需求主要体现为系统在设计和实现上的性能保障方向，而非具体的性能指标结论。

#### 3.3.2 安全性需求

食品安全监管平台涉及用户身份信息、企业备案信息、投诉信息、执法处理结果和预警记录等数据，因此系统必须具备较为明确的安全控制要求。

第一，系统需要实现统一身份认证。项目中用户登录后由用户服务签发 JWT，后续请求统一通过网关进行令牌校验和令牌内省，说明系统需要建立统一的身份识别机制。

第二，系统需要实现基于角色的访问控制。网关过滤器中明确配置了不同路径对应的角色访问规则，前端路由也设置了不同角色页面访问限制，说明系统需要通过角色划分保证不同用户只能访问与自身职责相匹配的功能。

第三，系统需要具备会话安全控制能力。用户服务借助 Redis 维护会话状态和黑名单信息，体现出平台对令牌失效控制和会话管理的安全需求。

第四，系统需要对关键接口进行访问保护。登录接口、投诉提交接口、文件上传预签名接口以及统计接口均设置了限流参数，体现出系统需要在安全层面防范高频访问和异常请求。

第五，系统需要对文件上传进行约束。文件服务在生成预签名上传地址时对文件大小和内容类型进行了校验，说明系统对上传资源安全性具有明确要求。

#### 3.3.3 可维护性需求

为了降低后续功能扩展和系统维护难度，平台需要具备较好的可维护性。结合项目结构，可以从以下方面理解这一需求。

第一，系统需要按业务边界进行模块拆分。项目中用户、监管主数据、监管操作、投诉、预警和统计功能分别由独立服务承担，体现出良好的职责划分。

第二，系统需要保持统一的技术体系。后端服务统一基于 Spring Boot、Spring Cloud、MyBatis-Plus、MySQL 和 Redis 构建，前端统一采用 Vue 3 技术栈，这种技术一致性有利于减少维护复杂度。

第三，系统需要具备清晰的目录组织和公共能力复用机制。项目通过父工程统一管理版本，通过 `platform-common` 提供公共组件，说明系统在工程层面已经考虑了维护便利性。

第四，系统需要保留一定测试基础。多个服务编写了控制器、服务实现和集成测试代码，为后续维护和功能回归提供支持。

#### 3.3.4 可扩展性需求

食品安全监管业务在实际应用中存在持续演进需求，因此平台需要具备一定可扩展性。

第一，平台需要支持业务模块的独立扩展。当前系统已经将投诉、预警、统计等能力独立拆分为服务，这说明在后续新增业务场景时，可以在现有服务基础上继续增强，或通过新增服务进行扩展。

第二，平台需要支持接口和页面功能扩展。前端采用路由化结构组织不同角色页面，后端按控制器分模块暴露接口，为后续新增页面和接口提供了较清晰的扩展空间。

第三，平台需要支持统计分析能力扩展。虽然查询服务当前以聚合查询为主，但数据库中已预留部分统计表结构，说明系统在设计上已经考虑了统计能力进一步深化的可能性。

第四，平台需要支持运行环境配置扩展。各服务均通过环境变量读取数据库、Redis、Nacos、MinIO 等配置，说明系统具备在不同环境下调整运行参数的基础条件。

#### 3.3.5 可用性需求

系统的可用性需求主要体现在业务连续性和用户可操作性两方面。

在业务连续性方面，系统采用前后端分离和微服务架构，各服务具备独立端口和独立启动入口，说明平台需要能够支持分服务运行和维护。网关对令牌内省设置超时控制，部分限流与调用逻辑设置了 `fail-open` 配置，预警与整改等任务还引入了定时任务和锁机制，这些都体现出系统在保证业务可用性方面的考虑。

在用户可操作性方面，前端按系统管理员、企业用户、公众用户、区域管理员和执法人员划分页面入口，不同角色登录后会跳转到对应工作台或首页，体现出系统需要具备清晰的角色导航和较好的操作组织方式。

#### 3.3.6 兼容性与部署环境需求

从项目配置来看，系统运行依赖较为明确。后端采用 Java 17 和 Spring Boot 3.2.5，前端采用 Vue 3 与 Vite，运行时至少依赖 MySQL、Redis 和 Nacos，在文件上传场景下还依赖 MinIO。因此，系统在部署环境方面需要满足 Java 运行环境、Node 前端构建环境及相关中间件环境配置要求。

同时，网关已配置本地前端开发地址的跨域访问，说明系统至少需要兼容基于浏览器的前端访问方式，并支持前后端分离的本地开发调试环境。由于当前项目未提供 Docker、Docker Compose 或 Kubernetes 部署文件，因此本节对部署环境的分析以本地和常规分服务部署方式为主，不扩展到未实现的容器化方案。

### 3.4 可行性分析

#### 3.4.1 技术可行性

从技术实现角度看，本项目具备较好的可行性。首先，系统所采用的 Spring Boot、Spring Cloud、Nacos、Gateway、OpenFeign、MyBatis-Plus、MySQL、Redis、JWT、MinIO 和 Vue 3 等技术均为成熟技术，配套生态完善，能够满足多角色、多业务模块监管平台的开发需求。其次，项目代码已经完整体现了微服务划分、统一网关、独立数据库、跨服务调用和前后端分离等核心实现路径，说明该技术路线不仅在理论上可行，而且已经在工程中落地。

此外，项目中的关键业务功能如企业备案、检查任务、抽检结果、整改处理、投诉流转、预警代理和统计查询均已有对应控制器、服务实现、数据库表结构和前端页面支撑，说明技术方案能够支撑核心监管场景。综上，从现有代码实现情况看，平台在技术层面具备明确可行性。

#### 3.4.2 操作可行性

从使用和操作角度看，本项目同样具备较好的可行性。系统前端已经按角色划分独立页面入口，并在登录后根据当前角色跳转到对应工作台或首页。系统管理员、区域管理员、执法人员、企业用户和公众用户均可在统一界面体系下完成与自身职责对应的操作，说明系统具有较清晰的使用路径。

同时，平台中的业务流程符合实际监管逻辑，例如企业备案后进入审核流程、检查发现问题后形成整改任务、公众投诉进入受理与处理流程、抽检结果在审核后向公众发布等。这些流程设计与操作习惯较为一致，降低了系统使用门槛。因此，从用户操作流程和界面组织方式来看，系统具备较好的操作可行性。

#### 3.4.3 法律与合规可行性

食品安全监管平台涉及企业信息、用户信息、投诉内容和监管处理记录等数据，因此系统建设需要满足基本的合法合规要求。从项目功能设计来看，系统围绕食品安全监管业务开展企业信息管理、抽检结果公示、投诉受理和风险预警等工作，业务方向本身具有明确的公共治理价值。

从系统实现角度看，平台已经通过统一认证、角色访问控制、文件上传限制和访问限流等机制对部分安全风险进行控制，这为数据保护和权限隔离提供了技术基础。同时，系统对公众公开的信息主要集中于公告、公示企业和已发布抽检结果，而内部监管处理信息则由角色权限进行隔离，符合监管平台内部处理与外部公开区分管理的基本要求。

需要说明的是，当前项目的论文分析主要从系统实现层面讨论合法合规可行性，不涉及具体法规条文逐条论证。因此，本文在该部分采用原则性分析，即平台的业务方向、权限控制和数据处理方式具备基本合规基础，但后续若进入更大规模应用场景，仍需要结合实际法规要求对数据保护和业务制度进行进一步细化。

#### 3.4.4 社会可行性

从社会价值角度看，本项目具有较强的现实意义。食品安全问题与公众日常生活密切相关，监管平台建设不仅关系到内部监管效率，也关系到社会公众对食品安全信息的获取和监督参与。项目中已实现的公告查询、企业公示、抽检结果公示和投诉提交等功能，使公众能够在平台中获取公开信息并反馈问题，这有助于增强食品安全监管工作的透明度和公众参与度。

与此同时，企业备案、检查、整改、投诉和预警等功能形成统一闭环，也有助于推动监管过程更加规范化、流程化和可记录化。对高校本科毕业设计而言，本项目围绕具有现实需求的公共治理场景完成系统实现，既具有工程实践价值，也具有一定社会应用意义。因此，从社会可行性角度看，该项目具备良好的建设基础和应用前景。
