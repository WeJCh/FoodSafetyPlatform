# 阶段1-项目事实核验基线.md

## 1. 项目概述

### 1.1 项目名称
- 项目名称为“food-safety-supervision-platform”，对应毕业设计题目“基于微服务的食品安全监管平台”。  
  证据来源：父工程 `pom.xml` 的 `artifactId`、`name`、`description`。

### 1.2 项目实际定位
- 项目定位为面向食品安全监管业务的多角色平台，覆盖用户认证、企业备案、产品档案、检查与抽检、整改、投诉、预警、公告和统计查询等业务。  
  证据来源：模块目录、后端控制器、前端路由、数据库脚本。

### 1.3 项目主要解决的问题
- 解决食品安全监管业务中分角色协同处理的问题，已实现的业务链条包括：
  - 企业用户提交备案资料与维护产品档案。
  - 区域管理员审核企业、创建并指派检查/抽检任务、复核整改、管理公告、查看预警与统计。
  - 执法人员执行检查/抽检任务、处理投诉、跟进整改、处理预警。
  - 公众用户查看公告、企业公示、抽检结果并提交/跟踪投诉。
  - 系统管理员创建监管人员账号并维护监管人员档案状态。  
  证据来源：控制器接口、前端路由、服务实现类、核心数据表。

### 1.4 面向的用户角色
- 已核实角色包括：系统管理员、公众用户、企业用户、区域管理员、执法人员。  
  证据来源：`user-service` 的 `sys_role` 初始化数据、`food-web/src/router/index.js` 的路由权限、网关鉴权规则。

### 1.5 总体架构形态
- 项目采用“前后端分离 + 网关统一入口 + 多业务微服务 + 独立数据库”的架构形态。  
  证据来源：父工程聚合模块、`gateway-service` 路由配置、各服务独立 `application.yml`、各服务独立 `schema.sql`、前端 `food-web` 目录。

### 1.6 是否确实为微服务架构
- 项目确实为微服务架构，依据如下：
  - 父工程 `pom.xml` 聚合了 `user-service`、`gateway-service`、`regulation-service`、`regulation-operation-service`、`complaint-service`、`query-service`、`warning-service`、`platform-common` 八个模块。
  - 各业务服务均为独立 Spring Boot 启动程序，并分别声明服务名与端口。
  - 各服务通过 Nacos 进行服务注册发现。
  - 网关通过 `lb://服务名` 将请求路由到不同服务。
  - 服务间存在 Feign 调用链。
  - 各服务连接独立数据库：`food_user_db`、`food_regulation_db`、`food_regulation_operation_db`、`food_complaint_db`、`food_query_db`、`food_warning_db`。  
  证据来源：父工程 `pom.xml`、各服务启动类、各服务 `application.yml`、Feign Client、各服务 `schema.sql`。

### 2.1 认证与鉴权方式
- 登录、登出、令牌校验、令牌内省由 `user-service` 提供。

- 网关 `JwtAuthFilter` 对请求进行签名校验、调用 `user-service` 内省接口、按路径和角色做访问控制，并向下游传递用户身份头信息。  
  证据来源：`AuthController`、`AuthServiceImpl`、`AuthRedisServiceImpl`、`TokenUtil`、`gateway-service/JwtAuthFilter.java`。

## 5. 已核实的数据库/核心实体

### 5.1 数据库划分
- `food_user_db`：用户、角色、用户角色关联
- `food_regulation_db`：行政区划、地址、企业、企业附件、产品、监管人员、监管辖区、重点监管原因、公告
- `food_regulation_operation_db`：检查任务、抽检任务、抽检结果、检查记录、检查项、整改任务、整改动作日志、预警事件 outbox
- `food_complaint_db`：投诉、投诉处理记录
- `food_query_db`：统计预留表
- `food_warning_db`：预警规则、预警记录、预警处理日志  
  证据来源：各服务 `application.yml` 与 `schema.sql`。

### 5.2 核心实体及关系
- 用户与角色：`sys_user`、`sys_role`、`sys_user_role` 支撑统一身份与权限。
- 企业主数据：`food_enterprise` 通过 `user_id` 关联企业账号，关联 `addr_region`、`addr_location`，并通过 `enterprise_profile_attachment` 存储备案附件。
- 企业产品：`food_product.enterprise_id` 关联企业，用于抽检任务和监管查看。
- 监管人员：`food_regulator.user_id` 关联监管账号，`food_regulator_region` 维护监管辖区。
- 公告：`public_bulletin` 支撑监管端发布与公众端查看。
- 检查业务：`inspection_task` 对应任务，`inspection_record` 保存检查结果，`inspection_item` 保存检查项明细。
- 整改业务：`rectification_task.inspection_id` 对应检查记录，`rectification_action_log.rectification_id` 记录整改动作流转。
- 抽检业务：`sampling_task` 关联企业和产品，`sampling_result.task_id` 保存抽检结论并控制公众发布状态。
- 投诉业务：`complaint.enterprise_id` 对应被投诉企业，`complaint_handle.complaint_id` 保存处理结果。
- 预警业务：`warning_record` 通过 `biz_type + biz_id` 关联投诉、整改等业务对象，`warning_process_log.warning_id` 记录处理过程。
- 预警事件投递：`warning_event_outbox` 记录由监管操作服务产生、待投递到预警服务的事件。  
  证据来源：各服务 `schema.sql`、服务实现类。

### 5.3 能支撑的业务流程
- 公众注册/企业注册/登录 -> 获取令牌 -> 按角色访问页面与接口。
- 企业提交备案 -> 监管审核 -> 企业进入已审核状态 -> 企业维护产品档案。
- 区域管理员创建并指派检查/抽检任务 -> 执法人员执行 -> 生成检查记录或抽检结果。
- 检查不合格 -> 形成整改任务 -> 企业提交整改 -> 监管复核确认或退回整改。
- 公众提交投诉 -> 管理员受理与指派 -> 执法人员处理 -> 形成反馈或驳回。
- 监管操作或投诉/整改相关事件 -> 预警记录生成与处理 -> 统计服务聚合展示。  
  证据来源：控制器、服务实现、核心表字段、前端路由/API。

## 6. 对论文写作最关键的事实结论

- 本项目不是单体系统，而是基于 Spring Cloud 与 Spring Cloud Alibaba 构建的微服务系统。
- 项目已形成“网关 + 用户服务 + 主数据监管服务 + 监管业务操作服务 + 投诉服务 + 预警服务 + 查询聚合服务 + 公共组件”的后端结构。
- 前端采用单独的 Vue 3 工程，通过网关统一访问后端接口，属于前后端分离实现。
- 身份认证采用 JWT，网关承担统一鉴权与角色访问控制，用户服务负责令牌签发、会话存储和内省。
- 数据层采用“按服务拆分数据库”的方式，符合微服务数据独立原则。
- 项目已实现的核心业务链条包括企业备案、产品档案、检查、抽检、整改、投诉、预警、公告、统计查询。
- 服务间协作主要通过 OpenFeign 完成；预警事件投递采用 Outbox 表重试机制，而不是消息队列。
- 系统支持本地独立启动各服务，也具备按服务端口分开部署的条件；运行依赖至少包括 MySQL、Redis、Nacos，且文件上传场景依赖 MinIO。  
  证据来源：父工程与各服务配置、Feign、控制器、服务实现、前端 API、数据库脚本。
