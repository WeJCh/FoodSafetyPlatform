# 阶段5-第4章系统设计正文初稿.md

## 第4章 系统设计

### 4.1 系统总体设计

#### 4.1.1 总体架构设计

根据第3章的需求分析结果，本系统采用“前后端分离 + 网关统一接入 + 多业务微服务 + 分库部署”的总体结构。前端由 `food-web` 工程提供统一浏览器访问入口，后端通过 `gateway-service` 对外暴露统一 API 入口，各业务能力按职责拆分到独立微服务中运行。该设计既满足了食品安全监管业务中多角色协同、流程链条长、模块边界清晰的需求，也与项目代码中的模块目录、服务启动类、网关路由和独立数据库脚本保持一致。

从运行结构看，系统访问链路为：浏览器端页面发起请求，经网关完成跨域处理、令牌校验和路径转发后，再进入具体业务服务处理；业务服务通过 Nacos 完成注册发现，并通过 OpenFeign 进行跨服务调用；数据最终分别写入各自服务对应的业务数据库。该结构使认证、企业主数据、监管操作、投诉处理、预警处理和统计查询形成既分工明确又可协同联动的服务体系。

从论文写作角度看，本项目的微服务设计亮点不在于抽象地使用微服务概念，而在于围绕监管业务边界完成了具体拆分：用户认证能力集中在 `user-service`，企业与监管基础信息集中在 `regulation-service`，检查、抽检和整改等执行性流程集中在 `regulation-operation-service`，投诉、预警、统计查询分别由独立服务承担。这种拆分方式直接对应了平台的实际业务结构。

#### 4.1.2 微服务模块划分设计

系统后端共包含网关服务、6个业务服务和1个公共模块，各模块职责如下。

`gateway-service` 作为统一入口，负责请求路由、JWT 校验、令牌内省、角色访问控制、跨域处理和部分接口限流。网关配置中已定义 `/api/auth/**`、`/api/users/**`、`/api/regulation/**`、`/api/regulation-operation/**`、`/api/complaints/**`、`/api/query/**` 等转发规则，因此该模块在总体设计中承担流量入口和安全边界的作用。

`user-service` 负责用户注册、登录、登出、令牌校验、角色绑定和监管账号创建。该服务对应系统统一身份认证设计，是多角色访问控制的基础。

`regulation-service` 负责企业备案、企业查询、产品档案、监管人员档案、行政区划、公告管理、文件预签名上传以及预警代理访问。该服务主要承载食品安全监管中的基础数据和基础管理能力。

`regulation-operation-service` 负责检查任务、抽检任务、检查记录、抽检结果、整改任务与整改日志等流程型业务，是监管执行闭环的核心业务服务。

`complaint-service` 负责公众投诉提交、投诉列表查询、投诉流转和投诉处理结果记录，是外部监督信息进入监管流程的重要入口。

`warning-service` 负责预警规则、预警记录和预警处理日志，支撑预警的登记、分派、处理和归档。

`query-service` 负责监管概览统计和预警统计查询。该服务当前采用聚合查询方式从其他服务获取统计数据，数据库中的 `stat_enterprise`、`stat_inspection`、`stat_complaint` 为后续扩展预留表，不属于当前主运行链路。

`platform-common` 不作为独立部署服务运行，主要提供统一响应、Redis/Redisson 等公共能力，用于减少服务间重复代码。

#### 4.1.3 服务关系与信息流设计

系统中的服务协同关系由实际 Feign 调用定义。`regulation-service` 调用 `user-service` 和 `warning-service`，用于用户信息联动和预警代理；`regulation-operation-service` 调用 `regulation-service` 和 `warning-service`，用于获取企业、产品、监管人员等主数据，并投递监管事件；`complaint-service` 调用 `regulation-service`，用于投诉对象企业信息校验与补充；`query-service` 调用 `regulation-service`、`regulation-operation-service`、`complaint-service` 和 `warning-service`，用于生成监管概览与预警统计结果。

结合上述关系，系统的主要信息流可概括为以下三类。

第一类为身份认证信息流。用户在前端登录后，由 `user-service` 签发 JWT，后续请求统一经过网关过滤器校验，并由网关调用 `user-service` 的内省接口确认令牌有效性，再将用户身份信息传递给下游业务服务。

第二类为业务主数据流。企业、产品、监管人员、区域等主数据统一由 `regulation-service` 管理，检查、抽检、投诉和统计等其他服务在需要时通过内部接口读取对应数据，以保证多服务场景下业务对象的一致性。

第三类为监管事件流。检查不合格、整改超时、投诉处理和预警处置等事件在业务服务中产生后，会进入预警或统计链路。其中监管操作服务通过 `warning_event_outbox` 表记录待投递事件，体现出该系统在设计上采用了基于出站事件表的可靠投递方案，而不是消息队列方案。

#### 4.1.4 前后端交互与权限设计

前端采用 Vue 3 单页应用结构，并通过 Vue Router 按角色组织页面入口。系统已实际划分公众用户、企业用户、系统管理员、区域管理员和执法人员五类路由空间。前端 API 客户端默认通过 `http://localhost:8080` 访问网关，因此前端并不直接访问各业务服务，而是依赖网关完成统一接入。

权限控制设计采用“前端路由限制 + 网关统一鉴权”的双层方式。前端路由通过 `requiresRole` 元数据约束页面访问范围，网关 `JwtAuthFilter` 则进一步按照接口路径执行角色校验。该设计既保证了界面层的导航有序，也保证了接口层的访问安全。需要特别指出的是，网关代码中明确对 `/api/warning/**` 做了阻断处理，监管端对预警能力的访问由 `regulation-service` 中的预警代理接口完成，因此论文中应将预警访问写为“代理式调用设计”，而不是“前端直接访问预警服务”。

### 4.2 数据库设计

#### 4.2.1 数据库总体设计

本系统采用按服务分库的数据库设计方式。`user-service`、`regulation-service`、`regulation-operation-service`、`complaint-service`、`warning-service` 和 `query-service` 均具有独立的数据库脚本和数据源配置，符合微服务架构下“服务独立、数据独立”的设计原则。该设计有利于将用户认证、监管基础数据、监管执行数据、投诉数据、预警数据和统计扩展数据分别管理，降低数据库层面的耦合度。

在数据库总体设计上，系统没有建立跨库外键约束，而是通过业务主键、服务接口和业务规则维护实体关联关系。例如企业信息在 `food_regulation_db` 中维护，而检查任务、抽检任务、投诉记录和预警记录分别在各自服务数据库中引用企业编号或业务编号。这种方式与系统的服务拆分策略保持一致。

#### 4.2.2 核心实体与关系设计

从概念模型上看，系统核心实体包括用户、角色、企业、产品、监管人员、区域、检查任务、检查记录、抽检任务、抽检结果、整改任务、投诉、投诉处理记录、预警记录和公告。

用户与角色之间通过 `sys_user`、`sys_role`、`sys_user_role` 构成多对多关系，用于支撑统一登录和多角色授权。

企业实体以 `food_enterprise` 为核心，通过 `user_id` 对应企业账号，通过 `region_id` 和 `address_id` 对应区域和地址信息，并通过 `enterprise_profile_attachment` 关联备案附件。企业与产品之间是一对多关系，对应 `food_product.enterprise_id`。

监管人员实体以 `food_regulator` 为核心，通过 `user_id` 对应用户账号，并通过 `food_regulator_region` 与行政区建立关联，从而形成“监管人员—辖区”的映射关系。

检查业务以 `inspection_task` 和 `inspection_record` 为核心。检查任务用于描述任务创建、分派和执行状态，检查记录用于固化执行结果，检查项明细通过 `inspection_item` 记录。整改业务建立在检查记录之上，`rectification_task.inspection_id` 直接关联检查记录，`rectification_action_log.rectification_id` 记录整改过程动作。

抽检业务以 `sampling_task` 和 `sampling_result` 为核心。抽检任务同时关联企业与产品，抽检结果通过 `task_id` 与任务一一对应，并使用 `public_status` 控制是否进入公众公示范围。

投诉业务以 `complaint` 和 `complaint_handle` 为核心。投诉表记录公众提交信息、流转状态和处理责任人，处理记录表记录最终处理结果。

预警业务以 `warning_record` 和 `warning_process_log` 为核心，其中 `warning_record` 通过 `biz_type + biz_id` 与投诉、整改等业务对象形成逻辑关联，`warning_process_log` 用于记录分派、处理、解决和自动升级等动作。

#### 4.2.3 主要数据表设计

用户认证相关表主要包括 `sys_user`、`sys_role` 和 `sys_user_role`。其中 `sys_user` 保存用户名、密码、用户类型和状态信息，`sys_role` 保存角色编码与角色名称，`sys_user_role` 用于完成用户与角色的绑定。该组表支撑了统一认证和网关鉴权设计。

企业监管基础数据表主要包括 `food_enterprise`、`enterprise_profile_attachment`、`food_product`、`food_regulator`、`food_regulator_region`、`enterprise_key_reason` 和 `public_bulletin`。其中，`food_enterprise` 中的 `approval_status`、`approved_by`、`approved_time` 支撑企业备案审核流程；`food_product` 中的 `enterprise_id`、`category`、`status` 支撑企业产品档案管理；`food_regulator` 和 `food_regulator_region` 共同支撑监管人员档案与辖区配置；`enterprise_key_reason` 用于记录企业被纳入重点监管的原因；`public_bulletin` 中的 `status`、`published_by`、`published_time` 支撑公告草稿、发布和下线管理。

监管执行数据表主要包括 `inspection_task`、`inspection_record`、`inspection_item`、`sampling_task`、`sampling_result`、`rectification_task`、`rectification_action_log` 和 `warning_event_outbox`。其中，`inspection_task` 的 `status`、`assigned_to`、`deadline` 体现任务管理设计；`inspection_record` 的 `result`、`problem_desc` 体现检查结果设计；`sampling_result` 的 `result`、`conclusion`、`public_status` 体现抽检结果及公示状态设计；`rectification_task` 的 `status`、`submit_deadline`、`review_deadline` 体现整改提交与复核期限设计；`rectification_action_log` 记录企业提交、监管复核和超期动作；`warning_event_outbox` 中的 `event_type`、`payload_json`、`status`、`retry_count` 用于实现监管事件可靠投递。

投诉数据表主要包括 `complaint` 和 `complaint_handle`。其中 `complaint` 的 `status`、`assigned_to`、`accepted_by`、`processed_by`、`feedback_summary` 和 `reject_reason` 支撑投诉从提交到办结或驳回的流转设计；`complaint_handle` 用于保存具体处理记录。

预警数据表主要包括 `warning_rule`、`warning_record` 和 `warning_process_log`。其中 `warning_record` 的 `warning_type`、`biz_type`、`biz_id`、`level`、`status`、`assigned_to` 和 `dedup_key` 支撑预警识别、归属、去重、分派和状态管理；`warning_process_log` 用于保存处理轨迹。

统计扩展表包括 `stat_enterprise`、`stat_inspection` 和 `stat_complaint`。根据数据库脚本注释，这三张表属于后续统计能力扩展预留，不作为当前查询服务运行时的真实数据来源，因此在本章中仅作为扩展设计说明，不作为当前核心设计链路展开。

#### 4.2.4 数据设计与业务流程对应关系

企业备案流程由 `food_enterprise` 与 `enterprise_profile_attachment` 支撑，产品档案流程由 `food_product` 支撑；检查与整改流程由 `inspection_task`、`inspection_record`、`inspection_item`、`rectification_task` 和 `rectification_action_log` 支撑；抽检与公示流程由 `sampling_task` 和 `sampling_result` 支撑；投诉处理流程由 `complaint` 和 `complaint_handle` 支撑；预警处理流程由 `warning_record` 和 `warning_process_log` 支撑；公告发布流程由 `public_bulletin` 支撑。由此可见，数据库设计与第3章归纳出的业务主线保持一致，没有出现脱离业务流程的孤立数据结构。

### 4.3 系统功能设计

#### 4.3.1 用户与认证模块设计

该模块的设计目标是为五类用户提供统一登录入口，并保证页面访问与接口访问的一致性控制。模块输入主要为注册信息、登录凭证和令牌；处理逻辑包括用户注册、密码校验、令牌签发、令牌失效、角色绑定和网关内省校验；输出结果为认证结果、用户身份信息和授权后的访问许可。

在模块关系上，`user-service` 负责认证核心能力，`gateway-service` 负责请求入口拦截与角色校验，前端路由负责页面级访问约束。三者共同构成系统统一认证设计。

#### 4.3.2 企业备案与产品档案模块设计

该模块的设计目标是完成企业主数据建档、备案审核和产品档案维护。模块输入包括企业基础信息、附件信息和产品信息；处理逻辑包括企业提交备案、监管审核备案、企业查询自身档案、监管端查询企业信息以及企业维护产品档案；输出结果包括企业档案状态、审核结果和产品档案数据。

在模块关系上，企业备案模块为后续检查、抽检、投诉和统计模块提供企业主数据支撑，产品档案模块则为抽检任务创建和企业详情展示提供基础对象。

#### 4.3.3 检查与抽检模块设计

该模块的设计目标是支撑监管部门围绕企业开展任务派发、现场执行和结果留痕。检查子模块的输入包括任务标题、企业对象、辖区信息、执行人员和检查结果；处理逻辑包括任务创建、任务分派、执法人员执行、检查记录生成和记录查询；输出结果为检查任务状态和检查记录。

抽检子模块的输入包括抽检企业、抽检产品、执行人员和抽检结论；处理逻辑包括抽检任务创建、任务分派、结果录入、结果发布或下线；输出结果为抽检任务状态、抽检结论和公众可见结果。该模块与企业、产品和监管人员主数据存在直接依赖，因此设计上由 `regulation-operation-service` 调用 `regulation-service` 的内部接口完成对象校验与补充。

#### 4.3.4 整改管理模块设计

该模块的设计目标是将检查发现的问题转化为可跟踪、可复核的整改流程。模块输入包括检查记录、不合格问题描述、企业整改进展、整改附件和监管复核意见；处理逻辑包括依据检查记录生成整改任务、企业提交整改、监管人员查看整改详情与动作日志、执行复核确认或退回；输出结果为整改任务状态、整改动作日志和整改闭环结果。

从设计关系上看，整改模块建立在检查模块之后，是监管闭环管理的关键衔接模块；同时，该模块还会与预警模块产生联动，特别是整改超期相关事件。

#### 4.3.5 投诉处理模块设计

该模块的设计目标是为公众监督提供结构化入口，并将投诉数据纳入监管处理流程。模块输入包括投诉人信息、联系方式、被投诉企业、投诉内容和图片材料；处理逻辑包括投诉提交、投诉查询、监管端受理、分派、处理、反馈和驳回；输出结果为投诉单状态、处理摘要和处理记录。

在模块关系上，投诉处理模块既服务公众端，也服务监管端，并可进一步向预警和统计模块提供输入数据，因此属于平台内外部协同的重要连接模块。

#### 4.3.6 公告公示与预警模块设计

公告公示子模块的设计目标是实现监管信息公开。模块输入包括公告标题、类别和内容，或经发布的企业与抽检结果信息；处理逻辑包括公告创建、编辑、发布、下线，以及公众端公告、企业公示和抽检结果查询；输出结果为公众可见的公开信息。

预警子模块的设计目标是将投诉、整改等业务异常统一纳入预警记录和处置流程。模块输入包括预警事件、业务对象标识、预警类型、责任人和处理意见；处理逻辑包括预警事件写入、预警记录生成、分派、处理、解决和日志记录；输出结果为预警状态、预警轨迹和预警统计结果。由于网关禁止前端直接访问 `warning-service`，因此监管端预警访问在设计上采用 `regulation-service` 代理 `warning-service` 的方式实现。

#### 4.3.7 统计查询模块设计

该模块的设计目标是为监管端提供跨服务的汇总信息视图。模块输入包括当前登录用户角色、辖区范围以及查询参数；处理逻辑包括调用企业、监管操作、投诉和预警相关服务，聚合形成监管概览与预警统计结果；输出结果包括监管概览、预警概览、预警趋势、预警类型分布和处置效率统计。

该模块的设计重点不在于单表统计，而在于服务层聚合。根据项目当前实现，统计结果主要来源于 Feign 聚合调用，而不是 `query-service` 中的预留统计表。

### 4.4 系统界面设计

#### 4.4.1 界面设计原则

从前端代码可确认，系统界面设计遵循按角色组织功能入口、按业务流程组织页面路由的原则。系统未在代码中单独给出完整的视觉规范文档，因此本节不对色彩、字号或风格作超出证据的描述，而仅依据实际路由、页面组件和角色分组说明界面组织设计。

系统界面首先体现为角色分区明确。公众端、企业端、系统管理员端、区域管理员端和执法人员端均具有独立页面空间，避免不同职责用户在同一导航结构中混杂操作。

#### 4.4.2 主要页面结构设计

公众端页面主要包括公众首页、公告列表与详情、企业公示、抽检结果、我要投诉、投诉提交成功、我的投诉和投诉详情等页面，设计目标是实现信息公开和投诉反馈。

企业端页面主要包括企业工作台、企业备案、备案详情、产品档案、新增产品、编辑产品、产品详情、检查记录、整改任务、整改详情和提交整改等页面，设计目标是支撑企业完成备案维护、产品维护和整改反馈。

系统管理员端页面主要包括工作台、监管人员列表、添加监管人员、核对信息、人员详情、编辑人员和状态切换确认等页面，设计目标是完成监管人员账号与档案管理。

执法人员端页面主要包括企业监管、我的任务、检查任务详情、检查结果提交、抽检任务、抽检结果提交、检查记录、投诉处理、整改跟进、风险预警和数据统计等页面，设计目标是支撑现场执行和业务反馈。

#### 4.4.3 路由与导航设计

前端使用 Vue Router 进行统一路由管理，并通过路由守卫控制登录态恢复、游客页面访问和角色权限校验。系统根据不同角色设定默认进入页面：系统管理员进入管理工作台，企业用户进入企业工作台，公众用户进入公众首页，区域管理员进入监管概述页，执法人员进入企业监管页。该设计与后端统一认证设计相配合，使用户登录后能够直接进入与自身职责匹配的功能空间。
