# 毕业答辩问答（模拟答辩委员提问与参考答案）

> **论文题目：** 基于微服务架构的食品安全监管平台设计与实现  
> **答辩角色：** 模拟答辩委员提问 + 学生参考答案  
> **说明：** 本文档覆盖论文核心论点与系统关键实现，建议答辩前通读并配合系统演示准备。

---

## 一、选题背景与研究意义

### Q1：为什么选择“食品安全监管平台”作为毕业设计课题？你的系统与现有监管平台相比有什么特点？

**答：** 食品安全监管具有监管对象多、业务链条长、参与主体复杂、协同要求高等特点。传统分散式、纸质化或单点电子化方式难以满足过程留痕、风险预警和多角色协同的需求。本课题以“赣溯源”等典型监管平台的业务为参考，抽取并整合企业备案、检查抽检、整改复核、公众投诉、公告公示、预警处理和统计查询等核心环节，构建一个**面向多角色协同的完整监管闭环原型**。

与部分现有系统相比，本系统的特点在于：  
（1）**业务闭环更完整**——从企业纳管到监管执行、问题整改、公众监督、风险预警形成链条；  
（2）**架构上采用微服务拆分**——按认证、主数据、监管执行、投诉、预警、统计等边界划分服务；  
（3）**工程上关注跨服务协同**——通过事件表、重试补偿、幂等控制和分布式锁保障关键链路稳定。

---

### Q2：论文中多次提到“赣溯源”平台，你的系统与它是什么关系？是复刻还是参考？

**答：** 本系统是**参考典型业务场景的原型实现**，并非对“赣溯源”平台的完整复刻。论文借鉴的是其在企业备案、监督检查、抽检公示、整改复核、投诉处理和风险预警等方面的**业务流程与角色分工思路**，再结合毕业设计的实现周期和条件，抽取核心链路进行建模与开发。因此，本课题的价值在于**服务化架构设计、原型实现和工程实践**，而非替代或复制某一具体政务系统。

---

### Q3：本课题的研究意义体现在哪些方面？

**答：** 主要体现在三方面：  
**业务层面**，将备案、检查、整改、投诉、公示等功能纳入统一平台，提升监管流程连续性和闭环能力；  
**技术层面**，采用前后端分离和微服务架构，通过网关、注册发现和服务调用实现模块解耦与可扩展；  
**工程层面**，完成了从需求分析、架构设计、编码实现到测试验证的完整软件工程过程，对同类政务监管信息化系统具有参考价值。

## 二、需求分析与业务设计

### Q4：系统面向哪些用户角色？各自职责是什么？

**答：** 系统面向**五类角色**：  

| 角色 | 核心职责 |
|------|----------|
| 系统管理员 | 监管人员账号创建、信息查看、状态维护 |
| 区域管理员 | 备案审核、检查/抽检任务管理、整改复核、投诉流转、公告与预警、统计概览 |
| 执法人员 | 执行检查/抽检、提交结果、处理投诉、跟进整改 |
| 企业用户 | 备案维护、产品档案、查看检查记录、提交整改 |
| 公众用户 | 查询公告/公示/抽检结果、提交与跟踪投诉 |

这种划分体现了食品安全监管中**政府内部管理、企业主体责任和公众社会监督**三类主体协同的特征。

---

### Q5：请简述系统的四条主要业务主线。

**答：**  
1. **企业备案主线**：企业注册并提交备案资料 → 区域管理员审核通过/驳回 → 企业进入纳管状态；  
2. **检查与整改主线**：管理员创建并分派检查任务 → 执法人员提交检查结果 → 不合格则生成整改任务 → 企业提交整改 → 监管复核确认/退回；  
3. **抽检与公示主线**：管理员创建抽检任务 → 执法人员录入结果 → 符合条件的结果发布 → 公众端查询；  
4. **投诉处理主线**：公众提交投诉 → 管理员受理分派 → 执法人员处理反馈 → 公众查看进度与结果。

四条主线共同构成“纳管—执行—整改—监督”的完整监管链。

---

### Q6：为什么要把“公众端”单独设计？公众参与对监管有什么价值？

**答：** 食品安全监管不仅是政府内部事务，也涉及**信息公开和社会监督**。公众端提供公告查询、企业公示、抽检结果查询和投诉提交等功能，使监管信息在合规范围内对外可见，同时把公众投诉纳入内部流转，而不是停留在信息收集层面。投诉数据还可作为后续重点监管和风险预警的输入，体现**多主体协同治理**的价值。

---

## 三、系统架构与微服务拆分

### Q7：为什么采用微服务架构，而不是单体架构？

**答：** 本平台业务边界相对清晰，包含认证授权、监管主数据、监管执行、投诉处理、预警管理和统计查询等多个模块，且存在跨模块协同、后续扩展和多角色并行的特点。微服务架构的优势在于：  
- 按业务边界拆分，降低单体内聚过高带来的复杂度；  
- 各服务可独立开发、部署和扩展；  
- 更符合“服务自治、数据自治”的设计原则。  

对于毕业设计原型而言，微服务也能更好地展示**服务治理、跨服务调用和分布式协同**等工程能力。若采用单体，在功能规模和角色复杂度下，后期维护和扩展成本会更高。

---

### Q8：系统一共拆分了哪些微服务？各自职责是什么？

**答：** 后端主要包含 8 个模块：  

| 服务 | 职责 |
|------|------|
| gateway-service | 统一入口、路由转发、JWT 鉴权、跨域、部分限流 |
| user-service | 注册、登录、登出、令牌内省、角色绑定 |
| regulation-service | 企业备案、产品档案、监管人员、区域、公告、预警代理访问 |
| regulation-operation-service | 检查任务、检查记录、抽检任务、抽检结果、整改任务 |
| complaint-service | 公众投诉提交、查询与流转处理 |
| warning-service | 预警记录、处理日志、预警统计 |
| query-service | 监管概览与预警统计等聚合查询 |
| platform-common | 公共返回体、工具类、通用组件 |

前端 food-web 作为统一 Web 入口，按角色组织页面，所有 API 经网关访问。

---

### Q9：为什么把“监管主数据”和“监管执行”拆成两个服务？

**答：** 这是按**变更频率和业务性质**划分的。regulation-service 管理企业、产品、监管人员、区域、公告等相对稳定的主数据；regulation-operation-service 管理检查、抽检、整改等**过程性、状态流转频繁**的执行数据。两者职责不同、数据表不同、访问模式也不同。拆分后，主数据服务可为多个执行类服务提供支撑，执行服务专注于任务流转和留痕，边界更清晰，也便于后续独立扩展（如增加移动执法、新的任务类型等）。

---

### Q10：为什么前端不直接访问 warning-service，而是通过 regulation-service 代理？

**答：** 这是**保持服务边界和访问域一致**的设计。预警能力在业务上属于监管域，监管人员通过区域管理员或执法人员身份访问预警，而不是作为独立对外域暴露。网关层也禁止了 `/api/warning/` 的直接外部访问。regulation-service 通过 `WarningProxyService` 代理转发，在统一鉴权前提下完成预警列表、详情和处理操作。这样前端只需面向监管 API，减少多服务域耦合，也便于权限统一管理。

---

### Q11：请描述一次完整请求从前端到后端的流转过程。

**答：** 以监管人员查询监管概览为例：  
1. 前端携带 JWT 发起 `/api/query/overview` 请求；  
2. 请求进入 **gateway-service**，执行 JWT 签名校验、令牌内省、角色路径匹配；  
3. 网关将 `X-User-Id`、`X-User-Roles` 等身份信息透传给下游；  
4. 请求路由到 **query-service**，按用户辖区范围裁剪查询条件；  
5. query-service 通过 OpenFeign 分别调用 regulation、regulation-operation、complaint、warning 等服务的统计接口；  
6. 聚合结果后写入 Redis 缓存（若命中则直接返回）；  
7. 统一 `ApiResponse` 返回前端展示。

## 四、核心技术选型

### Q12：为什么选择 Nacos 作为注册中心和配置中心？

**答：** Nacos 与 Spring Cloud Alibaba 生态集成成熟，支持服务注册发现和集中配置管理。本项目多服务并行运行，网关和业务服务需要通过**服务名**而非硬编码地址互相调用，Nacos 能满足这一需求。同时，集中配置有利于多环境下的参数维护和动态调整，符合微服务治理的基本要求。

---

### Q13：JWT 认证方案是如何工作的？为什么还需要 Redis？

**答：** 用户登录成功后，user-service 签发 JWT，后续请求在网关统一校验。JWT 适合无状态、前后端分离场景，但仅有 JWT 无法方便地实现**登出即时失效**和**会话控制**。因此系统配合 Redis 实现：  
- 登录会话缓存；  
- 令牌黑名单（登出后失效）；  
- 登录限流计数。  

网关除校验 JWT 签名外，还会调用 user-service 的**内省接口**确认令牌当前是否有效，再将用户身份通过请求头传递给下游服务。

---

### Q14：Redis 在系统中承担了哪些职责？

**答：** Redis 主要用于：  
1. **会话与令牌控制**——登录态、黑名单；  
2. **缓存**——企业公示、抽检公示、监管概览、预警统计等高频查询；  
3. **限流**——登录、投诉提交、统计查询等接口的访问频率控制；  
4. **分布式锁**——整改提交、抽检结果上报、投诉受理分派、Outbox 投递等关键操作的并发控制；  
5. **调度锁**——多实例下定时任务（整改超时扫描、预警升级、Outbox 重试）的单实例执行保障。

---

### Q15：文件上传为什么使用 MinIO？为什么不直接存数据库或本地磁盘？

**答：** 备案附件、投诉图片、整改材料等属于**非结构化大文件**，不适合存入 MySQL。MinIO 作为对象存储，支持**预签名上传**——后端生成上传地址，前端直传对象存储，减轻业务服务的 IO 压力。相比本地磁盘，对象存储更便于扩展、迁移和容器化部署，也符合前后端分离下的常见工程实践。

---

## 五、数据库与数据设计

### Q16：微服务架构下数据库是如何设计的？为什么不使用跨库外键？

**答：** 系统采用**按服务分库**设计：user、regulation、regulation-operation、complaint、warning、query 各服务维护独立数据库脚本和数据源。实体之间的关联通过**业务主键 + 服务接口**维护，而不是跨库外键。原因是微服务强调“服务自治、数据自治”，跨库外键会造成服务间强耦合，不利于独立部署和演进。例如 complaint-service 存储 `enterprise_id`，需要企业详情时通过 regulation-service 内部接口获取。

---

### Q17：整改任务是如何与检查记录关联的？数据上如何支撑业务闭环？

**答：** 检查完成后，regulation-operation-service 写入 `inspection_record` 和 `inspection_item`。若检查结果或检查项判定需要整改，则调用 `rectificationService.createFromInspection()` 生成 `rectification_task`，通过 `inspection_id` 关联源检查记录。企业提交整改后更新整改状态并记录 `rectification_action_log`；监管复核时再次写入动作日志。这样从“问题发现 → 整改生成 → 企业提交 → 监管复核”全链路都有结构化数据和状态留痕。

---

## 六、跨服务一致性与分布式控制

### Q18：监管操作触发预警时，如何保证跨服务数据一致性？为什么不用分布式事务？

**答：** 系统采用**本地事务 + 出站事件表（Outbox）+ 重试补偿 + 幂等控制**实现**最终一致性**，而非 Seata 等强一致分布式事务。  

典型流程：regulation-operation-service 完成检查/抽检/整改等本地写入后，将待投递预警事件写入 Outbox 表，立即返回业务结果；后台调度任务扫描 Outbox 并调用 warning-service 的 upsert 接口。若远端暂时失败，可重试而不影响本地业务已成功的事实。  

选择最终一致性的原因：预警属于**异步联动**，允许短暂延迟；强一致事务会增加耦合和性能开销，对原型系统而言 Outbox 模式更轻量、容错性更好。

---

### Q19：什么是 dedupKey？预警重复上报如何处理？

**答：** `dedupKey` 是预警事件的**幂等键**，格式如 `RECTIFICATION:1024:SLA_OVERDUE_SUBMIT`。warning-service 收到 upsert 请求时，若相同 dedupKey 已存在，则**不新建记录**，而是更新 `lastOccurTime`、`triggerCount`、级别（取较高等级）和 payload，并追加 `EVENT_UPSERT` 处理日志。这样同一业务事件多次上报不会产生重复预警单，而是合并为同一预警流的持续跟踪。

---

### Q20：分布式锁在哪些场景使用？锁粒度如何设计？

**答：** 分布式锁主要用于两类场景：  
1. **业务写操作**——整改提交、抽检结果上报、投诉受理/分派/处理、预警处理等，以**业务主键**为锁粒度，防止并发重复提交或状态覆盖；  
2. **后台调度任务**——整改超时扫描、预警升级、Outbox 重试投递等定时任务，以调度任务名为锁，保证多服务实例部署时只有一个实例执行。  

锁基于 Redis 实现，兼顾实现简单与原型系统的实际需求。

---

### Q21：统计查询如何保证性能？缓存失效策略是什么？

**答：** query-service 对监管概览等接口采用**“缓存优先、版本失效、锁控回源”**策略：  
- 以查询条件指纹构建 Redis 缓存 Key；  
- 命中缓存直接返回，未命中则加锁回源，聚合多个服务的统计接口；  
- 底层数据变更时，通过**缓存版本号递增或删除明细缓存**触发失效。  

同时配合查询限流，避免高频聚合查询压垮后端。该策略在一致性和性能之间取得平衡，适合原型系统的监管概览场景。

---

## 七、核心业务实现

### Q22：检查不合格后，整改任务是如何自动生成的？

**答：** 执法人员提交检查结果时，系统写入检查记录和检查项明细。随后调用 `needRectification(record.getResult(), items)` 判断是否需要整改——若总体结果不合格或存在不合格检查项，则调用 `rectificationService.createFromInspection()`。该方法会检查是否已存在关联整改任务（幂等），若无则创建状态为 ONGOING 的整改任务，设置企业提交截止时间，并写入系统创建动作日志。这保证了**问题发现到整改启动**的自动衔接。

---

### Q23：抽检结果发布与公众查询之间如何控制公开边界？

**答：** 抽检结果保存在 `sampling_result` 表中，具有 `public_status` 等状态字段。执法人员录入结果后，结果默认不公开；区域管理员根据业务规则执行**发布操作**后，才进入公众可查询范围。公众端接口只返回已发布记录。这样兼顾了监管内部处理和信息公开的合规边界，避免未审核数据对外暴露。

---

### Q24：投诉处理的完整状态流转是怎样的？

**答：** 典型流转为：  
**已提交（SUBMITTED）** → 区域管理员**受理** → **待处理（PENDING）** → **分派** → **已分派（ASSIGNED）** → 执法人员**处理** → **已反馈**；  
也可在受理前或处理中被**驳回**。  

每次状态变更通过 `transitionComplaint` 校验合法流转，并在受理、分派、处理等关键操作上加分布式锁。公众端可通过投诉跟踪接口查看进度和处理结果。

---

### Q25：预警有哪些类型和级别？升级规则是什么？

**答：** 系统围绕**整改超时、抽检不合格、检查连续不合格、投诉聚集**等场景生成预警。级别分为 L1、L2 等。业务服务只上报事实事件（如 SLA 超时），**级别升级（L1→L2）由 warning-service 的调度任务执行**，避免多处重复实现升级逻辑。upsert 时若已有 L2，后续 L1 上报不会降级，保证预警严重性只升不降。

---

### Q26：权限控制是如何实现的？仅靠前端路由守卫够吗？

**答：** 不够。系统采用**双层权限控制**：  
- **前端**：Vue Router 路由守卫，限制不同角色进入对应功能页面；  
- **后端**：网关 JwtAuthFilter 校验令牌并匹配路径与角色，无权限返回 403。  

即使绕过前端直接调用 API，网关仍会拦截。业务服务还可通过 `X-User-Id`、`X-User-Roles` 请求头做细粒度辖区范围校验（如执法人员只能处理辖区内企业）。

---

## 八、部署与工程实现

### Q27：系统如何部署？Docker 容器化带来了什么好处？

**答：** 项目支持本地分服务启动，也提供了 **Docker Compose** 统一部署方案。基础设施容器包括 MySQL、Redis、Nacos、MinIO；业务容器包括各微服务和 gateway；前端基于 Nginx 托管静态资源并代理 API。  

容器化的好处：  
- 减少“在我机器上能跑”的环境差异；  
- 提高部署可复现性和迁移便利性；  
- 便于答辩演示和后续运维扩展。

---

### Q28：platform-common 公共模块的作用是什么？

## 十一、答辩委员可能追问（挑战性题目）

### Q34：微服务拆分是否“过度设计”？对于一个毕业设计原型，单体是否更合适？

**答：** 这是合理的追问。若仅追求最快实现功能，单体确实更简单。但本课题题目明确是“**基于微服务架构**”，且业务本身具备清晰的模块边界和多服务协同需求。采用微服务是为了**紧扣课题目标**并展示服务治理、跨服务一致性等能力。同时，原型规模可控，7 个业务服务 + 1 网关 + 1 公共模块在毕业设计周期内可完成。若重新选型，我会评估团队规模和运维能力；但在本课题背景下，微服务拆分是有依据的，并非为了拆分而拆分。

---

### Q35：最终一致性会不会导致业务方看到“检查结果已提交但预警还没出现”的情况？你如何向用户解释？

**答：** 会存在**秒级到分钟级的短暂延迟**，这是最终一致性的固有特征。应对方案：  
1. 产品层面——预警中心注明“异步同步，可能有短暂延迟”；  
2. 技术层面——Outbox 快速重试、监控未投递事件积压；  
3. 架构层面——对强实时要求的场景可改为同步调用 + 降级，但本系统预警属于**风险跟踪**而非实时控制，短暂延迟可接受。  

答辩中应诚实说明这是**有意权衡**，而非实现疏漏。

---

### Q36：如果 warning-service 长时间不可用，Outbox 积压会带来什么问题？

**答：** 本地业务（检查、抽检、整改）不受影响，已成功写入；但预警记录会延迟生成，监管人员暂时看不到新风险。长期积压还需关注 Outbox 表膨胀和重试风暴。现有机制通过调度锁、重试间隔和幂等 upsert 缓解问题。生产环境应增加**积压告警、死信队列和人工补偿入口**，这是后续完善方向。

---

### Q37：query-service 聚合多个服务统计接口，若其中一个服务超时，整个概览请求会怎样？

**答：** 当前实现中，`loadOverview` 会分别调用各服务统计接口，任一失败会抛出异常并返回错误。这是**简单可靠**的策略。可优化方向：  
- 部分降级——某个模块失败时返回默认值并标记“数据暂不可用”；  
- 缩短超时 + 熔断；  
- 预聚合——定时将统计结果写入 query 库。  

原型阶段优先保证正确性，后续可引入 Resilience4j 等熔断降级组件。

### Q38：请用 2 分钟介绍你的系统（答辩开场常用）。

**答：**  

各位老师好，我的课题是《基于微服务架构的食品安全监管平台设计与实现》。  

系统面向系统管理员、区域管理员、执法人员、企业用户和公众用户五类角色，覆盖企业备案、产品档案、检查抽检、整改复核、公众投诉、公告公示、风险预警和统计查询等业务，形成较完整的监管闭环。  

技术上，前端采用 Vue 3，后端基于 Spring Boot 和 Spring Cloud 构建 7 个微服务，通过 Nacos 注册发现、Gateway 统一鉴权、OpenFeign 跨服务调用；数据层按服务分库，使用 MySQL 存储业务数据，Redis 负责缓存、限流和分布式锁，MinIO 存储附件。针对监管操作触发预警、整改提交等跨服务场景，采用 Outbox 事件表和 dedupKey 幂等实现最终一致性。  

系统已完成 Docker 容器化部署，并通过功能测试和基础运行验证，能够稳定支撑核心监管流程。
