# 阶段7-第6章系统测试正文初稿.md

## 第6章 系统测试

### 6.1 测试策略与方法

#### 6.1.1 测试目标

系统测试的目标是验证“基于微服务的食品安全监管平台”在现有实现范围内是否能够稳定完成核心业务处理，并检查统一认证、角色权限控制、跨服务调用、监管业务闭环和统计聚合等关键能力是否与前文需求分析、系统设计和系统实现保持一致。结合项目现有材料，本章测试重点不放在专项性能压测，而是放在功能正确性、接口可用性、权限边界和主要业务链路完整性验证上。

从仓库中的测试代码和验收文档可以确认，项目已经形成一定规模的后端自动化测试资产，覆盖网关鉴权、文件上传权限、产品档案、公告管理、公开企业查询、检查记录、检查任务、抽检任务、投诉处理、预警统计和监管概览等内容。同时，前端工程已形成较完整的页面与接口调用链，且阶段性验收文档记录了前端生产构建通过和后端多模块联合测试通过的结果。因此，本章采用“自动化测试证据为主、功能验证表达为辅”的写法，对系统测试情况进行说明。

#### 6.1.2 测试证据来源

本章测试内容主要依据以下几类已核实材料展开。

第一，后端测试代码。仓库 `src/test/java` 目录下共可确认 15 个测试类，分布于 `gateway-service`、`regulation-service`、`regulation-operation-service`、`complaint-service`、`query-service` 和 `warning-service`。这些测试类使用 JUnit 5、Spring Boot Test 和 MockMvc 等方式，对控制器、服务实现类和聚合接口进行了验证。

第二，阶段性验收文档。`docs/p0-acceptance-report.md`、`docs/p1-acceptance-report.md` 和 `docs/p2-acceptance-report.md` 记录了项目不同阶段执行 Maven 测试和前端构建验证的情况。其中，P0 文档记录了 `gateway-service`、`regulation-service` 和 `query-service` 的测试验证；P1 文档记录了 `regulation-service`、`regulation-operation-service`、`complaint-service` 和 `warning-service` 的联合测试；P2 文档进一步记录了 `regulation-service`、`regulation-operation-service`、`complaint-service`、`warning-service` 和 `query-service` 的联合测试，以及 `food-web` 前端生产构建通过。

第三，前后端联调代码痕迹。前端 `food-web/src/api` 中已经封装认证、监管、监管操作、投诉等接口，`src/views` 中则对应实现了企业端、公众端、系统管理员端、区域管理员端和执法人员端页面。这说明系统具备本地前后端联调条件，且主要业务页面与后端接口已形成对应关系。

第四，验收与纠偏文档。`docs/food-safety-platform-current-prd.md`、`docs/food-safety-platform-current-rectification-plan.md`、`docs/food-safety-platform-correction-landing-plan.md` 等文档对测试覆盖情况、联合测试结果和浏览器级手工联调缺口作了明确说明，可作为测试边界判断依据。

#### 6.1.3 测试方法

结合项目现有证据，本系统测试采用以下几种方法。

1. 黑盒功能测试。围绕用户登录、权限控制、企业备案相关信息访问、抽检结果公示、投诉处理和统计查询等功能，从接口输入、处理结果和返回信息角度验证系统行为是否符合预期。
2. 白盒单元与控制器测试。针对网关过滤器、控制器和服务实现类中关键分支逻辑进行断言验证，检查权限判定、状态流转、异常处理和业务联动是否正确执行。
3. 集成测试。对 `query-service` 中监管概览和预警统计接口使用 MockMvc 配合 MockBean 进行集成测试，验证聚合接口对内部服务参数透传、区域范围拼装和返回结构是否正确。
4. 构建与联调验证。结合阶段性验收文档中的 Maven 联合测试结果和前端 `npm run build` 结果，对系统当前代码状态的可构建性和接口联动基础进行验证。
5. 静态链路复核。对没有单独自动化测试覆盖、但代码实现明确的前端页面到后端接口链路进行复核，用于支撑论文中的规范化功能验证表达。

#### 6.1.4 测试环境与适用范围

从项目配置与验收文档可知，系统测试建立在现有开发运行环境基础上。后端采用 Java 17、Spring Boot 3.2.5、Spring Cloud 2023.0.1 和 Spring Cloud Alibaba 2023.0.1.0，前端采用 Vue 3、Vue Router 4 和 Vite 5。系统运行依赖 MySQL、Redis、Nacos，文件上传场景还依赖 MinIO。测试代码主要基于 Spring Boot Test、JUnit 5、MockMvc 和 Mockito 完成。

需要说明的是，项目材料中未发现专项性能压测报告、并发测试数据、持续集成流水线报告和完整浏览器录屏式联调记录，也未发现可直接作为论文插图引用的测试截图材料。因此，本章不编写吞吐量、响应时间或并发用户数等精确性能指标，不将未实施的在线录屏联调写成既有测试成果，而是如实说明系统当前已经具备后端自动化测试和阶段性构建验证基础。

### 6.2 测试用例与结果

#### 6.2.1 自动化测试覆盖情况

根据仓库中的测试代码，当前系统已确认存在以下自动化测试覆盖。

1. 网关鉴权测试：`JwtAuthFilterTest` 覆盖鉴权失败时拒绝访问、`fail-open` 与 `fail-closed` 行为差异、公众用户访问公开抽检接口、企业用户访问产品接口、企业访问本企业检查记录、系统管理员访问区域与监管员管理接口等场景。
2. 文件上传权限测试：`FileControllerTest` 覆盖公众投诉附件上传允许、公众整改单附件上传拒绝、企业整改附件上传允许、企业备案附件上传允许、企业上传检查附件拒绝等场景。
3. 监管基础数据测试：`ProductControllerTest`、`InternalProductControllerTest`、`InternalEnterpriseControllerTest`、`PublicEnterpriseControllerTest`、`PublicBulletinControllerTest` 和 `BulletinManageControllerTest` 覆盖企业产品查询、监管侧产品查看、内部主数据读取、公开企业查询和公告管理权限等内容。
4. 监管操作测试：`InspectionRecordControllerTest`、`InspectionTaskServiceImplTest` 和 `SamplingTaskServiceImplTest` 覆盖企业查看本企业检查记录、检查结果提交流转、连续不合格触发重点监管、抽检结果提交生成草稿、公示状态控制和预警联动等内容。
5. 投诉处理测试：`ComplaintCommandServiceTest` 覆盖投诉受理、分派、反馈、驳回、处理时限设置以及投诉过载触发重点监管等逻辑。
6. 统计聚合测试：`SupervisionOverviewControllerIntegrationTest` 和 `WarningStatsControllerIntegrationTest` 覆盖监管概览聚合、预警统计查询、区域范围扩展、查询参数透传和非法时间范围校验等内容。
7. 预警统计服务测试：`WarningStatsServiceImplTest` 对预警统计服务实现进行了补充验证。

从覆盖范围看，当前自动化测试已经涉及统一认证、权限控制、公开查询、监管闭环、投诉协同和统计聚合等论文中的主要实现点，但并非对所有前端页面和全部业务接口进行全量覆盖，因此更适合在论文中表述为“已形成关键模块测试基础”，而不是“已完成全面自动化测试”。

#### 6.2.3 测试结果分析

从现有自动化测试代码与阶段性验收结果看，系统在以下方面达到了预期目标。

第一，统一认证与权限控制机制能够支撑多角色访问隔离。网关测试、文件权限测试、企业检查记录测试和公告管理测试共同说明，系统没有将权限控制仅停留在页面跳转层，而是已经在网关和控制器层形成较清晰的访问边界。

第二，监管核心业务链路已经具备可验证的闭环特征。检查任务提交后触发整改和重点监管、抽检不合格后触发重点监管和预警事件、投诉受理后进入分派和反馈流程等测试，说明系统不再只是静态信息管理，而是已经实现了围绕监管事件的状态流转与业务联动。

第三，跨服务聚合查询功能具备基本正确性。监管概览和预警统计集成测试验证了查询服务可以基于内部接口汇总多服务数据，并对监管员范围、时间参数和查询条件进行规范处理。这与前文“轻量聚合查询服务”的设计定位相符。

第四，系统具备前后端联调和交付的基础条件。前端已有较完整的角色页面与接口封装，P2 验收文档记录了前端生产构建通过，说明主要页面代码已达到可构建状态；同时，多服务 Maven 测试通过说明后端关键模块在测试上下文中可正常装配。

需要如实指出的是，当前测试仍存在一定边界。项目中未发现完整浏览器级录屏联调记录，未发现专项性能压测数据，也未发现覆盖全部页面交互的前端自动化测试。因此，本系统当前更适合表述为“已完成关键功能、接口与业务链路验证”，而不应表述为“已完成全面性能与全场景自动化测试”。这也是后续系统完善和论文展望部分应继续关注的方向。
