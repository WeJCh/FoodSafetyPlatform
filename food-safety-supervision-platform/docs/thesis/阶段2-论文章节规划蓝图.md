# 阶段2-论文章节规划蓝图.md

## 1. 论文总体写作思路

- 论文类型按“软件开发研究类型”展开，核心主线应固定为：`业务问题 -> 需求分析 -> 架构与数据库设计 -> 模块实现 -> 测试验证 -> 总结展望`。
- 全文事实基线统一引用 [阶段1-项目事实核验基线.md](d:\JAVA\FoodSafetyPlatform\food-safety-supervision-platform\docs\thesis\阶段1-项目事实核验基线.md)，后续章节不得脱离该文档新增未经核实的内容。
- 本项目的论文亮点应落在“微服务拆分如何服务监管业务闭环”，而不是空泛讨论微服务概念。
- 章节分工要严格区分：
  - 第3章回答“为什么要做、需要做什么”。
  - 第4章回答“准备怎么设计、模块和数据如何组织”。
  - 第5章回答“实际是怎么编码落地的”。
- 写作时始终维护两条一致性链：
  - `功能需求 -> 功能设计 -> 功能实现 -> 功能测试`
  - `业务流程 -> 核心实体/数据库 -> 接口/模块 -> 页面/结果`

## 2. 各章节写作目标与内容边界

### 第一章 绪论
- 写作目标：交代课题背景、研究意义、国内外研究现状、本文研究内容和章节安排。
- 内容边界：只写选题背景和论文整体说明，不写具体模块实现细节，不写数据库字段。
- 应依托的项目事实：
  - 项目题目与工程名称。
  - 平台面向的角色与核心业务范围。
  - 系统采用微服务架构、前后端分离、多角色监管协同。
- 适合的呈现方式：
  - 表格：无必要，可少量列出“本文主要研究内容”。
  - 图：一般不强制；如需要可放“论文结构图”。
- 已有充分证据的部分：
  - 项目名称、角色、业务范围、架构形态。
- 项目未实现内容的规范表述：
  - 不在绪论中宣称“已实现智能预警决策、容器云部署、大数据分析”等未核实能力。

### 第二章 相关技术
- 写作目标：说明项目采用的关键技术及选型依据。
- 内容边界：写技术原理和项目中的实际用途，不写模块业务流程，不展开具体接口实现。
- 应依托的项目事实：
  - Spring Boot、Spring Cloud、Spring Cloud Alibaba、Gateway、Nacos、OpenFeign、MyBatis-Plus、MySQL、Redis、Redisson、JWT、MinIO、Vue 3、Vite。
  - `query-service` 已启用 OpenAPI；`user-service` 仅发现 Knife4j 依赖。
- 适合的呈现方式：
  - 表格：技术栈总表、技术选型对比表。
  - 图：可选技术架构关联图，不必过多。
- 已有充分证据的部分：
  - 各依赖、配置、服务注册与路由方式、前端技术栈。
- 项目未实现内容的规范表述：
  - 消息队列、Docker、Kubernetes、独立配置中心/认证中心只能写为“本项目未实现”或“未纳入本次实现范围”。

### 第三章 系统分析
- 写作目标：从业务和需求角度说明系统应该具备什么能力，以及这些能力为什么需要。
- 内容边界：只分析需求、角色、流程、功能和非功能需求，不写类名、控制器名、数据库建表细节。
- 应依托的项目事实：
  - 用户角色。
  - 企业备案、产品档案、检查、抽检、整改、投诉、公告、预警、统计查询等业务模块。
  - 网关统一鉴权、多角色访问控制、Redis 限流/缓存、服务独立部署依赖等非功能线索。
- 适合的呈现方式：
  - 图：业务流程图、用例图、活动图。
  - 表格：功能需求列表、非功能需求表。
- 已有充分证据的部分：
  - 多角色业务链条、主要功能点、公众端/企业端/监管端页面入口。
- 项目未实现内容的规范表述：
  - 若无性能压测数据，只能写性能需求目标，不能写具体吞吐结论。

### 第四章 系统设计
- 写作目标：说明系统总体架构、服务划分、数据库设计、功能模块设计、接口交互设计。
- 内容边界：写“设计方案”和“结构安排”，不展开实现代码，不贴大段源码。
- 应依托的项目事实：
  - 微服务模块划分、网关路由、Feign 调用链、独立数据库、核心实体关系。
  - JWT 鉴权路径规则、Outbox 重试机制、MinIO 文件上传流程。
- 适合的呈现方式：
  - 图：系统架构图、服务调用关系图、ER 图、时序图、模块结构图。
  - 表格：数据库表设计、模块职责表、接口/角色权限映射表。
- 已有充分证据的部分：
  - 各服务端口、职责、数据库划分、核心表、关键交互链路。
- 项目未实现内容的规范表述：
  - `query-service` 的 `stat_*` 表只能写为“统计扩展预留设计”，不能写成当前运行主链路。

### 第五章 系统实现
- 写作目标：说明设计内容如何在项目代码中落地，展示关键实现方式。
- 内容边界：写模块实现思路、关键代码逻辑、前后端联动和页面效果；不重复做需求分析。
- 应依托的项目事实：
  - 控制器、服务实现类、网关过滤器、前端路由、API 封装、文件上传逻辑、测试可支撑的实现点。
- 适合的呈现方式：
  - 图：页面截图、关键交互流程图。
  - 表格：关键代码说明表、模块实现映射表。
- 已有充分证据的部分：
  - 登录鉴权、企业备案、检查/抽检、整改、投诉、预警代理、统计查询、前端路由控制。
- 项目未实现内容的规范表述：
  - 未发现的功能不能以“界面预留”代替“已实现”，若只有原型图而无运行代码，应明确不写入实现章节。

### 第六章 系统测试
- 写作目标：验证系统主要功能与部分非功能要求是否满足预期。
- 内容边界：写测试目标、测试环境、测试方法、测试用例和结果，不重复介绍架构设计。
- 应依托的项目事实：
  - 仓库内已有 JUnit / Spring Boot Test / MockMvc 测试类。
  - 可从现有功能链中抽取手工测试用例。
- 适合的呈现方式：
  - 表格：测试用例表、测试结果表。
  - 图：必要时用运行截图辅助说明结果。
- 已有充分证据的部分：
  - 多个服务存在测试类，覆盖公告、产品、公开企业、检查记录、抽检、投诉、统计等。
- 项目未实现内容的规范表述：
  - 无专项压力测试时，应写“未开展专门性能压测，仅进行了功能与接口联调验证”。

### 第七章 总结与展望
- 写作目标：总结本文完成的工作、项目成果与不足，并提出后续改进方向。
- 内容边界：总结必须回扣前文已写内容，展望只能写合理扩展方向，不能回写未完成功能为既有成果。
- 应依托的项目事实：
  - 已完成的微服务划分、核心业务闭环、统一鉴权、数据库分库、前后端分离。
  - 未实现的消息队列、容器化部署、统计预留表落地等。
- 适合的呈现方式：
  - 列表：总结点、展望点。
- 已有充分证据的部分：
  - 已实现的核心功能链和系统结构。
- 项目未实现内容的规范表述：
  - 可写为“后续可进一步引入消息队列、容器化部署、完善统计数据仓储”等。

## 5. 前后章节衔接规则

### 5.1 功能主线衔接规则
- 第3章提出的每个核心功能，至少要在第4章出现对应设计，在第5章出现对应实现，在第6章出现对应测试或验证说明。
- 若某功能在第3章写入需求，但项目中未发现实现证据，则第4章和第5章不能按“已完成”书写，应改写为“需求目标”或删除。

### 5.2 数据主线衔接规则
- 第4章数据库设计中出现的核心实体，应能支撑第3章业务流程。
- 第5章实现章节引用的数据表，必须已在第4章数据库设计中出现。
- `query-service` 的预留统计表不能在第5章写成当前统计实现基础，应说明当前统计通过 Feign 聚合完成。

### 5.3 微服务主线衔接规则
- 第3章强调“需要分角色协同和业务解耦”。
- 第4章解释“因此采用网关 + 多微服务 + 分库设计”。
- 第5章证明“具体通过 Gateway、Feign、JWT、各服务控制器与前端接口落地”。
- 第6章验证“服务协同后的功能结果是否正确”。

### 5.4 章节去重规则
- 绪论不写模块细节。
- 相关技术不写业务流程。
- 系统分析不写具体类名和源码。
- 系统设计不贴大段代码。
- 系统实现不重新讲需求背景。
- 系统测试不重复描述数据库结构。

## 6. 写作时必须避免的问题

- 不要把“微服务”写成口号式优点，必须落到本项目中的具体拆分事实：网关统一入口、服务注册发现、Feign 调用、独立数据库、角色分工对应服务职责。
- 不要把“食品安全监管平台”的价值写成泛泛的“提高效率”，应结合项目已实现业务写成：支撑企业备案审核、检查抽检、整改闭环、投诉处理、信息公示和预警协同。
- 不要混淆第3章、第4章、第5章：
  - 第3章是需求与问题。
  - 第4章是设计方案。
  - 第5章是代码落地。
- 不要在第2章引入项目中未使用的技术做大篇幅说明。
- 不要把原型页面、预留表、依赖声明直接写成“系统已实现功能”。
- 不要虚构性能指标、并发指标、部署规模、用户规模。
- 不要把未发现的消息队列、容器化部署、独立认证中心写成现有成果。
- 不要让“功能需求—功能设计—功能实现”前后名称不一致，建议后续正文统一使用以下模块命名：
  - 用户与认证
  - 企业备案与产品档案
  - 检查与抽检
  - 整改管理
  - 投诉处理
  - 公告与信息公示
  - 预警管理
  - 统计查询
- 不要让“数据库设计—业务流程—模块实现”脱节，后续凡写到业务闭环，必须能追溯到对应表和控制器。

## 7. 难点处理原则

### 7.1 微服务架构如何写成设计亮点
- 不是写“微服务先进”，而是写“本项目按业务边界拆分用户、监管主数据、监管操作、投诉、预警、统计等服务，降低了职责耦合，并通过 Gateway、Nacos、Feign 实现统一入口和服务协同”。
- 可进一步强调两个具体设计点：
  - 网关统一鉴权与角色访问控制。
  - 预警事件通过 Outbox 表重试投递，而不是直接强耦合调用。

### 7.2 业务价值如何符合毕业论文口径
- 价值表述应围绕“支撑监管闭环”和“提升业务规范化”。
- 推荐表述方向：
  - 提升企业备案与监管审核的信息化程度。
  - 支撑检查、抽检、整改、投诉、公告、预警等业务联动。
  - 为公众信息查询和投诉反馈提供统一入口。

### 7.3 如何保证系统分析、设计、实现三章不重复
- 分析章只回答“要什么”。
- 设计章只回答“怎么规划”。
- 实现章只回答“怎么做出来”。
- 后续生成正文时，如果某段出现控制器类名、配置项、前端文件名，这段通常应属于第5章而不是第3章。

### 7.4 如何保证功能链一致
- 后续正文建议固定采用统一顺序：
  - 用户与认证
  - 企业备案与产品档案
  - 检查与抽检
  - 整改管理
  - 投诉处理
  - 公告与公示
  - 预警管理
  - 统计查询
- 这样第3章、第4章、第5章、第6章的模块顺序可以保持一致。

### 7.5 如何保证数据库、流程、模块一致
- 每条业务流程至少对应一个核心实体组：
  - 企业备案：`food_enterprise` + `enterprise_profile_attachment`
  - 产品档案：`food_product`
  - 检查整改：`inspection_task` + `inspection_record` + `inspection_item` + `rectification_task` + `rectification_action_log`
  - 抽检公示：`sampling_task` + `sampling_result`
  - 投诉处理：`complaint` + `complaint_handle`
  - 预警处理：`warning_record` + `warning_process_log`
- 后续正文凡写模块实现，都应能映射回这些表和相应控制器。
