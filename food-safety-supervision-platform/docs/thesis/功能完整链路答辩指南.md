# 功能完整链路答辩指南

> 答辩委员问「某个功能的完整链路逻辑是什么」时，按本文结构作答即可。  
> **万能答题模板见文末。**

---

## 一、先记住系统的「总骨架」

所有功能都遵循同一条技术链路：

```
用户操作（某角色某页面）
  → 前端 Vue 页面 / API 调用
  → gateway-service（JWT 鉴权 + 角色校验 + 路由转发）
  → 对应微服务 Controller
  → Service 业务逻辑（状态校验、分布式锁）
  → MySQL 写/读
  → （可选）Feign 调其他服务 / Outbox 发预警 / Redis 缓存失效
  → 返回前端展示
```

**7 个后端服务分工：**

| 服务 | 管什么 |
|------|--------|
| user-service | 注册、登录、登出、令牌 |
| regulation-service | 企业备案、产品、公告、监管员、**预警代理** |
| regulation-operation-service | 检查、抽检、整改 |
| complaint-service | 投诉 |
| warning-service | 预警存储与处置（**前端不直连**） |
| query-service | 监管概览、预警统计（**聚合多个服务**） |
| gateway-service | 统一入口 |

**5 类角色：** 系统管理员、区域管理员、执法人员、企业用户、公众用户。

## 二、各功能完整链路（答辩直接背这个）

### 功能 1：登录认证

| 步骤 | 谁操作 | 发生什么 |
|------|--------|----------|
| 1 | 用户 | 打开 `/login`，输入账号密码 |
| 2 | 前端 | `POST /api/auth/login` |
| 3 | 网关 | 白名单放行，不限流则通过 |
| 4 | user-service | 校验密码、账号状态 → 查角色 → 签发 JWT → Redis 存 session |
| 5 | 前端 | 保存 token，按角色跳转对应首页 |
| 6 | 后续请求 | 网关校验 JWT → 调内省接口 → 注入 `X-User-Id` 等头 → 转发业务服务 |

**登出：** `POST /api/auth/logout` → JWT 加入 Redis 黑名单 → session 删除。

**一句话：** 登录由 user-service 签发令牌，之后所有请求经网关统一鉴权，业务服务只读请求头里的身份信息。

---

### 功能 2：企业注册 + 备案 + 审批

这是**两条线**：先建账号，再建档案。

#### 2A 企业账号注册

| 步骤 | 谁 | 链路 |
|------|-----|------|
| 1 | 访客 | `/register/enterprise` 填账号 |
| 2 | 前端 | `POST /api/users/register/enterprise` |
| 3 | user-service | 写 `sys_user` + 绑定 ENTERPRISE 角色 |
| 4 | 结果 | 能登录，但**还没有企业档案** |

#### 2B 企业备案提交

| 步骤 | 谁 | 链路 |
|------|-----|------|
| 1 | 企业用户 | `/enterprise/profile` 填企业信息、上传附件 |
| 2 | 前端 | 先 `POST /api/files/presign` 拿 MinIO 上传地址 → 直传文件 |
| 3 | 前端 | `POST /api/regulation/enterprise/profile` |
| 4 | regulation-service | 写 `food_enterprise`（状态 **PENDING 待审核**）、附件表 |
| 5 | 副作用 | 企业相关 Redis 缓存失效 |

#### 2C 区域管理员审批

| 步骤 | 谁 | 链路 |
|------|-----|------|
| 1 | 区域管理员 | `/regulator/admin/approvals` 看待审列表 |
| 2 | 前端 | `GET /api/regulation/enterprise/pending` |
| 3 | 通过 | `PUT .../enterprise/{id}/approve` → 状态 **APPROVED**，指定包保执法员 |
| 4 | 驳回 | `PUT .../reject` → 状态 **REJECTED** |
| 5 | 结果 | 企业通过后可维护产品、被检查抽检；驳回后企业可修改重提 |

**状态流转：** `PENDING → APPROVED / REJECTED`

**一句话：** 企业在 regulation-service 提交档案进待审，区域管理员审核通过后企业才进入正式纳管，后续检查抽检都依赖这条线。

---

### 功能 3：产品档案

| 步骤 | 谁 | 链路 |
|------|-----|------|
| 前提 | — | 企业备案必须 **APPROVED** |
| 1 | 企业用户 | `/enterprise/products` 新增/编辑产品 |
| 2 | 前端 | `POST/PUT /api/regulation/products` |
| 3 | regulation-service | 写 `food_product`（ACTIVE/INACTIVE） |
| 4 | 用途 | 抽检任务创建时要选 **ACTIVE** 产品 |

**一句话：** 产品是 regulation-service 的主数据，备案通过后才能维护，给后续抽检提供产品对象。

---

### 功能 4：检查任务（完整链路 ★重点）

| 步骤 | 谁 | 操作 | 状态变化 |
|------|-----|------|----------|
| 1 | 区域管理员 | 创建检查任务 | → **CREATED** |
| 2 | 区域管理员 | 分派给执法人员 | → **ASSIGNED** |
| 3 | 执法人员 | 开始任务 | → **IN_PROGRESS** |
| 4 | 执法人员 | 提交检查结果（含检查项） | → **COMPLETED** |
| 5 | 系统 | 若不合格 → **自动生成整改任务** | 整改 → ONGOING |
| 6 | 系统 | 若连续不合格达阈值 → 标记重点监管 + **发预警** | Outbox → warning-service |

**关键 API（都在 regulation-operation-service）：**
- 创建 `POST /api/regulation-operation/tasks`
- 分派 `PUT .../tasks/{id}/assign`
- 提交 `POST .../tasks/{id}/submit`（**加分布式锁**）

**跨服务：** 提交时要 Feign 调 regulation-service 查企业是否在辖区、查执法员身份；不合格时写 Outbox 预警。

**涉及表：** `inspection_task` → `inspection_record` → `inspection_item` →（联动）`rectification_task`

**一句话：** 管理员建任务、派给执法员，执法员提交结果留痕；不合格自动开整改，连续不合格还会触发重点监管和预警。

---

### 功能 5：整改闭环（完整链路 ★重点）

| 步骤 | 谁 | 操作 | 状态变化 |
|------|-----|------|----------|
| 0 | 系统 | 检查不合格时自动创建 | **ONGOING** |
| 1 | 企业用户 | 提交整改说明+附件 | → **SUBMITTED** |
| 2 | 区域管理员 | 复核通过 | → **CONFIRMED**（闭环结束） |
| 2' | 区域管理员 | 复核退回 | → **REWORK** |
| 3 | 企业用户 | 退回后再次提交 | → **SUBMITTED** |
| 4 | 定时任务 | 扫描提交/复核超时 | 写日志 + Outbox 发 **整改超时预警** |

**关键 API：**
- 企业提交 `PUT /api/regulation-operation/rectifications/my/{id}/submit`
- 监管复核 `POST .../rectifications/{id}/review`（action=CONFIRM 或 REWORK）

**SLA（答辩可提）：** 首次提交 72h、退回后再提交 48h、监管复核 24h。

**一句话：** 检查不合格自动生成整改单，企业提交、管理员复核，通过则闭环；超时由定时任务扫出并推预警。

---

### 功能 6：抽检 + 公示（完整链路 ★重点）

| 步骤 | 谁 | 操作 | 说明 |
|------|-----|------|------|
| 1 | 区域管理员 | 创建抽检任务（选企业+产品） | → CREATED |
| 2 | 区域管理员 | 分派执法员 | → ASSIGNED |
| 3 | 执法人员 | 提交抽检结果 | → COMPLETED；结果默认 **DRAFT 未公开** |
| 4 | 系统 | 若不合格 | 标记重点监管 + Outbox 预警 |
| 5 | 区域管理员 | 发布抽检结果 | DRAFT → **PUBLISHED** |
| 6 | 公众用户 | 查询抽检公示 | 只能看到 **PUBLISHED** 的记录 |

**关键 API：**
- 提交结果 `POST /api/regulation-operation/sampling/tasks/{id}/result`
- 发布 `POST .../sampling/results/{id}/publish`
- 公众查询 `GET /api/regulation-operation/public/sampling/results`

**一句话：** 内部先录入抽检结果，管理员审核发布后才对外公示，公众端只看已发布数据。

---

### 功能 7：投诉处理（完整链路 ★重点）

| 步骤 | 谁 | 操作 | 状态变化 |
|------|-----|------|----------|
| 1 | 公众用户 | 选企业、填投诉内容 | → **SUBMITTED** |
| 2 | 区域管理员 | 受理 | → **PENDING** |
| 3 | 区域管理员 | 分派执法员 | → **ASSIGNED** |
| 4 | 执法人员 | 开始处理 | → **PROCESSING** |
| 5 | 执法人员 | 提交处理结果 | → **FEEDBACKED**（结束） |
| — | 区域管理员 | 也可驳回 | → **REJECTED** |

**关键 API（complaint-service）：**
- 提交 `POST /api/complaints/public`
- 受理 `PUT /api/complaints/{id}/accept`
- 分派 `PUT .../assign`
- 处理 `POST .../handle`

**副作用：** 受理时若该企业近期投诉量超阈值 → Feign 调 regulation-service 标重点监管 + 直接调 warning-service 发 **投诉聚集预警**（dedupKey 幂等）。

**一句话：** 公众投诉进 complaint-service，管理员受理分派，执法员处理反馈，公众可跟踪；投诉过多还会触发预警。

---

### 功能 8：预警（生成 + 查看 + 处置）

#### 8A 预警怎么产生？

| 来源 | 触发条件 | 投递方式 |
|------|----------|----------|
| 检查 | 连续不合格 | Outbox → warning-service |
| 抽检 | 结果不合格 | Outbox → warning-service |
| 整改 | 提交/复核超时（定时扫描） | Outbox → warning-service |
| 投诉 | 企业投诉量超阈值 | complaint-service 直接 Feign |

**Outbox 流程：** 本地事务写业务 + 写 `warning_event_outbox` → 后台任务 Feign 调 warning-service → 成功标 SENT，失败重试。

**幂等：** 同一 `dedupKey` 不重复建单，只累加 `trigger_count`。

#### 8B 监管人员怎么看、怎么处理？

| 步骤 | 说明 |
|------|------|
| 1 | 前端**不直连** warning-service（网关会拦） |
| 2 | 走 regulation-service **代理**：`/api/regulation/warnings/**` |
| 3 | 管理员：按辖区看预警，可 **分派 / 处理 / 结案** |
| 4 | 执法员：只看分派给自己的，可 **处理 / 结案** |
| 5 | 状态：OPEN → PROCESSING → RESOLVED |

**一句话：** 业务服务发现异常后异步推预警；监管端通过 regulation-service 代理访问，warning-service 统一存储和处置。

---

### 功能 9：公告发布 + 公众查询

| 步骤 | 谁 | 操作 | 状态 |
|------|-----|------|------|
| 1 | 区域管理员 | 创建公告 | **DRAFT** |
| 2 | 区域管理员 | 编辑、发布 | → **PUBLISHED** |
| 3 | 区域管理员 | 下线 | → **OFFLINE** |
| 4 | 公众用户 | 查公告列表/详情 | 只看到 **PUBLISHED** |

**服务：** regulation-service，`public_bulletin` 表，公众查询走 Redis 缓存。

**一句话：** 管理员起草发布公告，公众只能看已发布内容。

---

### 功能 10：监管概览 / 预警统计

| 步骤 | 链路 |
|------|------|
| 1 | 监管人员打开概览/统计页 |
| 2 | 前端 `GET /api/query/supervision/overview` 或 `/api/query/warnings/*` |
| 3 | query-service 按用户辖区裁剪查询范围 |
| 4 | **并行 Feign** 调 regulation、operation、complaint、warning 四个服务的内部统计接口 |
| 5 | 聚合结果，Redis 缓存后返回前端 |

**一句话：** query-service 不存业务明细，只负责按辖区聚合各服务统计数据，给监管人员一个统一看板。

## 三、答辩时怎么答「某一个功能的完整链路」

### 万能五段式模板（30 秒～1 分钟）

按下面顺序说，老师会觉得你逻辑清楚：

```
1.【业务目标】这个功能解决什么问题、谁在用
2.【参与角色】哪些角色、各做什么
3.【状态流转】关键状态怎么变（说 2～3 个核心状态即可）
4.【技术链路】页面 → 网关 → 哪个服务 → 写哪张表 → 有没有跨服务调用
5.【亮点/保障】分布式锁、Outbox、缓存、权限隔离等（挑 1 个相关的说）
```

### 示例：老师问「检查整改的完整链路是什么？」

> **业务目标：** 实现监督检查从任务下达到问题闭环。  
> **角色：** 区域管理员创建分派任务，执法人员现场检查提交结果，企业提交整改，管理员复核。  
> **状态：** 检查任务 CREATED→ASSIGNED→IN_PROGRESS→COMPLETED；不合格自动生成整改 ONGOING→SUBMITTED→CONFIRMED 或 REWORK。  
> **技术链路：** 前端经网关到 regulation-operation-service，写 inspection_task/record/item，不合格时内部调 RectificationService 写 rectification_task；提交时加 Redis 分布式锁；连续不合格通过 Outbox 异步推 warning-service。  
> **保障：** 跨服务用 Outbox 最终一致性，关键写操作有锁防重复提交。

### 示例：老师问「投诉怎么处理到反馈的？」

> 公众在 `/public/complaints/new` 提交，complaint-service 写 complaint 表，状态 SUBMITTED。区域管理员受理变 PENDING，分派执法员变 ASSIGNED。执法员处理完成后变 FEEDBACKED，公众可在我的投诉里看反馈。受理分派等步骤有分布式锁，投诉量超标会 Feign 调 regulation 和 warning 服务触发聚集预警。

## 四、功能之间的「串联关系」（答辩加分项）

如果老师问「这些功能怎么串起来」，可以这样说：

```
企业注册 → 备案审批（纳管）
    ↓
产品档案维护
    ↓
检查任务 / 抽检任务（监管执行）
    ↓
不合格 → 整改闭环 / 抽检公示
    ↓
异常事件 → 预警（Outbox 或 Feign）
    ↓
监管概览 / 预警统计（query-service 聚合展示）

公众投诉 ──并行──→ 也可触发重点监管和预警
公告公示 ──并行──→ 面向公众的信息公开
```

**核心闭环：** 纳管 → 执行 → 整改/公示 → 预警 → 统计。

## 五、高频追问速答

| 老师可能追问 | 你怎么答 |
|--------------|----------|
| 为什么预警不直连？ | 预警属监管域，由 regulation-service 代理，网关禁止外部访问 warning-service，统一权限和边界。 |
| Outbox 是什么？ | 本地事务先写业务和待发送事件，后台异步投递预警服务，失败可重试，保证最终一致。 |
| 公众为什么看不到未发布抽检？ | sampling_result 有 public_status，只有 PUBLISHED 才进公众查询接口。 |
| 企业没审批能检查吗？ | 不能，创建任务时会校验企业 approval_status=APPROVED。 |
| 统计数据从哪来？ | query-service 调各服务内部 stats 接口聚合，不是查一张大表。 |

## 六、建议演示顺序（答辩现场）

一条链走通最有说服力：

1. 企业登录 → 提交备案  
2. 管理员审批通过  
3. 管理员创建检查任务 → 分派  
4. 执法员提交**不合格**结果  
5. 企业提交整改 → 管理员复核通过  
6. 打开预警中心看是否生成预警  
7. 打开监管概览看统计数据
