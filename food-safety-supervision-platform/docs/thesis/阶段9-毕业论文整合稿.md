# 阶段9-毕业论文整合稿.md

## 第1章 绪论

### 1.1 项目背景及意义

食品安全直接关系到公众身体健康和社会公共安全，是公共治理中的重要内容。随着食品生产、流通和消费环节不断延伸，监管对象数量持续增加，监管业务流程也呈现出参与主体多、业务链条长、协同要求高等特点。在传统管理方式下，企业备案、监督检查、抽检公示、问题整改、公众投诉和风险预警等工作通常分散在不同业务环节中，容易出现信息分散、过程脱节和追踪困难等问题。因此，围绕食品安全监管业务建设统一的信息化平台，已成为提升监管规范化、流程化和协同化水平的重要手段。

结合本项目实际实现内容，食品安全监管并不是单一环节的信息录入，而是覆盖企业、监管部门和公众多方参与的闭环过程。企业需要完成基础信息备案并维护产品档案，监管部门需要开展备案审核、检查任务派发、抽检结果发布和整改复核，公众需要获取公开信息并进行投诉反馈，系统管理员还需要维护监管人员账号、角色类型和状态信息。上述业务天然具有明显的角色分工特征和数据协同需求，如果采用高度耦合的实现方式，后续在功能扩展、权限控制和服务协同方面都容易受到限制。基于这一背景，本课题以“基于微服务的食品安全监管平台”为题，围绕真实监管业务链构建面向多角色的管理平台。

本项目的研究意义主要体现在以下几个方面。第一，在业务层面，平台将企业备案、产品档案、检查任务、抽检结果、整改管理、投诉处理、公告公示、预警协同和统计查询等功能纳入统一系统，形成较完整的监管业务闭环，有助于提高业务过程的连续性和可追溯性。第二，在技术层面，项目采用前后端分离与微服务架构，将用户认证、基础监管数据、监管操作、投诉处理、预警处理和统计查询按业务边界拆分为多个服务，并通过统一网关、服务注册发现和服务间调用机制实现协同处理，体现了现代软件工程中面向业务边界进行系统拆分的设计思路。第三，在应用层面，系统同时面向系统管理员、区域管理员、执法人员、企业用户和公众用户，能够较真实地反映食品安全监管场景下多主体协同工作的业务特征，对本科毕业设计中软件开发研究类型论文的写作具有较好的支撑作用。

需要说明的是，本文所有结论均以仓库中已经实现的代码、配置、数据库脚本、页面和测试材料为依据。当前系统已经实现统一认证、企业备案、产品管理、检查与抽检、整改管理、投诉处理、公告管理、预警处理和统计查询等核心功能，但并未实现消息队列驱动的异步通信、容器化编排部署等扩展能力。因此，本文中的背景与意义分析均围绕已实现的平台能力展开，不对未实现内容作超出事实范围的延伸表述。

### 1.2 国内外研究现状

从信息化建设趋势看，围绕公共监管业务构建数字化平台已经成为普遍方向。相关系统研究与实践通常聚焦于业务流程电子化、数据集中管理、跨角色协同处理以及监管结果可追溯等方面。在食品安全领域，平台化建设的重点通常集中在企业主体信息维护、监督检查留痕、抽检信息发布、问题处置闭环以及公众参与渠道建设等内容。这说明食品安全监管系统已经不再局限于基础数据录入，而是逐步向流程联动、业务集成和服务化方向发展。

在系统架构层面，随着业务复杂度提升，越来越多的平台开始采用分层、模块化甚至服务化的实现方式。相较于传统单体架构，基于服务拆分的架构更适合处理多角色、多模块、多业务链条并行的场景，便于根据不同业务边界进行职责划分，并提升后续扩展和维护能力。与此同时，统一网关、服务注册发现、分布式鉴权和缓存机制等配套技术，也逐渐成为此类平台的重要组成部分。对于监管类系统而言，这种架构思路有助于将用户认证、业务主数据管理、业务处理和统计查询等职责分离，从而降低模块之间的直接耦合程度。

在业务功能层面，现有相关平台通常已经覆盖企业信息管理、执法检查、抽检管理和基础查询等内容，但在完整业务闭环方面仍存在进一步整合空间。一方面，不同业务流程之间的数据衔接往往不够紧密，例如检查结果、整改任务和风险预警之间缺少统一联动；另一方面，面向公众的信息公开和投诉反馈机制在许多系统中仍与内部监管流程相对分离，难以形成从问题发现、任务处理到结果反馈的连续链路。对于食品安全监管业务而言，仅实现单点功能并不能充分体现平台价值，真正有效的系统应当能够支撑多角色协同、状态流转和信息共享。

在技术选型方面，主流实践通常围绕微服务框架、网关组件、注册发现方案、持久层技术和前端框架进行组合应用，其共同目标是提高系统的可维护性、可扩展性和可用性。然而，从本科毕业设计的实现角度看，许多研究更偏重技术概念本身，而对“技术如何与具体业务边界对应”“不同服务如何围绕业务流程协同”“系统如何在已实现功能范围内体现架构价值”等问题关注不足。基于此，本项目的切入点不是简单构建一个技术演示系统，而是围绕食品安全监管平台的实际业务需求，将企业备案、检查抽检、整改处理、投诉流转、公告公示、预警协同和统计查询纳入统一架构，并在代码层面落实服务划分、统一鉴权和跨服务协作机制。

总体来看，国内外相关研究已经为监管信息化、平台化和服务化建设提供了较丰富的思路，但如何在一个面向真实业务链条的平台中实现多角色协同和完整监管闭环，仍然具有较强的实践价值。本项目在现有技术体系基础上，结合食品安全监管场景完成微服务化平台实现，具有一定的工程研究意义和教学应用价值。

### 1.3 论文研究内容

本文围绕“基于微服务的食品安全监管平台”展开研究与实现，重点结合项目代码中已经完成的系统功能与技术方案，对平台的需求分析、架构设计、功能实现和测试验证进行系统论述。论文的主要研究内容包括以下几个方面。

第一，围绕食品安全监管业务场景，分析平台所面向的主要用户角色和核心业务需求。项目实际面向系统管理员、区域管理员、执法人员、企业用户和公众用户五类角色，已经形成企业备案、产品档案、监督检查、抽检公示、整改复核、投诉处理、公告公示、预警处理和统计查询等业务模块。因此，本文首先从业务流程和角色分工出发，对系统功能需求与非功能需求进行分析。

第二，针对食品安全监管业务链条长、协同环节多的特点，完成平台总体架构设计与模块划分设计。项目采用前后端分离实现方式，前端基于 Vue 3 构建单页应用，后端基于 Spring Boot 和 Spring Cloud 构建网关服务、用户服务、监管服务、监管操作服务、投诉服务、预警服务和查询服务，并通过 Nacos、Gateway、OpenFeign、Redis 等技术完成统一入口、服务治理和服务协作。本文将对该架构组织方式及其设计依据进行说明。

第三，围绕核心业务对象完成数据库设计与实体关系梳理。项目按服务边界划分独立数据库，分别管理用户与角色、企业与产品、检查与抽检、整改、投诉、预警和统计扩展数据。本文将基于各服务的数据库脚本，对系统核心数据表、实体关系以及对业务流程的支撑方式进行分析。

第四，结合项目实际代码实现，对系统核心功能模块进行说明。系统已经实现统一登录认证与角色访问控制、企业备案审核与产品档案维护、检查任务与抽检任务管理、整改闭环处理、公众投诉与监管处置、公告管理、预警代理访问和统计查询等功能。本文将在后续章节中结合控制器、服务实现、前端路由与 API 调用等内容说明系统实现过程。

第五，对系统测试情况进行验证分析。项目中已经包含多项基于 JUnit 5、Spring Boot Test 和 MockMvc 的测试代码，覆盖网关鉴权、文件上传权限、产品档案、检查记录、抽检任务、投诉处理、预警统计和监管概览等内容。本文将在测试章节中结合功能测试与接口验证内容，对系统实现效果进行说明。

## 第2章 相关技术

### 2.1 项目选用技术简介

#### 2.1.1 Spring Boot 与 Spring Cloud 微服务开发框架

本项目后端采用 Java 17 作为开发语言，并基于 Spring Boot 3.2.5 构建各个业务服务。Spring Boot 具有自动配置能力强、工程结构清晰、生态成熟等特点，适合快速构建面向业务的独立服务。项目父工程采用 Maven 聚合管理方式，将 `gateway-service`、`user-service`、`regulation-service`、`regulation-operation-service`、`complaint-service`、`warning-service`、`query-service` 和 `platform-common` 组织在同一工程中，既便于统一依赖版本管理，也便于按服务边界进行独立开发与部署。

在微服务层面，项目引入 Spring Cloud 2023.0.1 和 Spring Cloud Alibaba 2023.0.1.0 作为技术基础，使各服务能够围绕统一的服务治理体系协同运行。对于本项目这类多角色、多模块的监管平台而言，将用户认证、监管主数据、业务操作、投诉处理、预警处理和统计查询拆分为多个服务，有利于降低单体系统中业务逻辑高度集中的复杂性，也使后续功能扩展更符合业务边界。

#### 2.1.2 Nacos 服务注册发现与配置管理

为了支撑多服务协同运行，本项目在各服务中统一引入 Nacos Discovery 和 Nacos Config。Nacos Discovery 主要用于服务注册与发现，使网关和服务调用方能够通过服务名访问目标服务，而不必将服务地址硬编码在系统中。各服务均在配置中定义了 `spring.application.name` 和 Nacos 地址，并通过服务名参与调用，为微服务架构提供了基础支撑。

Nacos Config 用于统一配置管理。虽然仓库中没有独立配置中心模块，但各服务已接入 Nacos Config，说明系统在运行时具备接入外部配置中心的能力。对于需要多环境切换和多服务协同的监管平台而言，注册发现和配置管理机制能有效降低运行与维护复杂度。

#### 2.1.3 Spring Cloud Gateway 网关技术

本项目采用 Spring Cloud Gateway 作为统一网关。网关负责请求路由、跨域处理、JWT 校验、令牌内省和部分接口限流，是前后端交互中的统一入口。项目中的 `gateway-service` 配置了 `/api/auth/**`、`/api/regulation/**`、`/api/regulation-operation/**`、`/api/complaints/**`、`/api/query/**` 等路由规则，并基于 `JwtAuthFilter` 对请求进行统一鉴权处理。

采用统一网关后，前端无需感知各业务服务的独立端口，只需面向网关地址访问接口。这样既简化了前端调用方式，也使权限控制和访问治理集中在网关层完成，更符合多服务系统的整体组织方式。

#### 2.1.4 OpenFeign 服务间调用技术

在服务间协作方面，项目使用 OpenFeign 组织跨服务调用。监管服务需要调用用户服务和预警服务，监管操作服务需要调用监管服务和预警服务，投诉服务需要调用监管服务，查询服务需要聚合调用多个统计接口。这些调用关系均通过 `@FeignClient` 接口实现。

OpenFeign 的引入使服务间依赖关系在接口层面得到明确表达，避免了大量底层 HTTP 请求代码重复编写，也更便于与 Spring Cloud 服务治理体系结合使用。对于本项目中多条业务链路协同的场景，声明式服务调用方式更加适合。

#### 2.1.5 MyBatis-Plus 持久层技术

本项目后端持久层采用 MyBatis-Plus。系统中存在较多结构清晰、状态字段较多、查询条件复杂但以业务表为核心的数据操作场景，例如企业备案、产品档案、检查任务、抽检结果、投诉记录和预警记录等。MyBatis-Plus 既保留了较强的 SQL 控制能力，又能减少单表基础操作的重复开发工作，适合本项目的工程实现方式。

#### 2.1.6 MySQL 数据库技术

项目使用 MySQL 作为主要业务数据库。系统核心数据包括用户与角色、企业与产品、检查与整改、抽检、公示、投诉和预警等，均具有结构明确、关系清晰、事务性要求较强的特点，因此采用关系型数据库更为合适。项目按服务边界划分数据库脚本，体现了“服务独立、数据独立”的设计原则。

#### 2.1.7 Redis 缓存与协同控制技术

本项目中 Redis 主要用于会话缓存、令牌黑名单、公共数据缓存、统计结果缓存、限流计数和分布式锁支持。用户服务通过 Redis 缓存会话与令牌状态，监管服务和查询服务通过 Redis 缓存热点查询结果，整改与监管操作场景则借助分布式锁控制关键操作一致性。Redis 的引入提升了系统在读写效率和协同处理方面的能力。

#### 2.1.8 JWT 统一认证技术

项目采用 JWT 作为身份认证令牌。用户在登录成功后由用户服务签发令牌，后续请求统一由网关进行校验并调用内省接口确认令牌有效性，再将用户身份信息传递给下游业务服务。该方案适合当前微服务结构，使统一认证、统一鉴权和角色访问控制能够在多服务场景下稳定实现。

#### 2.1.9 MinIO 文件存储技术

在文件处理方面，项目通过 `regulation-service` 引入 MinIO，用于支持备案附件和投诉、整改等场景中的文件上传。系统通过预签名上传方式生成文件上传地址，前端获得地址后直接上传到对象存储。该方式能够降低业务服务在文件传输上的负担，同时提高文件处理灵活性。

#### 2.1.10 Vue 3 前端技术栈

前端采用 Vue 3、Vue Router 4 和 Vite 5。Vue 3 适合构建组件化单页应用，Vue Router 用于按角色组织页面访问，Vite 用于提升开发与构建效率。项目中前端页面已按系统管理员、区域管理员、执法人员、企业用户和公众用户进行划分，并通过统一 API 客户端与网关交互，形成了较清晰的前后端协同结构。

#### 2.1.11 OpenAPI 文档与测试技术

在接口文档方面，`query-service` 集成了 Springdoc OpenAPI，并通过配置类定义接口文档信息。测试方面，项目统一引入 JUnit 5、Spring Boot Test 和 MockMvc，并在多个服务中编写了测试类，为后续系统测试章节提供了客观依据。

### 2.2 相关技术选型对比研究

#### 2.2.1 微服务架构与单体架构对比

对于食品安全监管平台而言，系统需要同时支撑用户认证、企业备案、产品档案、检查抽检、整改处理、投诉处理、预警管理和统计查询等多类业务。如果采用单体架构，所有模块集中在同一工程中，虽然初期实现较为直接，但随着模块增多，业务耦合、权限逻辑分散和维护成本上升的问题会逐渐显现。相比之下，微服务架构能够围绕业务职责进行拆分，使不同服务承担明确功能，并通过统一网关和服务治理机制完成协同处理。

本项目选择微服务架构，主要原因在于系统具有明显的多角色、多模块特征，用户服务、监管服务、监管操作服务、投诉服务、预警服务和查询服务之间存在天然业务边界，适合按服务拆分。同时，统一认证、统一网关和按服务分库的设计，也更符合本项目当前的工程组织方式。

#### 2.2.2 Gateway 网关方案与直接暴露服务方式对比

若由前端分别访问不同业务服务地址，则需要各服务自行处理跨域、鉴权和权限控制，前端也需要维护更多接口入口，增加复杂度。采用统一网关后，可以将路由转发、跨域处理、令牌校验和部分限流逻辑集中在网关层完成。

本项目选择 Spring Cloud Gateway 作为统一入口，一方面降低了前端接口调用复杂度，另一方面使认证和权限控制更集中、更便于维护，因此较直接暴露服务方式更适合本项目。

#### 2.2.3 Nacos 与静态地址配置方式对比

静态服务地址配置方式虽然简单，但在多服务场景下容易因环境变化、端口调整或服务扩展带来维护成本。Nacos 提供服务注册发现和配置管理能力，使系统能够通过服务名进行调用和寻址，提升服务治理灵活性。

本项目采用 Nacos，是因为后端已经划分为多个独立服务，且服务间协作关系较多，基于服务名和配置中心的组织方式更适合当前项目的运行结构。

#### 2.2.4 OpenFeign 与手工 HTTP 调用方式对比

手工 HTTP 调用方式虽然灵活，但容易产生大量重复代码，且调用关系不直观。OpenFeign 通过声明式接口封装服务调用，可以使依赖关系更加清晰，也更便于维护。

本项目中存在大量围绕主数据读取、统计聚合和预警代理展开的跨服务协同，因此选择 OpenFeign 更符合项目开发效率和结构清晰性的要求。

#### 2.2.5 MyBatis-Plus 与更重型 ORM 方案对比

对于本项目这类以状态流转、条件查询和结构化业务数据管理为主的系统，过于重型的 ORM 方案未必具有优势。MyBatis-Plus 兼顾开发效率与 SQL 控制能力，适合企业、检查、抽检、投诉和预警等业务表的实现方式，因此被选为本项目持久层方案。

#### 2.2.6 MySQL 与其他类型数据存储方案对比

本项目核心数据关系明确、事务性较强，涉及多表状态流转和结构化查询，因此更适合使用关系型数据库。与以非关系型数据库为主的数据方案相比，MySQL 更适合本项目的业务特征和工程实践需求。

#### 2.2.7 Redis 与纯数据库访问方式对比

如果系统完全依赖数据库处理会话、热点查询和限流控制，不仅会增加数据库压力，也不利于统一管理高频状态。Redis 更适合承担会话、缓存、限流和锁控制等职责，因此本项目引入 Redis 作为重要辅助组件，以满足访问效率和协同控制需要。

#### 2.2.8 JWT 统一鉴权方案与传统会话鉴权方案对比

传统服务端会话方案在多服务场景中容易带来会话同步和扩展复杂度，而 JWT 更适合在微服务之间传递认证结果。项目最终采用 JWT 与 Redis 会话缓存结合的方式，既保留了令牌方案的灵活性，也通过黑名单和会话机制增强了状态控制能力。

#### 2.2.9 Vue 3 与传统多页面开发方式对比

对于本项目这种多角色、多业务页面并存的前端系统，传统多页面方式会导致页面跳转逻辑分散、状态组织不统一。Vue 3 与 Vue Router 适合构建组件化单页应用，可以更清晰地组织不同角色下的功能入口。因此，本项目选择 Vue 3 技术栈作为前端实现方案。

#### 2.2.10 本项目技术选型结论

综合来看，本项目技术选型并不是对流行技术的简单堆叠，而是围绕食品安全监管平台的业务特征进行组织的。Spring Boot 与 Spring Cloud 支撑多服务结构，Nacos 提供服务治理基础，Gateway 实现统一入口与安全控制，OpenFeign 支撑服务协同，MyBatis-Plus 与 MySQL 负责结构化业务数据管理，Redis 支撑缓存与协同控制，JWT 保证统一认证鉴权，MinIO 满足文件上传场景，Vue 3 承担前端多角色交互界面实现任务。上述技术组合与项目当前代码结构和业务流程保持一致，具有较好的合理性与可实施性。

## 第3章 系统分析

### 3.1 系统业务需求

#### 3.1.1 平台建设目标

食品安全监管业务具有监管对象数量多、参与主体复杂、流程链条长和协同要求高等特点。企业备案、监管检查、抽检检测、问题整改、公众投诉、公告公示和风险预警等工作并不是孤立存在的，而是围绕食品安全治理目标相互关联、相互影响。若缺少统一平台，各业务环节容易形成数据分散、处理脱节和追踪困难等问题。因此，本系统建设目标是在统一平台上实现企业纳管、监管执行、问题整改、公众监督和统计查询等业务能力的协同运转。

结合项目实际实现内容，平台建设目标主要包括以下几个方面。第一，建立统一的食品安全监管业务平台，将企业备案、产品档案、检查任务、抽检任务、整改管理、投诉处理、公告发布、预警跟踪和统计查询纳入统一系统。第二，支撑多角色协同监管，使系统管理员、区域管理员、执法人员、企业用户和公众用户围绕各自职责完成工作。第三，提高监管过程的规范化和可追溯性，通过结构化数据记录业务状态流转。第四，兼顾监管内部管理与公众服务需求，使平台同时具备内部监管与外部信息公开能力。

#### 3.1.2 主要业务对象与用户角色

根据项目中的角色定义、网关权限规则和前端路由配置，系统涉及的主要业务对象包括监管部门、食品生产经营企业、社会公众以及系统维护人员。系统用户角色可划分为以下五类。

系统管理员主要负责监管人员账号创建、信息查看和状态维护，是系统管理层面的核心角色。区域管理员主要负责监管业务组织，包括企业备案审核、企业信息查看、检查与抽检任务管理、整改复核、投诉流转、公告管理、预警中心和统计概览等功能。执法人员主要承担一线业务执行工作，包括查看辖区企业、执行检查任务、提交检查结果、执行抽检任务、录入抽检结果、处理投诉和跟进整改等。企业用户主要负责企业备案资料维护、产品档案维护、查看检查记录、查看整改任务和提交整改结果。公众用户可以注册登录系统，查看公告、公示企业和抽检结果，并进行投诉提交与投诉跟踪。

#### 3.1.3 核心监管业务场景

结合后端控制器、前端页面和数据库设计，可以确认本项目围绕以下核心监管业务场景展开。

一是企业备案与基础信息审核场景。企业用户提交企业名称、许可证编号、统一社会信用代码、法定代表人、所属区域、地址及附件等备案信息，区域管理员对待审核企业进行查看、审核通过或驳回。

二是产品档案管理场景。企业用户在备案完成后维护本企业产品档案，监管人员端可以按企业查看产品信息，为抽检任务创建提供基础数据。

三是监督检查场景。区域管理员围绕企业创建检查任务并指派给执法人员，执法人员启动任务并提交检查结果，系统生成检查记录和检查项明细。若发现问题，后续可形成整改任务。

四是抽检与公示场景。区域管理员创建抽检任务并指定企业和产品，执法人员提交抽检结果，区域管理员决定是否发布抽检结果，公众用户查询已发布结果。

五是整改复核场景。检查发现问题后形成整改任务，企业提交整改进展和附件，监管人员查看整改详情和动作日志，并执行复核确认或退回整改。

六是投诉受理与处理场景。公众用户选择企业并提交投诉内容，区域管理员和执法人员围绕投诉完成受理、指派、处理、反馈或驳回。投诉信息既是社会监督的体现，也为后续监管重点识别和风险预警提供输入。

七是公告公示与预警统计场景。监管人员端管理公告发布与下线，公众用户查询公开信息；系统围绕整改超时、抽检不合格、投诉过载等业务事件形成预警记录，并通过查询服务向监管人员提供统计概览。

#### 3.1.4 主要业务流程

为保证系统分析与后续设计、实现章节保持一致，本项目主要业务流程可归纳为以下几条主线。

第一条主线为企业备案流程。企业用户注册登录后提交备案资料和附件，系统保存企业基础信息与附件信息，区域管理员查看待审核企业并执行审核或驳回，审核通过后企业进入可正常纳管状态。

第二条主线为检查与整改流程。区域管理员创建检查任务并分派给执法人员，执法人员执行检查并提交结果，系统生成检查记录；若结果不合格，则自动生成整改任务，企业提交整改内容，监管人员执行复核并形成闭环。

第三条主线为抽检与公示流程。区域管理员创建抽检任务，执法人员执行抽检并提交结果，系统保存抽检结果，区域管理员发布或下线结果，公众用户查询已发布的抽检信息。

第四条主线为投诉处理流程。公众用户提交投诉，区域管理员受理并指派给执法人员，执法人员处理后形成反馈结果，公众用户查看本人投诉详情和处理进度。

第五条主线为预警与统计流程。检查、抽检、整改和投诉等业务事件触发预警或重点监管联动，预警服务记录预警状态与处理日志，查询服务聚合多服务统计结果生成监管概览和预警统计信息。

### 3.2 系统功能需求

#### 3.2.1 功能需求总体划分

依据项目实际实现情况，系统功能需求可按角色和业务模块划分为用户与认证、系统管理员功能、区域管理员功能、执法人员功能、企业用户功能、公众用户功能以及统计查询功能七个部分。

#### 3.2.2 用户与认证功能需求

系统需要提供统一的用户认证能力，以支撑多角色用户安全访问平台。具体包括公众用户和企业用户注册功能、统一登录与退出功能、令牌校验与身份识别功能，以及基于角色的访问控制功能。该部分需求对应用户服务中的认证逻辑、网关中的统一鉴权逻辑和前端中的路由权限控制。

#### 3.2.3 系统管理员功能需求

系统管理员主要负责监管人员管理，因此其功能需求集中在账号与人员初始化层面。具体包括监管人员账号创建、监管人员信息查看和监管人员状态维护等功能。这些功能构成平台权限和角色初始化的基础。

#### 3.2.4 区域管理员功能需求

区域管理员是系统中最核心的监管管理角色，其功能需求覆盖企业备案审核、企业信息监管、检查任务管理、抽检任务管理、整改复核、投诉流转管理、公告管理、预警中心和统计概览等方面。该角色负责组织监管流程，是系统中监管管理业务的核心承担者。

#### 3.2.5 执法人员功能需求

执法人员承担监管执行任务，其功能需求主要围绕“执行”和“反馈”展开，包括辖区企业查看、检查任务执行、检查记录查看、抽检任务执行、抽检结果提交、投诉处理、整改跟进和个人预警处理等功能。

#### 3.2.6 企业用户功能需求

企业用户是被监管主体，其功能需求包括企业备案资料维护、产品档案管理、检查记录查看、整改任务处理和整改结果追踪等。企业端功能与监管人员端流程形成对应关系，共同完成企业纳管与问题整改闭环。

#### 3.2.7 公众用户功能需求

公众用户功能主要体现平台的信息公开与社会监督能力，包括公众注册登录、公告查询、企业公示查询、抽检结果查询、投诉提交和投诉跟踪等功能。公众端既承担信息服务作用，也承担问题反馈作用。

#### 3.2.8 统计查询功能需求

除具体业务处理外，系统还需要具备统计查询能力。包括监管概览查询功能、预警统计功能和多服务聚合查询功能，为监管看板和辅助决策提供基础支持。

### 3.3 系统非功能性需求

#### 3.3.1 性能需求

系统需要具备基本的并发处理与响应能力。结合代码可确认，项目通过 Redis 支持热点数据缓存，通过网关和部分接口实现访问限流，通过服务间调用和缓存机制控制统计查询开销。当前未发现专项性能压测结果，因此本节性能需求主要体现为设计与实现上的性能保障方向，而非具体量化指标。

#### 3.3.2 安全性需求

系统涉及用户身份信息、企业备案信息、投诉信息和监管处理记录，因此需要明确的安全控制要求。项目已通过 JWT、网关统一鉴权、角色访问控制、Redis 会话管理、关键接口限流和文件上传约束等机制对安全风险进行控制。由此可见，统一认证、角色隔离、会话安全和关键接口保护是本系统的重要非功能需求。

#### 3.3.3 可维护性需求

为降低后续维护难度，系统需要具备良好的可维护性。项目已按业务边界将用户、监管主数据、监管操作、投诉、预警和统计查询拆分为独立服务，后端统一采用 Spring Boot、Spring Cloud、MyBatis-Plus、MySQL 和 Redis 技术栈，前端统一采用 Vue 3 技术栈，并通过 `platform-common` 提供公共能力。这些实现均有助于提升系统维护便利性。

#### 3.3.4 可扩展性需求

食品安全监管业务存在持续演进需求，因此平台需要具备一定可扩展性。项目已经将投诉、预警和统计等能力独立拆分为服务，说明系统在新增业务场景时可基于现有服务继续增强或扩展。同时，前端路由化结构和后端控制器分模块暴露接口，也为后续页面与接口扩展保留了空间。

#### 3.3.5 可用性需求

系统需要支持多服务运行和多角色操作。项目采用前后端分离和微服务结构，各服务具备独立启动入口和独立端口；前端按角色划分功能入口，不同角色登录后进入对应工作台或首页。这说明系统在业务连续性和用户可操作性方面已有明确考虑。

#### 3.3.6 兼容性与部署环境需求

从配置可知，系统运行依赖 Java 17、Node.js、MySQL、Redis、Nacos 和 MinIO，支持前后端分离的本地联调环境。由于仓库中未提供 Docker、Docker Compose 或 Kubernetes 部署文件，因此当前部署环境需求主要面向本地与常规分服务部署方式。

### 3.4 可行性分析

#### 3.4.1 技术可行性

项目采用的 Spring Boot、Spring Cloud、Nacos、Gateway、OpenFeign、MyBatis-Plus、MySQL、Redis、JWT、MinIO 和 Vue 3 等技术均为成熟技术体系，能够满足多角色、多业务模块监管平台的开发需求。项目代码已经完整体现了微服务划分、统一网关、独立数据库、跨服务调用和前后端分离等核心实现路径，因此该技术路线在项目中具有明确可行性。

#### 3.4.2 操作可行性

前端已按角色划分独立页面入口，并在登录后根据用户角色进入对应工作空间；业务流程也符合监管工作逻辑，如企业备案后进入审核流程、检查发现问题后形成整改任务、抽检结果审核后对公众发布等。因此，从用户操作路径和界面组织方式看，系统具备较好的操作可行性。

#### 3.4.3 法律与合规可行性

项目围绕食品安全监管业务开展企业信息管理、抽检结果公示、投诉受理和风险预警等工作，业务方向本身具有明确公共治理价值。系统通过统一认证、角色控制、文件上传限制和访问限流等机制对部分安全风险进行控制，公开内容也主要集中于公告、企业公示和已发布抽检结果，内部处理信息则通过权限隔离。由此可见，系统具备基本的合规基础，但若进入更大规模应用，仍需结合具体法规对数据保护和业务制度进一步细化。

#### 3.4.4 社会可行性

食品安全问题与公众生活密切相关，监管平台建设不仅关系到内部监管效率，也关系到公众获取信息和参与监督的便利性。项目中已实现的公告查询、企业公示、抽检结果公示和投诉提交等功能，使公众能够获取公开信息并反馈问题，体现了平台在提升监管透明度和公众参与度方面的现实意义。因此，本项目具有较好的社会可行性。

## 第4章 系统设计

### 4.1 系统总体设计

#### 4.1.1 总体架构设计

根据第3章需求分析结果，本系统采用“前后端分离 + 网关统一接入 + 多业务微服务 + 按服务分库”的总体结构。前端由 `food-web` 提供统一浏览器访问入口，后端通过 `gateway-service` 对外暴露统一 API 入口，各业务能力按职责拆分到独立微服务中运行。该设计既满足了食品安全监管业务中多角色协同、业务链条长和模块边界清晰的要求，也与项目代码中的目录结构、服务启动类、网关路由和独立数据库脚本保持一致。

系统访问链路为：浏览器端页面发起请求，经网关完成跨域处理、令牌校验和路由转发后，再进入具体业务服务处理；各业务服务通过 Nacos 完成注册发现，并通过 OpenFeign 进行跨服务调用；数据最终分别写入各自服务对应的业务数据库。该结构使认证、企业主数据、监管操作、投诉处理、预警处理和统计查询形成既分工明确又可协同联动的服务体系。

#### 4.1.2 微服务模块划分设计

后端包含 `gateway-service`、`user-service`、`regulation-service`、`regulation-operation-service`、`complaint-service`、`warning-service`、`query-service` 和 `platform-common`。

`gateway-service` 作为统一入口，负责请求路由、JWT 校验、令牌内省、角色访问控制、跨域处理和部分接口限流。`user-service` 负责用户注册、登录、登出、令牌校验和角色绑定。`regulation-service` 负责企业备案、企业查询、产品档案、监管人员档案、行政区划、公告管理、文件预签名上传和预警代理访问。`regulation-operation-service` 负责检查任务、抽检任务、检查记录、抽检结果、整改任务与整改日志等流程型业务。`complaint-service` 负责公众投诉提交、投诉查询和投诉流转处理。`warning-service` 负责预警记录和预警处理日志。`query-service` 负责监管概览统计和预警统计查询。`platform-common` 作为公共模块提供统一返回体和公共组件支持。

#### 4.1.3 服务关系与信息流设计

系统中的服务协同关系由实际 Feign 调用定义。`regulation-service` 调用 `user-service` 和 `warning-service`；`regulation-operation-service` 调用 `regulation-service` 和 `warning-service`；`complaint-service` 调用 `regulation-service`；`query-service` 调用 `regulation-service`、`regulation-operation-service`、`complaint-service` 和 `warning-service`。据此可以归纳出三类主要信息流。

第一类是身份认证信息流。用户登录后由 `user-service` 签发 JWT，后续请求统一经过网关校验，再由网关调用内省接口确认令牌有效性，并将用户身份头透传给下游业务服务。

第二类是业务主数据流。企业、产品、监管人员和区域等主数据统一由 `regulation-service` 管理，其他服务在需要时通过内部接口读取对应数据，以保证多服务场景下业务对象的一致性。

第三类是监管事件流。检查不合格、抽检不合格、整改超时和投诉过载等事件触发预警或重点监管联动。监管操作服务通过 `warning_event_outbox` 表记录待投递事件，体现了基于出站事件表的可靠投递方案。

#### 4.1.4 前后端交互与权限设计

前端采用 Vue 3 单页应用结构，并通过 Vue Router 按角色组织页面入口。系统已划分公众用户、企业用户、系统管理员、区域管理员和执法人员五类路由空间。前端 API 客户端统一通过网关访问后端，前端不直接访问具体业务服务。

权限控制采用“前端路由限制 + 网关统一鉴权”的双层方式。前端通过 `requiresRole` 元数据控制页面访问，网关通过 `JwtAuthFilter` 对请求路径执行角色校验。需要特别说明的是，网关代码中对 `/api/warning/**` 做了直接阻断，监管人员端对预警能力的访问通过 `regulation-service` 中的预警代理接口完成，因此预警访问在设计上应表述为代理式访问，而不是前端直接访问预警服务。

### 4.2 数据库设计

#### 4.2.1 数据库总体设计

系统采用按服务分库的数据库设计方式。`user-service`、`regulation-service`、`regulation-operation-service`、`complaint-service`、`warning-service` 和 `query-service` 均具备独立的数据库脚本和数据源配置，符合微服务架构下“服务独立、数据独立”的设计原则。这种设计有利于将用户认证、监管基础数据、监管执行数据、投诉数据、预警数据和统计扩展数据分别管理，降低数据库层面的耦合度。

系统没有建立跨库外键约束，而是通过业务主键、服务接口和业务规则维护实体关联关系。例如企业信息在监管数据库中维护，而检查任务、抽检任务、投诉记录和预警记录分别在各自服务数据库中引用企业编号或业务编号。该方式与服务拆分策略一致。

#### 4.2.2 核心实体与关系设计

系统核心实体包括用户、角色、企业、产品、监管人员、区域、检查任务、检查记录、抽检任务、抽检结果、整改任务、投诉、投诉处理记录、预警记录和公告。

用户与角色之间通过 `sys_user`、`sys_role` 和 `sys_user_role` 构成多对多关系，用于支撑统一登录和多角色授权。企业实体以 `food_enterprise` 为核心，通过 `user_id` 对应企业账号，通过 `region_id` 和 `address_id` 对应区域和地址信息，并通过 `enterprise_profile_attachment` 关联备案附件。企业与产品之间是一对多关系，对应 `food_product.enterprise_id`。

监管人员实体以 `food_regulator` 为核心，通过 `user_id` 对应用户账号，并通过 `food_regulator_region` 与行政区建立关联。检查业务以 `inspection_task`、`inspection_record` 和 `inspection_item` 为核心，整改业务通过 `rectification_task` 和 `rectification_action_log` 与检查记录关联。抽检业务以 `sampling_task` 和 `sampling_result` 为核心。投诉业务以 `complaint` 和 `complaint_handle` 为核心。预警业务以 `warning_record` 和 `warning_process_log` 为核心。公告业务以 `public_bulletin` 为核心。

#### 4.2.3 主要数据表设计

用户认证相关表主要包括 `sys_user`、`sys_role` 和 `sys_user_role`，用于保存用户、角色及用户角色绑定信息。企业监管基础数据表主要包括 `food_enterprise`、`enterprise_profile_attachment`、`food_product`、`food_regulator`、`food_regulator_region`、`enterprise_key_reason` 和 `public_bulletin`。其中，`food_enterprise` 中的 `approval_status`、`approved_by` 和 `approved_time` 支撑备案审核流程；`food_product` 支撑企业产品档案管理；`food_regulator` 和 `food_regulator_region` 支撑监管人员档案与辖区配置；`enterprise_key_reason` 用于记录企业被纳入重点监管原因；`public_bulletin` 用于支撑公告草稿、发布和下线管理。

监管执行数据表主要包括 `inspection_task`、`inspection_record`、`inspection_item`、`sampling_task`、`sampling_result`、`rectification_task`、`rectification_action_log` 和 `warning_event_outbox`。其中，`sampling_result.public_status` 支撑抽检结果公示状态控制，`warning_event_outbox` 用于实现监管事件可靠投递。

投诉数据表主要包括 `complaint` 和 `complaint_handle`。预警数据表主要包括 `warning_rule`、`warning_record` 和 `warning_process_log`。统计扩展表包括 `stat_enterprise`、`stat_inspection` 和 `stat_complaint`，根据数据库脚本注释，这些表属于后续统计能力扩展预留，不作为当前查询服务的真实数据来源。

#### 4.2.4 数据设计与业务流程对应关系

企业备案流程由 `food_enterprise` 与 `enterprise_profile_attachment` 支撑，产品档案流程由 `food_product` 支撑，检查与整改流程由 `inspection_task`、`inspection_record`、`inspection_item`、`rectification_task` 和 `rectification_action_log` 支撑，抽检与公示流程由 `sampling_task` 和 `sampling_result` 支撑，投诉流程由 `complaint` 和 `complaint_handle` 支撑，预警流程由 `warning_record` 和 `warning_process_log` 支撑，公告发布流程由 `public_bulletin` 支撑。由此可见，数据库设计与第3章归纳出的业务主线保持一致。

### 4.3 系统功能设计

#### 4.3.1 用户与认证模块设计

该模块设计目标是为五类用户提供统一登录入口，并保证页面访问与接口访问的一致控制。输入包括注册信息、登录凭证和令牌；处理逻辑包括用户注册、密码校验、令牌签发、令牌失效、角色绑定和网关内省校验；输出为认证结果、用户身份信息和授权后的访问许可。模块关系上，`user-service` 负责认证核心能力，`gateway-service` 负责请求入口拦截与角色校验，前端路由负责页面级访问约束。

#### 4.3.2 企业备案与产品档案模块设计

该模块设计目标是完成企业主数据建档、备案审核和产品档案维护。输入包括企业基础信息、附件信息和产品信息；处理逻辑包括企业提交备案、区域管理员审核备案、企业查询自身档案、监管人员端查询企业信息以及企业维护产品档案；输出包括企业档案状态、审核结果和产品档案数据。该模块为后续检查、抽检、投诉和统计模块提供主数据支撑。

#### 4.3.3 检查与抽检模块设计

该模块设计目标是支持监管部门围绕企业开展任务派发、现场执行和结果留痕。检查子模块的输入包括任务标题、企业对象、辖区信息、执法人员和检查结果；处理逻辑包括任务创建、任务分派、执法执行、检查记录生成和记录查询；输出为检查任务状态和检查记录。抽检子模块的输入包括抽检企业、抽检产品、执行人员和抽检结论；处理逻辑包括任务创建、任务分派、结果录入、结果发布或下线；输出为抽检任务状态、抽检结论和公众可见结果。

#### 4.3.4 整改管理模块设计

该模块设计目标是将检查发现的问题转化为可跟踪、可复核的整改流程。输入包括检查记录、不合格问题描述、企业整改进展、整改附件和监管复核意见；处理逻辑包括依据检查记录生成整改任务、企业提交整改、监管人员查看整改详情与动作日志、执行复核确认或退回；输出为整改任务状态、整改动作日志和整改闭环结果。

#### 4.3.5 投诉处理模块设计

该模块设计目标是为公众监督提供结构化入口，并将投诉数据纳入监管处理流程。输入包括投诉人信息、联系方式、被投诉企业、投诉内容和图片材料；处理逻辑包括投诉提交、投诉查询、区域管理员受理与分派、执法人员处理、结果反馈和驳回；输出为投诉单状态、处理摘要和处理记录。该模块既服务公众用户，也服务监管人员，并向预警与统计模块提供输入数据。

#### 4.3.6 公告公示与预警模块设计

公告公示子模块的设计目标是实现监管信息公开。输入包括公告标题、类别和内容，或经发布的企业与抽检结果信息；处理逻辑包括公告创建、编辑、发布、下线，以及公众端公告、企业公示和抽检结果查询；输出为公众可见的公开信息。

预警子模块的设计目标是将投诉、整改、抽检等业务异常统一纳入预警记录和处置流程。输入包括预警事件、业务对象标识、预警类型、责任人和处理意见；处理逻辑包括预警事件写入、预警记录生成、分派、处理、解决和日志记录；输出为预警状态、预警轨迹和预警统计结果。由于网关禁止前端直接访问 `warning-service`，监管人员端预警访问在设计上采用 `regulation-service` 代理 `warning-service` 的方式实现。

#### 4.3.7 统计查询模块设计

该模块设计目标是为监管人员端提供跨服务的汇总视图。输入包括当前登录用户角色、辖区范围和查询参数；处理逻辑包括调用企业、监管操作、投诉和预警相关服务，聚合形成监管概览与预警统计结果；输出包括监管概览、预警概览、预警趋势、类型分布和处理效率统计。该模块的设计重点在于服务层聚合，而不是依赖查询服务自身预留统计表。

### 4.4 系统界面设计

#### 4.4.1 界面设计原则

从前端代码可确认，系统界面设计遵循按角色组织功能入口、按业务流程组织页面结构的原则。系统未单独给出完整视觉规范文档，因此本节不对颜色、字体和动画等视觉细节作超出代码证据的描述，仅依据实际路由、页面组件和角色分组说明界面组织方式。需要说明的是，部分系统管理员页面中的审计日志、筛选器和权限等级展示仍存在占位交互或待接入提示，因此本节仅将其作为界面结构的一部分进行说明，不将其写为已完整落地的后端能力。

#### 4.4.2 主要页面结构设计

公众端页面主要包括首页、公告列表与详情、企业公示、抽检结果、我要投诉、投诉提交成功、我的投诉和投诉详情等页面。企业端页面主要包括企业工作台、企业备案、备案详情、产品档案、检查记录、整改任务、整改详情和整改提交等页面。系统管理员端页面主要包括工作台、监管人员列表、添加监管人员、人员详情、编辑人员和状态切换确认等页面。区域管理员端页面主要包括监管概览、企业管理、备案审核、检查任务、抽检任务、整改复核、投诉流转、预警中心、公告管理和统计页面。执法人员端页面主要包括企业监管、我的任务、检查任务详情、检查结果提交、抽检任务、抽检结果提交、投诉处理、整改跟进、个人预警和统计页面。

#### 4.4.3 路由与导航设计

前端使用 Vue Router 进行统一路由管理，并通过路由守卫控制登录态恢复和角色权限校验。系统根据不同角色设定默认进入页面：系统管理员进入管理工作台，企业用户进入企业工作台，公众用户进入公众首页，区域管理员进入监管概览页，执法人员进入企业监管页。该设计与后端统一认证设计相配合，使用户登录后能够进入与自身职责匹配的功能空间。

## 第5章 系统实现

### 5.1 系统实现概述

#### 5.1.1 开发环境与运行环境

根据父工程 `pom.xml` 和前端 `package.json` 配置，本项目后端采用 Java 17，基于 Spring Boot 3.2.5、Spring Cloud 2023.0.1 和 Spring Cloud Alibaba 2023.0.1.0 实现微服务开发；前端采用 Vue 3、Vue Router 4 和 Vite 5 构建单页应用。后端工程通过 Maven 管理依赖与构建，前端工程通过 npm 脚本完成开发与构建。

系统本地运行至少需要 MySQL、Redis 和 Nacos 环境。其中，MySQL 用于各服务独立业务数据存储，Redis 用于会话、缓存、限流和分布式锁支持，Nacos 用于服务注册发现与配置管理。`regulation-service` 还额外依赖 MinIO 用于生成文件预签名上传地址。各服务配置文件中同时存在 Sentinel 相关参数，说明系统保留了流量治理接入能力；但更细粒度的流控规则主要依赖运行时配置，因此本文不将具体规则内容写成固定实现结果。

#### 5.1.2 主要开发工具与工程组织

系统后端采用 Maven 多模块工程组织方式，父工程统一管理依赖版本，子模块分别对应网关服务、用户服务、监管基础服务、监管操作服务、投诉服务、统计查询服务、预警服务和公共模块。前端以 `food-web` 目录独立存在，与后端形成前后端分离结构。

从代码结构看，后端各服务均采用较清晰的分层组织方式，包括控制器、服务、数据访问、实体对象、数据传输对象和返回对象等部分。前端则按角色和业务页面划分视图目录，并通过 `src/api` 统一封装接口调用，通过 `src/router` 管理页面路由，通过 `src/session` 管理本地会话恢复逻辑。

#### 5.1.3 项目结构说明与启动方式

项目启动入口由各服务的 `*Application.java` 提供，`gateway-service`、`user-service`、`regulation-service`、`regulation-operation-service`、`complaint-service`、`query-service` 和 `warning-service` 均定义了独立 Spring Boot 启动类。部分服务启用了 `@EnableFeignClients`，`regulation-service`、`regulation-operation-service` 和 `warning-service` 还启用了 `@EnableScheduling` 用于整改 SLA 与预警事件重试等定时任务处理。

前端 `food-web` 通过 `npm run dev` 启动 Vite 开发服务，通过 `npm run build` 生成生产构建文件。后端各服务可分别以 Spring Boot 应用方式独立启动，默认端口分别为网关 8080、用户服务 8081、监管服务 8082、查询服务 8083、预警服务 8084、投诉服务 8085、监管操作服务 8086。网关配置中已对前端本地开发地址 `http://localhost:5173` 和 `http://localhost:5174` 开启跨域支持，因此项目具备本地前后端联调运行条件。项目中未发现 Docker、Docker Compose 或 Kubernetes 部署文件，因此本章仅将启动方式表述为本地多服务独立启动和常规分服务部署。

### 5.2 功能模块实现

#### 5.2.1 登录认证与权限控制实现

统一认证是本系统实现层最基础、也是最关键的模块之一。该模块的实现目标是完成多角色用户登录、令牌签发、令牌校验、会话失效和接口权限控制。

在后端实现中，`user-service` 的 `AuthController` 提供登录、登出、校验和内省接口，`AuthServiceImpl` 负责令牌校验与内省逻辑。其实现不仅执行 JWT 签名验证，还会进一步检查 Redis 黑名单、查询缓存的内省结果，并在必要时回源数据库读取用户、角色和状态信息，再将结果缓存回 Redis。这样既保留了 JWT 的无状态特性，又通过 Redis 会话缓存和黑名单机制实现了令牌失效控制。

在网关实现中，`gateway-service` 的 `JwtAuthFilter` 负责统一拦截认证请求。过滤器先放行登录、注册和健康检查等白名单请求，再对其余请求提取 `Authorization` 头中的令牌并校验签名。签名通过后，网关调用 `http://user-service/api/auth/introspect` 获取当前用户是否有效、用户类型及角色列表，再依据接口路径与角色规则进行访问控制。认证通过后，网关将 `X-User-Id`、`X-Username`、`X-User-Type` 和 `X-User-Roles` 等头信息传递给下游业务服务，为业务服务提供统一身份上下文。

该实现体现了两个特点。第一，权限控制不是单点实现，而是“用户服务签发与内省 + 网关统一鉴权”的组合方式。第二，权限控制规则围绕真实业务路径配置，例如公众用户可以访问投诉提交和公开查询接口，企业用户可访问备案、产品和整改相关接口，监管人员则可访问监管、操作和统计接口。

在前端实现中，`food-web/src/api/auth.js` 对登录、注册、校验、内省和登出接口进行了统一封装，`food-web/src/session/authRuntime.js` 实现了浏览器端会话恢复逻辑。页面刷新或路由切换时，前端会先读取本地保存的会话，再调用 `verify` 和 `introspect` 接口确认令牌是否仍然有效，并用返回的身份信息恢复当前登录状态。`food-web/src/router/index.js` 中的路由守卫则根据 `requiresRole` 元数据进一步限制不同角色访问不同页面。

#### 5.2.2 网关路由与服务调用实现

网关与服务调用模块的实现目标是将分散的微服务对外组织成统一访问入口，并在服务间建立清晰的协作关系。

在网关路由实现上，`gateway-service/src/main/resources/application.yml` 中使用 `lb://服务名` 的方式将 `/api/auth/**`、`/api/users/**`、`/api/regulation/**`、`/api/regulation-operation/**`、`/api/complaints/**`、`/api/query/**` 和 `/api/warning/**` 等路径分别转发到对应服务。由于网关同时开启了服务发现定位和全局跨域配置，因此前端在开发阶段只需访问网关地址，而不需要直接感知各服务端口。

在服务调用实现上，项目使用 OpenFeign 组织跨服务协作。`regulation-service` 通过 Feign 调用 `user-service` 和 `warning-service`，`regulation-operation-service` 调用 `regulation-service` 和 `warning-service`，`complaint-service` 调用 `regulation-service`，`query-service` 则聚合调用多个服务的内部统计接口。与单体系统中直接调用本地业务类相比，这种实现方式更符合项目的微服务拆分结构。

该模块中较有代表性的实现细节，是系统对预警访问采取了代理式路径控制。虽然网关配置中存在 `/api/warning/**` 路由，但 `JwtAuthFilter` 明确禁止前端直接访问该路径；监管人员端访问预警时，实际调用的是 `regulation-service` 中的 `WarningProxyController` 和 `WarningProxyServiceImpl`。代理服务会根据当前监管人员身份构造辖区或责任人过滤条件，再转发给 `warning-service`，从而避免前端绕过监管域边界直接访问预警服务。

#### 5.2.3 企业备案与基础监管数据实现

企业备案与基础监管数据模块是监管业务的主数据基础。其实现目标是完成企业档案建档、备案审核、产品档案维护、监管人员档案维护以及公开查询。

在企业备案实现中，`EnterpriseProfileController` 对外提供企业提交备案、查询备案、查看待审核企业、审核通过、审核驳回、批量审核和删除等接口。控制器通过 `JwtUserResolver` 解析当前用户身份，再根据企业用户或监管人员角色进行访问限制，随后调用 `EnterpriseProfileService` 完成具体业务处理。

`EnterpriseProfileServiceImpl` 的实现体现了较完整的业务落地过程。企业提交备案时，服务会校验区域信息、写入或更新地址信息、保存企业基础字段，并将审核状态统一重置为 `PENDING`；若企业存在附件，则通过附件表保存附件信息；最后清理企业主数据缓存和公开缓存，保证后续查询获取到更新后的数据。审核通过或驳回逻辑则围绕 `approval_status`、`approved_by`、`approved_time` 和审核意见等字段展开，体现了主数据与审核状态在同一业务服务中集中管理的实现思路。

在产品档案实现中，`ProductController` 提供企业用户的产品查询、新增、修改，以及监管人员端查看企业产品的接口。由于抽检任务依赖产品档案，因此产品模块与后续监管操作模块形成了直接联动。

在监管人员数据实现中，系统管理员通过用户服务创建监管账号，监管服务再通过 `RegulatorProfileController` 完成监管人员档案维护和辖区配置，实现了“账号创建”与“监管档案维护”在不同服务内的协同。

在前端实现上，企业端提供备案总览、备案详情、产品列表、新增产品、编辑产品和产品详情等页面；监管人员端提供备案审核、企业管理和企业详情页面。页面层通过 `food-web/src/api/regulation.js` 完成与后端接口的联调。

#### 5.2.4 检查、抽检与整改闭环实现

检查、抽检与整改模块构成了本项目最能体现食品安全监管业务特色的实现链路。其实现目标是把监管任务从创建、分派、执行、结果记录一直推进到整改复核和公开结果展示，形成完整闭环。

在检查任务实现中，`InspectionTaskController` 提供任务创建、分派、分页查询、执法人员我的任务、任务启动、结果提交和任务关闭等接口。控制器通过 `RequestIdentityResolver` 获取当前请求身份，并将角色限制在监管人员范围内，再调用 `InspectionTaskService` 完成业务处理。

`InspectionTaskServiceImpl` 是该链路的核心实现类。区域管理员创建任务时，服务先通过 `OperationMasterDataSupport` 校验当前监管人员身份、验证目标企业已通过备案审核，并检查企业是否在当前监管人员辖区内；任务创建后写入 `inspection_task` 表。任务分派时，服务进一步校验被分派执法人员是否属于可分派辖区。执法人员提交结果时，系统在事务中写入 `inspection_record` 和多条 `inspection_item`，如果检查结果或检查项存在不合格情况，则立即调用整改服务创建整改任务。

整改实现由 `RectificationController` 和 `RectificationServiceImpl` 完成。服务在检查不合格后自动生成整改任务，设置企业提交截止时间；企业端提交整改时，服务更新整改进展、变更状态并写入整改动作日志；监管人员复核时，可执行确认或退回重改。服务内部通过 `OperationLockSupport` 对提交和复核操作加锁，避免并发场景下重复处理。

抽检实现由 `SamplingTaskController`、`SamplingResultManageController` 和 `SamplingTaskServiceImpl` 共同完成。区域管理员创建抽检任务时，系统校验企业处于已审核状态、产品为该企业有效产品；执法人员提交抽检结果后，服务写入 `sampling_result` 表，并将结果初始设置为 `DRAFT`；只有区域管理员执行发布操作后，结果才进入公众查询范围。

该模块中还有一个重要实现细节，即业务异常与预警事件联动。无论是检查连续不合格还是抽检不合格，监管操作服务都会构造预警事件并通过 `WarningEventOutboxService` 记录到 `warning_event_outbox` 表。后续由 `WarningEventOutboxRetryScheduler` 定时扫描待投递事件，并调用预警服务内部接口进行重试投递。该实现说明项目未使用消息队列，而是采用了基于出站事件表和定时重试的可靠事件投递机制。

在前端方面，区域管理员端实现了任务派发、检查记录、抽检任务和整改复核页面；执法人员端实现了我的任务、检查结果提交、抽检结果提交和整改跟进页面；企业端实现了整改任务查看、整改详情和整改提交页面。这说明该监管闭环不仅在后端实现了接口与服务逻辑，也在前端完成了交互落地。

#### 5.2.5 投诉处理与监管协同实现

投诉模块体现了平台面向公众监督的实现能力。其实现目标是使公众投诉能够进入监管内部流转，并形成可查询、可反馈的处理结果。

在公众端实现中，`PublicComplaintController` 提供投诉提交、我的投诉列表和投诉详情接口，`ComplaintCommandService` 中的 `submitPublic` 方法先校验被投诉企业是否存在，再生成投诉单号、写入投诉人信息、投诉内容、图片地址和投诉状态，并返回可供前端展示的投诉跟踪结果。

在监管人员端实现中，`RegulatorComplaintController` 提供投诉分页查询、详情查看、受理、分派、开始处理、办结和驳回等接口。核心业务逻辑集中在 `ComplaintCommandService` 中。该类对投诉处理流程进行了较完整的状态控制：区域管理员受理投诉后将状态转为 `PENDING`，再由区域管理员将投诉分派给执法人员，执法人员启动处理后状态转为 `PROCESSING`，提交处理结果后写入单条处理记录并将投诉状态转为 `FEEDBACKED`，如不予受理，则由区域管理员执行驳回并记录驳回原因。

该模块还有一个较有价值的监管联动实现，即在投诉受理后，系统会统计一定时间窗口内企业被受理投诉的数量；若达到阈值，则调用监管基础服务将企业自动标记为重点监管对象。这说明投诉模块并不是孤立存在，而是能够将社会监督数据回流到监管主数据管理中。

在前端方面，公众端实现了我要投诉、提交成功、我的投诉和投诉详情页面；监管人员端实现了投诉流转列表和投诉详情页面。页面调用主要集中在 `food-web/src/api/complaint.js`，前后端交互链路完整。

#### 5.2.6 统计查询与预警代理实现

统计查询模块的实现目标是向监管人员端提供跨服务聚合后的概览结果，而不是依赖单一业务表直接出报表。

在后端实现中，`SupervisionOverviewController` 和 `WarningStatsController` 对外提供监管概览、预警概览、趋势、类型分布和处置效率等接口。其核心业务逻辑分别在 `SupervisionOverviewQueryServiceImpl` 和 `WarningStatsQueryServiceImpl` 中实现。以监管概览为例，服务先构造查询范围，再分别调用企业统计、监管操作统计、投诉统计和预警统计接口，最终组合成统一的概览结果返回给前端。同时，查询服务还利用 `QueryRedisCacheSupport` 为统计结果生成作用域指纹缓存键，以降低重复聚合查询开销。

该实现说明项目中的统计查询并不是通过 `query-service` 自身统计表直接读取完成，而是通过内部接口聚合形成。数据库脚本中的 `stat_enterprise`、`stat_inspection` 和 `stat_complaint` 在当前阶段仍属于扩展预留设计，并未进入主运行链路。

预警访问实现则体现为“网关禁直连、监管服务做代理”的模式。监管人员端页面调用 `regulation-service` 中的预警代理接口，代理服务根据当前监管人员身份补充辖区或责任人过滤条件，再转发至 `warning-service`。这种实现使预警能力在系统中以监管业务的一部分呈现，而不是作为前端直接访问的独立域。

在前端方面，区域管理员和执法人员均实现了统计页面，区域管理员和执法人员还分别实现了预警列表与预警详情页面。对应接口主要分布在 `food-web/src/api/regulation.js` 中，包括预警查询、预警处理以及监管概览和预警统计查询接口。

#### 6.2.3 测试结果分析

从现有自动化测试代码与阶段性验收结果看，系统在以下方面达到了预期目标。第一，统一认证与权限控制机制能够支撑多角色访问隔离。第二，监管核心业务链路已经具备可验证的闭环特征，检查、整改、抽检、投诉和预警联动均可在测试中找到直接证据。第三，跨服务聚合查询功能具备基本正确性，监管概览和预警统计接口能够按辖区范围和查询条件输出预期结果。第四，系统具备前后端联调和交付的基础条件，前端构建通过、后端多模块联合测试通过。

需要如实指出的是，当前测试仍存在一定边界。项目中未发现完整浏览器级录屏联调记录，未发现专项性能压测数据，也未发现覆盖全部页面交互的前端自动化测试。因此，本系统当前更适合表述为“已完成关键功能、接口与业务链路验证”，而不应表述为“已完成全面性能与全场景自动化测试”。

## 第7章 总结与展望

### 7.1 工作总结

本文围绕“基于微服务的食品安全监管平台”这一课题，结合项目代码、配置文件、数据库脚本、前端页面、接口调用链和测试材料，对系统的需求分析、架构设计、功能实现与测试验证进行了系统整理与论述。论文完成的主要工作，是在真实工程实现基础上形成一套较完整的软件开发研究型毕业设计成果，使系统从需求、设计、实现到测试之间具备较清晰的对应关系。

从系统建设结果看，项目已经完成了食品安全监管业务中的多条核心主线。系统实现了统一登录认证与权限控制机制，实现了企业备案、产品档案、监管人员档案、公告管理和公开查询等基础数据能力，实现了检查任务、检查记录、整改任务、抽检任务、抽检结果、投诉处理和预警处置等核心监管流程，也实现了公众公告查询、企业公示、抽检结果公示和公众投诉等功能，并通过监管概览与预警统计查询为监管人员提供基础的数据支持。

在架构层面，本项目的微服务设计并非停留在概念层面，而是围绕业务边界完成了较明确的服务划分。网关服务、用户服务、监管基础服务、监管操作服务、投诉服务、预警服务和查询服务分别承担不同职责，并通过 Nacos、OpenFeign、Redis 和统一网关机制协同工作。尤其是预警代理访问、出站事件表重试和监管概览聚合查询等实现方式，都体现了微服务架构服务于业务落地的实际意义。

从食品安全监管业务价值看，本系统较好地体现了“企业纳管、过程监管、问题整改、社会监督和数据辅助决策”相结合的建设思路。企业备案与产品档案帮助监管部门建立被监管对象基础底数，检查、整改和抽检功能支撑监管执行闭环，投诉处理和公开公示增强了公众参与和信息透明，预警与统计功能则为监管重点识别和辅助分析提供了数据支持。总体而言，本课题已在既定题目范围内完成了一个可运行、可说明、可验证的食品安全监管平台原型系统。

### 7.2 未来展望

虽然本系统已经完成了毕业设计要求范围内的主要工作，但从工程完善程度和后续应用角度看，仍存在继续优化的空间。

第一，可以继续完善现有业务链路中的细节能力。在当前实现中，企业备案、检查整改、抽检、公示、投诉和预警已经形成主线，但系统管理员侧的审计日志、企业侧的部分设置能力、产品档案的个别管理操作以及部分页面中的占位交互仍未与完整后端能力闭合。后续可在不扩张业务边界的前提下，围绕现有角色与流程补齐这些细节。

第二，可以进一步提升系统的安全与治理能力。当前系统已经实现 JWT、网关鉴权、角色隔离、Redis 会话缓存和部分接口限流，但默认密钥、内部令牌和部分运行配置的规范化程度仍有提升空间。后续可以围绕配置外置化、敏感配置治理、网关严格模式、细粒度归属校验和上传资源安全控制等方向继续增强系统安全性。

第三，可以继续增强测试与交付验证能力。当前项目已经具备后端自动化测试基础，并完成了阶段性联合测试和前端构建验证，但尚未形成完整浏览器级联调记录，也未覆盖全部前端页面交互。后续可围绕登录认证、企业备案、检查整改、抽检公示、投诉闭环和预警处置等关键路径补充更完善的手工验收记录或自动化测试。

第四，可以逐步提升统计分析与数据支撑能力。当前 `query-service` 主要采用聚合调用方式组织监管概览和预警统计，数据库中的 `stat_enterprise`、`stat_inspection` 和 `stat_complaint` 等表仍处于扩展预留状态。后续若业务场景进一步稳定，可以在保持当前轻量聚合结构基础上，逐步完善统计数据沉淀、主题分析和趋势展示能力。

第五，可以完善系统部署与运维支撑能力。当前项目具备本地分服务启动与前后端联调条件，但尚未形成容器化部署、统一持续集成流水线和完整运行说明。后续可继续补充更规范的部署文档、环境说明、配置模板和服务启动顺序，在此基础上再逐步推进更标准化的部署和运维方案。

综上所述，本课题已经完成了食品安全监管平台的核心功能实现和论文写作基础工作，后续改进方向也较为明确。未来若继续围绕现有业务边界开展迭代，在安全治理、测试验证、统计分析和部署规范等方面逐步完善，系统将具备更好的工程质量和更强的实际应用价值。
