# 论文定性表述量化改写清单

> 适用对象：`docs/thesis/论文初稿 - 副本.md`
>
> 目标：按现有论文内容，集中处理“正常、符合预期、较稳定、可运行”等空泛表述，将其改写为可量化、可复核、可对应项目代码事实的写法。

---

## 1. 使用原则

本清单不是逐句校对稿，而是按“高风险段落”列出必须处理的位置。处理原则如下：

1. 删除纯结论、无证据支撑的句子。
2. 将“符合预期/正常返回”改成“执行次数 + 成功次数 + 成功率 + 关键结果”。
3. 将“稳定/可运行”改成“响应时间统计 + 连续调用结果 + 构建/测试结果”。
4. 将“具备性能保障”改成“限流阈值、缓存 TTL、重试参数、锁租约”等代码中可确认的参数。
5. 不虚构未完成的压测结论，不把“设计参数”直接写成“实测性能结果”。

---

## 2. 先统一替换的写法模板

以下词语原则上不要单独出现，必须跟具体数字一起出现：

| 原写法 | 建议改法 |
|---|---|
| 符合预期 | 执行 `N` 次，其中成功 `M` 次，成功率 `M/N` |
| 正常返回 | 平均响应时间 `x ms`，最大响应时间 `y ms`，成功率 `z%` |
| 较稳定 | 在连续 `N` 次调用或 `N` 轮测试中未出现异常，成功率 `z%` |
| 能够完成 | 完成 `A->B->C` 共 `n` 个状态流转，最终状态与预期一致 |
| 基本可运行 | 前端生产构建通过；后端核心链路完成 `N` 项验证；关键接口成功率 `z%` |
| 页面展示正常 | 页面对应接口返回 `N` 次成功，字段完整率 `z%`，页面渲染无报错 |

建议统一采用下面 4 类结果句式：

1. 功能类：
   `对某功能执行 N 组用例，其中通过 M 组，通过率为 xx.xx%。`

2. 接口类：
   `对某接口连续调用 N 次，平均响应时间为 x ms，P95 为 y ms，成功率为 z%。`

3. 并发/控制类：
   `对同一业务对象并发发起 N 次请求，最终成功写入 1 条记录，其余 N-1 次被锁控或状态校验拦截。`

4. 恢复/一致性类：
   `在下游服务不可用持续 T 秒的条件下，Outbox 事件共重试 R 次后恢复投递成功，总恢复时间为 S 秒。`

## 4. 摘要部分

### 4.1 位置

- `论文初稿 - 副本.md:59`

### 4.2 当前问题

原文核心表述：

> 测试结果表明，系统能够较稳定地完成主要业务处理，具备食品安全监管平台原型系统的基本功能正确性和可运行性。

问题：

1. “较稳定”没有标准。
2. “基本功能正确性”没有通过率。
3. “可运行性”没有量化证据。

### 4.3 处理方式

- 删除“较稳定地”“基本”等形容词性结论。
- 换成“测试覆盖范围 + 核心结果类型 + 是否完成构建/验证”。

### 4.4 建议改写方向

不要在摘要里堆太多细节，但至少加 3 个量化锚点：

1. 测试资产规模：如测试类数、测试用例数。
2. 验证对象规模：如覆盖登录认证、备案审核、检查整改、投诉处理、统计查询等几类核心链路。
3. 构建/运行结果：前端生产构建是否通过；核心接口是否完成连续调用验证。

### 4.5 建议替换句式

可改为：

> 项目围绕统一认证、企业备案、检查整改、投诉处理、预警统计等核心模块开展验证。结合仓库中现有自动化测试资产、前端生产构建结果和核心接口运行数据，系统在原型范围内完成了主要业务链路验证，具备支撑多角色食品安全监管场景演示与原型论证的基础条件。

注意：摘要中如果没有最终实测数据，不要直接写“成功率 100%”。摘要只写“结合运行数据”，正文再展开。
