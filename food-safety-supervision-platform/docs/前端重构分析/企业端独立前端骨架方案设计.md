
# 企业端独立前端骨架方案设计

更新时间：2026-04-10

## 1. 本次目标

基于现有扫描结果，先完成企业端“独立前端骨架方案设计”，暂不编写业务代码。

本次方案设计目标：

- 新建一个与 `food-web` 平行存在的企业端独立前端项目
- 采用 `Vue 3 + Vite + vue-router`
- 先按 Stitch 原型的信息架构拆页面，不继续沿用 `food-web` 中 `EnterpriseProfileView.vue` 的单组件分栏切换方式
- 优先复用现有项目中的命名方式、API 模块边界和环境变量约定

本次明确不做：

- 不改 `food-web`
- 不实现接口调用逻辑
- 不实现登录后的跨项目跳转逻辑
- 不接入真实状态持久化

## 2. 设计结论

建议新增独立企业端前端目录：

- `food-enterprise-web/`

建议理由：

- 与现有 `food-web/` 平行，避免影响旧前端
- 与已存在的 `food-auth-web/` 命名风格一致
- 便于后续认证前端、企业前端分别独立演进

建议技术栈：

- `Vue 3`
- `Vite`
- `vue-router`
- 原生 `fetch`

说明：

- 这是基于现有 `food-auth-web` 和 `food-web` 的实际实现方式做出的延续性设计建议
- 当前不建议第一步就引入 `Pinia`、`Vuex` 或 `axios`

## 3. 第一阶段应落地的最小页面骨架

第一阶段建议只落地 4 个一级页面，对齐企业端原型的主导航：

- 工作台
- 企业备案
- 产品档案
- 整改任务

说明：

- `检查记录` 虽然也是一级导航，但从原型和现有实现看，它更多依赖列表筛选、详情展示和整改关联；如果第一阶段要更稳，可以放入第一批骨架，也可以与产品档案并列进入第二批
- 如果严格按原型一级导航完整性落地，建议第一阶段仍然包含 `检查记录`

因此更推荐的第一阶段页面集合是：

- 工作台
- 企业备案
- 产品档案
- 检查记录
- 整改任务

这些页面第一阶段只需要完成：

- 路由可访问
- 公共布局可复用
- 左侧导航可切换
- 页面标题、说明文案、空态占位可见

## 4. 路由设计建议

### 4.1 第一阶段正式路由

建议先定义以下正式路由：

- `/`：重定向到 `/dashboard`
- `/dashboard`：企业工作台
- `/profile`：企业备案
- `/products`：产品档案
- `/inspections`：检查记录
- `/rectifications`：整改任务
- `/:pathMatch(.*)*`：兜底重定向到 `/dashboard`

### 4.2 第二阶段预留路由

待第一阶段骨架稳定后，再补以下详情页和操作页：

- `/profile/detail`：企业备案详情
- `/products/new`：新增产品档案
- `/products/:id`：产品详情
- `/products/:id/edit`：编辑产品
- `/inspections/:id`：检查记录详情
- `/rectifications/:id`：整改任务详情
- `/rectifications/:id/submit`：提交整改
- `/rectifications/:id/success`：整改提交成功

说明：

- 以上路径是方案建议，不是当前仓库已存在的事实
- 这些路由名称是基于企业端原型页面关系和 `food-web` 现有能力做出的最小拆分

## 7. API 模块复用策略

建议直接复用 `food-web/src/api/` 中已有的模块边界和文件命名，不要重新发明新的接口分类。

建议保留的 API 文件名：

- `src/api/client.js`
- `src/api/regulation.js`
- `src/api/regulationOperation.js`
- `src/api/file.js`

建议原因：

- 与旧项目一致，迁移成本最低
- 企业端现有能力本来就主要落在这三个模块中
- 后续从 `food-web` 迁移具体接口函数时，不需要重新命名

建议在第一阶段骨架中预留的接口函数分组如下：

### `regulation.js`

- `fetchEnterpriseProfile`
- `submitEnterpriseProfile`
- `fetchRegions`
- `fetchMyProducts`
- `createProduct`
- `updateProduct`

### `regulationOperation.js`

- `fetchEnterpriseInspectionRecords`
- `fetchEnterpriseInspectionRecordDetail`
- `fetchMyRectifications`
- `fetchRectificationDetail`
- `fetchRectificationActions`
- `submitMyRectification`

### `file.js`

- `presignUpload`

说明：

- 第一阶段不必真正接入这些接口
- 但建议骨架中的模块名称和未来导出函数名称提前按旧项目约定留好

## 8. 状态管理策略

第一阶段建议不要引入独立状态库。

建议采用：

- 路由负责页面切换
- 顶层布局负责导航高亮
- 各页面内部使用 `ref` / `reactive` 维护本页占位状态

原因：

- 当前 `food-web` 也没有 `Pinia` 或 `Vuex`
- 第一阶段只是骨架搭建，不值得先引入全局状态复杂度
- 等到真正接接口、处理跨页缓存和权限状态时，再决定是否需要 store

## 9. 布局与组件拆分建议

建议不要把企业端所有页面都做成一个巨型 `EnterpriseProfileView.vue`。

建议拆分方式如下：

### 9.1 布局层

- `EnterpriseShell.vue`
  - 负责整体页面框架
  - 负责左侧导航和顶部区域插槽
- `EnterpriseSidebar.vue`
  - 负责主导航
  - 只处理导航展示与路由跳转
- `EnterpriseTopbar.vue`
  - 负责标题区、搜索占位、用户信息占位

### 9.2 通用层

- `StatusAlert.vue`
  - 复用状态提示
- `EmptyState.vue`
  - 复用空列表或“暂未接入”占位

### 9.3 页面层

- 每个主路由一个独立 view 文件
- 详情页和操作页单独拆 view，不再用弹窗模拟完整页面

## 10. 样式策略

建议继续沿用企业端原型的视觉来源，不直接复用 `food-web` 的后台样式。

建议做法：

- 以 `企业端原型页面/stitch_/sentinel_governance/DESIGN.md` 作为视觉基准
- 使用统一全局样式入口 `src/styles/main.css`
- 第一阶段先实现：
  - 左侧导航骨架
  - 顶部栏骨架
  - 页面标题区
  - 卡片容器
  - 空态占位

第一阶段不建议做：

- 复杂表格交互
- 上传交互
- 详情页审计轨迹
- 大量逐像素还原

## 11. 页面跳转关系设计

第一阶段至少保证以下跳转逻辑在骨架层成立：

- 工作台 -> 企业备案
- 工作台 -> 产品档案
- 工作台 -> 检查记录
- 工作台 -> 整改任务
- 企业备案 -> 产品档案
- 产品档案 -> 新增产品
- 产品档案 -> 产品详情
- 产品详情 -> 编辑产品
- 检查记录 -> 检查记录详情
- 检查记录详情 -> 整改任务详情
- 整改任务 -> 整改任务详情
- 整改任务详情 -> 提交整改
- 提交整改 -> 提交成功
- 提交成功 -> 整改任务列表

说明：

- 第一阶段可以只把一级页面的跳转做通
- 第二阶段再补详情页与操作页的跳转闭环

## 12. 与现有项目的关系

建议企业端独立前端与现有项目保持以下关系：

- `food-web` 继续作为旧版可运行前端保留
- `food-auth-web` 继续作为认证前端独立存在
- `food-enterprise-web` 只承接企业端页面，不承接公众端、监管端、管理员端

不建议第一步做的事情：

- 不建议直接复制 `food-web/src/views/EnterpriseProfileView.vue` 进新项目
- 不建议先把所有接口逻辑原样搬过去
- 不建议先做认证与企业端的整合跳转

原因：

- 这样会把旧项目的单组件结构直接带进新项目
- 会在骨架阶段过早耦合接口与状态
- 会削弱按原型拆页的改造目的

## 13. 推荐实施顺序

建议后续按以下顺序推进：

1. 先新建 `food-enterprise-web/` 基础项目，不改 `food-web`
2. 先落路由和公共布局，不接业务接口
3. 先完成 5 个一级页面骨架
4. 再补 4 类详情页和 2 类操作页骨架
5. 最后按模块逐个接入真实接口

如果严格控制范围，下一步最适合做的是：

- 只新建企业端独立前端项目骨架
- 只接入 `vue-router`
- 只落一级页面和左侧导航
- 不写任何真实业务请求

## 14. 当前风险点

- 企业端原型是多页面结构，而旧项目是单组件结构，拆页时必须先坚持路由边界，不能边写边回退成单页切 section
- 如果第一步就把接口、上传、分页、详情弹窗一起搬入新项目，骨架会迅速失控
- 工作台页在旧项目中没有现成对应页面，后续需要确认其数据是完全新组装还是从多个接口聚合
- 后续若要和 `food-auth-web` 联动，还需要额外设计登录成功后的项目承接策略，本方案暂未覆盖
