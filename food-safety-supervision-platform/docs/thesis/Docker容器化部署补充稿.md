### 5.1.4 基于Docker的容器化部署实现

在本地开发联调基础上，项目进一步完成了基于 Docker 的容器化部署实现，使前端、网关、业务微服务以及基础依赖环境能够以统一方式构建、启动和协同运行。相较于分别在宿主机手工安装和启动各类运行环境的方式，容器化部署将运行依赖、服务启动命令和网络连接关系固化为可重复执行的部署描述，有利于降低环境差异对系统运行结果的影响，并提升原型系统的部署规范性。

本项目的容器化部署并未采用“在镜像中直接编译全部源码”的方式，而是采用“先构建产物，再进行镜像封装”的实现路径。后端部分通过 `deploy/build/build-artifacts.ps1` 或 `deploy/build/build-artifacts.sh` 脚本统一执行 Maven 打包，生成 `user-service`、`gateway-service`、`regulation-service`、`regulation-operation-service`、`complaint-service`、`query-service` 和 `warning-service` 七个可执行 JAR 文件；前端部分在 `food-web` 目录下执行 `npm ci` 与 `npm run build`，生成 `dist` 静态资源目录。完成上述构建后，Docker 再基于已经生成的 JAR 包和前端静态资源进行镜像封装。这种实现方式与当前项目的 Maven 聚合结构和 Vue 前端构建方式保持一致，也便于在资源有限的演示环境中直接复用现有构建产物。

在镜像设计方面，后端服务采用统一的通用镜像构建方案。项目在根目录中定义了 `Dockerfile.backend`，以 `eclipse-temurin:17-jre` 作为基础镜像，通过 `APP_JAR` 构建参数指定不同服务对应的 JAR 文件路径，并使用 `java -jar /app/app.jar` 方式启动应用。该设计避免了为每个后端服务重复编写独立 Dockerfile，同时保留了端口和 JVM 参数的可配置能力。前端部分则在 `food-web/Dockerfile` 中以 `nginx:1.27-alpine` 作为基础镜像，将 `dist` 目录复制到 Nginx 静态资源目录，并加载自定义的 `nginx.conf` 与 `default.conf` 配置，用于统一提供页面访问入口和反向代理能力。

从服务编排结构看，项目通过 `docker-compose.yml` 对整体部署进行统一管理。编排结果包括 4 个基础设施容器、7 个后端服务容器和 1 个前端容器，共同组成完整的部署单元。其中，基础设施容器包括 MySQL、Redis、Nacos 和 MinIO，分别负责业务数据存储、缓存与会话控制、服务注册发现以及文件对象存储；后端容器包括用户服务、监管主数据服务、监管执行服务、投诉服务、预警服务、统计查询服务和网关服务；前端容器则负责承载 Vue 3 单页应用并对外提供统一 Web 访问入口。各容器均加入 `fsp-net` 桥接网络，从而保证服务之间能够直接以容器名完成访问。

为使部署过程与系统实际运行关系保持一致，`docker-compose.yml` 中明确描述了各服务的依赖关系。MySQL、Redis、Nacos 和 MinIO 优先提供底层运行支撑；用户服务、监管服务、投诉服务、预警服务、监管执行服务和统计服务在启动后通过 Nacos 进行服务注册；网关服务再通过服务名将外部 API 请求转发到对应业务服务；前端 Nginx 容器则进一步将浏览器发起的 `/api/` 请求反向代理到 `gateway-service:8080`。这样形成了“浏览器访问前端容器 - Nginx 转发 `/api` - 网关统一路由 - 业务服务处理请求”的完整访问链路。该链路与系统前后端分离、统一网关接入和微服务协同的总体架构设计保持一致。

在配置注入方面，项目当前容器化部署主要采用环境变量方式完成运行参数传递。根目录 `.env` 文件统一给出了数据库账号、Redis 密码、Nacos 地址、MinIO 访问参数、内部调用令牌以及各服务 JVM 内存参数等配置项。Compose 在启动容器时将这些变量注入对应服务，使各微服务能够通过 `application.yml` 中的占位符读取数据库主机、缓存主机、对象存储端点和内部认证参数。从当前实现看，Nacos 在容器化部署链路中主要承担服务注册发现作用；虽然项目保留了 Nacos Config 相关依赖与配置入口，但当前运行所需关键参数主要由 Compose 环境变量直接提供。这种方式实现简单、部署路径明确，适合毕业设计原型系统的演示与复现实验。

项目在数据库初始化方面也针对容器环境进行了适配。MySQL 容器挂载了 `deploy/mysql/init/` 目录，并利用官方镜像的初始化机制，在数据卷首次创建时自动执行用户、监管、监管执行、投诉、统计查询和预警等数据库的建表与初始化脚本。这样可以在首次部署时直接完成基础表结构与部分演示数据准备，减少手工导入 SQL 的步骤。与此同时，投诉服务在应用配置中将 `spring.sql.init.mode` 设为 `never`，避免业务服务启动时再次执行初始化逻辑，与容器化场景下由数据库容器统一初始化的实现方式保持一致。

在前端访问路径设计上，项目容器化部署采用了“同源访问 + 网关转发”的实现思路。前端静态资源由 Nginx 容器统一对外暴露，浏览器默认访问根路径即可加载页面；当前端发起 `/api/` 请求时，Nginx 再将请求代理到网关服务。由于前端生产构建未强制写死独立 API 域名，而是保留相对路径访问方式，因此容器部署后浏览器可以直接以当前站点地址访问后端接口，既减少了跨域配置复杂度，也与网关中统一路由控制的实现方式形成配合。这一设计说明容器化部署不仅完成了服务封装，也同步考虑了前后端通信路径的统一性。

从资源控制与部署适配角度看，项目在 `.env` 中为各服务设置了较保守的 JVM 参数和 Nacos 内存参数，体现了原型系统面向低配置演示环境的部署考虑。例如，用户服务、投诉服务、预警服务、查询服务和网关服务均采用较小堆内存配置，Nacos 也采用了较低的初始堆和最大堆设置。这些配置虽然不面向生产级高并发场景，但能够在 1 核 CPU、约 2GB 内存的轻量虚拟机环境中维持基础运行，有利于完成论文实现阶段的部署验证与功能展示。

总体而言，项目现有 Docker 容器化部署实现已经形成了较完整的工程闭环，即先生成后端可执行 JAR 和前端静态资源，再通过 Docker 镜像完成运行环境封装，最后借助 Docker Compose 统一编排数据库、缓存、注册中心、对象存储、网关、业务服务和前端入口。该实现使系统从“可在本地分服务运行”进一步扩展为“可在统一容器环境下整体部署”，增强了平台原型系统的可迁移性、可复现性和工程完整性。

### 表5-X 容器化部署服务组成说明表

| 服务名称 | 容器角色 | 主要作用 | 关键部署特征 |
| --- | --- | --- | --- |
| mysql | 基础设施容器 | 存储各业务库数据 | 挂载 `deploy/mysql/init/` 自动初始化，使用 `mysql_data` 数据卷持久化 |
| redis | 基础设施容器 | 会话、缓存、限流与分布式锁支持 | 启用 AOF 持久化，使用 `redis_data` 数据卷 |
| nacos | 基础设施容器 | 服务注册与发现 | 作为各微服务注册中心运行 |
| minio | 基础设施容器 | 备案、投诉、整改等文件对象存储 | 使用 `minio_data` 数据卷持久化 |
| user-service | 业务服务容器 | 登录、注册、用户与角色管理 | 基于通用后端 Dockerfile 构建 |
| regulation-service | 业务服务容器 | 企业备案、主数据管理、公告与预警协同 | 依赖 MySQL、Redis、Nacos、MinIO |
| regulation-operation-service | 业务服务容器 | 检查、抽检、整改等监管执行流程 | 依赖监管服务与预警服务 |
| complaint-service | 业务服务容器 | 公众投诉提交、受理、分派和反馈 | 关闭应用级 SQL 自动初始化 |
| warning-service | 业务服务容器 | 预警记录、升级与归档处理 | 提供预警统计与内部协同能力 |
| query-service | 业务服务容器 | 监管概览、趋势与统计查询 | 聚合调用多个业务服务接口 |
| gateway-service | 网关容器 | 统一 API 路由、鉴权与跨服务入口 | 对内按服务名转发请求 |
| food-web | 前端容器 | 提供 Web 页面访问入口 | Nginx 托管静态资源并代理 `/api/` |
