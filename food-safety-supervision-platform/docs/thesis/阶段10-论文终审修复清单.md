# 阶段10-论文终审修复清单.md

## 1. 总体评价

`阶段9-毕业论文整合稿.md` 已基本具备本科软件开发研究类型论文的提交基础。全文章节结构完整，能够覆盖绪论、相关技术、系统分析、系统设计、系统实现、系统测试、总结与展望七章内容；系统名称、微服务架构、核心业务模块、数据库边界、测试边界等大部分关键表述与项目代码事实一致；对“未实现消息队列”“未实现容器化部署”“统计表为预留设计”“测试未覆盖性能压测和全量前端自动化”等边界也已有较明确说明。

当前仍存在少量需要收口的问题，主要集中在术语一致性、个别能力表述偏宽，以及少数章节中“角色集合称谓”和“具体角色称谓”混用。整体问题不多，但建议在定稿前完成统一修正。

## 2. 必修问题（必须修改）

### 2.1 角色术语混用，需统一到固定口径

- 影响范围：第3章、第4章、第5章、第6章多处。
- 具体表现：
  - 文中同时使用了“区域管理员、执法人员”与“监管端、监管用户、监管管理员、监管员”等称谓。
  - 例如整合稿中第3章业务场景、功能需求，第4章功能设计，第5章实现描述，第6章测试用例均存在混用。
- 风险：
  - 容易造成“监管角色是否只有一种”的理解歧义。
  - 会削弱第3章需求分析与第5章实现、第6章测试之间的一一对应关系。
- 最小修正建议：
  - 将角色固定为五类：`系统管理员`、`区域管理员`、`执法人员`、`企业用户`、`公众用户`。
  - 仅在需要概括两类监管角色时使用“`监管人员`”作为集合称谓。
  - 将“监管端”改为“区域管理员端/执法人员端”或“监管人员端”。
  - 将“监管管理员”统一改为“区域管理员”。
  - 将“监管员”统一改为“监管人员”或按上下文改成“区域管理员/执法人员”。

### 2.2 系统管理员能力表述略宽，需收缩到代码已实现范围

- 影响范围：第1章 `1.1`，第3章 `3.1`、`3.2.3`，第5章系统管理员相关实现表述。
- 具体表现：
  - 文中有“系统管理员维护监管人员账号和基础权限”等表述。
  - 但前端与后端实际证据更明确支持的是：监管账号创建、角色类型选择、监管人员档案查看、状态维护、辖区配置协同；同时前端存在“权限级别”“审计日志 API”等占位或 TODO。
- 风险：
  - “基础权限”容易被理解为细粒度权限模型、权限等级体系、权限点配置，而仓库中未形成独立权限模型说明。
- 最小修正建议：
  - 将“维护监管人员账号和基础权限”改为“维护监管人员账号、角色类型和状态信息”。
  - 将系统管理员职责固定描述为：`监管账号创建`、`监管人员信息查看`、`状态维护`、`与监管档案建立协同关系`。
  - 不把前端占位的“权限级别”“审计日志中心”写成已实现能力。

## 3. 可优化问题（建议修改）

### 3.1 “监管闭环”表述可再克制一些

- 影响范围：第1章、第3章、第7章总结。
- 当前情况：
  - 文中多处使用“形成较完整的监管业务闭环”“较好体现”等表述，整体仍属可接受范围。
- 建议：
  - 个别位置可统一成“形成覆盖企业备案、检查抽检、整改、投诉、预警和统计查询的主要业务闭环”。
  - 这样更具体，也更贴近代码已实现链路。

### 3.2 第6章测试对象名称可与第5章模块名称进一步对齐

- 影响范围：第5章、第6章。
- 当前情况：
  - 第5章按“统一认证、基础监管数据、检查整改与抽检、投诉处理、统计查询与预警代理”展开。
  - 第6章测试用例中有时直接写“监管概览”“预警统计”“公众公开查询”，与第5章模块命名风格略有差异。
- 建议：
  - 可在第6章测试用例前增加一句“测试对象对应第5章各核心实现模块”，或将表头中的测试目标改写为与第5章一致的模块表述。

### 3.3 第4章界面设计可再补一句“界面存在占位交互”

- 影响范围：第4章 `4.4`。
- 当前情况：
  - 整合稿已经写了主要页面布局与角色页面划分，但没有在界面设计处再次强调部分系统管理员页面存在占位交互。
- 建议：
  - 在 `4.4` 末尾补一句：系统管理员部分审计日志与筛选等交互仍为页面占位，未纳入已实现后端能力范围。
  - 这样与第7章展望中的后续完善点呼应更自然。

### 3.4 第2章可补强 Sentinel 的边界说明

- 影响范围：第2章 `2.1`、`2.2`。
- 当前情况：
  - 文中提到了网关限流与 Sentinel 相关参数，但没有在相关技术章节中明确“规则内容主要依赖运行时配置”。
- 建议：
  - 增加一句：代码库中已接入 Sentinel 依赖、网关规则配置类和相关参数，但更细粒度规则工程化仍属于后续完善方向。
  - 这样能避免老师继续追问“具体熔断规则在哪里”。

## 4. 已确认无问题项

- 项目名称表述基本统一，均围绕“`基于微服务的食品安全监管平台`”展开，未发现实质性冲突。
- 微服务架构表述与代码事实一致，能够对应 `gateway-service`、`user-service`、`regulation-service`、`regulation-operation-service`、`complaint-service`、`warning-service`、`query-service`、`platform-common` 等模块。
- 技术栈主线表述基本准确，Java 17、Spring Boot 3.2.5、Spring Cloud、Spring Cloud Alibaba、Vue 3、Vue Router 4、Vite 5、MySQL、Redis、Nacos、Gateway、OpenFeign、MyBatis-Plus、JWT、MinIO、Springdoc OpenAPI 等均能找到代码或配置证据。
- 对“未实现消息队列驱动异步通信”“未提供 Docker/Kubernetes 部署文件”“`query-service` 统计表为预留设计”“预警通过代理访问而非前端直连”等边界说明准确。
- 第3章需求、第4章设计、第5章实现、第6章测试整体对应关系成立，未发现“测试对象脱离实现模块”的实质性问题。
- 第6章测试写法总体真实克制，未虚构压测数据、并发指标、持续集成结果或浏览器级完整联调成果。
- 第7章展望整体合理，没有出现与现有系统完全脱节的幻想式扩展。

## 5. 最终定稿建议

1. 先执行一次全局术语替换，优先统一“区域管理员/执法人员/监管人员”的使用边界。
2. 再收缩系统管理员相关表述，删除或改写“基础权限”“权限级别”等容易被理解为已实现细粒度权限体系的表达。
3. 对第4章界面设计和第6章测试对象名称做小幅润色，使“需求—设计—实现—测试”链路在命名上完全一致。
4. 完成以上修正后，全文已可以进入学校模板排版阶段。
